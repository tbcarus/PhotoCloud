# PhotoCloud — правила совместной разработки

**Назначение:** переносимый контекст для новых чатов с ChatGPT и заданий Codex / Claude Code.  
**Актуально на:** 27 октября 2026 г.  
**Область:** порядок работы, документы, репозитории, агенты, проверки, Git и Miro. Это **не** замена System SPEC и не перечень всех текущих задач.

> **Коротко:** функциональный сценарий → изучение System SPEC и кода **без правок** → критическое обсуждение поведения и приоритетов → согласование решения → строгое задание агенту → реализация и тесты → при необходимости ручная проверка → итоговый CHECK → актуализация единой System SPEC → просмотр diff → отдельные коммиты → обновление плана Miro по согласованию.

## 1. Что мы разрабатываем

**PhotoCloud** — личное облако для резервного копирования и работы с фотографиями и файлами.

- **Android:** Kotlin, Jetpack Compose, Room, Hilt, Retrofit/OkHttp, WorkManager. Обнаружение медиа через MediaStore; локальная подготовка, контрольная сумма и загрузка на сервер.
- **Server:** Java / Spring Boot, PostgreSQL, Liquibase, JWT, файловое хранилище. Сервер принимает файлы, ведёт метаданные, предоставляет REST API.
- **System SPEC:** единое описание системного поведения, модели и согласованных решений.

Система развивается по работающим пользовательским сценариям. Не нужно заранее строить сложную универсальную архитектуру для гипотетических возможностей.

Проверять фактические пути и `git status` перед задачей: дерево и названия со временем могут меняться. Корневой `PhotoCloud` / `system-spec` имеет собственную историю Git, отличную от клиентского и серверного репозиториев.

**Другие места:**

- `AGENTS.md` — если присутствует в рабочем дереве, читать как постоянные инженерные правила для агента. Не дублировать и не переписывать без причины.

- **Miro, доска «Photo cloud»:** https://miro.com/app/board/uXjVIJeXHxs=/ — основной рабочий план, приоритеты, решения, статусы и отложенные вопросы.

**Важно:** старые отдельные `Server As-Is`, `Android As-Is`, архивная `System As-Is v1` были **удалены сознательно**. Их **не восстанавливать**, новых component specs не создавать, отсутствие таких папок не считать дефектом. Поддерживаем только `system-spec/docs/spec/system/`.

## 3. Источники истины и работа с противоречиями

1. **System SPEC** фиксирует текущее и согласованное целевое **поведение**, продуктовые правила, системные сценарии и модель.
2. **`01-system-model.md`** — единый источник определений сущностей, полей и состояний. Остальные сценарии ссылаются на них, не изобретают собственные поля.
3. **Production-код** показывает, что **фактически реализовано**; **тесты и ручные испытания** — что удалось подтвердить.
4. **Miro** показывает **план, приоритеты, историю решений и TODO**; при необходимости уточняем по System SPEC и коду.
5. **Git** показывает историю конкретных изменений и незакоммиченных правок.

Ни код, ни старое TO-BE автоматически не считаются правильными. При расхождении **сначала установить факт, затем обсудить и принять решение**, после чего менять код и/или System SPEC. Не исправлять документ только для того, чтобы оправдать ошибочную реализацию.

## 4. Наш обычный рабочий цикл

### Шаг 1. Выбрать сценарий и оценить приоритет

Берём пользовательскую функцию или компактную группу тесно связанных сценариев. Сверяем с текущим планом Miro. Разделяем:

- **Обязательное:** неправильное поведение, риск потери данных, нарушение базового сценария, существенная безопасность, необходимая зависимость.
- **Желательное:** улучшение UX, диагностики, удобства и сопровождаемости.
- **Отложенное:** редкие гонки, гипотетические крайние случаи, преждевременные абстракции, оптимизации без подтверждённой проблемы.

**TODO — не команда немедленно реализовывать.** Не превращать низкоприоритетный технический долг в «следующий этап» без решения пользователя.

### Шаг 2. Глубокий анализ БЕЗ изменений

Если задача — **аудит / анализ / CHECK**, агент по умолчанию работает **READ-ONLY**: не правит production-код, тесты, конфигурацию, System SPEC и Git.

Изучает соответствующий сценарий System SPEC, соседние зависимости, реальный код Android и/или Server, API, БД, ошибки, разрешения, тесты, TODO. Сравнивает текущее поведение с целевым, критически проверяет само TO-BE. Подтверждает выводы путями к файлам, методами, условиями или тестами.

Отчёт: **факты → существенные дефекты/последствия → альтернативы → необходимые изменения и отдельные необязательные TODO → предлагаемые небольшие этапы → вопросы для решения**. Не нужен каталог косметических замечаний.

### Шаг 3. Обсудить и принять продуктовые решения

Мы обсуждаем варианты, компромиссы и реальную цену исправления. Пользователь утверждает поведение и приоритет; агент не меняет продуктовые правила молча. Можно сознательно принять ограничение — тогда честно указать его в плане и/или спецификации.

**Типичный пример:** при отказе в `ACCESS_MEDIA_LOCATION` backup продолжает работать (мягкий режим); система предупреждает о возможной потере GPS, а не блокирует всю синхронизацию.

### Шаг 4. Составить строгое ТЗ агенту

Не давать расплывчатых указаний «улучшить всё». В задании должны быть:

1. Цель и уже принятые решения.
2. Граница задачи: затронутые проекты, сценарии, методы/файлы (при наличии).
3. **Что изменить** и наблюдаемое поведение до/после.
4. **Чего НЕ делать**: не расширять архитектуру, не трогать соседние функции, не менять БД/API/интервалы/разрешения без решения, не делать коммит.
5. Тесты и критерии приёмки, включая отрицательные сценарии.
6. Правила обновления System SPEC, если оно входит в этап.
7. Формат отчёта: изменённые файлы, тесты, сборки, непроверенное, `git diff`, `git status`.

Задания обычно оформляем на **русском языке**. Для разных частей можно выдавать разные задания Android и Server. Не просить одновременно огромный аудит и неопределённый рефакторинг.

### Шаг 5. Реализовать и проверить

После утверждения агент вносит минимальные изменения и целевые тесты. Допускаются локальные инженерные решения в пределах ТЗ, но не скрытая смена поведения.

Проверки по риску:

- Быстрые unit-тесты, Robolectric на Android; интеграционные тесты Server/PostgreSQL (часто Testcontainers), сборки debug/release или bootJar, где обоснованно.
- **Не путать unit/Robolectric с реальным Android.** WorkManager, MediaStore, runtime permissions, Doze, перезапуск процесса и поведение разных устройств могут требовать испытания на эмуляторе или телефоне.
- Иногда достаточно анализа и существующих тестов. Не настаивать на сложных конкурентных/нагрузочных тестах без реальной пользы.
- Для спорного бага полезно доказать, что тест падает на прежней реализации и проходит после исправления.
- Не утверждать `PASS`, если проверка не выполнена; разделять **проверено**, **проверено частично** и **не проверено**.

Особенно осторожно с тестовым устройством, личной медиатекой, токенами, серверной БД и файлами: **не удалять данные, не сбрасывать приложение и не выполнять разрушительные команды без согласования**.

### Шаг 6. Актуализировать System SPEC

После проверки описываем **реально принятое и внедрённое поведение** в существующих сценариях. Не дублируем код Kotlin/Java и детали Spring/WorkManager, если они не важны для системного контракта.

- Если принятое TO-BE реализовано — переносим его в основное описание сценария по правилам `README.md`, не оставляя одновременно старый и новый варианты.
- Не добавляем поля в сценариях без `01-system-model.md`.
- Не переводим **весь** сценарий в `ACCEPTED` только потому, что один его подпункт или тест прошёл.
- Не переписываем unrelated разделы; устаревшие ссылки и очевидные противоречия исправляем целенаправленно.

### Шаг 7. Итоговый CHECK, diff, Git и план

Проверяем, что Android ↔ Server ↔ System SPEC согласованы в затронутой части, необходимые тесты прошли, ограничения документированы. Перед фиксацией читаем **итоговый diff**; не доверяем одному только резюме агента.

**По умолчанию агент не коммитит.** Коммит — по явной просьбе пользователя после просмотра результата. Android, Server и корневая System SPEC — **раздельные Git-репозитории**, коммиты делаются отдельно. Беречь уже имеющиеся незакоммиченные изменения, не смешивать их с новой задачей, не выполнять сбросы/очистку Git без разрешения.

Затем по согласованию актуализируем Miro: итог, статус, тесты/ограничения, зависимости и оставшиеся TODO. **Не менять карточки Miro самостоятельно без явного поручения или одобрения.**

## 5. Правила System SPEC

Основная навигация и определения — в `system-spec/docs/spec/system/README.md`. Не вводить параллельные схемы статусов.

**Status (жизненный цикл сценария):**

| Статус | Смысл |
|---|---|
| `AS-IS` | Зафиксированное фактическое поведение, ещё не принятое осознанно |
| `OPEN` | Решение не принято |
| `TO-BE` | Согласованное целевое поведение |
| `IMPLEMENTING` | Реализация в работе |
| `IMPLEMENTED` | Реализация заявлена завершённой; ещё не означает итоговую приёмку |
| `CHECK` | Нужна сквозная проверка спецификации, модели и кода |
| `ACCEPTED` | Проверено и принято |
| `DEFERRED` | Сознательно отложено |
| `REMOVE` | Принято решение удалить поведение |

**Availability (фактическая доступность, отдельно от Status):** `END_TO_END`, `SERVER_ONLY`, `ANDROID_ONLY`, `STUB`, `NOT_PRESENT`.

Особенности:

- Статусы относятся **к целому сценарию**; частный успешно завершённый этап не должен автоматически менять статус целого.
- `CHECK` — не формальность: в пределах сценария сверяем System SPEC, System Model, production-код, межкомпонентный контракт и результаты проверок.
- Сохраняем существующие человекочитаемые идентификаторы сценариев (например, `BACKUP-BACKGROUND`, `AUTH-REG`), не заводим произвольную цифровую нумерацию.
- Правила и фактические определения из актуального `README.md` имеют приоритет над кратким конспектом в этом файле.

## 6. Стиль кода и конфигурация

### Комментарии и TODO

- Комментарии в исходниках — **редкие, короткие, на русском**, только там, где без них непонятны инвариант, причина нестандартного решения, важное ограничение или особенность Android/Spring.
- Не пересказывать очевидный код и не засорять его комментариями «на будущее».
- `TODO` оставлять **только когда это действительно помогает найти конкретную отложенную работу**; обычно достаточно зафиксировать её в Miro или System SPEC. Указывать причину/границу, избегать бесконечных TODO.
- Не оставлять устаревшие комментарии: если интервал в коде 30 минут, KDoc не должен говорить «1 час».

### YAML и настраиваемые значения

- Там, где оправданно, **параметры Server выносить в `application.yml`** (или принятое профильное YAML): сроки токенов/кодов, лимиты, пороги, таймауты, параметры хранения и другие реальные настройки развёртывания.
- **YAML — один источник значений по умолчанию** для соответствующей настройки. Не дублировать дефолт одновременно в YAML, Java и шаблонах; читать настройку через принятый механизм Spring-конфигурации.
- Выбирать понятные имена и единицы измерения (`*-minutes`, `*-days`, `*-bytes`); учитывать диапазоны чисел и преобразование единиц; тестировать границы.
- **Не переносить всё в YAML без разбора:** неизменяемые инварианты, алгоритмы, внутренние технические константы и настройки Android следует оставлять там, где это естественно для соответствующей платформы.
- **Не менять параметры по собственной инициативе.** Например, нынешний 30-минутный интервал Android и временная поддержка `Pictures` сохраняются, пока пользователь явно не решит иначе.

### Общие инженерные принципы

- Минимальные изменения с понятной причиной и проверяемым результатом.
- Сохранность пользовательских данных и идемпотентность важнее архитектурной «красоты».
- Без миграций БД, новых сущностей, зависимостей, сервисов, потоков и лишних уровней абстракции «на перспективу».
- Не скрывать ошибки, не превращать временный сетевой сбой в удаление данных/сессии.
- Не логировать пароли, токены, коды подтверждения, содержимое фото и бинарных HTTP-тел. Не раскрывать чувствительные параметры в URL/логах.
- Уважать уже принятые решения, даже если теоретически возможна более сложная архитектура. Предлагать изменения только с конкретным основанием.

## 7. Работа с Miro

**Доска:** [Photo cloud](https://miro.com/app/board/uXjVIJeXHxs=/).

Используем Miro как **живой план**: рабочие направления, P0/P1/P2, этапы, принятые решения, статус, результат проверок, зависимости, риски и TODO.

Основные направления доски на момент составления файла:

| Приоритет | Направление |
|---|---|
| P0 | `01` Хранилище, папки и имена; `02` Камера и оригиналы |
| P1 | `03` Автономный backup; `04` Сессия/доступ к серверу; `05` Надёжность/восстановление |
| P2 | `06` Файловая библиотека; `07` Состояние копирования |

**Это ориентир, не жёсткая очередь задач.** Статусы и следующий приоритет проверять **в самой доске** и обсуждать с пользователем. Нельзя делать вывод «после A4.3 обязательно A5» только из наличия A5 в списке: A5 — техническая задача о гонках `KEEP`, пользователь не назначал её ближайшим приоритетом.

После завершения согласованного этапа уместно предложить обновить соответствующую карточку, указав **что реально проверено** и **что ещё не проверялось**. Не записывать неподтверждённое как PASS. Миро не заменяет System SPEC и Git.

## 8. Как работать в новом чате

Если пользователь прикладывает этот файл, исходный порядок таков:

1. Принять документ как **рабочие соглашения**, но перед новыми действиями прочитать актуальные System SPEC / Miro / `AGENTS.md` и проверить Git-состояние, если есть доступ.
2. Не считать упомянутые здесь даты, версии и состояния вечными: они могут устареть.
3. Продолжать **последнюю выбранную пользователем задачу**, не переназначая следующий этап самостоятельно.
4. Если запрошен аудит — **никаких правок**; если запрошена задача агенту — дать **полное точное ТЗ**, а не начинать реализацию без запроса.
5. Разделять **факты из исходников/тестов**, **результаты ручной проверки пользователя**, **гипотезы** и **рекомендации**.
6. Отвечать по-русски, **коротко, структурированно, без воды**. Не повторять принятые решения и не задавать вопросы, на которые уже есть ответы в истории.
7. Для пользовательских команд на Windows/PowerShell писать **команды в нижнем регистре** (если команда или параметр позволяет); не предлагать Unix-команды как единственный вариант. Не выполнять потенциально разрушительные действия без согласования.

## 9. Что фиксировать по завершении каждой задачи

Короткий шаблон для агента или чата:

```text
Задача / сценарий:
Принятое поведение:
Изменённые файлы и репозитории:
Тесты и сборка: (команда, сколько прошло, что не запускали)
Ручная проверка: (устройство/ОС, шаги, фактический результат)
System SPEC: (какие сценарии обновлены, их статус)
Известные ограничения и TODO:
Git: (чистота деревьев, commit SHA при наличии)
Miro: (карточка, статус, нужен ли апдейт)
Следующий этап: (только утверждённый пользователем)
```

---

**Главное правило:** **анализ → обсуждение решения → строгое ТЗ → минимальная реализация → проверка → единая System SPEC → Git → Miro**. Не превращать отдельную техническую находку в новый приоритет без согласования.
