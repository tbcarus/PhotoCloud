# PhotoCloud — правила совместной разработки и контекст для нового чата

**Версия документа:** 4 ноября 2026 г.  
**Место хранения:** корень общего проекта `PhotoCloud/PhotoCloud_WORKFLOW.md`.  
**Назначение:** переносимый контекст для продолжения совместной работы пользователя, ChatGPT, Codex и Claude Code.  
**Область:** процесс, источники истины, правила разработки, проверки, Git, Miro и краткий срез состояния проекта. **Не заменяет System SPEC, код и актуальную доску Miro.**

> **Принцип:** пользовательский сценарий → необходимый анализ → обсуждение и решение → строгое ТЗ → ограниченная реализация → проверка → актуализация System SPEC → приёмка → коммиты пользователя → Miro → следующий согласованный этап.
>
> **Не превращать каждую техническую находку в новый проект, каждую задачу — в аудит, а каждую успешную проверку — в утверждение о полной готовности системы.**

## 1. Проект и рабочее пространство

**PhotoCloud** — личное облако для резервного копирования фотографий, выбранных папок Android и работы с файлами в серверной библиотеке.

- **PhotoCloudClient:** Kotlin, Jetpack Compose, Room, Hilt, Retrofit/OkHttp, WorkManager, SAF и MediaStore.
- **PhotoCloudServer:** Java / Spring Boot, PostgreSQL, Liquibase, JWT, физическое файловое хранилище, REST API.
- **System SPEC:** единая системная модель, пользовательские сценарии, согласованные ограничения и recovery.

Ориентировочное рабочее дерево:

```text
PhotoCloud/                          # отдельный корневой Git-репозиторий
├── PhotoCloud_WORKFLOW.md           # этот документ
├── PhotoCloudClient/                # самостоятельный Git-репозиторий Android
├── PhotoCloudServer/                # самостоятельный Git-репозиторий Server
└── system-spec/
    └── docs/spec/system/
        ├── README.md                # соглашения по сценариям, Status и Availability
        ├── 00-system-overview.md
        ├── 01-system-model.md       # единая модель сущностей, полей и состояний
        ├── 02-account-and-auth.md
        ├── 03-profile-and-settings.md
        ├── 04-backup-and-sync.md
        ├── 05-file-library.md
        ├── 06-sharing-and-access.md
        └── 07-system-rules-and-recovery.md
```

Пути и наличие файлов **проверять в актуальном рабочем дереве**. `AGENTS.md`, если присутствует, читать перед работой в соответствующем репозитории.

**Не восстанавливать** старые отдельно поддерживаемые Server As-Is, Android As-Is и System As-Is v1: их удалили осознанно. Единственная поддерживаемая системная спецификация — `system-spec/docs/spec/system/`. Локальные API-контракты и тесты продолжают существовать как инженерные документы, но не заменяют System SPEC.

**Miro:** доска [Photo cloud](https://miro.com/app/board/uXjVIJeXHxs=/) — план этапов, решений, зависимостей, ограничений, задач и отложенных вопросов.

## 2. Роли и границы ответственности

| Участник | Основная роль |
|---|---|
| **Пользователь** | Выбирает приоритет, утверждает продуктовые и архитектурные развилки, принимает реализацию, самостоятельно делает Git-коммиты. |
| **ChatGPT** | Помогает анализировать отчёты и варианты, обсуждать решения, писать строгое ТЗ, оценивать результаты, предлагать точечные правки, вести согласованный план Miro. |
| **Codex** | Обычно анализ и реализация Server; работает только в границах выданного задания. |
| **Claude Code** | Обычно анализ и реализация Android; работает только в границах выданного задания. |

Распределение Codex/Claude Code — сложившаяся практика, а не запрет на другое назначение.

- **Аудит/CHECK по умолчанию READ-ONLY**: агент не изменяет production-код, тесты, конфигурацию, System SPEC, Git и рабочие данные.
- **Реализация разрешена только в рамках конкретного утверждённого задания.** Агент может самостоятельно принять локальное техническое решение, если оно не меняет утверждённые правила.
- **Агент не делает коммиты** и не выполняет `git reset`, `git clean`, force-push, переключение с потерей изменений и подобные действия без отдельного разрешения.
- **ChatGPT не подменяет проверку исходников выводами из отчёта агента.** Правильная формулировка: «по отчёту агента подтверждено…», если сам код не проверялся независимо.
- Не выдавать следующее ТЗ автоматически при отчёте о предыдущем этапе. Сначала приёмка, коммит пользователя и его решение двигаться дальше.

## 3. Источники истины

1. **System SPEC** — утверждённое поведение системы, состояния и сценарии, текущие и целевые правила.
2. **`01-system-model.md`** — единственный источник системных сущностей, полей и состояний. Остальные сценарии на него ссылаются.
3. **Production-код** — что реально реализовано, даже если документация отстаёт.
4. **Тесты и изолированные ручные проверки** — какая часть реализации фактически проверена, в каком окружении.
5. **Git** — фактические коммиты, ветка и рабочие изменения в каждом из трёх репозиториев.
6. **Miro** — план, история согласований, текущие этапы, зависимости, ограничения, отложенные работы.

При расхождении **сначала установить факты, потом обсудить нужное поведение, затем исправить код и/или SPEC**. Нельзя менять спецификацию лишь для оправдания ошибочной реализации или считать любой старый TO-BE правильным без обсуждения.

### Статусы System SPEC

Правила и определения из **актуального** `system-spec/docs/spec/system/README.md` имеют приоритет перед этим конспектом.

- **Status:** `AS-IS`, `OPEN`, `TO-BE`, `IMPLEMENTING`, `IMPLEMENTED`, `CHECK`, `ACCEPTED`, `DEFERRED`, `REMOVE`.
- **Availability:** `END_TO_END`, `SERVER_ONLY`, `ANDROID_ONLY`, `STUB`, `NOT_PRESENT`.
- Статус относится **к целому сценарию**, а не к одному выполненному подпункту. Принятый подэтап сам по себе не переводит весь сценарий в `ACCEPTED`.
- `CHECK` означает реальную сверку System Model, сценария, кода Server/Android и доступных результатов тестов; **не** формальный заголовок.
- Идентификаторы сценариев человекочитаемые (`AUTH-REG`, `BACKUP-SOURCE-SYNC`), без произвольной числовой нумерации.
- После реализации принятого TO-BE оно становится основным поведением; не оставлять рядом взаимоисключающие описания старого и нового.
- Не объявлять не реализованную возможность доступной: например, серверное копирование папок пока `NOT_PRESENT`.

**Важно:** статусы карточек Miro («Обсуждаем», «Принято», «Готово» и т. п.) — **не** статусы сценариев System SPEC.

## 4. Рабочий цикл

### 4.1. Выбор задачи и краткая ориентировка

- Отправная точка — пользовательский сценарий, дефект или ясно определённая функция; сверяем Miro и соседние System SPEC.
- Делим задачи на небольшие проверяемые этапы (например, серверная возможность → клиентский интерфейс → восстановление после ошибок).
- Перед началом агента: проверить текущую ветку и `git status` **каждого затрагиваемого репозитория**, последние нужные коммиты, актуальные контракты. Не переносить старый `git status` из предыдущего отчёта: однажды это ошибочно породило утверждение о незакоммиченном этапе.
- Классифицировать находки: **блокирует текущую задачу / желательно исправить / отложить**. TODO не становится новой задачей без решения пользователя.

### 4.2. Анализ — достаточный по масштабу задачи

**Не обязательно проводить новый глубокий аудит перед каждым маленьким этапом.**

- Для локальной UI-операции достаточно проверить соответствующий Server API, контракты, существующую ViewModel/репозиторий и ограничения.
- Для архитектурного изменения, миграции, риска потери данных, гонки или межкомпонентного сценария — полноценный READ-ONLY-анализ.
- Если запрошен именно анализ, аудит или CHECK — **никаких правок вообще**.
- Отчёт анализа: **подтверждённые факты → последствия → варианты → рекомендация → вопросы, без которых нельзя решить**. Ссылаться на конкретный код и контракты, а не на догадки.
- Если в ТЗ отсутствует необходимый API/возможность, **остановиться и сообщить**, а не самостоятельно изобретать клиентский обход, новый серверный метод или сложную архитектуру. Пример: в 6.2 Server не имел копирования папок — реализовали три имеющиеся операции, копирование папок отложили.

### 4.3. Обсуждение и фиксация решений

- Пользователь утверждает поведение, допустимые ограничения, приоритет и объём этапа.
- Обсуждаем реальную цену альтернатив, не подменяем её абстрактной «правильностью архитектуры».
- Если выбран простой подход с известным ограничением — документируем ограничение, не возвращаемся к тому же вопросу без новой причины.
- Новые вопросы задаём только для **существенной** развилки; не просим повторить уже принятые ответы.
- Для UX полезно сначала согласовать модель экрана и действия пользователя, затем делать узкое ТЗ.

### 4.4. Строгое ТЗ агенту

Пишем **по-русски**, ясно, без расплывчатого «улучшить всё». Обычная структура:

1. **Цель, контекст и уже принятые решения.**
2. **Граница:** проекты, сценарии, API, затрагиваемые компоненты; что заранее проверить READ-ONLY.
3. **Позитивные сценарии:** наблюдаемое поведение и конкретные операции.
4. **Негативные сценарии:** ошибки, потери связи/ответа, прерывание, доступ, пересечение с другими функциями.
5. **Запреты:** чего не реализовывать и какие части системы не менять.
6. **Тесты:** адресные и регрессионные, при необходимости изолированный smoke.
7. **System SPEC:** какие сценарии обновить, когда и по каким правилам.
8. **Критерии приёмки, итоговый отчёт, запрет коммитов и самостоятельного начала следующего этапа.**

Не объединять в одно ТЗ большой аудит, новый Server API, весь Android UI и гипотетические улучшения, если можно разделить.

### 4.5. Реализация и проверки

- Реализовать минимальное решение, переиспользуя существующие сервисы, DAO, конфигурацию, WorkManager и UI; не строить новый фреймворк без причины.
- Сначала адресные тесты, затем оправданная регрессия. После изменения бизнес-логики обычно запускать полный набор тестов соответствующего проекта.
- Проверять реальные системы, когда единичные unit/Robolectric-тесты не подтверждают нужное: разрешения Android, SAF, MediaStore, WorkManager, перезапуск процесса, Room migration, физические файлы, HTTP и PostgreSQL.
- **Smoke только на изолированном Server/DB/storage**, если работа изменяет файлы, API или миграции; не делать громоздких нагрузочных испытаний «на всякий случай».
- Если тестовая ошибка вызвана тестовой заглушкой, это нужно доказать; не «лечить» production-код под неправильный fake.
- Не скрывать пропуски проверок. Разделять «подтверждено unit», «проверено на эмуляторе», «не проверено».
- После мелкого дополнительного исправления, уже покрытого адресными тестами, **не всегда нужен повторный полный smoke**; объём проверки зависит от риска.

### 4.6. System SPEC и контрактные документы

- Обновлять вместе с реализацией затронутые сценарии и, где нужно, API-контракты. Не добавлять поля только в сценарии — сначала `01-system-model.md`.
- Описывать системное поведение, инварианты и восстановление, а не пересказывать строчки Kotlin/Java.
- Не переписывать несвязанные разделы. Исправлять очевидно устаревшие ссылки и утверждения точечно.
- Изменить Availability лишь когда соответствующая возможность реально стала доступной Android/Server.
- Точное число сценариев и их статусы проверять в текущем README, не копировать устаревшие числа из старых отчётов.

### 4.7. Приёмка: PASS / PASS WITH MINOR FIX / BLOCKED

ChatGPT оценивает отчёт **по предоставленным доказательствам**, не делает вид, что выполнил независимую кодовую проверку.

- **PASS:** заявленное поведение соответствует ТЗ, достаточные проверки пройдены, блокирующих вопросов нет.
- **PASS WITH MINOR FIX:** работа в целом принята, нужна узкая исправляющая задача (например, некорректный код ошибки или неправильная классификация ответа). Не запускать новый полный аудит.
- **BLOCKED:** нет нужного API, обнаружен существенный риск для данных или требуемое поведение нельзя безопасно реализовать в согласованной границе. Обсудить новую развилку.

После исправления — адресные тесты, регрессия по риску и краткий отчёт; дальше **не переоткрывать** все закрытые решения.

### 4.8. Git и Miro

- Итоговый `git diff`, `git status`, результаты тестов — до коммита. Если доступен только отчёт агента, честно так и говорить.
- Коммит делает пользователь; **каждый репозиторий отдельно**. Предлагать понятные названия вида `A12.4: Удаление файлов и папок в Library` и отдельное название для System SPEC.
- Повышение номера сборки — по сложившейся практике проекта, но проверить текущую версию; не привязывать вечно номера к этому файлу.
- После слов пользователя «закоммитил» считать этап зафиксированным, **не спорить со старым статусом**. Если новый отчёт утверждает обратное, попросить агента проверить актуальные branch/status/log и объяснить расхождение, без сбросов.
- **Miro обновлять по принятому порядку:** при согласовании этапа, его приёмке и подтверждённом коммите; сообщать пользователю об изменении. Новые приоритеты и продуктовые развилки **не назначать самостоятельно**. Если Miro недоступен, не утверждать, что доска обновлена, и не блокировать работу.
- В Miro фиксировать суть принятого решения, тесты, ограничения, зависимости и отложенные работы. Не писать неподтверждённое `PASS`.

## 5. Инженерные правила, выработанные на практике

### 5.1. Сохранность данных и неизвестные результаты

- Любая запись с неизвестным результатом — **не обязательно неуспех**. Например, HTTP-запрос на move/copy/delete выполнился, но ответ потерян или успешный 2xx не разобрался.
- Для неидемпотентной операции **не повторять автоматически** после такого исхода. Сообщить «результат неизвестен», заблокировать немедленное подтверждение и предложить обновить источник и назначение.
- Если операция документированно идемпотентна по стабильному ключу/ID (например, определённые запросы регистрации источника или повтор `DELETE /folders/{id}/backup`), повтор возможен **в рамках доказанной семантики**, без создания нового UUID/имени.
- После массовой операции не объявлять общий успех при частичных ошибках. Учитывать `SUCCESS`, `FAILED`, `UNKNOWN`, `NOT_PROCESSED`; не скрывать остаток пакета.
- Не обновлять оптимистично пользовательский список при необратимом действии без подтверждения Server.
- Не превращать временную сетевую ошибку в удаление локальных сведений, выход из сессии или повторную регистрацию источника.

### 5.2. Android: Room, SAF, WorkManager

- Каждая миграция Room — **явная добавляющая или отдельно согласованная преобразующая**, без destructive fallback, который может стереть Camera/backup очередь. Тестировать миграцию на БД с существующими данными.
- Сохранять SAF-разрешения и связь `sourceUuid` / серверной папки; удалённое отключение источника — окончательное для текущей регистрации, **не делать автоматическое POST-регистрации заново**.
- Для Camera/A8 и резервирования папок — отдельные очереди и логика; изменения в одной не должны бесконтрольно затрагивать другую.
- WorkManager: учитывать бюджеты, прерывания, повтор, backoff, пересечение periodic и one-time; следовать **реально принятой** реализации, не копировать устаревшие дефекты.
- Не объявлять «всё проверено» только по Robolectric: реальные SAF/permissions, ANR, restart и работу провайдера при необходимости проверять на эмуляторе/устройстве.

### 5.3. Server и ограничения библиотеки

- **Server является источником истины** по разрешениям, ownership и допустимости операций. UI скрывает/блокирует явно запрещённые действия, но не заменяет серверную проверку.
- ROOT, Camera, AutoUploads и активные источники различаются по правилам. Не предполагать, что любые файлы Camera имеют те же права, что и сама системная папка.
- Активный корень автоматического источника помечен `backupSource=UUID`; **вложенные папки не несут этот маркер**. Принадлежность к управляемому дереву определяется по предкам или известному пути. Ручная запись в управляемое дерево запрещена.
- После отключения источник остаётся обычной USER-папкой; содержимое остаётся, папку можно редактировать и переносить из AutoUploads, если это разрешено Server.
- Изменённый файл автоматического backup: прежняя серверная версия сначала переименовывается **с сохранением старого ID**, новая загружается **с новым ID**; промежуточные состояния и архивное имя сохраняются в Room для recovery.
- Не изобретать отсутствующий Server API. Например, копирование папки сейчас не реализовано; нельзя молча заменять его десятками клиентских запросов.
- Серверное удаление папки может быть рекурсивным и необратимым для пользователя. Для UI нужно понятное подтверждение и проверка фактического Server-контракта.
- Удаление файла владельцем на текущем Server удаляет также другие FileItem, если они разделяют тот же StoredObject. Сейчас upload и copy создают независимые StoredObject; **при будущей реализации sharing пересмотреть это правило и тесты удаления**.

### 5.4. Код, конфигурация, безопасность

- Небольшие целевые изменения, понятный контракт, тесты. Не плодить слои, сущности, миграции, зависимости и рефакторинг «на будущее».
- **Комментарии** в исходниках — короткие, редкие, на русском, для инварианта, нетривиальной причины и существенного ограничения. Не комментировать очевидное, не оставлять устаревших TODO/KDoc.
- **TODO** — конкретная отложенная работа с причиной; предпочтительно Miro/System SPEC, а не бессистемные комментарии повсюду.
- **Server YAML:** переносить туда реальные настройки развёртывания (лимиты, сроки, пороги, таймауты) при необходимости; использовать единый default и ясные единицы измерения. Не переносить алгоритмы/инварианты в YAML и не менять параметры без решения пользователя.
- **Android:** централизованная конфигурация в принятом Kotlin-месте, а не имитация серверного YAML.
- Не логировать секреты, токены, пароли, содержимое файлов или бинарные тела HTTP. Не публиковать учетные данные из изолированного smoke.
- Не менять dev-сервер, порт 8080, его рабочую БД/хранилище, не делать destructive операции с реальными медиа и приложением без явного согласования. Тестировать на отдельных DB/Server/storage. Числа тестовых портов из старых отчётов — не гарантия текущего окружения.

## 6. Стандарты отчёта агента и принятия результата

Использовать короткий проверяемый отчёт, без длинного журнала каждого действия:

```text
Этап, цель и итог:
Что реализовано / что НЕ реализовано:
Изменённые компоненты и репозитории:
Необходимые продуктовые решения / отклонения от ТЗ:
Тесты: команды, количество, PASS/FAIL, что НЕ запускалось:
Smoke: изолированное окружение, шаги, сверка DB/файлов, ограничения:
Надёжность: retry, unknown result, прерывания, идемпотентность:
System SPEC / API contracts: обновлённые сценарии и Availability:

Известные ограничения и отложенные вопросы:
Следующий шаг: не начинать самостоятельно:
```

**Отчёт не равен независимому аудиту.** Для риска потери данных или неясных контрактов может понадобиться отдельная проверка. Для обычной принятой функции с полным набором тестов и изолированным smoke повторный аудит обычно избыточен.
