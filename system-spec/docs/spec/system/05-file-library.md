# Библиотека файлов и папок

## Что пользователь может делать через Android сейчас

Android Files показывает локальную очередь в текстовом виде. Удалённой галереи, списка и скачивания файлов Server, управления удалёнными файлами/папками в Android нет. Автоматический поиск папки, checksum pre-check и upload относятся к [backup](04-backup-and-sync.md).

Используемая модель: [LocalMedia](01-system-model.md#local-media), [Folder](01-system-model.md#folder), [RemoteFile](01-system-model.md#remote-file), [StoredObject](01-system-model.md#stored-object) и [FileMetadata](01-system-model.md#file-metadata).

<a id="files-local"></a>

## FILES-LOCAL — Просмотр локальной очереди на Files

**Status:** AS-IS

**Availability:** ANDROID_ONLY

### Назначение

Показать известные Android фотографии и ход их обработки.

### Текущее поведение

Пользователь открывает Files.

1. Files доступен независимо от входа. При входе с tokens+URL проверяется permission: если он уже есть, пересматривается фон без UI scan; если нет — запускается системный запрос.
2. После grant Android пересматривает фон и выполняет UI scan; после отказа тоже пытается выполнить scan для карточки PermissionDenied.
3. Список показывает все LocalMedia, новые по createdAt первыми: displayName, relativePath, size, status, наличие checksum и краткую failureReason.
4. Показываются Total, счётчики семи используемых состояний, последний UI scan и последний общий результат sync.

Пользователь видит локальную историю обработки, а не список файлов Server.

### Ошибки и recovery

Permission/error cards относятся к UI scan. Общая карточка может показывать SUCCESS при FAILED строках или сохранять прежний результат после permission failure worker. LastScanResult не обновляется worker scan; ScanResult.insertedOrUpdated обозначает число строк снимка, а не число реально изменённых записей.

### Текущие ограничения

Нет фото/thumbnail/preview, serverFileId, подробных background errors, retry counters, времени ошибки и устойчивой истории sync. Индикатор isSyncing учитывает только RUNNING разовой задачи, не periodic. При UI scan или такой задаче Files показывает диалог загрузки, который нельзя закрыть обычным действием dismiss; он также перекрывает нижнюю навигацию. Нет кнопок Sync now, Scan, Pre-check, Upload, retry/reset/cancel, byte progress или resume. Последний общий outcome теряется с процессом.

## Что Server поддерживает, но Android не использует

Следующие операции доступны внешнему API-клиенту. Для них нужны действующий access и собственные файлы/папки. Поиск чужого или отсутствующего объекта возвращает 404; общие правила доступа — [ACCESS-OWNER](06-sharing-and-access.md#access-owner). Ошибки ниже дополняют эту общую границу. Здесь не подразумевается существующий web UI.

<a id="files-list"></a>

## FILES-LIST — Список удалённых файлов

**Status:** AS-IS

**Availability:** SERVER_ONLY

### Назначение

Просмотреть каталог файлов текущего пользователя.

### Текущее поведение

Внешний клиент запрашивает список с page/size и необязательной folderId.

1. При переданной folderId Server проверяет принадлежность папки.
2. Возвращает страницу только прямых файлов этой папки, а без folderId — всех файлов пользователя.
3. Порядок фиксирован: capturedAt, затем uploadedAt, затем ID по убыванию. Ответ содержит [FilePage](01-system-model.md#file-page) с файлами и данными страниц.

Получены логические записи; наличие и читаемость физических байтов не проверяются.

### Развилки и условия

По умолчанию page=0, size=10. Page должен быть неотрицательным, size — положительным; верхний предел size не задан.

### Ошибки и recovery

Отрицательный page/нулевой size → 400; отсутствующая/чужая папка → 404. При недоступном Server нет результата списка.

### Текущие ограничения

Нет фильтров по типу или дате или настраиваемой сортировки. Android не запрашивает этот список.

<a id="files-metadata"></a>

## FILES-METADATA — Метаданные удалённого файла

**Status:** AS-IS

**Availability:** SERVER_ONLY

### Назначение

Получить свойства конкретного RemoteFile.

### Текущее поведение

Внешний клиент запрашивает файл по логическому ID.

Server возвращает [FileItemDto](01-system-model.md#api-projections) с данными RemoteFile, свойствами StoredObject и доступной FileMetadata. StoredObject.filePath, filename и id не раскрываются.

Получены сведения из серверного каталога без чтения физических байтов.

### Ошибки и recovery

Отсутствующий/чужой file ID → 404. При этом запись может успешно возвращаться даже при отсутствии физических байтов.

### Текущие ограничения

Эта операция не проверяет целостность или читаемость содержимого. Смысл metadata и дат — [BACKUP-METADATA](04-backup-and-sync.md#backup-metadata).

<a id="files-download"></a>

## FILES-DOWNLOAD — Скачивание удалённого файла

**Status:** AS-IS

**Availability:** SERVER_ONLY

### Назначение

Получить байты, сохранённые на Server.

### Текущее поведение

Внешний клиент запрашивает download по ID логического файла. Для успеха нужны собственный RemoteFile и его читаемые физические байты.

1. Server проверяет владельца записи и доступность байтов.
2. В обычном ответе возвращает 200 с исходные байты без преобразования, сохранённым MIME и attachment с логическим именем файла.

Клиент получает текущие физические байты; checksum заново не вычисляется.

### Ошибки и recovery

Отсутствующий/чужой файл либо отсутствующие/нечитаемые байты → 404 FILE_ITEM_NOT_FOUND. Логическая запись при отсутствии байтов остаётся в list/exists. Другие ошибки ввода-вывода не имеют единого прикладного формата ответа; некорректные сохранённые MIME/path могут дать 400.

### Текущие ограничения

Android download не вызывает. Полное буферизование ответа при логировании Server не позволяет обещать постоянную память при больших файлах. Собственный контракт Range/206/416, ETag/conditional/cache поведения не закреплён; Поведение framework остаётся нерешённым вопросом и не объявляется отсутствующим.

<a id="folders-browse"></a>

## FOLDERS-BROWSE — ROOT и прямые подпапки

**Status:** AS-IS

**Availability:** SERVER_ONLY

### Назначение

Просмотреть логическую иерархию Server через API.

### Текущее поведение

Внешний клиент запрашивает ROOT либо children известной папки.

1. ROOT возвращается или лениво создаётся, если отсутствует.
2. Children возвращает только прямых потомков, отсортированных без учёта регистра имени, затем по ID. Рекурсивного ответа и pagination нет.

Клиент получает [FolderDto](01-system-model.md#api-projections). Для ROOT parentId отсутствует.

### Ошибки и recovery

Неизвестный/чужой parent → 404. Конкурентное создание ROOT может завершиться ошибкой БД или выполнения; единый путь восстановления с ответом 409 не гарантирован.

### Текущие ограничения

Android использует те же ROOT/children только для автоматического CAMERA lookup ([BACKUP-TARGET](04-backup-and-sync.md#backup-target)); пользовательского remote browsing в Android нет. GET ROOT сам не создаёт CAMERA/FILES. Full-tree/breadcrumb API отсутствует.

<a id="folders-create"></a>

## FOLDERS-CREATE — Создание пользовательской папки

**Status:** AS-IS

**Availability:** SERVER_ONLY

### Назначение

Создать USER-папку в своей удалённой иерархии.

### Текущее поведение

Внешний клиент передаёт имя и необязательный parentId. Родитель принадлежит пользователю и имеет тип ROOT или USER; без parentId используется ROOT.

1. Server убирает пробелы по краям имени, проверяет непустоту, длину до 255 и конфликт с занятыми/зарезервированными именами.
2. Создаёт USER-папку и возвращает её описание с 200.

Создаётся логическая Folder; физический каталог для неё не создаётся.

### Ошибки и recovery

Недопустимый родитель/имя → 400; отсутствующий/чужой родитель → 404; занятое/зарезервированное имя → 409. Гонка сохранения может дать 500.

### Текущие ограничения

Имена папок с общим родителем уникальны без учёта регистра. CAMERA/FILES — системные конечные папки, под ними нельзя создавать USER. Создание системных папок выполняет default upload, не эта операция.

<a id="folders-rename"></a>

## FOLDERS-RENAME — Переименование папки

**Status:** AS-IS

**Availability:** SERVER_ONLY

### Назначение

Изменить имя USER-папки.

### Текущее поведение

Внешний клиент передаёт ID папки и новое имя. Собственная USER-папка.

Server убирает пробелы по краям имени, проверяет непустоту, длину до 255 и конфликты с именами соседних папок и зарезервированными именами. Затем меняет Folder.name и Folder.updatedAt, возвращает 200 с описанием.

Меняется логическое имя; физические байты не перемещаются.

### Ошибки и recovery

Системная папка/некорректное имя → 400; отсутствующая/чужая папка → 404; конфликт имени → 409, при гонках возможна DB ошибка.

### Текущие ограничения

ROOT/CAMERA/FILES переименовывать нельзя; тип папки не меняется.

<a id="folders-move"></a>

## FOLDERS-MOVE — Перемещение папки

**Status:** AS-IS

**Availability:** SERVER_ONLY

### Назначение

Перенести USER-папку в другую часть своей иерархии.

### Текущее поведение

Внешний клиент задаёт targetParentId. Собственная USER-папка, target — собственный ROOT/USER.

1. Server проверяет исходную и целевую папки, исключает перемещение в себя/потомка и конфликт имени.
2. Меняет Folder.parent и Folder.updatedAt, возвращает 200 с описанием.

Меняется логическая иерархия; физическое хранилище не перемещается.

### Ошибки и recovery

Системная исходная/целевая папка, перемещение в себя или потомка → 400; отсутствующая/чужая папка → 404; конфликт имени → 409; возможны ошибки БД.

### Текущие ограничения

Проверка циклов при последовательном запросе не гарантирует ацикличность конкурентных перестановок. Android команды перемещения не имеет.

<a id="folders-delete"></a>

## FOLDERS-DELETE — Удаление пустой папки

**Status:** AS-IS

**Availability:** SERVER_ONLY

### Назначение

Удалить ненужную USER-папку.

### Текущее поведение

Внешний клиент отправляет delete по ID. Собственная USER-папка без children и files.

Server проверяет тип и пустоту, удаляет логическую Folder и возвращает 204 без тела.

Папка исчезает из каталога; физическое хранилище не затрагивается.

### Ошибки и recovery

Системная/непустая папка → 400; отсутствующая/чужая папка и повтор после успешного удаления → 404; гонка может дать DB ошибку.

### Текущие ограничения

Рекурсивное удаление не реализовано. Удаление папки не является командой массового удаления файлов.

<a id="files-rename"></a>

## FILES-RENAME — Переименование файла

**Status:** AS-IS

**Availability:** SERVER_ONLY

### Назначение

Изменить отображаемое имя RemoteFile.

### Текущее поведение

Внешний клиент передаёт логический ID и новое originalName.

Server проверяет непустое имя длиной до 255, убирает пробелы по краям и заменяет недопустимые символы, проверяет конфликт имени, сохраняет RemoteFile.originalName и возвращает 200 с описанием.

В ответе меняется originalFilename; физические имя/путь и FileMetadata остаются прежними.

### Ошибки и recovery

Некорректное имя → 400; отсутствующий/чужой файл → 404; занятое имя без учёта регистра вне CAMERA → 409; гонки могут дать DB ошибку.

### Текущие ограничения

В CAMERA совпадение имён допускается. Rename не меняет байты и не переименовывает оригинал на устройстве Android.

<a id="files-move"></a>

## FILES-MOVE — Перемещение файла

**Status:** AS-IS

**Availability:** SERVER_ONLY

### Назначение

Изменить Folder удалённого RemoteFile.

### Текущее поведение

Внешний клиент задаёт targetFolderId. Собственные file и target folder; допустима любая своя папка, включая системную.

Server проверяет имя в target, меняет папку и возвращает 200 с описанием. StoredObject и физические байты остаются прежними.

Файл находится в другой удалённой папке; локальное состояние Android автоматически не меняется.

### Ошибки и recovery

Отсутствующий/чужой файл или папка → 404; конфликт имени вне CAMERA → 409. Отдельного checksum pre-check в move нет: если в target уже есть тот же checksum и проверка имени прошла или пропущена, нарушение ограничения БД даёт 500 DATABASE_CONSTRAINT_VIOLATION.

### Текущие ограничения

Move не объединяет duplicate и не является успешной dedup-веткой upload. Обратная сверка отсутствует ([FILES-RECONCILE](05-file-library.md#files-reconcile)).

<a id="files-copy"></a>

## FILES-COPY — Копирование файла

**Status:** AS-IS

**Availability:** SERVER_ONLY

### Назначение

Создать независимую удалённую копию.

### Текущее поведение

Внешний клиент отправляет copy с необязательными targetFolderId и originalName; пустое тело-объект допустимо.

1. Без target используется исходная папка; пустое/отсутствующее имя означает исходное, другое имя очищается и проверяется.
2. Server проверяет принадлежность исходного файла и целевой папки и конфликты имени/checksum.
3. Копирует физические байты и создаёт новые StoredObject, RemoteFile и копию FileMetadata.
4. Возвращает 200 с новым ID; uploadedAt новый, capturedAt прежний.

Результат — независимая физическая копия без общей ссылки на прежний объект.

### Ошибки и recovery

Копирование в исходную папку конфликтует по checksum даже с новым именем; любой target с тем же checksum → 409. Конфликт имени вне CAMERA также → 409. Отсутствующий исходный файл или целевая папка → 404; отсутствующие физические байты источника дают ошибку ввода-вывода, не специальный 404. Гонка может дать 500; восстановление согласованности БД и файловой системы — [SYSTEM-STORAGE](07-system-rules-and-recovery.md#system-storage).

### Текущие ограничения

Checksum, размер, MIME, тип и расширение наследуются из исходного каталога, не пересчитываются по байтам. Изменение расширения нового имени не меняет унаследованное fileExtension.

<a id="files-delete"></a>

## FILES-DELETE — Удаление удалённого файла

**Status:** AS-IS

**Availability:** SERVER_ONLY

### Назначение

Удалить RemoteFile с учётом владения логической записью и физическим объектом.

### Текущее поведение

Внешний клиент отправляет delete по ID логического файла. Пользователь владеет RemoteFile. В обычном upload/copy он владеет и StoredObject.

1. Server находит собственный RemoteFile и сравнивает StoredObject.user с текущим пользователем.
2. Если пользователь владеет StoredObject, в одной транзакции БД удаляются все ссылающиеся на него RemoteFile, соответствующая FileMetadata и StoredObject. Только после фиксации транзакции Server пытается удалить байты.
3. Если пользователь владеет только RemoteFile, ссылающимся на чужой StoredObject, удаляется лишь его RemoteFile и FileMetadata; StoredObject и байты сохраняются.
4. Server возвращает 204 без тела.

Удаление логических записей завершено. Владелец StoredObject удаляет все ссылки на него, не ожидая последней. Удаление ссылки другим пользователем сохраняет StoredObject даже при последней ссылке.

### Ошибки и recovery

Отсутствующий/чужой файл и повтор успешного delete → 404. При ошибке БД до фиксации удаление байтов не начинается. Отсутствующие байты не мешают успеху; IOException их удаления только логируется и не отменяет 204. Повтор delete старого ID не повторяет прежнюю очистку файловой системы.

### Текущие ограничения

API upload/copy не создаёт cross-owner references; ветка удаления описывает допустимое состояние модели, не sharing feature ([SHARING-ABSENT](06-sharing-and-access.md#sharing-absent)). Trash/restore нет. Android не вызывает remote delete и не сбрасывает SYNCED от внешнего удаления.

<a id="files-checksums"></a>

## FILES-CHECKSUMS — Полный список checksum

**Status:** AS-IS

**Availability:** SERVER_ONLY

### Назначение

Получить контрольные суммы логических файлов пользователя через API.

### Текущее поведение

Внешний клиент запрашивает полный список checksum.

Server возвращает для всех RemoteFile пользователя [FileChecksumDto](01-system-model.md#api-projections): id, originalFilename и checksum из StoredObject.

Результат содержит логические ссылки и сохранённые checksum, без folderId.

### Текущие ограничения

Нет постраничной выдачи, фильтров и установленного порядка; байты не читаются. Этот список не является delta/reconciliation протоколом. Android использует только отдельный folder pre-check ([BACKUP-EXISTING](04-backup-and-sync.md#backup-existing)).

## Операции, отсутствующие в текущей системе

<a id="files-trash"></a>

## FILES-TRASH — Корзина, восстановление и версии

**Status:** AS-IS

**Availability:** NOT_PRESENT

### Назначение

Зафиксировать, можно ли отменить удаление или выбрать старую версию файла.

### Текущее поведение

Система не предоставляет корзину/восстановление, историю версий, перезапись или автоматическое переименование. Удаление файла физически удаляет записи; RemoteFile.deletedAt не заполняется активным API и не создаёт корзину.

Прикладного восстановления удалённого удалённый файл и выбора предыдущей версии нет.

### Текущие ограничения

Прежние удалённые копии после изменения локального изображения сохраняются по [BACKUP-CHANGE](04-backup-and-sync.md#backup-change), но не образуют историю версий. Внешние backup/restore неизвестны ([SYSTEM-STORAGE](07-system-rules-and-recovery.md#system-storage)).

<a id="files-reconcile"></a>

## FILES-RECONCILE — Remote reconciliation и bidirectional sync

**Status:** AS-IS

**Availability:** NOT_PRESENT

### Назначение

Определить реакцию Android на изменения удалённого каталога.

### Текущее поведение

Внешний клиент переименовал, переместил или удалил удалённый файл либо Server потерял bytes.

Android не получает удалённые изменения, не применяет их к изображениям устройства и не пересматривает обычный SYNCED. Общего протокола delta/tombstones/device/sync sessions/push нет.

Локальная история может расходиться с текущей удалённой библиотекой. Наличие Server list/checksums/CRUD не создаёт двустороннюю сверку.

### Текущие ограничения

Нет Android remote gallery/download/организации папок и файлов. Local delete propagation также отсутствует ([BACKUP-DELETE](04-backup-and-sync.md#backup-delete)); remote loss не запускает автоматический repair/re-upload SYNCED.

### Нерешённый вопрос

Направления синхронизации, retention и роль Android при удалённых изменениях ещё не приняты как продуктовая модель.
