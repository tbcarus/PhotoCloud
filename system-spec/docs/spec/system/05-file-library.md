# Библиотека файлов и папок

## Что пользователь может делать через Android сейчас

Android Files показывает локальную очередь в текстовом виде, Library — содержимое серверной библиотеки ([FILES-BROWSE](05-file-library.md#files-browse)). На Library пользователь вручную скачивает отдельный файл ([FILES-DOWNLOAD](05-file-library.md#files-download)), загружает в открытую папку файлы ([FILES-UPLOAD-MANUAL](05-file-library.md#files-upload-manual)) или целую папку ([FOLDERS-UPLOAD-MANUAL](05-file-library.md#folders-upload-manual)), создаёт папку ([FOLDERS-CREATE](05-file-library.md#folders-create)), переименовывает отдельную папку ([FOLDERS-RENAME](05-file-library.md#folders-rename)) или файл ([FILES-RENAME](05-file-library.md#files-rename)), перемещает папку ([FOLDERS-MOVE](05-file-library.md#folders-move)) или файл ([FILES-MOVE](05-file-library.md#files-move)), копирует файл ([FILES-COPY](05-file-library.md#files-copy)) и удаляет папку ([FOLDERS-DELETE](05-file-library.md#folders-delete)) или файл ([FILES-DELETE](05-file-library.md#files-delete)). Ручные передачи не входят в автоматическую очередь backup Camera. Выделенные объекты одной папки перемещаются, удаляются, а файлы копируются группой ([групповые операции](05-file-library.md#files-browse-batch)). Содержимое папки показывается списком или плиткой, с миниатюрами изображений ([FILES-THUMBNAIL](05-file-library.md#files-thumbnail)). Изображения открываются в полноэкранном просмотре ([просмотр](05-file-library.md#files-browse-viewer)), видео воспроизводится потоком во встроенном плеере ([воспроизведение видео](05-file-library.md#files-browse-video)), PDF открывается в постраничном просмотре ([просмотр PDF](05-file-library.md#files-browse-pdf)). Остальные файлы открываются установленными приложениями Android ([внешнее приложение](05-file-library.md#files-browse-external)). Файлы и папки, которыми поделились другие пользователи, доступны только для чтения в разделе «Доступно мне» ([SHARED-WITH-ME](05-file-library.md#shared-with-me)). Замены и корзины в Android нет; копирования папки нет и на Server. Автоматический поиск папки, checksum pre-check и upload Camera относятся к [backup](04-backup-and-sync.md).

Используемая модель: [LocalMedia](01-system-model.md#local-media), [Folder](01-system-model.md#folder), [RemoteFile](01-system-model.md#remote-file), [StoredObject](01-system-model.md#stored-object) и [FileMetadata](01-system-model.md#file-metadata).

## FILES-LOCAL — Просмотр локальной очереди на Files

**Status:** IMPLEMENTING

**Availability:** ANDROID_ONLY

### Назначение

Показать известные Android фотографии и ход их обработки.

### Текущее поведение

Пользователь открывает Files.

1. Files доступен независимо от входа и системных запросов разрешений не выполняет: разрешения выдаются на Settings ([BACKUP-DISCOVER](04-backup-and-sync.md#backup-discover)). При входе с tokens+URL и полном доступе к фото пересматривается фон.
2. Вверху — одна карточка состояния резервного копирования по [BackupState](01-system-model.md#backup-state): «Выполняется резервное копирование» (с немодальным индикатором), «Ожидает продолжения» или «Ожидает проверки фотографий», «Требуется внимание», «Все обнаруженные фото сохранены». Под заголовком — все актуальные причины: нет доступа ко всем фото (в том числе при частичном «выбранные фото»; разрешение — на Settings), вход не выполнен (фото готовятся, но не отправляются), адрес сервера не задан (Network), не удалось проверить фото, фото ещё не проверялись, сервер не отвечает или ошибка отправки — с временем возникновения и повтором автоматически, число FAILED. Проблема одной части показывается и во время работы другой. Строки при отсутствии доступа не удаляются. Полный доступ к фото перечитывается при открытии и каждом возврате на экран.
3. Список показывает все LocalMedia, новые по createdAt первыми: displayName, relativePath, size, status, наличие checksum и краткую failureReason.
4. В карточке — пять счётчиков из агрегирующего запроса Room: Всего, Сохранено, Ошибки, Подготовка (PENDING, HASHING), К отправке (CHECKSUM_READY, PENDING_UPLOAD, UPLOADING); время последней успешной проверки фото и, если известно, последней подтверждённой отправки файла. Процента выполнения и прогресс-бара нет; предупреждения «давно не проверялось» нет. Собственного scan Files не запускает: изображения обнаруживает Поставщик, синхронизацию выполняют фоновые задачи ([BACKUP-BACKGROUND](04-backup-and-sync.md#backup-background)).
5. При полном доступе без ACCESS_MEDIA_LOCATION показывается пояснение «Нет доступа к геоданным фото»: backup продолжается, но координаты съёмки могут не сохраниться в копии; доступ выдаётся на экране Settings.

Пользователь видит локальную историю обработки, а не список файлов Server.

### Ошибки и recovery

Причины отсутствия доступа, входа и адреса отражают текущее состояние; сохранённая ошибка части — последний известный итог с временем возникновения, она скрывается, когда часть снова выполняется или не может её объяснить. При FAILED и до первой успешной проверки «Все обнаруженные фото сохранены» не показывается. Состояние переживает перезапуск процесса: счётчики — Room, итоги — DataStore, активность — WorkManager. Ошибки отдельных файлов видны в списке как краткая failureReason.

### Текущие ограничения

Нет фото/thumbnail/preview, serverFileId, подробного текста фоновых ошибок, retry counters, времени ошибки отдельного файла и истории sync. Индикатор выполнения учитывает RUNNING разовых и periodic задач Поставщика и Загрузчика; список и навигация остаются доступны. Время проверки и отправки — конец прогона по часам устройства. Нет кнопок Sync now, Scan, Pre-check, Upload, retry/reset/cancel, byte progress или resume. Список загружает все строки индекса одним запросом в транзакции чтения.

<a id="files-browse"></a>

## FILES-BROWSE — Просмотр серверной библиотеки на Library

**Status:** IMPLEMENTING

**Availability:** END_TO_END

### Назначение

Показать на Android папки и файлы, которые хранятся на Server, независимо от локальной очереди backup.

### Текущее поведение

Пользователь открывает пункт Library нижней панели.

1. Android проверяет, что адрес Server задан и есть сессия, запрашивает ROOT ([FOLDERS-BROWSE](05-file-library.md#folders-browse)), затем прямые подпапки и первую страницу файлов ([FILES-LIST](05-file-library.md#files-list)).
2. Экран показывает название «Библиотека», путь вида «Корень / Проекты / Светильники», кнопку переключения вида ([список и плитка](05-file-library.md#files-browse-grid)), кнопку обновления, в ROOT и USER вне управляемого дерева — кнопку «+» с пунктами «Создать папку» ([FOLDERS-CREATE](05-file-library.md#folders-create)), «Загрузить файлы» и «Загрузить папку» ([FILES-UPLOAD-MANUAL](05-file-library.md#files-upload-manual)), панель текущей ручной передачи и содержимое папки списком или плиткой: сначала подпапки в порядке Server, затем файлы. В списке папок Camera стоит первой. Camera отображается, только если уже существует: просмотр выполняет только GET и папок не создаёт.
3. Нажатие на папку открывает её. Стрелка у пути и системный Back переходят к родителю; в ROOT Back работает по обычным правилам приложения. В ROOT первой строкой стоит виртуальный элемент «Доступно мне» ([SHARED-WITH-ME](05-file-library.md#shared-with-me)).
4. Файлы ROOT и USER запрашиваются с sort=name, файлы Camera — без sort, в порядке по дате.
5. Строка папки показывает значок и имя, у специальных папок — подпись типа. Значки: Camera — камера («Резервные копии фото»), AutoUploads — облако с загрузкой («Автоматическая загрузка папок»), корень активного источника — папка с отметкой синхронизации («Источник автоматической загрузки»), остальные папки, в том числе вложенные папки источника и отключённые источники, — обычная папка без подписи.
6. Строка файла показывает слева миниатюру JPEG, PNG и WebP ([FILES-THUMBNAIL](05-file-library.md#files-thumbnail-android)), для остальных типов — иконку по FileType, затем исходное имя и краткий тип, размер и дату: uploadedAt, в Camera — capturedAt, без пересчёта пояса. capturedAt без даты в файле равен времени загрузки, поэтому экран не называет его датой съёмки. Нажатие на строку изображения JPEG, PNG или WebP открывает [полноэкранный просмотр](05-file-library.md#files-browse-viewer), на строку видео — встроенный плеер ([воспроизведение видео](05-file-library.md#files-browse-video)), на строку PDF — [просмотр PDF](05-file-library.md#files-browse-pdf), на строку остального файла с ID и SHA-256 — [внешнее приложение](05-file-library.md#files-browse-external).
7. Кнопка «⋮» строки открывает меню только с разрешёнными действиями. У файла — «Скачать» ([FILES-DOWNLOAD](05-file-library.md#files-download)), пока не идёт другая ручная передача, «Переименовать» ([FILES-RENAME](05-file-library.md#files-rename)), «Переместить» ([FILES-MOVE](05-file-library.md#files-move)), «Копировать» ([FILES-COPY](05-file-library.md#files-copy)) и «Удалить» ([FILES-DELETE](05-file-library.md#files-delete)); у USER-папки — «Переименовать» ([FOLDERS-RENAME](05-file-library.md#folders-rename)), «Переместить» ([FOLDERS-MOVE](05-file-library.md#folders-move)) и «Удалить» ([FOLDERS-DELETE](05-file-library.md#folders-delete)). «Копировать» у папки нет: на Server такой операции нет. У папки без доступных действий кнопки нет. Правила доступности — в «Развилках».
8. Файлы загружаются страницами по 50. При прокрутке к концу списка запрашивается следующая страница, пока hasNext истинно; одновременно выполняется не больше одного такого запроса. Файл, вернувшийся повторно из-за сдвига offset, отбрасывается по ID.
9. Кнопка обновления заново запрашивает текущий каталог с первой страницы.

Открытая папка, загруженный список, вид и положение прокрутки сохраняются при переключении вкладок без новых запросов. Путь хранится только в памяти процесса: после его гибели Library начинается с ROOT. Данные библиотеки не пишутся в LocalMedia и не влияют на backup.

### Развилки и условия

Смена адреса Server, пользователя (subject access token) или выход сразу сбрасывают путь, списки, открытый диалог имени и незавершённые загрузки; следующий показ Library начинается с ROOT нового контекста. Обновление токенов того же пользователя контекст не меняет. Запоздавший ответ прежней папки или прежнего контекста игнорируется.

Доступность изменений Android определяет по FolderDto и открытому пути; окончательно решает Server ([FOLDERS-MANAGED-TREE](05-file-library.md#folders-managed-tree)):

| Где | «Создать папку», загрузка | «Переименовать», «Переместить», «Удалить» папку | «Переименовать», «Копировать», «Удалить» файл | «Переместить» файл |
| --- | --- | --- | --- | --- |
| ROOT, обычная USER-папка, отключённый источник и его вложенные папки | Есть | У USER-папок | Есть | Есть |
| Camera | Нет | — | Есть, по правилам Camera | Нет |
| AutoUploads | Нет | Только у отключённых источников | — | — |
| Корень активного источника и любая папка ниже него | Нет | Нет | Нет | Нет |

ROOT, Camera, AutoUploads и корень активного источника не переименовываются, не перемещаются и не удаляются; отдельные файлы Camera удалять можно. Файл Camera не перемещается: Server не переносит файлы между Camera и библиотекой, а другой папки Camera нет. Вложенные папки активного источника backupSource не имеют: принадлежность дереву определяется по корню источника на открытом пути, а не по самой папке.

<a id="files-browse-grid"></a>

**Список и плитка.** Кнопка в верхней панели переключает вид содержимого открытой папки; её значок показывает вид, в который она переключит: «Показать плиткой» в списке и «Показать списком» в плитке. По умолчанию — список. Вид — состояние экрана: он сохраняется при переходах между папками, при обновлении, смене вкладок, а также при смене сервера или пользователя, пока жив процесс; после гибели процесса Library снова начинается со списка.

1. Оба вида показывают одни и те же загруженные папки и файлы в одном порядке (подпапки, затем файлы) и используют общие выделение, постраничную загрузку, меню действий и правила доступности. Переключение не запрашивает каталог заново, не сбрасывает выделение и сохраняет первую видимую позицию; смещение внутри строки сбрасывается.
2. Плитка — сетка с числом столбцов по ширине экрана (не уже 120 dp). Плитка папки — значок её вида (Camera, AutoUploads, корень активного источника, обычная папка), имя до двух строк и «⋮», если у папки есть действия; миниатюр папок по содержимому нет. Плитка файла — квадратная область с миниатюрой ([FILES-THUMBNAIL](05-file-library.md#files-thumbnail-android)), вписанной без искажения, или значком типа, имя до двух строк и «⋮».
3. Нажатие на плитку папки открывает её, нажатие на плитку изображения — полноэкранный просмотр, на плитку видео — плеер, на плитку PDF — просмотр PDF, на плитку остального файла — внешнее приложение, как в списке. Долгое нажатие включает выделение; в режиме выделения нажатие переключает отметку, у плитки появляется флажок, выделенная плитка обведена и подсвечена, вместо «⋮» флажок.
4. Следующая страница запрашивается при приближении к концу сетки так же, как в списке; индикатор подгрузки и ошибка с «Повторить» занимают всю ширину. Пустая папка, загрузка и ошибки каталога показываются одинаково в обоих видах.
5. Выбор папки назначения всегда показывается списком, кнопка вида в это время недоступна; после подтверждения или отмены возвращается выбранный вид.

<a id="files-browse-viewer"></a>

**Полноэкранный просмотр изображений.** Вне выделения и выбора назначения нажатие на файл JPEG, PNG или WebP (MIME Server по содержимому, с ID и checksum) в списке или плитке открывает просмотр поверх всего приложения. Library под ним не меняется: папка, вид, прокрутка, загруженные страницы и выделение остаются прежними; «Назад» и крестик закрывают просмотр. В режиме выделения нажатие по-прежнему переключает отметку.

1. Показывается оригинал файла: Android скачивает его тем же запросом, что [FILES-DOWNLOAD](05-file-library.md#files-download), через авторизованный клиент, потоком во временный файл приложения, проверяет размер и SHA-256 и только после совпадения атомарно переносит в приватный кеш оригиналов. Повреждённые и незавершённые файлы удаляются. Это не ручное скачивание: файл не сохраняется в выбранную пользователем папку или галерею, TransferManager и SAF не участвуют.
2. Кеш оригиналов — каталог в cacheDir приложения; имя файла — SHA-256 содержимого, без исходного имени, адреса Server, пользователя и токенов. Проверенная копия открывается без сети, в том числе для другого ID или после смены адреса Server при том же checksum; копия с неожиданным размером удаляется и скачивается заново. Объём ограничен 1 ГиБ, при нехватке вытесняются давно не открывавшиеся файлы; файл, открытый в просмотре, не вытесняется. Одно содержимое не скачивается параллельно дважды. Если свободного места на устройстве не хватает, скачивание не начинается. Android может сам очистить кеш: тогда оригинал скачивается снова. Выход, смена пользователя или Server кеш оригиналов не очищают.
3. Пока оригинал загружается, показывается миниатюра из кеша и небольшой индикатор; «Назад» доступен. Оригинал декодируется ImageDecoder с учётом EXIF-ориентации и прореживанием: кадр не больше 4096 px по длинной стороне и 12 Мп, многомегапиксельный оригинал целиком в память не разворачивается. Декодирования отдельных областей при глубоком увеличении нет.
4. Двойное нажатие увеличивает изображение в 2,5 раза к точке нажатия и возвращает исходный вид, сведение пальцев масштабирует от 1 до 5 раз, перетаскивание сдвигает увеличенное изображение; сдвиг ограничен краями изображения.
5. Горизонтальный жест листает изображения текущей папки в порядке Library: только просматриваемые файлы из уже загруженных страниц, без папок, видео и документов. При увеличении листание выключено, и жест сдвигает изображение. Когда до конца загруженной части остаётся не больше трёх изображений, запрашивается следующая страница тем же механизмом, что у списка. Оригинал скачивается только для открытой страницы; страница, ушедшая с экрана, отменяет своё скачивание.
6. Ошибка показывается на месте изображения и не закрывает Library: «Нет связи с сервером», «Файл не найден на сервере» (404), «Требуется вход» (401/403), «Недостаточно места на устройстве», «Скачанные данные не совпадают с файлом на сервере», «Не удалось загрузить изображение», «Не удалось показать изображение» (ошибка декодирования). Повтор — только кнопкой «Повторить», автоматических повторов нет.
7. Смена Server, пользователя или выход закрывают просмотр и отменяют его скачивание; поздний ответ прежней сессии просмотр не открывает. Если открытый файл пропал из загруженного списка, просмотр закрывается.

<a id="files-browse-video"></a>

**Воспроизведение видео.** Вне выделения и выбора назначения нажатие на файл с MIME Server `video/*` (тип по содержимому, с ID) в списке или плитке открывает встроенный плеер Media3 поверх всего приложения. Library под ним не меняется, как при просмотре изображений; «Назад» и крестик закрывают плеер. Видео не входит в листание изображений. В режиме выделения нажатие по-прежнему переключает отметку.

1. Видео воспроизводится потоком тем же запросом, что [FILES-DOWNLOAD](05-file-library.md#files-download), через авторизованный клиент приложения: access token передаётся только в заголовке и при истечении обновляется тем же механизмом, что у остальных запросов; в адрес токен не попадает. Оригинал заранее целиком не скачивается и на диск не сохраняется: кеш оригиналов, TransferManager и SAF не участвуют. Без связи с Server видео не воспроизводится.
2. Воспроизведение начинается после готовности плеера. Перемотка за пределы загруженного выполняется штатно Media3: тот же адрес запрашивается с заголовком `Range: bytes=N-`, Server отвечает 206 с запрошенной частью. Закрытие плеера прерывает загрузку.
3. Управление — штатные элементы Media3: воспроизведение и пауза, шаг назад и вперёд, шкала перемотки, позиция и длительность, индикатор буферизации. Видео вписывается в экран с сохранением пропорций.
4. На открытое видео создаётся один плеер; закрытие его освобождает. Уход приложения в фон ставит паузу, после возврата воспроизведение само не продолжается. При повороте экрана прежний плеер освобождается, новый продолжает с той же позиции. Смена Server, пользователя или выход закрывают плеер. Фонового воспроизведения и «картинки в картинке» нет.
5. Ошибка закрывает видео и элементы управления сообщением и не закрывает Library: «Файл недоступен на сервере» (404), «Требуется вход» (401/403), «Нет связи с сервером», «Формат видео не поддерживается на этом устройстве», в остальных случаях «Не удалось воспроизвести видео». Перед показом ошибки загрузки Media3 сам повторяет запрос по своей штатной политике; дальше повтор — кнопкой «Повторить», с прежней позиции. Если ни одна видеодорожка файла не поддерживается устройством, плеер не играет один звук, а показывает «Формат видео не поддерживается на этом устройстве».
6. Server видео не перекодирует: воспроизводятся форматы, которые поддерживают Media3 и декодеры устройства. Основной формат — MP4 (H.264, AAC); WebM (VP8, VP9), HEVC, AV1 и прочие кодеки зависят от устройства. Тип по содержимому для MP4 может быть `video/quicktime`; такой файл тоже открывается в плеере.

<a id="files-browse-pdf"></a>

**Просмотр PDF.** Вне выделения и выбора назначения нажатие на PDF (MIME Server `application/pdf`, при общем `application/octet-stream` — по расширению `.pdf`; с ID и checksum) в списке или плитке открывает просмотр поверх всего приложения. Library под ним не меняется; «Назад» и крестик закрывают просмотр. В режиме выделения нажатие по-прежнему переключает отметку.

1. Документ берётся из того же кеша оригиналов, что у [просмотра изображений](05-file-library.md#files-browse-viewer): тот же запрос [FILES-DOWNLOAD](05-file-library.md#files-download), проверка размера и SHA-256, ключ — checksum, общий предел 1 ГиБ. Проверенная копия открывается без сети и без повторного скачивания; открытый документ не вытесняется. Отдельного кеша PDF и сохранения страниц на диск нет.
2. Страницы показывает системный PdfRenderer. Просмотр постраничный: на экране одна страница, вписанная в экран; переход кнопками «Предыдущая» и «Следующая» и горизонтальным жестом в обычном масштабе; внизу «Страница N из M». Рендерится только текущая страница, вне главного потока, в изображение не больше 3072 px по длинной стороне и 6 Мп.
3. Двойное нажатие и сведение пальцев масштабируют страницу так же, как изображение (до 5 раз), перетаскивание сдвигает увеличенную страницу; при увеличении жест страницу не переключает.
4. Пока документ загружается, показывается «Загрузка документа», пока рендерится страница — индикатор. Ошибки: «Нет связи с сервером», «Файл не найден на сервере» (404), «Требуется вход» (401/403), «Недостаточно места на устройстве», «Скачанные данные не совпадают с файлом на сервере», «Не удалось загрузить документ» — с кнопкой «Повторить»; «Документ повреждён или не читается» и «Документ защищён паролем: такие PDF не открываются» — без повтора: проверенное содержимое от повтора не изменится; «Недостаточно памяти для показа страницы» — с повтором страницы. Некорректный документ приложение не закрывает.
5. Закрытие освобождает PdfRenderer, файл и защиту копии от вытеснения. Смена Server, пользователя или выход закрывают просмотр и отменяют загрузку; кеш оригиналов не очищается. Если файл пропал из загруженного списка, просмотр закрывается. При повороте экрана документ открывается заново из кеша на той же странице.
6. Первая версия: нет непрерывной прокрутки, поиска и выделения текста, аннотаций, печати и PDF с паролем.

<a id="files-browse-external"></a>

**Открытие во внешнем приложении.** Обычное нажатие выбирает просмотр по типу: JPEG, PNG и WebP — [просмотр изображений](05-file-library.md#files-browse-viewer), видео — [плеер](05-file-library.md#files-browse-video), PDF — [просмотр PDF](05-file-library.md#files-browse-pdf), остальные файлы с ID и SHA-256 (TXT, DOCX, XLSX, ZIP, STEP, HEIC и прочие) — установленное приложение Android. В режиме выделения и при выборе назначения нажатие работает по-прежнему.

1. Копия берётся из того же кеша оригиналов: тот же запрос [FILES-DOWNLOAD](05-file-library.md#files-download), проверка размера и SHA-256, ключ — checksum, общий предел 1 ГиБ; уже скачанная копия открывается без повторного скачивания. Пока копия загружается, показывается «Открытие файла» с именем и кнопкой «Отмена». Отмена, смена Server, пользователя или выход прерывают загрузку, и внешнее приложение не запускается. Файл больше 1 ГиБ в кеш не загружается: сообщение предлагает сохранить его через «Скачать».
2. Файл передаётся системным просмотром (ACTION_VIEW): Android предлагает подходящее приложение или открывает выбранное по умолчанию. Адрес — `content://` FileProvider приложения, которому доступен только каталог кеша оригиналов. Внешнее приложение получает временное право только на чтение этого адреса, без записи и постоянного доступа, и видит исходное имя файла; копия под исходным именем не создаётся.
3. Тип файла — MIME Server; при `application/octet-stream`, внутреннем типе Tika (`application/x-tika-*`, например `application/x-tika-ooxml` у DOCX и XLSX) или пустом — по расширению исходного имени, иначе `application/octet-stream`. Запрос типа у провайдера тоже отвечает по расширению исходного имени, а не по имени копии в кеше.
4. Пока открыто внешнее приложение, копия защищена от вытеснения из кеша; защита снимается, когда пользователь возвращается в PhotoCloud. Library при этом не меняется.
5. Ошибки показываются сообщением, Library продолжает работать: «Нет связи с сервером», «Файл не найден на сервере», «Требуется вход», «Недостаточно места на устройстве», «Скачанные данные не совпадают с файлом на сервере», «Не удалось загрузить файл», файл больше 1 ГиБ, «Нет приложения для открытия файлов этого типа».
6. Внешнее приложение работает с копией только на чтение: изменения в нём на Server не попадают.

<a id="files-browse-destination"></a>

**Выбор папки назначения.** «Переместить» и «Копировать» переводят Library в режим выбора назначения. Над списком панель: операция и имя объекта, причина, по которой открытая папка не подходит, «Отмена» и «Переместить сюда» / «Копировать сюда». Выбор начинается в папке объекта; навигация, путь, стрелка «назад», обновление и постраничная загрузка — обычные Library. Подпапки открываются нажатием, файлы видны приглушёнными для сверки имён, меню строк, «+» и отключение источника скрыты. Системный Back поднимается к родителю, в ROOT — отменяет выбор. Недопустимое назначение не подтверждается:

| Назначение | Перемещение файла | Копирование файла | Перемещение папки |
| --- | --- | --- | --- |
| Папка объекта | Нет: «уже находится здесь» | Да, с другим именем | Нет: «уже находится здесь» |
| ROOT, USER-папка, отключённый источник | Да | Да | Да, кроме самой папки и её поддерева |
| Camera | Только для файла Camera, поэтому не предлагается | Нет: из библиотеки запрещено, внутри Camera — конфликт содержимого | Нет |
| AutoUploads | Нет | Нет | Нет |
| Корень активного источника и его поддерево | Нет | Нет | Нет |

Сама перемещаемая папка, Camera, когда она не подходит, и корень активного источника показаны в списке приглушёнными с причиной и не открываются. В AutoUploads войти можно: отключённые источники в нём — допустимые назначения. Кнопка подтверждения открывает итог: объект, папка «Из», папка «В»; для копии — редактируемое имя, по умолчанию исходное. Отмена на любом шаге ничего не меняет на Server и возвращает исходную папку с прежним списком и прокруткой без запросов; если запрос уже отправлялся, исходная папка перечитывается.

<a id="files-browse-batch"></a>

**Множественный выбор и групповые операции.** Долгое нажатие на файл или папку открывает режим выделения и отмечает объект; в режиме нажатие переключает отметку, вместо «⋮» в строке флажок. Выделяются только объекты, допускающие изменения ([таблица доступности](05-file-library.md#files-browse)): системные папки, корень активного источника и всё в активном дереве не отмечаются, и нажатие на них в режиме ничего не делает. Выделение хранится по типу и ID объекта, поэтому подгрузка страниц его не меняет, а один ID учитывается один раз. Панель режима показывает «Выбрано: N», кнопку выхода, команды «Выделить загруженные» (только уже загруженные строки, без догрузки каталога) и «Снять выделение», а также «Переместить», «Копировать» и «Удалить». Системный Back сначала закрывает режим; переход в другую папку, смена адреса Server, пользователя или выход сбрасывают выделение, обновление той же папки — нет.

| Операция | Набор | Условия |
| --- | --- | --- |
| Переместить | Файлы и папки | Не в Camera. Назначение — [выбор папки](05-file-library.md#files-browse-destination); оно должно подходить каждому объекту, иначе подтверждения нет и указан объект с причиной |
| Копировать | Только файлы | При выделенной папке недоступно: копирования папок на Server нет. Назначение — не исходная папка (копии совпали бы по именам; копия с другим именем — одиночным копированием) и не Camera. Имена копий исходные, без суффиксов |
| Удалить | Файлы и папки | Подтверждение «Удалить N выбранных объектов?» с именами; при выбранных папках — предупреждение, что их содержимое тоже удаляется; корзины нет. N — число выделенных объектов, содержимое папок не подсчитывается |

Отмена выбора назначения возвращает исходную папку вместе с выделением. После подтверждения набор и сессия фиксируются, выделение закрывается и выполняется пакет: одиночные запросы move, copy или delete по одному объекту, последовательно, без атомарности и отката. Диалог показывает «Обработано k из N», текущий объект и «Остановить»: следующие объекты не отправляются, уже отправленный запрос завершается и учитывается. Итог каждого объекта:

| Итог | Когда | Пакет |
| --- | --- | --- |
| Успешно | Server подтвердил операцию | Продолжается |
| Ошибка | Определённый отказ: 400, 404, 409 (в том числе конфликт имени и FOLDER_MANAGED) | Продолжается со следующим объектом |
| Ошибка, доступ | 401/403 | Останавливается; после закрытия итога — предложение выполнить вход |
| Результат неизвестен | Обрыв связи после отправки, 2xx с неразобранным ответом или 5xx: нет гарантии, что операция не выполнена | Останавливается |
| Не обработано | Запрос не отправлялся: остановка пользователем или пакетом | — |

Итог показывает «Обработано: k из N», число успешных, ошибок, неизвестных и необработанных объектов, имена объектов с ошибкой или неизвестным результатом и причины. Общего «успешно» при неполном результате нет; «Повторить всё» нет. При неизвестном результате итог предлагает проверить исходную папку и папку назначения («Открыть назначение»). Повторных запросов Android сам не отправляет. После пакета перемещения или удаления исходная папка перечитывается с первой страницы; после копирования она не меняется. Смена адреса Server, пользователя или выход во время пакета прекращают его: следующие объекты не отправляются, поздний ответ игнорируется. Пакет и его итог живут только в памяти экрана: после гибели процесса не восстанавливаются и не продолжаются.

### Ошибки и recovery

Адрес не задан → сообщение и переход на Network. Нет сессии, либо Server отказал в доступе (401/403) → предложение выполнить вход. Ошибка запроса ROOT, подпапок или первой страницы → текст ошибки и «Повторить»; частичный каталог не показывается. Папка не найдена (404) → возврат в ROOT с сообщением. Ошибка следующей страницы оставляет загруженный список, номер страницы не меняется, повтор выполняется кнопкой «Повторить».

### Текущие ограничения

Нет встроенного просмотра HEIC/HEIF и документов, кроме PDF (они открываются внешними приложениями), миниатюр видео и документов, воспроизведения видео без сети, сохранения выбранного вида между запусками, поиска, фильтров, замены, корзины и копирования папок; выделение ограничено одной открытой папкой. В самом AutoUploads, в активном источнике и во всех его вложенных папках нет кнопки «+» и пунктов «Переименовать», «Переместить», «Копировать» и «Удалить» ([FOLDERS-MANAGED-TREE](05-file-library.md#folders-managed-tree)). Сведения пути не перечитываются, поэтому после удалённого отключения действия вернутся только при повторном переходе в папку. Отключённые источники и остальная библиотека сохраняют ручную загрузку, создание папок и переименование. На самом корне активного источника под путём есть отметка «Источник автоматической загрузки» и «Отключить резервирование» ([BACKUP-SOURCE-DISABLE](04-backup-and-sync.md#backup-source-disable-android)); после подтверждённого отключения папка перечитывается на месте, без возврата в ROOT, как обычная: с кнопкой «+» и прежним содержимым. Файлы, загруженные резервированием папок ([BACKUP-SOURCE-SYNC](04-backup-and-sync.md#backup-source-sync)), и архивные версии изменённых файлов ([BACKUP-SOURCE-ARCHIVE](04-backup-and-sync.md#backup-source-archive)) видны в дереве источника после обновления каталога. Экран не обновляется сам: изменения Server видны после обновления каталога; исключение — завершение ручной загрузки в открытую папку. Если каталог меняется во время прокрутки, часть записей может появиться только после обновления: пагинация остаётся offset-пагинацией. При возврате к родителю каталог запрашивается заново. После создания, переименования, перемещения, удаления и копирования в исходную папку открытая папка перечитывается с первой страницы, положение прокрутки сбрасывается. Перечитывается только исходная папка; папка назначения обновится при переходе в неё.

<a id="files-list"></a>

## FILES-LIST — Список удалённых файлов

**Status:** IMPLEMENTING

**Availability:** END_TO_END

### Назначение

Просмотреть каталог файлов текущего пользователя или прямые файлы предоставленной ему папки.

### Текущее поведение

Клиент запрашивает список с page/size, необязательной folderId и необязательным sort. Android запрашивает его на Library ([FILES-BROWSE](05-file-library.md#files-browse)).

1. При переданной folderId Server проверяет право чтения папки: собственная или открытая действующим USER-доступом ([ACCESS-READ](06-sharing-and-access.md#access-read)).
2. Возвращает страницу только прямых файлов этой папки, принадлежащих её владельцу, а без folderId — всех собственных файлов пользователя.
3. Без sort порядок: capturedAt, затем uploadedAt, затем ID по убыванию. При sort=name порядок: имя по возрастанию без учёта регистра по правилам русского языка, затем ID по возрастанию. Кириллица идёт по алфавиту и раньше латиницы, Ё сортируется как вариант Е. Порядок применяет БД до выбора страницы и не зависит от её локали. Ответ содержит [FilePage](01-system-model.md#file-page) с файлами и данными страниц.

Получены логические записи; наличие и читаемость физических байтов не проверяются.

### Развилки и условия

По умолчанию page=0, size=10. Page должен быть неотрицательным, size — положительным; верхний предел size не задан.

### Ошибки и recovery

Отрицательный page/нулевой size → 400; значение sort, отличное от name, в том числе пустое → 400; отсутствующая папка либо чужая без действующего доступа → 404. При недоступном Server нет результата списка.

### Текущие ограничения

Нет фильтров по типу или дате и других вариантов сортировки. Для sort=name БД должна поддерживать collation ru-x-icu; без него запрос завершается ошибкой Server.

<a id="folders-browse"></a>

## FOLDERS-BROWSE — ROOT и прямые подпапки

**Status:** IMPLEMENTING

**Availability:** END_TO_END

### Назначение

Просмотреть логическую иерархию Server через API.

### Текущее поведение

Клиент запрашивает ROOT либо children известной папки. Android делает это на Library ([FILES-BROWSE](05-file-library.md#files-browse)).

1. ROOT возвращается или лениво создаётся, если отсутствует.
2. Children читаемой папки ([ACCESS-READ](06-sharing-and-access.md#access-read)) возвращает только её прямых потомков, выбранных по владельцу папки и отсортированных по имени в порядке [FILES-LIST](05-file-library.md#files-list) при sort=name, затем по ID. Рекурсивного ответа и pagination нет.

Клиент получает [FolderDto](01-system-model.md#api-projections). Для ROOT parentId отсутствует.

### Ошибки и recovery

Неизвестный parent либо чужой без действующего доступа → 404. Конкурентные запросы создают один ROOT и получают его оба.

### Текущие ограничения

Для children БД должна поддерживать collation ru-x-icu; без него запрос завершается ошибкой Server. ID CAMERA для backup Android получает отдельным запросом ([BACKUP-TARGET](04-backup-and-sync.md#backup-target)). GET ROOT сам не создаёт CAMERA. Full-tree/breadcrumb API и запроса папки по ID нет: путь на Library строится из открытых папок.

<a id="files-upload-manual"></a>

## FILES-UPLOAD-MANUAL — Ручная загрузка файлов на Library

**Status:** IMPLEMENTING

**Availability:** END_TO_END

### Назначение

Отправить выбранные на телефоне файлы в открытую папку серверной библиотеки под исходными именами.

### Текущее поведение

Пользователь открывает ROOT или USER-папку на Library, нажимает «+» и выбирает «Загрузить файлы». В Camera, AutoUploads и дереве активного источника кнопки нет; пока идёт другая ручная передача, пункты загрузки недоступны ([FILES-BROWSE](05-file-library.md#files-browse)).

1. Android запоминает ID открытой папки и открывает системный выбор документов Storage Access Framework; можно выбрать один или несколько файлов. Переход в другую папку не меняет назначение начатой загрузки.
2. Android читает имена и размеры выбранных документов, затем содержимое папки назначения: прямые подпапки и все страницы её файлов.
3. До отправки каждый файл проверяется по правилам из «Развилок». Файл Server с тем же именем без учёта регистра сравнивается с локальным: сначала по размеру, затем по SHA-256 локального содержимого.
4. Остальные файлы отправляются по одному: upload с folderId папки назначения, тело читается потоком из документа без копии в памяти. Server применяет обычные правила имени и повторной загрузки ([правила имён](01-system-model.md#library-names)).
5. Панель над списком показывает «Загрузка N из M», текущий файл, общий прогресс по байтам и «Отмену». Если размер хотя бы одного файла неизвестен, прогресс показывается без процента. Пока идёт передача, экран не гаснет.
6. Итог показывает, сколько файлов загружено, сколько уже существовало и сколько ошибок; «Подробности» перечисляют пропущенные файлы с причинами. Если пользователь остался в папке назначения той же сессии, папка обновляется без возврата в ROOT.

Ручная загрузка не создаёт LocalMedia, не входит в очередь backup Camera и не влияет на её статусы. Одновременно выполняется одна ручная передача — загрузка или скачивание.

### Развилки и условия

| Ситуация | Результат |
| --- | --- |
| Имя и содержимое совпадают с файлом Server | Файл не передаётся и учитывается как уже существующий |
| Имя совпадает, содержимое другое | Пропуск с указанием конфликта; файл Server не меняется |
| Имя занято папкой | Пропуск |
| Имя недопустимо по правилам библиотеки или это Camera в ROOT | Пропуск с причиной; имя не исправляется и не нормализуется |
| Пустой файл | Пропуск: Server пока не принимает пустые файлы |
| Известный размер больше 100 МиБ | Пропуск до передачи |
| Размер неизвестен и содержимое больше 100 МиБ | Передача файла прерывается на лимите, файл пропускается |
| Документ не читается | Пропуск |
| Server ответил 409, 400, 413 или 5xx | Пропуск с причиной, остальные файлы продолжаются |
| Server ответил 404 для папки назначения | Оставшиеся файлы этой папки пропускаются без отправки; в ROOT ничего не перенаправляется |

Существующие файлы Server никогда не заменяются.

### Ошибки и recovery

При сетевой ошибке файл отправляется ещё один раз с заново открытым документом. Если первый ответ потерян после сохранения на Server, повтор получает тот же файл по правилу повторной загрузки. Повторная ошибка связи, отказ доступа (401/403 после refresh) или отсутствие папки назначения при подготовке останавливают загрузку: уже загруженные файлы остаются, итог показывает причину. «Отмена» прерывает текущий HTTP-запрос и закрывает документ; итог показывает число уже загруженных файлов. Файл, который Server успел принять до отмены, может остаться на Server. Смена адреса Server, пользователя или выход отменяют загрузку и убирают её панель.

### Текущие ограничения

Загрузка выполняется только при живом процессе приложения: незавершённая очередь не сохраняется и после гибели процесса не возобновляется, фоновая передача не гарантируется. Докачки нет: прерванный файл отправляется заново. Предпроверка имени и размера в Android повторяет правила Server, окончательное решение принимает Server; лимит 100 МиБ задан в Android отдельно от конфигурации Server. Замены, автопереименования и версий нет.

<a id="folders-upload-manual"></a>

## FOLDERS-UPLOAD-MANUAL — Ручная загрузка папки на Library

**Status:** IMPLEMENTING

**Availability:** END_TO_END

### Назначение

Перенести выбранную на телефоне папку вместе с вложенными папками и файлами в открытую папку серверной библиотеки.

### Текущее поведение

Пользователь в ROOT или USER-папке нажимает «+», выбирает «Загрузить папку» и папку в системном выборе Storage Access Framework.

1. Android запоминает ID открытой папки и обходит выбранное дерево через Storage Access Framework, без файловых путей. Каждая папка провайдера обходится один раз, глубина ограничена 64 уровнями.
2. В папке назначения создаётся папка с исходным именем выбранной ([FOLDERS-CREATE](05-file-library.md#folders-create)), затем вложенные папки, в том числе пустые. Скрытые папки и файлы не исключаются.
3. Папка Server с тем же именем без учёта регистра используется как есть: содержимое объединяется, её файлы проверяются по правилам [FILES-UPLOAD-MANUAL](05-file-library.md#files-upload-manual).
4. Файлы каждой папки загружаются как в FILES-UPLOAD-MANUAL, последовательно, папка за папкой.
5. Прогресс и итог общие для всего дерева; в подробностях указан путь от выбранной папки.

### Развилки и условия

Папка с именем, занятым файлом, с недопустимым именем или нечитаемая пропускается вместе со всем содержимым; в подробностях указано число её файлов. Выбранная папка Camera при загрузке в ROOT пропускается: имя зарезервировано и не переименовывается. Ниже ROOT имя Camera допустимо. Если ответ на создание папки потерян, повтор получает 409, Android находит созданную папку среди потомков и использует её.

### Ошибки и recovery

Частичная ошибка не откатывает дерево: созданные папки и загруженные файлы остаются. Остановка, отмена и смена сессии — как в FILES-UPLOAD-MANUAL. Повторная загрузка той же папки добавляет только недостающее: папки объединяются, совпавшие файлы учитываются как уже существующие.

### Текущие ограничения

Документы без локального содержимого (виртуальные документы облачных провайдеров) пропускаются. Дерево читается целиком до начала передачи, поэтому у большого дерева первый файл отправляется не сразу.

<a id="files-download"></a>

## FILES-DOWNLOAD — Скачивание удалённого файла

**Status:** IMPLEMENTING

**Availability:** END_TO_END

### Назначение

Получить байты, сохранённые на Server.

### Текущее поведение

Клиент запрашивает download по ID логического файла. Android делает это пунктом «Скачать» меню «⋮» строки файла на Library в любой папке, включая Camera и дерево активного источника. Для успеха нужны RemoteFile с правом чтения — собственный или открытый действующим USER-доступом ([ACCESS-READ](06-sharing-and-access.md#access-read)) — и его читаемые физические байты.

1. Server проверяет право чтения записи и доступность байтов.
2. В обычном ответе возвращает 200 с исходными байтами без преобразования, сохранённым MIME и attachment с логическим именем файла в кодировке UTF-8 (RFC 5987); исходное имя в БД и на диске не меняется.
3. Android пишет ответ потоком во временный файл приложения, считает размер и SHA-256 и сравнивает их с size и checksum файла из списка Library.
4. Только после совпадения открывается системный диалог сохранения Storage Access Framework (ACTION_CREATE_DOCUMENT) с исходным именем. Совпадения имён Android сам не разрешает: если система предлагает другое имя, принимается её выбор.
5. Проверенное содержимое копируется в выбранный документ, временный файл удаляется, панель Library сообщает «Файл сохранён».

Server checksum заново не вычисляет; проверку целостности при скачивании выполняет Android. Скачивание не создаёт LocalMedia и не связано с backup. Тот же запрос использует [полноэкранный просмотр](05-file-library.md#files-browse-viewer), но сохраняет оригинал только в приватный кеш приложения, и [воспроизведение видео](05-file-library.md#files-browse-video) — потоком, без сохранения; [просмотр PDF](05-file-library.md#files-browse-pdf) и [внешнее приложение](05-file-library.md#files-browse-external) пользуются тем же кешем оригиналов.

### Ошибки и recovery

Отсутствующий файл, чужой без действующего доступа либо отсутствующие/нечитаемые байты → 404 FILE_ITEM_NOT_FOUND. Если файл переместили после чтения записи, путь вычисляется заново один раз. Логическая запись при отсутствии байтов остаётся в list/exists. Путь, выходящий из хранилища через junction или ссылку, не читается.

На Android ошибка связи, отказ Server или несовпадение размера и SHA-256 завершают скачивание с сообщением: повреждённый файл для сохранения не предлагается, временный файл удаляется. Отказ от выбора места тоже удаляет временный файл. Ошибка записи в выбранный документ удаляет этот документ. «Отмена» прерывает HTTP-запрос или копирование. Смена адреса Server, пользователя или выход отменяют скачивание. Временные файлы, оставшиеся после гибели процесса, удаляются при следующем запуске приложения.

### Текущие ограничения

Android скачивает один файл за раз и только при живом процессе; скачивания папок и нескольких файлов нет. Файл сначала целиком записывается в кеш приложения: нужно свободное место на его размер. Логирование Server тело download не кеширует ([SYSTEM-DIAGNOSTICS](07-system-rules-and-recovery.md#system-diagnostics)): байты идут клиенту без промежуточного буфера размером с файл; нагрузочно это не измерялось. Собственный контракт Range/206/416, ETag/conditional/cache поведения не закреплён; Поведение framework остаётся нерешённым вопросом и не объявляется отсутствующим. Перемотка при [воспроизведении видео](05-file-library.md#files-browse-video) опирается на ответ framework: на `Range: bytes=N-` он возвращает 206 с Content-Range.

## FILES-THUMBNAIL — Миниатюра изображения

**Status:** IMPLEMENTING

**Availability:** END_TO_END

### Назначение

Показать в списке Library уменьшенные копии изображений без скачивания оригиналов.

### Текущее поведение

Android запрашивает миниатюры для строк файлов Library ([FILES-BROWSE](05-file-library.md#files-browse)); другой клиент может запросить их так же. Клиент запрашивает миниатюру по ID логического файла (`GET /api/v1/files/{id}/thumbnail`) с access token. Параметров размера и формата нет: размер задаёт Server.

1. Server проверяет право чтения RemoteFile по тем же правилам, что download: недоступный и отсутствующий файл неразличимы.
2. Тип определяется по StoredObject.detectedMimeType — MIME, найденному по байтам при загрузке; имя и расширение файла не учитываются. Поддерживаются JPEG, PNG и статический WebP.
3. Server вычисляет ETag из checksum StoredObject, версии алгоритма и размера миниатюры. ETag непрозрачен: checksum и идентификаторы в нём не видны. Если If-None-Match содержит этот ETag (в том числе слабый `W/`), Server отвечает 304 без тела и без чтения оригинала. Проверка права чтения и формата выполняется раньше: 304 не раскрывает недоступный файл и не выдаётся для неподдерживаемого типа. «*» не считается совпадением.
4. Иначе Server читает размеры изображения до декодирования, проверяет пределы и декодирует оригинал с прореживанием, затем уменьшает до 320 px по длинной стороне с сохранением пропорций; меньшие изображения не увеличиваются. Учитывается EXIF Orientation 1–8, включая повороты на 90° и отражения. Прозрачность PNG и WebP заменяется белым фоном.
5. Ответ 200: JPEG (`Content-Type: image/jpeg`) без EXIF, GPS и других метаданных исходника, `ETag` и `Cache-Control: max-age=86400, private`.

Миниатюра создаётся при каждом запросе без совпадающего ETag и нигде не сохраняется: нет каталога производных файлов, записей в БД и изменений StoredObject, RemoteFile и FileMetadata. Оригинал не меняется. Повторную передачу экономит HTTP-кеш клиента. Логирование Server тело ответа не пишет ([SYSTEM-DIAGNOSTICS](07-system-rules-and-recovery.md#system-diagnostics)).

<a id="files-thumbnail-android"></a>

**Android Library.** В списке миниатюра стоит слева от имени файла в слоте 48 dp, в плитке занимает квадратную область плитки; запросы, кеш и обработка ошибок у видов общие, при смене вида изображение может заново декодироваться из кеша под другой размер, но не скачивается повторно. Миниатюра запрашивается только для файлов, у которых MIME из FileItemDto — `image/jpeg`, `image/png` или `image/webp` (тип по содержимому, а не по расширению), есть ID и checksum. HEIC/HEIF, GIF, AVIF, видео, PDF и прочие сразу показывают прежний значок типа и не запрашиваются. Изображение вписывается в слот с сохранением пропорций; пока оно грузится — нейтральная подложка, при любой ошибке — значок типа. Папкам миниатюры не показываются; их значок стоит в слоте той же ширины. Нажатия обрабатывает строка: в режиме выделения нажатие на миниатюру переключает отметку, обычное нажатие на файл по-прежнему ничего не открывает.

1. Запрос идёт, когда строка появляется на экране, через тот же авторизованный клиент, что и остальные запросы Library: токен добавляет AuthInterceptor, 401 обрабатывает обычное обновление токена. Токена нет ни в URL, ни в ключах кеша. Оригинал не скачивается; TransferManager и MediaStore не участвуют.
2. Одновременно выполняется не больше трёх запросов миниатюр, остальные ждут в очереди HTTP-клиента; обычные запросы API этим пределом не ограничены. Строка, ушедшая с экрана, отменяет свой запрос.
3. Ключ кеша — версия варианта миниатюры, хеш адреса Server и subject пользователя, ID файла и checksum. Новый checksum, другой пользователь или Server дают другой ключ.
4. Кеш в памяти ограничен 15% памяти приложения, на диске — 50 МБ в кеш-каталоге приложения. Свежесть дискового кеша определяет Cache-Control ответа: в пределах max-age миниатюра показывается без сети; после него отправляется условный запрос с If-None-Match, и 304 возвращает сохранённую миниатюру.
5. 503 SERVICE_BUSY повторяется один раз после Retry-After, но не дольше 2 с; ожидание прекращается отменой запроса. После второго отказа, обрыва связи или повреждённого ответа показывается значок; при следующем появлении строки запрос допустим снова.
6. 404, 415 и 422 не повторяются: до смены пользователя или Server строка с этим ключом сразу показывает значок. Ошибка миниатюры не меняет состояние экрана и не показывает сообщений.
7. Выход, вход другим пользователем и смена Server очищают кеш миниатюр в памяти и на диске и список отказов. Запрос, начатый в прежнем контексте, не отправляется, а его поздний результат не показывается. Обновление токенов того же пользователя кеш не сбрасывает.

### Развилки и условия

| Ситуация | Результат |
| --- | --- |
| Нет или недействителен access | 401 |
| Чужой или отсутствующий RemoteFile, отсутствующие или нечитаемые байты | 404 FILE_ITEM_NOT_FOUND |
| Тип не JPEG, PNG или WebP (HEIC/HEIF, AVIF, GIF, видео, PDF и прочие), анимированный WebP | 415 UNSUPPORTED_MEDIA_TYPE |
| Повреждённое или недекодируемое изображение, нулевые размеры | 422 IMAGE_UNREADABLE |
| Ширина×высота больше `thumbnail.max-source-pixels` (100 Мп); WebP lossless или с прозрачностью больше `thumbnail.max-full-decode-pixels` (8 Мп) | 422 IMAGE_TOO_LARGE |
| Заняты все `thumbnail.max-concurrent` (4) слота генерации | 503 SERVICE_BUSY, `Retry-After: 1`; очереди нет, клиент повторяет запрос |
| Прочая ошибка чтения хранилища | 500 INTERNAL_ERROR |

Ошибки возвращаются JSON ErrorResponse и при `Accept: image/*`; то же относится к 404 download.

### Ошибки и recovery

Отказ не меняет ни оригинал, ни записи; повторный запрос безопасен. После любой ошибки генерации слот освобождается. Изменение версии алгоритма или `thumbnail.max-side` меняет ETag, и клиент получает новую миниатюру.

### Текущие ограничения

На Android нет плитки и полноэкранного предпросмотра. Нет миниатюр HEIC/HEIF, AVIF, GIF, видео и документов, нет серверного кеша миниатюр: каждый запрос без ETag снова читает и декодирует оригинал. Декодер WebP уменьшает при чтении только lossy WebP без прозрачности; lossless WebP и WebP с прозрачностью он читает в полный размер, поэтому для них отдельный, меньший предел. Прореживание при декодировании JPEG и PNG всё равно читает весь поток оригинала; для прогрессивного JPEG декодер может держать вне heap буфер, пропорциональный размеру исходника. Нагрузочно генерация не измерялась. Поздний ответ прежнего контекста может записаться в кеш под прежним ключом уже после очистки; показан он не будет и вытесняется по размеру кеша.

<a id="folders-create"></a>

## FOLDERS-CREATE — Создание пользовательской папки

**Status:** IMPLEMENTING

**Availability:** END_TO_END

### Назначение

Создать USER-папку в своей удалённой иерархии.

### Текущее поведение

Клиент передаёт имя и необязательный parentId. Android создаёт папки на Library пунктом «+» → «Создать папку» и при ручной загрузке папки ([FOLDERS-UPLOAD-MANUAL](05-file-library.md#folders-upload-manual)), всегда с parentId и без backupSource. Родитель принадлежит пользователю и имеет тип ROOT или USER; без parentId используется ROOT.

На Library пользователь в ROOT или USER-папке вне управляемого дерева ([FILES-BROWSE](05-file-library.md#files-browse)) вводит имя в диалоге и нажимает «Создать». Android проверяет имя по [правилам имён](01-system-model.md#library-names) и зарезервированное Camera в ROOT, не изменяя его, и отправляет запрос с ID открытой папки. Пока запрос выполняется, повторное подтверждение, правка имени и закрытие диалога недоступны. После успешного ответа диалог закрывается, открытая папка перечитывается с первой страницы: новая папка занимает место по сортировке Server. Локально папка до ответа Server не добавляется.

1. Server проверяет имя по правилам библиотеки, не изменяя его, и под блокировкой структуры пользователя — родителя и занятость имени файлом или папкой, включая зарезервированное.
2. Создаёт USER-папку и возвращает её описание с 200.

Создаются Folder и физический каталог с тем же именем. Имя, занятое на диске без записи в БД, даёт 409: существующий объект не удаляется и не присваивается.

### Ошибки и recovery

Недопустимый родитель (CAMERA или AUTO_UPLOADS)/имя → 400; отсутствующий/чужой родитель → 404; занятое/зарезервированное имя → 409; родитель в активном дереве без UUID его источника либо UUID вне активного дерева → 409 FOLDER_MANAGED ([FOLDERS-MANAGED-TREE](05-file-library.md#folders-managed-tree)).

На Library недопустимое имя отклоняется до запроса с причиной в диалоге. 409 → «Имя уже занято файлом или папкой», FOLDER_MANAGED → «Папку изменяет только автоматическое резервирование», 400 → текст Server, ошибка связи или 5xx → текст ошибки: диалог остаётся открытым с введённым именем, список не меняется, имя можно исправить или повторить. Автоматического переименования при совпадении нет. 404 закрывает диалог и перечитывает папку; если её нет, Library возвращается в ROOT ([FILES-BROWSE](05-file-library.md#files-browse)). 401/403 → предложение выполнить вход.

### Текущие ограничения

Если ответ на успешное создание потерян, повтор с тем же именем получает 409; созданная папка видна после обновления каталога. CAMERA — системная конечная папка, под ней нельзя создавать USER. Создание CAMERA выполняют запрос получения CAMERA ([BACKUP-TARGET](04-backup-and-sync.md#backup-target)) и upload без папки, не эта операция. В AutoUploads папки создаёт только регистрация источника ([BACKUP-SOURCE-REGISTER](04-backup-and-sync.md#backup-source-register)); внутри активного источника эта операция создаёт USER-папки только с UUID источника, внутри отключённого — как обычно.

<a id="folders-rename"></a>

## FOLDERS-RENAME — Переименование папки

**Status:** IMPLEMENTING

**Availability:** END_TO_END

### Назначение

Изменить имя USER-папки.

### Текущее поведение

Клиент передаёт ID папки и новое имя. Собственная USER-папка. Android делает это пунктом «Переименовать» меню «⋮» строки папки на Library ([FILES-BROWSE](05-file-library.md#files-browse)): диалог открывается с текущим именем, «Сохранить» отправляет введённое имя без backupSource. Неизменённое имя закрывает диалог без запроса.

Server проверяет имя по правилам библиотеки, не изменяя его, и под блокировкой структуры пользователя — конфликты с соседними файлами, папками и зарезервированным именем; сама папка конфликтом не считается, поэтому смена только регистра допустима. Затем меняет Folder.name и Folder.updatedAt, возвращает 200 с описанием.

Меняются Folder.name и имя физического каталога. Переносится только сам каталог: ID папки, записи и ID вложенных объектов не меняются, их пути вычисляются из дерева. Android после ответа перечитывает открытую папку с первой страницы, путь навигации сохраняется.

### Ошибки и recovery

Системная папка/некорректное имя → 400; отсутствующая/чужая папка → 404; конфликт имени, в том числе только на диске, и занятый файл внутри папки → 409 без изменений; корень активного источника, папка активного дерева без UUID его источника, UUID вне активного дерева → 409 FOLDER_MANAGED ([FOLDERS-MANAGED-TREE](05-file-library.md#folders-managed-tree)).

На Library ошибки показываются в диалоге с сохранённым введённым именем, как в [FOLDERS-CREATE](05-file-library.md#folders-create); 404 закрывает диалог, сообщает, что папка не найдена, и перечитывает открытую папку.

### Текущие ограничения

ROOT, CAMERA и AUTO_UPLOADS переименовывать нельзя; тип папки не меняется. Корень активного источника не переименовывается и механизмом резервирования; отключённый — как обычная USER-папка, в том числе на Library. Android не меняет локальные записи источников (BackupSource) при ручном переименовании.

<a id="files-rename"></a>

## FILES-RENAME — Переименование файла

**Status:** IMPLEMENTING

**Availability:** END_TO_END

### Назначение

Изменить отображаемое имя RemoteFile.

### Текущее поведение

Клиент передаёт логический ID и новое originalName. Android делает это пунктом «Переименовать» меню «⋮» строки файла на Library ([FILES-BROWSE](05-file-library.md#files-browse)): диалог открывается с полным текущим именем, основа до расширения выделена. Редактируется полное имя: расширение Android само не добавляет и не меняет. Имя проверяется по [правилам имён](01-system-model.md#library-names) и в Camera, отправляется без backupSource; неизменённое имя закрывает диалог без запроса.

В обычной библиотеке Server проверяет имя по правилам, не изменяя его, и под блокировкой структуры пользователя — конфликт с файлами, папками и зарезервированным именем; сам файл конфликтом не считается, поэтому смена только регистра допустима. В CAMERA Server прежним способом убирает пробелы по краям и заменяет недопустимые символы, имя не проверяется на занятость. Затем сохраняет RemoteFile.originalName и возвращает 200 с описанием.

В ответе меняется originalFilename. В обычной библиотеке вместе с записью переименовывается физический файл, в том числе при смене только регистра; ID и FileMetadata прежние. В CAMERA физические имя и путь не меняются. Android после ответа перечитывает первую страницу открытой папки: файл занимает новое место по сортировке Server, путь навигации сохраняется, остальные страницы догружаются прокруткой.

### Ошибки и recovery

Некорректное имя → 400; отсутствующий/чужой файл, в том числе удалённый параллельным запросом → 404; занятое имя без учёта регистра вне CAMERA, в том числе только на диске, и занятый файл → 409 без изменений; файл активного дерева без UUID его источника либо UUID вне активного дерева → 409 FOLDER_MANAGED.

На Library ошибки показываются в диалоге с сохранённым введённым именем, как в [FOLDERS-CREATE](05-file-library.md#folders-create); 404 закрывает диалог, сообщает, что файл не найден, и перечитывает открытую папку.

### Текущие ограничения

В CAMERA совпадение имён допускается. Rename не меняет байты и не переименовывает оригинал на устройстве Android.

<a id="folders-move"></a>

## FOLDERS-MOVE — Перемещение папки

**Status:** IMPLEMENTING

**Availability:** END_TO_END

### Назначение

Перенести USER-папку в другую часть своей иерархии.

### Текущее поведение

Клиент задаёт targetParentId. Собственная USER-папка, target — собственный ROOT/USER. Android делает это пунктом «Переместить» меню «⋮» строки папки на Library: назначение выбирается в Library ([выбор назначения](05-file-library.md#files-browse-destination)), после подтверждения итога отправляется один запрос без backupSource.

1. Под блокировкой структуры пользователя Server проверяет исходную и целевую папки, исключает перемещение в себя/потомка и конфликт имени с файлами и папками target.
2. Меняет Folder.parent и Folder.updatedAt, возвращает 200 с описанием.

Меняются Folder.parent и расположение физического каталога со всем содержимым; ID папки, записи и ID вложенных объектов не меняются. Android до ответа ничего не переносит; после ответа возвращается в исходную папку, перечитывает её с первой страницы и сообщает «Папка … перемещена в …».

### Ошибки и recovery

Системная исходная папка, target CAMERA или AUTO_UPLOADS, перемещение в себя или потомка → 400; исходная папка или target в активном дереве, включая его корень → 409 FOLDER_MANAGED; отсутствующая/чужая папка → 404; конфликт имени, в том числе только на диске, и занятый файл внутри папки → 409 без изменений. Перенос в текущего родителя Server выполняет без изменений; Android такое назначение не подтверждает.

<a id="library-relocation-errors"></a>

На Library: 400, 409, FOLDER_MANAGED и 5xx показываются в окне итога с текстом причины, выбранное назначение сохраняется, Library не меняется, повтор — той же кнопкой. 404 завершает выбор, возвращает в исходную папку с сообщением и перечитывает её. 401/403 → предложение выполнить вход. Обрыв связи после отправки или ответ 2xx, тело которого не удалось разобрать, означает неизвестный результат: Android не повторяет запрос сам, сообщает, что результат неизвестен, и блокирует подтверждение до обновления открытой папки; повтор выполняет пользователь после проверки. Смена адреса Server, пользователя или выход во время операции сбрасывают выбор, поздний ответ игнорируется.

### Текущие ограничения

Одна папка — один запрос; несколько папок Library перемещает пакетом одиночных запросов без атомарности ([групповые операции](05-file-library.md#files-browse-batch)). Копирования папки на Server нет — ни API, ни сценария; Android его не предлагает и не собирает из копий отдельных файлов.

<a id="files-move"></a>

## FILES-MOVE — Перемещение файла

**Status:** IMPLEMENTING

**Availability:** END_TO_END

### Назначение

Изменить Folder удалённого RemoteFile.

### Текущее поведение

Клиент задаёт targetFolderId. Собственные file и target folder внутри обычной библиотеки, включая ROOT. Android делает это пунктом «Переместить» меню «⋮» строки файла вне Camera ([выбор назначения](05-file-library.md#files-browse-destination)), без backupSource.

Под блокировкой структуры пользователя Server проверяет имя в target среди файлов и папок, меняет папку, переносит физический файл без замены существующих объектов и возвращает 200 с описанием. StoredObject прежний.

Файл находится в другой удалённой папке с прежним ID; локальное состояние Android автоматически не меняется. Android до ответа файл не переносит; после ответа возвращается в исходную папку, перечитывает её с первой страницы и сообщает «Файл … перемещён в …».

### Ошибки и recovery

Перенос через границу Camera в любую сторону и в AUTO_UPLOADS → 400; файл или target в активном дереве → 409 FOLDER_MANAGED; отсутствующий/чужой файл или папка, в том числе удалённые параллельным запросом → 404; конфликт имени, в том числе имя, занятое только на диске, и занятый файл → 409 без изменений. Move файла CAMERA в ту же CAMERA → 200 без изменений. Checksum в move не проверяется: тот же checksum под другим именем в target допустим. Групповое перемещение — [пакетом](05-file-library.md#files-browse-batch). Обработка ошибок на Library — как в [FOLDERS-MOVE](05-file-library.md#library-relocation-errors).

### Текущие ограничения

Move не объединяет файлы и не является успешной dedup-веткой upload. Обратная сверка отсутствует ([FILES-RECONCILE](05-file-library.md#files-reconcile)).

<a id="files-copy"></a>

## FILES-COPY — Копирование файла

**Status:** IMPLEMENTING

**Availability:** END_TO_END

### Назначение

Создать независимую удалённую копию.

### Текущее поведение

Клиент отправляет copy с необязательными targetFolderId и originalName; пустое тело-объект допустимо. Android делает это пунктом «Копировать» меню «⋮» строки файла ([выбор назначения](05-file-library.md#files-browse-destination)) и всегда передаёт targetFolderId и имя копии из окна итога, без backupSource. Имя по умолчанию — исходное; Android проверяет его по [правилам имён](01-system-model.md#library-names), зарезервированное Camera в ROOT и, при копировании в ту же папку, отличие от исходного без учёта регистра. Суффиксы вида «(2)» не добавляются.

1. Без target используется исходная папка; пустое/отсутствующее имя означает исходное. Для обычной библиотеки имя, в том числе исходное имя Camera-файла, проверяется по правилам и не изменяется; для CAMERA другое имя очищается прежним способом.
2. Server проверяет принадлежность исходного файла, затем что его StoredObject принадлежит текущему пользователю, затем целевую папку и её правила: копирование из обычной библиотеки в CAMERA запрещено, в CAMERA конфликтует checksum, в обычной библиотеке — только имя среди файлов и папок. Проверка повторяется при сохранении под блокировкой структуры пользователя.
3. Вне блокировки копирует физические байты во временный файл. Если источник успел переместиться, читает его заново по новому пути. Затем под блокировкой создаёт новые StoredObject, RemoteFile и копию FileMetadata и публикует копию без перезаписи по пути из дерева целевой папки, с именем копии и без UUID. Физического ключа у копии нет, в том числе при копировании из CAMERA. Публикация — как у upload ([SYSTEM-STORAGE](07-system-rules-and-recovery.md#system-storage)): недописанная копия в конечный каталог не попадает.
4. Возвращает 200 с новым ID; uploadedAt новый, capturedAt прежний.

Результат — независимая физическая копия без общей ссылки на прежний объект; Android байты не передаёт. После ответа Library возвращается в исходную папку: если копия создана в другой папке, список возвращается без запросов, если в той же — перечитывается с первой страницы. Сообщение — «Копия … создана в …».

### Ошибки и recovery

Копирование из обычной библиотеки в CAMERA, в AUTO_UPLOADS и некорректное имя → 400. Исходный файл или target в активном дереве → 409 FOLDER_MANAGED. В CAMERA тот же checksum → 409. Конфликт имени в обычной библиотеке → 409, в том числе имя, занятое только на диске; тот же checksum под другим именем в той же папке допустим. Собственный RemoteFile, ссылающийся на StoredObject другого пользователя, → 403 FORBIDDEN до операций с файловой системой: копирование чужих и расшаренных объектов не поддерживается. Отсутствующий исходный файл или целевая папка, в том числе источник, удалённый параллельно, → 404. Отсутствующие байты источника при существующей записи, занятый служебный путь и другие ошибки физической записи → 500 INTERNAL_ERROR без изменения существующих файлов. Восстановление согласованности БД и файловой системы — [SYSTEM-STORAGE](07-system-rules-and-recovery.md#system-storage).

На Library 409 «Имя уже занято файлом или папкой» оставляет окно итога с введённым именем для исправления; остальные ошибки и неизвестный результат — как в [FOLDERS-MOVE](05-file-library.md#library-relocation-errors). Повтор после неизвестного результата с тем же именем получает 409, если копия уже создана. Групповое копирование файлов — [пакетом](05-file-library.md#files-browse-batch) с исходными именами; копирования папок нет.

### Текущие ограничения

Checksum, размер, MIME, тип и расширение наследуются из исходного каталога, не пересчитываются по байтам. Изменение расширения нового имени не меняет унаследованное fileExtension.

<a id="folders-delete"></a>

## FOLDERS-DELETE — Удаление папки

**Status:** IMPLEMENTING

**Availability:** END_TO_END

### Назначение

Удалить ненужную USER-папку со всем содержимым.

### Текущее поведение

Клиент отправляет delete по ID. Собственная USER-папка; вложенные папки и файлы удаляются вместе с ней. Android делает это пунктом «Удалить» меню «⋮» строки папки на Library ([подтверждение](05-file-library.md#library-delete)); отключённый источник в AutoUploads удаляется так же.

В одной транзакции под блокировкой структуры пользователя Server проверяет тип, удаляет записи всего поддерева: FileMetadata, RemoteFile, StoredObject и Folder, затем переносит верхний каталог в `{storage root}/.pending-delete/folder-{id}` без замены существующих объектов и фиксирует транзакцию. Содержимое не перебирается. Возвращает 204 без тела.

Папка, её содержимое и имя освобождаются при фиксации. Физическое содержимое, включая файлы без записей, удаляет фоновая очистка ([SYSTEM-STORAGE](07-system-rules-and-recovery.md#system-storage)).

<a id="library-delete"></a>

**Удаление на Library.** До подтверждения запросов нет. Диалог — «Удалить файл?» с текстом «Удалить файл „…“?» или «Удалить папку?» с текстом «Удалить папку „…“ вместе со всеми вложенными папками и файлами?», в обоих случаях с предупреждением, что восстановления через корзину нет; для файла Camera — что фото на телефоне останется и повторно автоматически не загрузится. «Отмена» ничего не меняет. «Удалить» отправляет один DELETE без backupSource; пока он выполняется, повторное подтверждение и закрытие диалога недоступны. Строка исчезает только после ответа Server: открытая папка перечитывается с первой страницы, путь сохраняется, показывается «Файл … удалён» / «Папка … удалена». Room автоматического резервирования и файлы устройства не меняются.

### Ошибки и recovery

Системная папка → 400; отсутствующая/чужая папка, повтор после успешного удаления, удаление вложенного объекта после родителя → 404; файл внутри папки занят → 409 без изменений; папка в активном дереве, включая его корень → 409 FOLDER_MANAGED.

На Library 400, 409 (в том числе «занят»), FOLDER_MANAGED и 5xx показываются в диалоге с причиной; Library не меняется, повтор — только новым подтверждением. 404 закрывает диалог, сообщает, что объект не найден, и перечитывает папку. 401/403 → предложение выполнить вход. Обрыв связи после отправки или 2xx с неразобранным ответом — неизвестный результат: повторного «Удалить» нет, диалог предлагает «Обновить»; после обновления каталог показывает фактическое состояние, исчезнувшая строка ошибкой не считается. Смена адреса Server, пользователя или выход закрывают диалог до отправки; поздний ответ игнорируется.

### Текущие ограничения

Удаляется поддерево целиком. Несколько выделенных файлов и папок Library удаляет [пакетом](05-file-library.md#files-browse-batch) одиночных запросов после одного подтверждения. Android не показывает число вложенных объектов: достоверных данных о поддереве у него нет. Физическое содержимое исчезает после ответа, при очередном проходе очистки `.pending-delete`; корзины и восстановления нет.

<a id="files-delete"></a>

## FILES-DELETE — Удаление удалённого файла

**Status:** IMPLEMENTING

**Availability:** END_TO_END

### Назначение

Удалить RemoteFile с учётом владения логической записью и физическим объектом.

### Текущее поведение

Клиент отправляет delete по ID логического файла. Android делает это пунктом «Удалить» меню «⋮» строки файла на Library, в том числе в Camera ([подтверждение и ошибки](05-file-library.md#library-delete)). Пользователь владеет RemoteFile. В обычном upload/copy он владеет и StoredObject.

1. В одной транзакции под блокировкой структуры пользователя Server находит собственный RemoteFile и сравнивает StoredObject.user с текущим пользователем.
2. Если пользователь владеет StoredObject, удаляются все ссылающиеся на него RemoteFile, соответствующая FileMetadata и StoredObject, затем файл переносится в `{storage root}/.pending-delete/file-{id}` без замены существующих объектов. Имя освобождается при фиксации. Байты удаляет фоновая очистка ([SYSTEM-STORAGE](07-system-rules-and-recovery.md#system-storage)). Для файла CAMERA механизм тот же.
3. Если пользователь владеет только RemoteFile, ссылающимся на чужой StoredObject, удаляется лишь его RemoteFile и FileMetadata; StoredObject и байты сохраняются.
4. Server возвращает 204 без тела.

Удаление логических записей завершено. Владелец StoredObject удаляет все ссылки на него, не ожидая последней. Удаление ссылки другим пользователем сохраняет StoredObject даже при последней ссылке.

### Ошибки и recovery

Отсутствующий/чужой файл и повтор успешного delete, в том числе параллельный → 404. Занятый файл → 409 без изменений. Файл активного дерева → 409 FOLDER_MANAGED. Служебное имя занято → 500 без удаления каких-либо данных. Отсутствующие байты не мешают успеху. Перенесённый объект считается предназначенным к удалению, даже если COMMIT завершился ошибкой: очистка завершит удаление записей и байтов.

### Текущие ограничения

API upload/copy не создаёт cross-owner references; ветка удаления описывает допустимое состояние модели, не sharing feature: Share не создаёт RemoteFile ([SHARING-ABSENT](06-sharing-and-access.md#sharing-absent)). Сейчас у каждого RemoteFile свой StoredObject, поэтому удаление на Library убирает только выбранный файл. Trash/restore нет. Удаление файла Camera не сбрасывает SYNCED и не вызывает повторную загрузку ([FILES-RECONCILE](05-file-library.md#files-reconcile)).

<a id="shared-with-me"></a>

## SHARED-WITH-ME — «Доступно мне» и отказ от доступа

**Status:** IMPLEMENTING

**Availability:** END_TO_END

### Назначение

Показать получателю ресурсы, открытые ему другими пользователями, и дать убрать ненужный ресурс из своей библиотеки.

### Текущее поведение

<a id="shared-with-me-android"></a>

**Android Library.** В корне собственной библиотеки первой строкой (в плитке — первой плиткой) стоит виртуальный элемент «Доступно мне». Это не папка Server: Folder и записи Room для него не создаются, ROOT не меняется. Элемент виден только в ROOT, вне выбора назначения, выделения и группового пакета; в пустом ROOT он остаётся вместо сообщения «Папка пуста».

1. Нажатие открывает раздел: Android запрашивает первую страницу списка ниже, путь показывается как «Доступно мне». Строки идут в порядке Server: значок папки или миниатюра и значок файла как в [FILES-BROWSE](05-file-library.md#files-browse), имя и вторая строка «Владелец: имя (иначе email) · тип и размер файла · доступ до дд.мм.гггг чч:мм». Срок приходит моментом UTC и показывается в часовом поясе устройства; без срока часть «доступ до» отсутствует. Список всегда показывается списком, даже если выбрана плитка: владельцу и сроку нужна вторая строка. Следующие страницы по 50 подгружаются при прокрутке, как файлы папки. Пустой список — сообщение «Вам пока ничего не предоставили…».
2. Предоставленная папка открывается обычной навигацией Library: children и файлы ([FOLDERS-BROWSE](05-file-library.md#folders-browse), [FILES-LIST](05-file-library.md#files-list)) по её ID, проверку права выполняет Server ([ACCESS-READ](06-sharing-and-access.md#access-read)). Путь начинается с неё: «Доступно мне / Trips / Day1». Внутри можно спускаться во вложенные папки, плитка работает как обычно. Файлы корня доступа сортируются по имени: тип папки список доступов не передаёт.
3. Back и стрелка у пути поднимаются по предоставленному дереву; из его корня — к списку «Доступно мне» (список перечитывается), из списка — в собственную библиотеку, к прежнему виду ROOT без запросов. Папки владельца выше корня доступа не запрашиваются и не показываются; parentId чужих папок для навигации не используется.
4. Файлы открываются теми же средствами, что в библиотеке: изображения — [полноэкранный просмотр](05-file-library.md#files-browse-viewer), видео — [плеер](05-file-library.md#files-browse-video) с Range, PDF — [просмотр PDF](05-file-library.md#files-browse-pdf), остальные — [внешнее приложение](05-file-library.md#files-browse-external); оригиналы — через общий кеш оригиналов, миниатюры — [FILES-THUMBNAIL](05-file-library.md#files-thumbnail-android). Соседние изображения просмотра — изображения открытой предоставленной папки, а в списке — только непосредственно предоставленные файлы. «Скачать» в меню файла — [FILES-DOWNLOAD](05-file-library.md#files-download) с системным выбором места.
5. Раздел только для чтения, и это определяет контекст Library, а не тип папки или наличие backupSource. Нет кнопки «+» (создание папки и загрузка), переименования, перемещения, копирования, удаления, выделения и групповых операций, отключения источника. В меню файла — только «Скачать»; у элемента самого списка ещё «Убрать из моей библиотеки», у папок внутри дерева меню нет.
6. «Убрать из моей библиотеки» спрашивает подтверждение: файл или папка у владельца остаются, вернуть доступ может только он. После подтверждения Android отправляет отказ ниже; пока запрос идёт, диалог не закрывается. Успех и 404 (доступа уже нет) перечитывают список с начала с сообщением «„имя“ убран из „Доступно мне“». При другой ошибке элемент остаётся, диалог показывает причину и допускает повтор.

**Список** (`GET /api/v1/shared-with-me`, page и size как у [FILES-LIST](05-file-library.md#files-list)): страница [SharedResourceDto](01-system-model.md#api-projections), от новых доступов к старым.

1. Элемент — один прямой USER-доступ текущего пользователя: файл или папка, предоставленные напрямую. Объекты внутри предоставленной папки отдельными элементами не показываются. Отдельно предоставленный вложенный объект присутствует собственным элементом.
2. Показываются только доступы, которые открыла бы проверка чтения [ACCESS-READ](06-sharing-and-access.md#access-read):
   - срок не истёк;
   - владелец активен и не заблокирован;
   - Share.owner совпадает с владельцем ресурса;
   - ROOT и AUTO_UPLOADS не показываются.
   Удалённый ресурс или владелец исчезает из списка вместе с Share.
3. Элемент содержит ID доступа, тип, ID и имя ресурса, владельца, срок и дату выдачи, а у файла — FileItemDto для отображения в списке. backupSource папки, tokenHash и encryptedToken не выдаются. Виртуальные Folder или RemoteFile не создаются.
4. Содержимое открывается обычными read-endpoints по ID ресурса: children и список файлов папки, метаданные, download и миниатюра файла.

**Отказ** (`DELETE /api/v1/shared-with-me/{shareId}`): Server удаляет USER-доступ с этим ID, только если получатель — текущий пользователь, и отвечает 204.

Ресурс, доступы других получателей и другие доступы того же пользователя не меняются. Последующее чтение проходит обычную проверку [ACCESS-READ](06-sharing-and-access.md#access-read): если файл остаётся открыт другой предоставленной папкой или собственным доступом, он по-прежнему читается. Отдельного скрытия ресурса без удаления доступа нет.

### Ошибки и recovery

Отрицательный page или нулевой size → 400. Отказ от отсутствующего доступа, доступа другого получателя или уже удалённого → 404: чужие ID не перечисляются.

На Android 404 при открытии или подгрузке предоставленной папки (доступ отозван, истёк, папка удалена) возвращает к перечитанному списку «Доступно мне» с сообщением «Папка больше недоступна…». Ни собственный ROOT, ни выход из аккаунта при этом не происходят; 401/403 обрабатываются как в остальной Library. 404 файла показывает просмотр, плеер, PDF, внешнее открытие или скачивание своим сообщением, как в библиотеке; закрывает его пользователь. Отказ Server или связи при загрузке списка — сообщение с «Повторить». Смена адреса Server, пользователя или выход закрывают раздел и открытые просмотры, отменяют запросы и сбрасывают список. Ранее скачанные оригиналы в кеше не удаляются.

### Текущие ограничения

Истёкшие доступы получатель не видит, но может удалить по известному ID. Сортировки и фильтров нет. На Android раздел и предоставленное дерево живут только в памяти процесса: после его гибели Library начинается с ROOT. Отказ от доступа отдельного вложенного объекта внутри дерева недоступен: убрать можно только элемент самого списка. Тип корня предоставленной папки неизвестен, поэтому предоставленная Camera сортируется по имени, а не по дате.

## Что Server поддерживает, но Android не использует

Следующие операции доступны внешнему API-клиенту. Для них нужны действующий access и собственные файлы/папки; метаданные файла читаются и по USER-доступу ([ACCESS-READ](06-sharing-and-access.md#access-read)). Поиск чужого или отсутствующего объекта возвращает 404; общие правила доступа — [ACCESS-OWNER](06-sharing-and-access.md#access-owner). Ошибки ниже дополняют эту общую границу. Здесь не подразумевается существующий web UI. Правила имён, общее пространство файлов и папок, граница Camera и библиотеки и очередь структурных изменений — [Camera, обычная библиотека и имена](01-system-model.md#library-names).

<a id="files-metadata"></a>

## FILES-METADATA — Метаданные удалённого файла

**Status:** IMPLEMENTING

**Availability:** SERVER_ONLY

### Назначение

Получить свойства конкретного RemoteFile.

### Текущее поведение

Внешний клиент запрашивает файл по логическому ID. Нужно право чтения: собственный файл или открытый действующим USER-доступом ([ACCESS-READ](06-sharing-and-access.md#access-read)).

Server возвращает [FileItemDto](01-system-model.md#api-projections) с данными RemoteFile, свойствами StoredObject и доступной FileMetadata. StoredObject.filePath, filename и id не раскрываются.

Получены сведения из серверного каталога без чтения физических байтов.

### Ошибки и recovery

Отсутствующий file ID либо чужой без действующего доступа → 404. При этом запись может успешно возвращаться даже при отсутствии физических байтов.

### Текущие ограничения

Эта операция не проверяет целостность или читаемость содержимого. Смысл metadata и дат — [BACKUP-METADATA](04-backup-and-sync.md#backup-metadata).

<a id="folders-auto-uploads"></a>

## FOLDERS-AUTO-UPLOADS — Системный контейнер AutoUploads

**Status:** IMPLEMENTING

**Availability:** SERVER_ONLY

### Назначение

Держать корни автоматических источников Android отдельно от Camera и от обычных папок пользователя.

### Текущее поведение

Контейнер появляется при первой регистрации источника ([BACKUP-SOURCE-REGISTER](04-backup-and-sync.md#backup-source-register)):

```
ROOT/
├── Camera/          CAMERA
├── AutoUploads/     AUTO_UPLOADS
│   ├── Documents/   USER, backupSource = UUID-1
│   └── Projects/    USER, backupSource = UUID-2
└── Работа/          USER
```

1. У пользователя не больше одного AUTO_UPLOADS, всегда прямой потомок ROOT, с именем AutoUploads. Просмотр выполняет только GET и контейнер не создаёт.
2. Прямые потомки контейнера — корни активных источников ([Folder](01-system-model.md#folder).backupSource) и отключённые источники, ещё не перенесённые из него. Обычное создание папки в нём, перемещение в него папки, upload, move и copy файла в него → 400. Сам контейнер нельзя переименовать, переместить или удалить → 400.
3. Изменения дерева активного источника ограничены ([FOLDERS-MANAGED-TREE](05-file-library.md#folders-managed-tree)). Отключённый источник ([BACKUP-SOURCE-DISABLE](04-backup-and-sync.md#backup-source-disable)) — обычная USER-папка: его можно перенести в обычную библиотеку, но не обратно. В обоих случаях действуют правила имён, общее пространство файлов и папок и физическое дерево `{userId}/files/AutoUploads/...` ([PhysicalBytes](01-system-model.md#physical-bytes)).
4. В FolderDto у корня активного источника выдаётся backupSource, у остальных папок, включая отключённые, оно отсутствует (null).

### Текущие ограничения

Имя AutoUploads в ROOT не зарезервировано: пользовательская папка с этим именем, созданная раньше контейнера, им не становится и блокирует регистрацию (409).

<a id="folders-managed-tree"></a>

## FOLDERS-MANAGED-TREE — Защита дерева активного источника

**Status:** IMPLEMENTING

**Availability:** SERVER_ONLY

### Назначение

Не допустить ручного изменения папок и файлов, которые поддерживает автоматическое резервирование, оставив путь записи самому механизму резервирования.

### Текущее поведение

Папка принадлежит активному дереву, если у неё самой или у предка до AutoUploads задан [Folder](01-system-model.md#folder).backupSource; RemoteFile — если ему принадлежит его папка. Механизм резервирования передаёт UUID своего источника как необязательный backupSource: multipart-параметр upload, поле тела создания папки, rename папки и rename файла.

| Операция | Без backupSource | С backupSource источника этого дерева |
| --- | --- | --- |
| Просмотр папок и файлов, metadata, download | Разрешено | — |
| Создание вложенной папки, upload | 409 | Разрешено |
| Rename файла, rename вложенной папки | 409 | Разрешено |
| Rename корня источника | 409 | 409 |
| Delete файла или папки, включая корень | 409 | Параметра нет, 409 |
| Move файла или папки в дерево, внутри него или из него, включая корень | 409 | Параметра нет, 409 |
| Copy файла в дерево, внутри него или из него | 409 | Параметра нет, 409 |

1. Все отказы — 409 с кодом FOLDER_MANAGED ([ErrorResponse](01-system-model.md#error-response)).
2. backupSource, переданный для объекта вне активного дерева или из дерева другого источника, тоже даёт 409 FOLDER_MANAGED: после отключения ([BACKUP-SOURCE-DISABLE](04-backup-and-sync.md#backup-source-disable)) запросы резервирования с прежним UUID не выполняются как обычные. Без параметра операции вне активного дерева выполняются как прежде.
3. Разрешённые операции подчиняются обычным правилам: имена, конфликты, повторная загрузка того же имени и checksum, физическое дерево. Повтор rename файла с тем же новым именем ничего не меняет.
4. Проверки выполняют сервисы, поэтому они действуют для обоих endpoint-ов upload и любых других путей к той же операции. Upload и copy проверяют доступ до работы с байтами и повторно — под блокировкой структуры пользователя, перед записью. Rename, move, create и delete проверяют его только под блокировкой.

<a id="files-archive-names"></a>

Архивные версии ([BACKUP-SOURCE-ARCHIVE](04-backup-and-sync.md#backup-source-archive)) — обычные RemoteFile той же папки: прежний FileItem переименовывается rename-ом резервирования, его ID, содержимое и StoredObject не меняются, физический файл переименовывается вместе с записью. Имя архивной версии строит Android:

| Исходное имя | Архивное имя |
| --- | --- |
| `Чертёж.pdf` | `Чертёж_20261104-120000.pdf` |
| `archive.tar.gz` | `archive.tar_20261104-120000.gz` |
| `README`, `.secret` | `README_20261104-120000`, `.secret_20261104-120000` |
| Имя занято | `Чертёж_20261104-120000_2.pdf`, `_3`, … до `_20` |

Отметка — время начала архивирования в UTC с точностью до секунды; вставляется перед расширением (от последней точки; у имени, начинающегося с точки и без других точек, расширения нет). Если имя длиннее 255 байт UTF-8, укорачивается основа по целым символам, отметка, номер и расширение сохраняются. Имя проверяется [правилами имён](01-system-model.md#library-names); занятое имя без учёта регистра не перезаписывается. Архивные версии не удаляются и не скрываются: в Library они видны как обычные файлы дерева источника.

Корень источника всегда прямой потомок AutoUploads, а AutoUploads и ROOT нельзя переименовать, переместить или удалить, поэтому перенос родителя защиту не обходит. Операции над самим AutoUploads отвечают по [FOLDERS-AUTO-UPLOADS](05-file-library.md#folders-auto-uploads), 400.

### Ошибки и recovery

Некорректный UUID в backupSource → 400. Upload с backupSource без folderId → 400 до любых изменений: default routing в Camera для механизма резервирования не применяется, Camera не создаётся. Чужие папки и файлы → 404, как и без параметра: backupSource не секрет и не самостоятельная авторизация, JWT и проверки владельца действуют как прежде.

### Текущие ограничения

Android передаёт backupSource при регистрации, создании папок, upload резервирования ([BACKUP-SOURCE-SYNC](04-backup-and-sync.md#backup-source-sync)) и rename файла при архивировании прежней версии ([BACKUP-SOURCE-ARCHIVE](04-backup-and-sync.md#backup-source-archive)); rename папок резервированием не выполняется. Library убирает в активном дереве кнопку «+» (создание папки и ручная загрузка) и пункты «Переименовать», «Переместить», «Копировать», «Удалить» и не предлагает активное дерево назначением ([FILES-BROWSE](05-file-library.md#files-browse)); ручные create, rename, move, copy и delete Android отправляет без backupSource. Отключить источник можно в Settings и на его корне в Library ([BACKUP-SOURCE-DISABLE](04-backup-and-sync.md#backup-source-disable-android)): защита снимается, дерево остаётся в AutoUploads. Ручное удаление активного источника целиком возможно только после его отключения. Отключённый источник Library позволяет перенести из AutoUploads в обычную библиотеку или удалить.

<a id="files-checksums"></a>

## FILES-CHECKSUMS — Полный список checksum

**Status:** AS-IS

**Availability:** SERVER_ONLY

### Назначение

Получить контрольные суммы логических файлов пользователя через API.

### Текущее поведение

Внешний клиент запрашивает полный список checksum.

Server возвращает для всех RemoteFile пользователя [FileChecksumDto](01-system-model.md#api-projections): id, originalFilename и checksum из StoredObject.

Результат содержит логические ссылки и сохранённые checksum, без folderId.

### Текущие ограничения

Нет постраничной выдачи, фильтров и установленного порядка; байты не читаются. Этот список не является delta/reconciliation протоколом. Android использует только отдельный folder pre-check ([BACKUP-EXISTING](04-backup-and-sync.md#backup-existing)).

## Операции, отсутствующие в текущей системе

<a id="files-trash"></a>

## FILES-TRASH — Корзина, восстановление и версии

**Status:** AS-IS

**Availability:** NOT_PRESENT

### Назначение

Зафиксировать, можно ли отменить удаление или выбрать старую версию файла.

### Текущее поведение

Система не предоставляет корзину/восстановление, историю версий, перезапись или автоматическое переименование. Удаление файла или папки сразу удаляет записи, байты удаляет фоновая очистка; RemoteFile.deletedAt не заполняется активным API и не создаёт корзину.

Прикладного восстановления удалённого удалённый файл и выбора предыдущей версии нет.

### Текущие ограничения

Прежние удалённые копии после изменения локального изображения сохраняются по [BACKUP-CHANGE](04-backup-and-sync.md#backup-change), но не образуют историю версий. Внешние backup/restore неизвестны ([SYSTEM-STORAGE](07-system-rules-and-recovery.md#system-storage)).

<a id="files-reconcile"></a>

## FILES-RECONCILE — Remote reconciliation и bidirectional sync

**Status:** AS-IS

**Availability:** NOT_PRESENT

### Назначение

Определить реакцию Android на изменения удалённого каталога.

### Текущее поведение

Внешний клиент переименовал, переместил или удалил удалённый файл либо Server потерял bytes.

Android не получает удалённые изменения, не применяет их к изображениям устройства и не пересматривает обычный SYNCED. Общего протокола delta/tombstones/device/sync sessions/push нет.

Локальная история может расходиться с текущей удалённой библиотекой. Наличие Server list/checksums/CRUD не создаёт двустороннюю сверку.

### Текущие ограничения

Library показывает текущий каталог Server; ручные операции Library (загрузка, скачивание, создание, переименование, перемещение, копирование файла, удаление) не меняют LocalMedia и записи источников резервирования. Local delete propagation также отсутствует ([BACKUP-DELETE](04-backup-and-sync.md#backup-delete)); remote loss не запускает автоматический repair/re-upload SYNCED.

### Нерешённый вопрос

Направления синхронизации, retention и роль Android при удалённых изменениях ещё не приняты как продуктовая модель.
