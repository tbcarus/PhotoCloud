# Sharing и доступ

Изменять файлы и папки может только их владелец. Читать чужие файлы и папки Server позволяет по действующему USER-разрешению [Share](01-system-model.md#share). Выдать или отозвать разрешение через API пока нельзя, публичных ссылок нет.

Используемая модель: [User](01-system-model.md#user), [Folder](01-system-model.md#folder), [RemoteFile](01-system-model.md#remote-file), [StoredObject](01-system-model.md#stored-object) и [Share](01-system-model.md#share).

<a id="access-owner"></a>

## ACCESS-OWNER — Доступ к собственным файлам и папкам

**Status:** IMPLEMENTING

**Availability:** SERVER_ONLY

### Назначение

Ограничить изменение удалённой библиотеки владельцем объектов.

### Текущее поведение

Клиент выполняет защищённую операцию с файлом или папкой. Server установил пользователя по [AUTH-ACCESS](02-account-and-auth.md#auth-access).

1. Операции изменения и owner-only операции ищут RemoteFile/Folder по ID вместе с текущим User. К ним относятся upload, создание, переименование, перемещение, копирование и удаление файлов и папок, отключение источника, `checksums` и `checksums/exists`, а также целевая папка move/copy/upload.
2. Собственный объект передаётся операции. Отсутствующий и чужой объект одинаково дают 404, даже если у текущего пользователя есть Share на этот объект или его предка.
3. Чтение отдельной папки или файла по ID проверяется правами [ACCESS-READ](06-sharing-and-access.md#access-read): владелец проходит её так же, как раньше. Для download достаточно права чтения RemoteFile; отдельная проверка ACL StoredObject не выполняется.

Списки без указания папки (`GET /api/v1/files` без folderId, `checksums`) и ROOT всегда относятся к текущему пользователю.

Клиент работает в своём логическом каталоге. Android использует эту проверку при backup, но не предоставляет отдельного UI управления доступом.

### Текущие ограничения

Роль ADMIN не даёт обхода проверки владельца; отдельных действующих операций по ролям нет. Модель допускает несовпадение владельцев связанных записей, но обычные upload/copy создают объекты одного владельца. Поведение удаления в таком состоянии описано в [FILES-DELETE](05-file-library.md#files-delete).

<a id="access-read"></a>

## ACCESS-READ — Чтение предоставленных файлов и папок

**Status:** IMPLEMENTING

**Availability:** SERVER_ONLY

### Назначение

Дать получателю читать файлы и папки другого пользователя без копий и без права изменения.

### Текущее поведение

Клиент запрашивает одну из операций чтения:
- children папки ([FOLDERS-BROWSE](05-file-library.md#folders-browse));
- список файлов папки ([FILES-LIST](05-file-library.md#files-list));
- метаданные файла ([FILES-METADATA](05-file-library.md#files-metadata));
- download ([FILES-DOWNLOAD](05-file-library.md#files-download));
- миниатюру ([FILES-THUMBNAIL](05-file-library.md#files-thumbnail)).

1. Server находит объект по ID. Владелец объекта читает его без дальнейших проверок.
2. Иначе чтение папки разрешено, если у текущего пользователя есть действующий USER-доступ к этой папке или к одному из её предков. Чтение файла разрешено при доступе к самому файлу, к его папке или к любому её предку.
3. Действующим считается Share, у которого kind=USER, recipient — текущий пользователь, expiresAt отсутствует или текущее время строго меньше expiresAt. Кроме того:
   - Share.owner совпадает с фактическим владельцем объекта;
   - владелец активен (enabled) и не заблокирован (banned).
4. Предки учитываются только в пределах владельца объекта. Для файла его папка и StoredObject должны принадлежать тому же владельцу, что и RemoteFile. Share на ROOT и AUTO_UPLOADS не учитывается.
5. Объект без права чтения неотличим от отсутствующего: 404, как и прежде для чужого объекта.
6. Children и список файлов предоставленной папки выбираются по её владельцу. Ответы имеют прежний вид FolderDto, FileItemDto и FilePage, но в FolderDto чужой папки backupSource не выдаётся: получатель видит его отсутствующим, владелец — как прежде. Download и миниатюра работают так же, как у владельца, включая Range/206 и ETag.

Правила дерева следуют из текущего Folder.parent и RemoteFile.folder в момент запроса, отдельных копий нет:
- доступ к папке распространяется на её существующие и будущие объекты;
- файл, перенесённый внутрь предоставленного дерева, становится доступен, а вынесенный из него — перестаёт;
- перемещённая предоставленная папка остаётся доступной, так как её ID не меняется;
- несколько разрешений действуют по логическому ИЛИ: истечение одного не отменяет другое;
- доступ к вложенной папке не открывает её родителей и соседей;
- удаление объекта, владельца или получателя удаляет связанные Share.

Получатель не может переименовать, переместить, скопировать или удалить предоставленный объект, загрузить файл или создать папку в чужой папке, перенести в неё свой файл и проверить в ней checksum: эти операции остаются owner-only ([ACCESS-OWNER](06-sharing-and-access.md#access-owner)) и дают 404.

### Текущие ограничения

API выдачи, изменения и отзыва Share нет: записи появляются только при прямой записи в БД, поэтому для пользователя функция недоступна ([SHARING-ABSENT](06-sharing-and-access.md#sharing-absent)). Раздела «Доступно мне», списка полученных доступов и Android UI нет; получатель должен знать ID объекта. Глобальный список файлов, checksums и ROOT показывают только собственные объекты.

Блокировка или деактивация получателя на уже выданный access token не влияет: действует общее правило [AUTH-BLOCK](02-account-and-auth.md#auth-block).

<a id="sharing-absent"></a>

## SHARING-ABSENT — Выдача доступа и публичные ссылки

**Status:** AS-IS

**Availability:** NOT_PRESENT

### Назначение

Однозначно установить, чего в sharing PhotoCloud пока нет.

### Текущее поведение

В Android и Server нет API/UI для выдачи доступа другому пользователю, его изменения и отзыва. Нет действия получателя «Убрать из моей библиотеки», раздела «Доступно мне», публичных ссылок и публичных endpoints. Модель [Share](01-system-model.md#share) содержит поля LINK, но токены ссылок не генерируются и не шифруются, а проверка чтения учитывает только USER. Обычные upload и copy не создают Share и общих ссылок между владельцами.

Пользователь не может поделиться файлом или папкой как функцией PhotoCloud.

### Текущие ограничения

Структура данных допускает несколько RemoteFile, ссылающихся на StoredObject. Реализованной функции sharing из этого не следует. Copy создаёт независимые байты ([FILES-COPY](05-file-library.md#files-copy)). Наличие ветки удаления ссылки пользователем, не владеющим StoredObject, не доказывает предоставление совместного доступа.
