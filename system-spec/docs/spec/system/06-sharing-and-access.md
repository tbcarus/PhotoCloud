# Sharing и доступ

Изменять файлы и папки может только их владелец. Читать чужие файлы и папки Server позволяет по действующему USER-разрешению [Share](01-system-model.md#share). Владелец выдаёт, изменяет и отзывает такие разрешения, в том числе на Android ([поделиться](05-file-library.md#files-browse-sharing)); получатель видит их в «Доступно мне» ([SHARED-WITH-ME](05-file-library.md#shared-with-me)). Владелец создаёт публичные ссылки, в том числе на Android ([SHARING-LINK-MANAGE](06-sharing-and-access.md#sharing-link-manage), [поделиться](05-file-library.md#files-browse-sharing)); по ним файл или дерево папки читаются без входа ([ACCESS-LINK-READ](06-sharing-and-access.md#access-link-read)), папку браузер показывает простой страницей просмотра ([FILES-PUBLIC-READ](05-file-library.md#files-public-read)). О новом USER-доступе Server сохраняет уведомление получателю ([NOTIFICATIONS-READ](06-sharing-and-access.md#notifications-read)).

Используемая модель: [User](01-system-model.md#user), [Folder](01-system-model.md#folder), [RemoteFile](01-system-model.md#remote-file), [StoredObject](01-system-model.md#stored-object), [Share](01-system-model.md#share) и [Notification](01-system-model.md#notification).

<a id="access-owner"></a>

## ACCESS-OWNER — Доступ к собственным файлам и папкам

**Status:** IMPLEMENTING

**Availability:** SERVER_ONLY

### Назначение

Ограничить изменение удалённой библиотеки владельцем объектов.

### Текущее поведение

Клиент выполняет защищённую операцию с файлом или папкой. Server установил пользователя по [AUTH-ACCESS](02-account-and-auth.md#auth-access).

1. Операции изменения и owner-only операции ищут RemoteFile/Folder по ID вместе с текущим User. К ним относятся upload, создание, переименование, перемещение, копирование и удаление файлов и папок, отключение источника, `checksums` и `checksums/exists`, выдача и отзыв доступа, а также целевая папка move/copy/upload.
2. Собственный объект передаётся операции. Отсутствующий и чужой объект одинаково дают 404, даже если у текущего пользователя есть Share на этот объект или его предка.
3. Чтение отдельной папки или файла по ID проверяется правами [ACCESS-READ](06-sharing-and-access.md#access-read): владелец проходит её так же, как раньше. Для download достаточно права чтения RemoteFile; отдельная проверка ACL StoredObject не выполняется.

Списки без указания папки (`GET /api/v1/files` без folderId, `checksums`) и ROOT всегда относятся к текущему пользователю.

Клиент работает в своём логическом каталоге. Android использует эту проверку при backup, но не предоставляет отдельного UI управления доступом.

### Текущие ограничения

Роль ADMIN не даёт обхода проверки владельца; отдельных действующих операций по ролям нет. Модель допускает несовпадение владельцев связанных записей, но обычные upload/copy создают объекты одного владельца. Поведение удаления в таком состоянии описано в [FILES-DELETE](05-file-library.md#files-delete).

<a id="access-read"></a>

## ACCESS-READ — Чтение предоставленных файлов и папок

**Status:** IMPLEMENTING

**Availability:** END_TO_END

### Назначение

Дать получателю читать файлы и папки другого пользователя без копий и без права изменения.

### Текущее поведение

Клиент запрашивает одну из операций чтения:
- children папки ([FOLDERS-BROWSE](05-file-library.md#folders-browse));
- список файлов папки ([FILES-LIST](05-file-library.md#files-list));
- метаданные файла ([FILES-METADATA](05-file-library.md#files-metadata));
- download ([FILES-DOWNLOAD](05-file-library.md#files-download));
- миниатюру ([FILES-THUMBNAIL](05-file-library.md#files-thumbnail)).

1. Server находит объект по ID. Владелец объекта читает его без дальнейших проверок.
2. Иначе чтение папки разрешено, если у текущего пользователя есть действующий USER-доступ к этой папке или к одному из её предков. Чтение файла разрешено при доступе к самому файлу, к его папке или к любому её предку.
3. Действующим считается Share, у которого kind=USER, recipient — текущий пользователь, expiresAt отсутствует или текущее время строго меньше expiresAt. Кроме того:
   - Share.owner совпадает с фактическим владельцем объекта;
   - владелец активен (enabled) и не заблокирован (banned).
4. Предки учитываются только в пределах владельца объекта. Для файла его папка и StoredObject должны принадлежать тому же владельцу, что и RemoteFile. Share на ROOT и AUTO_UPLOADS не учитывается.
5. Объект без права чтения неотличим от отсутствующего: 404, как и прежде для чужого объекта.
6. Children и список файлов предоставленной папки выбираются по её владельцу. Ответы имеют прежний вид FolderDto, FileItemDto и FilePage, но в FolderDto чужой папки backupSource не выдаётся: получатель видит его отсутствующим, владелец — как прежде. Download и миниатюра работают так же, как у владельца, включая Range/206 и ETag.

Правила дерева следуют из текущего Folder.parent и RemoteFile.folder в момент запроса, отдельных копий нет:
- доступ к папке распространяется на её существующие и будущие объекты;
- файл, перенесённый внутрь предоставленного дерева, становится доступен, а вынесенный из него — перестаёт;
- перемещённая предоставленная папка остаётся доступной, так как её ID не меняется;
- несколько разрешений действуют по логическому ИЛИ: истечение одного не отменяет другое;
- доступ к вложенной папке не открывает её родителей и соседей;
- удаление объекта, владельца или получателя удаляет связанные Share.

Получатель не может переименовать, переместить, скопировать или удалить предоставленный объект, загрузить файл или создать папку в чужой папке, перенести в неё свой файл и проверить в ней checksum: эти операции остаются owner-only ([ACCESS-OWNER](06-sharing-and-access.md#access-owner)) и дают 404.

### Текущие ограничения

Доступы выдаёт и отзывает владелец ([SHARING-USER-MANAGE](06-sharing-and-access.md#sharing-user-manage)); получатель находит их в [SHARED-WITH-ME](05-file-library.md#shared-with-me). Android читает предоставленные ресурсы только в разделе «Доступно мне» ([SHARED-WITH-ME](05-file-library.md#shared-with-me), [Android Library](05-file-library.md#shared-with-me-android)). Глобальный список файлов, checksums и ROOT показывают только собственные объекты.

Блокировка или деактивация получателя на уже выданный access token не влияет: действует общее правило [AUTH-BLOCK](02-account-and-auth.md#auth-block).

<a id="sharing-user-manage"></a>

## SHARING-USER-MANAGE — Выдача и управление USER-доступами

**Status:** IMPLEMENTING

**Availability:** END_TO_END

### Назначение

Дать владельцу открыть файл или папку зарегистрированным пользователям на просмотр и скачивание, изменить срок и отозвать доступ.

### Текущее поведение

Владелец выполняет запрос с действующим access ([AUTH-ACCESS](02-account-and-auth.md#auth-access)). Android делает это из меню «Поделиться» объекта библиотеки и раздела «Предоставлено мной» ([поделиться](05-file-library.md#files-browse-sharing)).

**Выдача** (`POST /api/v1/shares/users`): ровно один из fileId и folderId, один или несколько emails, необязательный expiresAt.
1. Server проверяет вход: ровно один ресурс, непустой список корректных адресов, expiresAt отсутствует или позже текущего момента.
2. В одной транзакции Server блокирует дерево владельца той же блокировкой строки ROOT, что у структурных изменений ([Camera, обычная библиотека и имена](01-system-model.md#library-names)), и только затем ищет ресурс среди собственных объектов. Удаление ресурса не может пройти между проверкой и созданием доступа; удалённый до блокировки ресурс даёт 404.
3. ROOT и AUTO_UPLOADS отклоняются; CAMERA, обычные USER-папки, корни активных источников и любые файлы допустимы.
4. Каждый адрес ищется по тем же правилам, что при входе: email сравнивается без учёта регистра. Адреса одного аккаунта считаются одним получателем.
5. Если хотя бы один адрес не подходит, не создаётся и не меняется ни один доступ. Не подходят адрес без аккаунта, неактивный или заблокированный аккаунт и собственный адрес владельца.
6. Для каждого получателя существующий USER-доступ к этому ресурсу получает новый expiresAt, в том числе истёкший доступ продлевается; иначе создаётся новый Share. Дубликат не появляется: на пару ресурс + получатель остаётся одна запись.
7. Для каждого нового Share в той же транзакции создаётся [Notification](01-system-model.md#notification) SHARE_GRANTED его получателю: targetType FILE или FOLDER и targetId ресурса, заголовок «Предоставлен доступ», текст «Вам предоставлен доступ к файлу „{имя}“» или «…к папке „{имя}“» с именем ресурса на момент выдачи. Обновление существующего, в том числе истёкшего, Share уведомления не создаёт: при групповой выдаче уведомление получают только новые получатели. Отклонённая или откаченная операция не оставляет ни Share, ни уведомлений; отдельной асинхронной доставки нет.
8. Ответ — список ShareDto по одному на получателя в порядке первого упоминания адресов.

**Список** (`GET /api/v1/shares`): страница ShareDto всех USER-доступов, выданных текущим пользователем, от новых к старым. Можно указать fileId или folderId собственного ресурса. Истёкшие доступы остаются в списке со статусом EXPIRED.

**Изменение срока** (`PATCH /api/v1/shares/{id}`): expiresAt — будущий момент, а явный null делает доступ бессрочным. Истёкший доступ продлевается так же.

**Отзыв**: `DELETE /api/v1/shares/{id}` удаляет один доступ, `DELETE /api/v1/shares/users` с fileId или folderId — все USER-доступы к собственному ресурсу. Запись Share удаляется физически, отсутствие доступов у ресурса — тоже успех.

Изменение срока, отзыв, истечение и отказ получателя уведомлений не создают и ранее созданные не удаляют. После отзыва или отказа записи Share нет, поэтому следующая выдача тому же получателю создаёт новый Share и новое уведомление.

Изменения сразу учитываются проверкой чтения ([ACCESS-READ](06-sharing-and-access.md#access-read)): фоновой обработки сроков нет, наступивший expiresAt закрывает доступ при следующем запросе. Файлы и RemoteFile не копируются. Срок передаётся в ISO-8601 со смещением, хранится и возвращается как момент UTC.

### Ошибки и recovery

- 400 — некорректный вход:
  - ни одного или два ресурса;
  - пустой список адресов либо некорректный email;
  - expiresAt не в будущем;
  - PATCH без поля expiresAt;
  - fileId и folderId одновременно в списке;
  - ROOT или AUTO_UPLOADS.
- 400 SHARE_RECIPIENT_UNAVAILABLE — недопустимые получатели. fieldErrors сопоставляет каждый отклонённый адрес с причиной: «Recipient is not available» для отсутствующего, неактивного и заблокированного аккаунта без различия либо «Cannot share with yourself».
- 404 — ресурс отсутствует или принадлежит другому пользователю, в том числе получателю доступа к нему. Также 404 — Share отсутствует, выдан другим владельцем или повторно отзывается.

Владелец видит и меняет только выданные им доступы: чужой ID неотличим от отсутствующего. Получатель не может выдать доступ к чужому объекту дальше, изменить срок или затронуть других получателей.

### Текущие ограничения

Верхний предел числа адресов в одном запросе не задан. Пользовательского поиска получателей и автодополнения нет: нужен точный email. Уведомление о выдаче сохраняется на Server, но Android его пока не показывает; push и email нет ([NOTIFICATIONS-READ](06-sharing-and-access.md#notifications-read)).

<a id="sharing-link-manage"></a>

## SHARING-LINK-MANAGE — Публичные ссылки: создание и управление

**Status:** IMPLEMENTING

**Availability:** END_TO_END

### Назначение

Дать владельцу открыть файл или папку любому, у кого есть секретная ссылка, без входа в PhotoCloud, и управлять такими ссылками.

### Текущее поведение

Владелец выполняет запросы `/api/v1/shares/links` с действующим access ([AUTH-ACCESS](02-account-and-auth.md#auth-access)). Android делает это из режима «По ссылке» окна «Поделиться» и раздела «Предоставлено мной» ([поделиться](05-file-library.md#files-browse-sharing)): копирует URL из ответа и передаёт его через системный выбор приложения.

**Создание** (`POST`): ровно один из fileId и folderId, необязательный expiresAt (null — бессрочно, иначе только будущий момент).
1. Под той же блокировкой дерева владельца, что у выдачи USER-доступа, Server ищет ресурс среди собственных объектов. ROOT и AUTO_UPLOADS отклоняются; файлы, CAMERA, USER-папки и корни активных источников допустимы.
2. Каждый вызов создаёт новый независимый Share kind=LINK. Секрет — 32 случайных байта из криптостойкого генератора в URL-safe Base64 без padding.
3. В БД сохраняются только SHA-256 секрета (Share.tokenHash) и сам секрет, зашифрованный AES-GCM ключом конфигурации Server с новым случайным nonce (Share.encryptedToken). Открытым текстом секрет не хранится.
4. Ответ — [LinkShareDto](01-system-model.md#api-projections) с полным URL `{sharing.public-base-url}/s/{секрет}`. Адрес строится из настроенного публичного адреса Server, а не из заголовка Host запроса.

**Список** (`GET`, page и size, необязательно fileId или folderId собственного ресурса) — ссылки владельца от новых к старым, включая истёкшие (EXPIRED). URL восстанавливается расшифровкой секрета, его можно скопировать повторно.

**Изменение срока** (`PATCH /{id}`) — как у USER: будущий момент или явный null; истёкшая ссылка продлевается тем же URL.

**Отзыв**: `DELETE /{id}` — одна ссылка, `DELETE ?fileId=` или `?folderId=` — все ссылки ресурса. Запись удаляется физически. USER-доступы не затрагиваются, как и отзыв USER-доступа не затрагивает ссылки: API USER и LINK разделены, ссылки не попадают в списки USER-доступов.

Чтение по ссылке — [ACCESS-LINK-READ](06-sharing-and-access.md#access-link-read).

### Ошибки и recovery

- 400 — ни одного или два ресурса, срок не в будущем, PATCH без expiresAt, ROOT или AUTO_UPLOADS.
- 404 — ресурс чужой или отсутствует; ссылка чужая, отсутствует или уже отозвана.
- 503 LINK_SHARING_UNAVAILABLE — не настроены ключ `sharing.link-key` или адрес `sharing.public-base-url`. Создание, список и изменение срока недоступны, остальные API Server работают. Отзыв выполняется и без конфигурации, а уже выданные ссылки читаются: поиск идёт по хешу.

### Текущие ограничения

Ключ шифрования задаётся внешней конфигурацией (Base64 32 байт) и должен сохраняться вместе с резервной копией конфигурации Server. С другим ключом выданные ссылки продолжают работать, но их URL повторно не получить: в ответе url отсутствует. Ротации ключа и отдельного хранилища секретов нет. Внешний адрес — только HTTPS; HTTP допускается лишь для localhost. Неверно заданные ключ или адрес останавливают запуск Server. Android показывает такую ссылку без адреса и позволяет её продлить или отозвать. Пароля, подтверждения получателем и ограничения числа скачиваний нет; EXIF оригиналов не удаляется.

<a id="access-link-read"></a>

## ACCESS-LINK-READ — Чтение по публичной ссылке

**Status:** IMPLEMENTING

**Availability:** SERVER_ONLY

### Назначение

Открыть предоставленный по ссылке файл или дерево папки без аккаунта и не дать выйти за его границы.

### Текущее поведение

Запрос к `/s/{секрет}` или `/api/v1/public/s/{секрет}/…` выполняется без JWT. Анонимно разрешены только GET и HEAD; заголовок Authorization на этих маршрутах не проверяется. Каждый запрос, включая каждый Range-запрос, проходит проверку:
1. Секрет ищется только по SHA-256. Строка другой длины или алфавита отклоняется до поиска.
2. Ссылка существует, kind=LINK, текущее время строго меньше expiresAt или срока нет.
3. Владелец активен (enabled) и не заблокирован (banned). Цель принадлежит владельцу: у файла — и RemoteFile, и StoredObject; у папки — не ROOT и не AUTO_UPLOADS.
4. Ссылка на файл открывает только этот файл. Ссылка на папку открывает её и текущее поддерево того же владельца: папку — если она сама или её предок является папкой ссылки, файл — если такова его папка.

Правила дерева те же, что у USER ([ACCESS-READ](06-sharing-and-access.md#access-read)): файл, перенесённый внутрь, становится доступен, вынесенный — нет; перемещённый объект самой ссылки остаётся доступным. Родители и соседи не открываются. Отзыв, истечение срока, блокировка владельца и удаление объекта закрывают новые запросы. Уже начатое потоковое скачивание может завершиться, полученные байты не отзываются.

Неизвестный, неверный по форме, отозванный и истёкший секрет, а также объект вне ссылки дают одинаковый 404 «Not found»; секрет в ответ не попадает. Операции изменения по ссылке отсутствуют: прочие методы на публичных маршрутах требуют входа (401). Операции чтения — [FILES-PUBLIC-READ](05-file-library.md#files-public-read). Страница папки в браузере прав не добавляет: её HTML выдаётся только по действующей ссылке, а каждый запрос содержимого со страницы проверяется заново; путь во фрагменте адреса — лишь навигация.

### Текущие ограничения

Ограничения частоты анонимных запросов нет. Перебор секрета практически исключён (256 бит). Генерацию миниатюр ограничивает общий лимит одновременных генераций ([FILES-THUMBNAIL](05-file-library.md#files-thumbnail)). Журналы reverse proxy и балансировщика видят полный URL с секретом и настраиваются отдельно ([SYSTEM-DIAGNOSTICS](07-system-rules-and-recovery.md#system-diagnostics)).

<a id="notifications-read"></a>

## NOTIFICATIONS-READ — Получение и прочтение уведомлений

**Status:** IMPLEMENTING

**Availability:** SERVER_ONLY

### Назначение

Сообщить пользователю о событиях, касающихся его, — сейчас о новом USER-доступе — и дать отмечать прочитанное.

### Текущее поведение

Пользователь выполняет запрос `/api/v1/notifications` с действующим access ([AUTH-ACCESS](02-account-and-auth.md#auth-access)). Уведомления создаёт Server: сейчас только SHARE_GRANTED при выдаче нового USER-доступа ([SHARING-USER-MANAGE](06-sharing-and-access.md#sharing-user-manage)).

**Список** (`GET`, page и size как у [FILES-LIST](05-file-library.md#files-list)): страница [NotificationDto](01-system-model.md#api-projections) текущего пользователя от новых к старым по createdAt, при равном времени — по убыванию id. Уведомление показывается независимо от того, существует ли ещё объект и действует ли Share.

**Количество непрочитанных** (`GET /unread-count`): число уведомлений текущего пользователя без readAt; при отсутствии уведомлений — 0.

**Прочтение одного** (`PATCH /{id}/read`): readAt получает текущее время Server; уже прочитанное сохраняет исходный readAt. Ответ — NotificationDto. Повтор не меняет данные.

**Прочтение всех** (`PATCH /read-all`): одной операцией readAt получают все непрочитанные уведомления текущего пользователя; у прочитанных readAt не меняется. Ответ — 204, повтор не меняет данные.

targetType и targetId — указатель для будущего перехода к объекту, а не право: чтение объекта проверяет [ACCESS-READ](06-sharing-and-access.md#access-read), и после удаления объекта или отзыва Share оно даёт 404, хотя уведомление остаётся.

### Ошибки и recovery

- 401 — запрос без действующего access.
- 404 — уведомление отсутствует или принадлежит другому пользователю: чужие ID неотличимы от отсутствующих, ни содержимое, ни состояние чужого уведомления не меняются.
- 400 — отрицательный page или нулевой size.

### Текущие ограничения

Android уведомления не запрашивает и не показывает. Push, email, WebSocket и фоновой доставки нет; уведомления об изменении срока, отзыве и истечении доступа, о новых файлах в общей папке и о публичных ссылках не создаются. Удаления уведомлений пользователем и срока их хранения нет. Верхний предел size не задан.

<a id="sharing-absent"></a>

## SHARING-ABSENT — Уведомления sharing и веб-интерфейс владельца

**Status:** AS-IS

**Availability:** NOT_PRESENT

### Назначение

Однозначно установить, чего в sharing PhotoCloud пока нет.

### Текущее поведение

USER-доступы выдаются и управляются в Android и через API ([SHARING-USER-MANAGE](06-sharing-and-access.md#sharing-user-manage)), полученные показываются в «Доступно мне» ([SHARED-WITH-ME](05-file-library.md#shared-with-me)). О новом доступе Server сохраняет уведомление, доступное через API ([NOTIFICATIONS-READ](06-sharing-and-access.md#notifications-read)); показа уведомлений в Android, push, email и уведомлений об изменении и отзыве нет, поиска пользователей и автодополнения адресов нет. Публичные ссылки создаются и управляются в Android и через API ([SHARING-LINK-MANAGE](06-sharing-and-access.md#sharing-link-manage)); получатель открывает их в браузере ([ACCESS-LINK-READ](06-sharing-and-access.md#access-link-read), [FILES-PUBLIC-READ](05-file-library.md#files-public-read)). Веб-интерфейса владельца нет; уведомлений о создании, изменении и отзыве ссылок нет. Обычные upload и copy не создают Share и общих ссылок между владельцами.


### Текущие ограничения

Структура данных допускает несколько RemoteFile, ссылающихся на StoredObject. Реализованной функции sharing из этого не следует. Copy создаёт независимые байты ([FILES-COPY](05-file-library.md#files-copy)). Наличие ветки удаления ссылки пользователем, не владеющим StoredObject, не доказывает предоставление совместного доступа.
