# Аккаунт и доступ

Путь пользователя: регистрация → письмо → подтверждение вне Android → вход → запросы с авторизацией и refresh → выход. Восстановление пароля через Server API описано здесь же; встроенного восстановления в Android нет.

Используемая модель: [User](01-system-model.md#user), [EmailRequest](01-system-model.md#email-request), [RefreshSession](01-system-model.md#refresh-session) и [TokenPair](01-system-model.md#token-pair).

<a id="auth-reg"></a>

## AUTH-REG — Регистрация пользователя

**Status:** IMPLEMENTING

**Availability:** END_TO_END

### Назначение

Создать аккаунт, который можно активировать и использовать для backup.

### Текущее поведение

При настроенном адресе Server пользователь вводит email и пароль в общую форму Register/Login на Auth и выбирает Register.

1. Android отправляет email/password без Bearer; формат email и длину пароля локально не проверяет. User.displayName не входит в запрос регистрации. Пока запрос выполняется, второй Register не отправляется: кнопки формы заблокированы, а нажатие, пришедшее до блокировки, игнорируется.
2. Если на этом экране для того же email (без учёта регистра) уже получен 201, Android перед отправкой просит подтвердить намеренный повтор: новая регистрация аннулирует ссылку из предыдущего письма, продолжать стоит, если ссылка истекла или письмо не пришло. При отмене запрос не отправляется.
3. Server требует непустой корректный email длиной до 128 символов и непустой пароль длиной 4–20 символов, приводит email к нижнему регистру и ищет пользователя.
4. В одной транзакции БД Server либо создаёт нового User (пароль хранится только как BCrypt-хеш в User.passwordHash, роль USER, User.enabled=false, User.banned=false), либо для существующего неактивированного пользователя проверяет лимит повторов, заменяет пароль и помечает все его неиспользованные ACTIVATE-коды used=true. В той же транзакции создаётся новый EmailRequest с назначением ACTIVATE.
5. После commit Server синхронно отправляет письмо со ссылкой подтверждения через почтовую инфраструктуру; содержимое письма — [AUTH-ACT](02-account-and-auth.md#auth-act).
6. 201 возвращается, только если почтовая инфраструктура приняла письмо на отправку. Android показывает инструкцию: письмо отправлено на указанный email; нужно проверить почту, в том числе «Спам», открыть ссылку и после подтверждения войти кнопкой Login. Автоматического входа нет. Далее применяется [AUTH-ACT](02-account-and-auth.md#auth-act).

До активации аккаунта вход отклоняется.

### Развилки и условия

- Некорректные данные → 400.
- Email уже активированного пользователя → 409 с сообщением, что аккаунт активирован и можно войти; данные не меняются, письмо не отправляется.
- Лимит: у пользователя не больше `auth.request.active-max` (по умолчанию 3) ACTIVATE-кодов, ещё действующих по сроку `auth.request.activation-valid-days`. Учитываются код первичной регистрации, использованные и аннулированные коды и коды, письмо для которых не отправилось; код учитывается, пока createdAt + срок позже текущего времени. При превышении → 429 с `Retry-After` и сообщением, когда можно повторить, и предложением написать на `my-cld@yandex.ru`; данные не меняются, письмо не отправляется. Значение лимита меньше 1 — ошибка конфигурации, Server не запускается.
- Ошибку из ответа Server Android показывает текстом сообщения Server.

### Ошибки и recovery

Отправка письма не входит в транзакцию БД. Если письмо не удалось сформировать, SMTP вернул ошибку или истёк timeout, сохранённые User, пароль и код остаются, код учитывается в лимите. Server возвращает 503: регистрационные данные сохранены, письмо не отправлено, регистрацию стоит повторить позже или написать на `my-cld@yandex.ru`. При timeout письмо могло быть фактически принято. Штатный recovery — повторная регистрация неактивированного пользователя по лимиту; повторной отправки того же письма нет ([AUTH-RESEND](02-account-and-auth.md#auth-resend)). 201 не удостоверяет доставку письма.

Register Android выполняет отдельным HTTP-клиентом: connect и write timeout 5 с, read timeout 30 с, общий call timeout 40 с (включая DNS); автоматический повтор при сбое соединения отключён, потому что повторный POST аннулировал бы ссылку из уже отправленного письма. На Server SMTP ограничен timeout отдельных операций: подключение, каждое чтение и каждая запись — по 5 с. Разрешение DNS и общая длительность отправки ими не ограничены, поэтому общего гарантированного времени выполнения SMTP на Server нет, и Server может не ответить до истечения call timeout Android.

Если ответ Server не получен (IOException, в том числе timeout), Android сообщает, что результат регистрации неизвестен: Server мог сохранить регистрацию и отправить письмо. Android предлагает сначала проверить почту, в том числе «Спам», и предупреждает, что повторная регистрация аннулирует ссылку из ранее отправленного письма. POST автоматически не повторяется.

### Текущие ограничения

Конкурентные запросы регистрации одного email не защищены блокировкой: параллельные повторы проверяют лимит независимо, одновременная первичная регистрация может завершиться 500 на ограничении уникальности, а согласование повтора с подтверждением ([AUTH-ACT](02-account-and-auth.md#auth-act)) не обеспечено. Это требование целевого поведения не реализовано.

Email с полученным 201 Android помнит только в состоянии текущего экрана: после неизвестного результата (IOException) или перезапуска приложения подтверждение повтора не запрашивается.

Правила сложности пароля отсутствуют; частота первичных регистраций разных email и reset request не ограничена. Поле пароля Android не маскируется и явно не очищается после операций; пароль не сохраняется в локальных настройках.

## Целевое поведение

1. **Разрешить повторную регистрацию неактивированного пользователя.**

При запросе регистрации Server проверяет существование пользователя с указанным email:
- если пользователя нет — выполняется обычная регистрация;
- если пользователь существует и уже активирован — возвращается `409 Conflict` с однозначным сообщением, что аккаунт уже активирован и можно войти; пароль, коды и состояние пользователя не меняются, письмо не отправляется;
- если пользователь существует, но не активирован — допускается повторная регистрация.

При повторной регистрации:
- проверяется количество активных `EmailRequest` типа `ACTIVATE` за период, равный сроку действия ACTIVATE-кода;
- в лимит входит и код первичной регистрации: при N = 3 в пределах срока допускаются первичная регистрация и ещё два повтора;
- при посчёте лимита значения used не учитывается;
- максимальное количество запросов N задаётся конфигурацией; N меньше 1 — ошибка конфигурации, Server не запускается;
- если лимит не превышен, пароль существующего пользователя заменяется новым;
- все предыдущие неиспользованные ACTIVATE-коды этого пользователя помечаются used=true;
- создаётся новый ACTIVATE-код, новый User не создаётся, отправляется новое activation email;
- клиент получает стандартный успешный ответ регистрации;
- активным считается запрос, срок действия которого ещё не истёк; граница та же, что при подтверждении: код учитывается, пока createdAt + срок позже текущего времени;
- срок действия ACTIVATE-кода задаётся конфигурацией независимо от срока PASSWORD_RESET-кода ([EmailRequest](01-system-model.md#email-request)) и одновременно определяет период, в котором учитываются активные запросы;
Если лимит превышен, клиент получает `429 Too Many Requests` с заголовком `Retry-After` (секунды до истечения кода, после которого попытка снова доступна) и сообщением с указанием, когда можно повторить попытку, и предложением обратиться по адресу `my-cld@yandex.ru`, если восстановить доступ самостоятельно не получается. Пароль, коды и состояние пользователя при этом не меняются, письмо не отправляется.

2. **Сделать изменение БД атомарным.**

Для первичной регистрации создание `User` и `EmailRequest(ACTIVATE)` выполняется в одной транзакции.
Для повторной регистрации в одной транзакции выполняются:
- проверка допустимости повторной регистрации
- изменение пароля существующего пользователя
- пометка предыдущих неиспользованных ACTIVATE как used
- создание нового `EmailRequest(ACTIVATE)`
Конкурентные запросы регистрации должны быть защищены так, чтобы лимит, состояние пользователя и activation-коды изменялись согласованно.
Отправка email выполняется после успешного завершения транзакции и в неё не входит.

3. **Обработать ошибку отправки activation email.**

Отправка activation email выполняется синхронно после успешного завершения транзакции БД.
`201` возвращается только если почтовая инфраструктура успешно приняла письмо на отправку.
Чтобы регистрационный HTTP-запрос не зависал на неопределённое время, для SMTP должны быть явно заданы ограниченные connection/read/write timeout.
Эти timeout ограничивают отдельные сетевые операции (подключение, каждое чтение, каждую запись), а не всю отправку; разрешение DNS ими не ограничено, поэтому общий предел ожидания не гарантируется.
Timeout Android-запроса регистрации должен быть согласован с максимальным временем ожидания Server при отправке email.
Если изменения БД успешно сохранены, но письмо не удалось сформировать, SMTP возвращает ошибку или превышен timeout:
- созданный/обновлённый пользователь и activation-код сохраняются;
- созданный EmailRequest не удаляется и учитывается в лимите N;
- Server возвращает `503`;
- клиенту сообщается, что регистрационные данные сохранены, но письмо отправить не удалось ипредлагается повторить регистрацию позже либо обратиться по адресу `my-cld@yandex.ru`.

Неопределённость результата SMTP при timeout принимается: письмо могло быть фактически принято почтовой инфраструктурой, поэтому activation-код сохраняется.
Повторная регистрация неактивированного пользователя является штатным recovery для такого состояния.

4. **Усилить валидацию email.**

Server должен проверять:
- email не пустой;
- значение имеет корректный формат email;
- длина email не превышает установленный предел.
Ограничение длины задаётся validation/data model, а не `application.yml`; ограничение должно быть согласовано с размером поля в БД (то есть не больше указанного в БД).
Текущий предел — `128` символов.

5. **Пароль.**

Текущие серверные требования к паролю сохраняются: непустой пароль длиной `4–20` символов.
Дополнительные complexity rules пока не вводятся.
Отсутствие маскирования пароля на Android на текущем этапе разработки не входит в данное изменение.

## AUTH-ACT — Подтверждение email

**Status:** IMPLEMENTING

**Availability:** SERVER_ONLY

### Назначение

Активировать зарегистрированный аккаунт. Этот этап регистрации выполняется вне Android.

### Текущее поведение

Пользователь открывает ссылку из регистрационного письма в почтовом клиенте/браузере. Существует ACTIVATE-код, созданный при [AUTH-REG](02-account-and-auth.md#auth-reg).

1. Письмо содержит ссылку на GET /api/v1/auth/register/confirm с UUID-кодом. Server строит адрес ссылки из scheme/host/port/context входящего запроса. Ссылка в письме кликабельна, полный URL виден для копирования. Письмо сообщает срок действия ссылки (значение срока ACTIVATE-кода из конфигурации) и поясняет: для активации аккаунта нужно подтвердить почту, перейдя по ссылке, при повторной регистрации действует только ссылка из последнего письма, письмо можно проигнорировать, если регистрацию не запрашивали.
2. Server находит код и проверяет назначение ACTIVATE, отсутствие отметки used и срок действия ACTIVATE-кода с момента создания: по умолчанию 3 дня, настраивается независимо от PASSWORD_RESET ([EmailRequest](01-system-model.md#email-request)).
3. В одной транзакции включает аккаунт (enabled=true) и помечает текущий код использованным.
4. Возвращает 200 с HTML-страницей «Адрес подтверждён»: пользователь может вернуться в Android и выполнить [AUTH-LOGIN](02-account-and-auth.md#auth-login).

Аккаунт активирован; это разрешает login при верном пароле и отсутствии ban. Сессия подтверждением не создаётся.

### Развилки и условия

Ответ — всегда HTML-страница в UTF-8, без JSON ErrorResponse. Правило приёма кода не зависит от причины отказа; причина определяется только для текста страницы, в таком порядке, и состояние User и EmailRequest при отказе не меняется:

- отсутствующий параметр code, неизвестный код или код другого назначения → 400 «Ссылка недействительна»;
- пользователь кода уже активирован → 400 «Адрес уже подтверждён» с предложением войти;
- код used у неактивированного пользователя (аннулирован повторной регистрацией) → 400 «Ссылка устарела» с предложением открыть ссылку из последнего письма;
- срок кода истёк → 400 «Срок действия ссылки истёк» с предложением зарегистрироваться повторно.

Ошибка БД при фиксации активации обрабатывается общим обработчиком ошибок и возвращается JSON 500. Другие ACTIVATE-коды пользователя автоматически не погашаются.

### Ошибки и recovery

Повторной отправки того же письма нет ([AUTH-RESEND](02-account-and-auth.md#auth-resend)). При недоставленном письме, истёкшей или устаревшей ссылке recovery — повторная регистрация неактивированного пользователя по лимиту [AUTH-REG](02-account-and-auth.md#auth-reg): она аннулирует прежние ссылки и отправляет новое письмо. Доступность адреса из письма зависит от фактического размещения Server.

### Текущие ограничения

Android не имеет экрана/запроса подтверждения. Одноразовость проверяется флагом used; однократное выполнение при конкурентном использовании кода не гарантировано.

### Нерешённый вопрос

Доступность адреса подтверждения при фактическом размещении Server не проверена.

### Связанное TO-BE после реализации AUTH-REG

Аннулирование прежних ACTIVATE при повторной регистрации, отказ «Ссылка устарела» и recovery через повторную регистрацию реализованы и описаны выше. Не реализовано согласование подтверждения с повторной регистрацией одного пользователя: если повтор закоммичен первым, старый код не должен активировать аккаунт; если подтверждение первым — регистрация отклоняется как для активированного пользователя; код подтверждает аккаунт с актуальным сохранённым паролем. Сейчас такой порядок не обеспечен блокировкой ([AUTH-REG](02-account-and-auth.md#auth-reg), текущие ограничения). Проверка внешней доступности ссылки остаётся открытой.

## AUTH-RESEND — Повторная отправка письма активации

**Status:** AS-IS

**Availability:** STUB

### Назначение

Зафиксировать текущую границу восстановления неподтверждённой регистрации.

### Текущее поведение

Внешний клиент вызывает повторную отправку письма регистрации.

1. Server возвращает 501 с сообщением, что повторная отправка не реализована.
2. Пользователь, код и SMTP этим вызовом не изменяются.

Новое письмо не отправляется.

### Текущие ограничения

В Android нет соответствующего UI. Рабочего альтернативного пути повторной отправки сейчас нет.

### Связанное TO-BE после реализации AUTH-REG

Отдельный resend endpoint остаётся STUB 501 и не меняет БД/SMTP. Альтернативный recovery появляется через повторный Register: он заменяет пароль, инвалидирует старые ACTIVATE и создаёт новый код по лимиту AUTH-REG. Это не повторная отправка того же кода и не новый Android экран. Утверждение об отсутствии альтернативного пути выше относится только к As-Is.

<a id="auth-login"></a>

## AUTH-LOGIN — Вход и сохранение локальной сессии

**Status:** IMPLEMENTING

**Availability:** END_TO_END

### Назначение

Получить доступ к аккаунту и включить возможность фонового backup.

### Текущее поведение

При настроенном адресе Server пользователь вводит email/password и выбирает Login. Для успешного входа аккаунт должен быть активирован.

1. Android отправляет запрос входа без Bearer. Server валидирует email/password; длина пароля 4–20.
2. Server проверяет пользователя, пароль, enabled и banned.
3. При успехе обновляет User.lastLoginAt и User.lastUpdate, выдаёт access и refresh со сроками из конфигурации Server (по умолчанию 24 часа и 180 дней), сохраняя refresh на Server.
4. Android принимает ответ только с двумя непустыми строками токенов и сохраняет пару в зашифрованном локальном хранилище.
5. Android пересматривает условия фонового backup, ставит разовый Загрузчик для накопленной очереди и показывает успешный вход. Auth показывает email из subject токена; это не запрос профиля.

У Server есть refresh-сессия, у Android — сохранённая пара. Periodic Загрузчика требует также URL и media permission; Поставщик от входа не зависит ([BACKUP-BACKGROUND](04-backup-and-sync.md#backup-background)).

### Развилки и условия

- Неизвестный email, неверный пароль, enabled=false или banned=true приводят к одинаковому 401 INVALID_CREDENTIALS.
- Повторный успешный login создаёт ещё одну серверную refresh-сессию, не отзывая предыдущие.

### Ошибки и recovery

Ошибка входа показывается пользователю; прежняя пара сама не очищается. Ответ без двух непустых токенов не принимается как успешный login.

### Текущие ограничения

Наличие пары определяет локальное состояние входа, но не доказывает действительность токенов или то, что их срок не истёк. Раздельное хранение контекста аккаунта и Server описано в [SYSTEM-SCOPE](07-system-rules-and-recovery.md#system-scope). MFA/OAuth отсутствуют. Начальная проверка сессии и явный Test Auth — [AUTH-ACCESS](02-account-and-auth.md#auth-access).

### Связанное TO-BE после реализации AUTH-REG

После активации вход использует актуальный сохранённый пароль; принятый повтор регистрации меняет его даже при последующем SMTP503. Отклонённый повтор (validation, activated409, limit) пароль не меняет. Проверки enabled/banned, ответы login и lifecycle сессии сохраняются. Техническое обновление lastLoginAt не должно перезаписывать конкурентно изменённые hash/enabled.

<a id="auth-access"></a>

## AUTH-ACCESS — Обычный запрос с авторизацией и проверка сессии

**Status:** AS-IS

**Availability:** END_TO_END

### Назначение

Выполнить защищённую операцию от имени текущего пользователя.

### Текущее поведение

Android отправляет запрос с авторизацией либо пользователь выбирает Test Auth. Для успешного доступа нужен действительный access; наличие пары само по себе недостаточно.

1. Android читает текущую пару и добавляет access Bearer. Без пары запрос всё равно отправляется, без Bearer. Локальной проверки срока или упреждающего refresh нет.
2. Server проверяет подпись, срок и тип ACCESS, находит пользователя и использует его текущие роли.
3. Защищённая операция выполняет собственные проверки доступа к данным. При 401 применяется [AUTH-REFRESH](02-account-and-auth.md#auth-refresh).
4. Явный Test Auth показывает результат пользователю. Начальная автоматическая verifySession выполняет Test Auth, но игнорирует его результат.

Успех относится к конкретному запросу. Test Auth подтверждает прохождение auth в этот момент, но не готовность хранилища или SMTP.

### Ошибки и recovery

Невалидный или истёкший Bearer, в том числе refresh вместо access, → 401. Для удалённого из БД пользователя проверка access не обеспечивает стабильный 401. Ошибка сети при начальной проверке может оставить UI в состоянии входа.

### Текущие ограничения

Enabled/banned в этом пути не перепроверяются ([AUTH-BLOCK](02-account-and-auth.md#auth-block)). Все вкладки доступны независимо от входа. Очистка пары переключает живой Auth на форму, но не вызывает принудительный переход или уведомление об истечении сессии.

<a id="auth-refresh"></a>

## AUTH-REFRESH — Обновление access и повтор запроса

**Status:** IMPLEMENTING

**Availability:** END_TO_END

### Назначение

Продолжить запрос после 401, пока refresh остаётся действительным.

### Текущее поведение

Защищённый запрос получил 401. Для попытки обновления нужны текущий URL и пара; в одной цепочке допускается только один повтор.

1. Android прекращает refresh/replay после уже выполненного повтора.
2. Если access неудавшегося запроса отличается от текущего сохранённого access, Android повторяет запрос с текущим токеном без refresh.
3. Иначе отправляет текущий refresh без Authorization.
4. Server проверяет наличие refresh и пользователя, отзыв, подпись, тип, срок и subject, затем enabled и banned.
5. Если до истечения refresh R1 остаётся больше порога (по умолчанию 30 дней), Server выдаёт только новый access. Иначе в одной транзакции условно отзывает R1 (только если он ещё не отозван), создаёт R2 с полным сроком (по умолчанию 180 дней) и возвращает access вместе с R2.
6. Android сохраняет новый access с прежним refresh, а при R2 в ответе — новую пару; пару с R2 записывает синхронно и проверяет запись ([TokenPair](01-system-model.md#token-pair)). Сохранение выполняется, только если пара в хранилище не сменилась с начала refresh, затем исходный запрос один раз повторяется. Если пару за это время сменил login, она не перезаписывается и повтор выполняется с ней; если logout очистил пару, она не восстанавливается и исходный запрос получает 401.

При успехе исходная операция получает окончательный ответ. Refresh вне окна замены не продлевается; замена даёт новый полный срок. Поэтому сессия устройства, которое хоть раз делает refresh в окне замены, не истекает, а без refresh она переживает остаток срока refresh: от 30 до 180 дней после последнего refresh при сроках по умолчанию.

### Развилки и условия

- Неизвестный, невалидный или истёкший refresh, access вместо refresh, отсутствующий, неактивный (enabled=false) или заблокированный (banned=true) пользователь → 401 `INVALID_REFRESH_TOKEN`. Отозванный refresh, в том числе R1 после замены, → 403 `REFRESH_TOKEN_REVOKED`. Для найденного пользователя отзыв проверяется до подписи и срока, enabled и banned — после них. Отказ не отзывает и не заменяет refresh.
- Из параллельных refresh одного R1 в окне замены R1 заменяет только один; остальные получают 403.
- Ошибка сохранения R2 на Server откатывает и отзыв R1: R1 остаётся действующим, ответ 5xx — временный отказ.
- 2xx с непустым access → сохранить и повторить; refreshToken в ответе необязателен.
- Окончательный отказ — только 401 с кодом ErrorResponse `INVALID_REFRESH_TOKEN` или 403 с кодом `REFRESH_TOKEN_REVOKED` → Android очищает пару (если она не сменилась) и исходный запрос получает 401.
- Временный отказ — всё остальное: 400, 408, 429, 5xx и прочие статусы; 401/403 с другим или отсутствующим кодом; 2xx без тела, с пустым или нечитаемым access, с пустой строкой refresh; IOException/timeout → пара не меняется, исходный запрос получает IOException без токенов в тексте. Неподтверждённая запись пары с R2 тоже даёт IOException, но в памяти уже новая пара.
- Повторный 401 → дальнейшего refresh нет; эта ветка сама пару не очищает.

Код ошибки учитывается, а не только статус: необработанная ошибка Server может вернуться как 401 с кодом `UNAUTHORIZED`.

### Ошибки и recovery

Временная недоступность Server при refresh не удаляет локальную сессию: следующий запрос повторит refresh.

После окончательного отказа для восстановления доступа остаётся обычный login. После очистки пары живой Auth показывает форму; фоновый прогон без пары останавливает фон сам ([BACKUP-BACKGROUND](04-backup-and-sync.md#backup-background)).

### Текущие ограничения

Параллельные refresh сериализуются между собой; login/logout защищены от запоздалого refresh атомарной заменой пары. <a id="auth-logout"></a>

## AUTH-LOGOUT — Выход из текущей сессии

**Status:** IMPLEMENTING

**Availability:** END_TO_END

### Назначение

Отозвать текущий refresh и завершить локальную сессию Android.

### Текущее поведение

Пользователь выбирает Logout в Auth. Android требует настроенный URL и пару токенов.

1. Android отправляет защищённый запрос с текущим refresh R1; при 401 действует [AUTH-REFRESH](02-account-and-auth.md#auth-refresh).
2. Server проверяет наличие и принадлежность refresh пользователю и устанавливает RefreshSession.revoked=true и RefreshSession.revokedAt в текущее время. Уже выданный access продолжает действовать до истечения срока.
3. Если истёкший access вызвал refresh с заменой R1 на R2, повтор запроса всё равно содержит R1: Server отвечает 200, R1 уже отозван заменой. Увидев после ответа в хранилище другой refresh, Android отправляет второй logout с R2.
4. После HTTP-ответов Android очищает пару, затем оценивает их успешность.
5. После полученного результата Android пересматривает фон: при очищенной паре отменяет periodic Загрузчика; наблюдатель MediaStore, observer и periodic Поставщика при полном доступе к изображениям продолжают работу.

При обычном успехе текущий refresh, а при замене во время logout и R2, отозван и локальная пара удалена. Это не немедленный отзыв ранее выданного access: он действует до 24 часов при сроке по умолчанию.

### Развилки и условия

- 200 → серверный отзыв и локальная очистка. Повторный logout собственного уже отозванного refresh тоже возвращает 200.
- Неизвестный refresh → 404, чужой → 403. Android всё равно очищает пару после HTTP-ответа и показывает ошибку; серверный отзыв этим не подтверждён.

### Ошибки и recovery

IOException/ошибка создания запроса до очистки пары может оставить пару; пользователь может повторить Logout. Если не удался второй logout с R2, остаётся пара с R2, и повторный Logout отзывает его. Запоздалый параллельный refresh не восстанавливает очищенную пару ([TokenPair](01-system-model.md#token-pair)).

### Текущие ограничения

Если параллельный фоновый refresh заменит refresh уже после ответа logout и очистки пары, его R2 не сохраняется и остаётся действующим на Server до истечения срока. Logout не очищает локальную очередь, адрес Server, сохранённые итоги прогонов или поля формы; Files сразу показывает «Вход не выполнен». Уже поставленный разовый Загрузчик не отменяется, но без пары завершается до сетевых запросов ([BACKUP-BACKGROUND](04-backup-and-sync.md#backup-background)); отмена фоновой работы не гарантирует мгновенного прекращения передачи. Подробности условий исполнения — [BACKUP-BACKGROUND](04-backup-and-sync.md#backup-background).

<a id="auth-logout-all"></a>

## AUTH-LOGOUT-ALL — Выход из всех серверных сессий

**Status:** AS-IS

**Availability:** SERVER_ONLY

### Назначение

Отозвать все refresh-сессии пользователя.

### Текущее поведение

Внешний клиент вызывает операцию Server с действующим access.

1. Server отзывает все неотозванные refresh текущего пользователя; RefreshSession.revokedAt при массовом отзыве не заполняется.
2. Возвращает 200.

Отозванные refresh больше не дают новый access. Уже выданные access действуют до обычного истечения срока.

### Ошибки и recovery

Применяются обычные ошибки авторизации или сети. Очистка пар на других устройствах не выполняется этим вызовом.

### Текущие ограничения

Android не вызывает эту операцию и не имеет UI управления сессиями. Server не отправляет уведомление об отзыве; Android узнаёт отказ при последующем refresh.

<a id="auth-logout-others"></a>

## AUTH-LOGOUT-OTHERS — Выход из остальных серверных сессий

**Status:** AS-IS

**Availability:** SERVER_ONLY

### Назначение

Отозвать refresh-сессии пользователя кроме указанной.

### Текущее поведение

Внешний клиент вызывает операцию Server с действующим access. Передан существующий refresh текущего пользователя.

1. Server проверяет наличие и принадлежность переданного refresh.
2. Отзывает остальные неотозванные refresh пользователя без заполнения RefreshSession.revokedAt и возвращает 200.

Отозванные refresh больше не дают новый access. Уже выданные access действуют до обычного истечения срока.

### Ошибки и recovery

Неизвестный token → 404, чужой → 403; некорректный запрос → 400. Истечение срока и отзыв исключаемого токена не проверяются: исключение не делает его действующим.

### Текущие ограничения

Android не вызывает эту операцию и не имеет UI управления сессиями. Server не отправляет уведомление об отзыве; Android узнаёт отказ при последующем refresh.

<a id="auth-reset"></a>

## AUTH-RESET — Запрос и подтверждение сброса пароля

**Status:** AS-IS

**Availability:** SERVER_ONLY

### Назначение

Изменить забытый пароль через текущую серверную цепочку восстановления.

### Текущее поведение

Внешний клиент отправляет запрос сброса для email. Аккаунт существует; пользователь должен получить PASSWORD_RESET-код и передать новый пароль для завершения.

1. Server принимает обязательный непустой email как query-параметр reset/request, находит пользователя, создаёт PASSWORD_RESET UUID-код и синхронно отправляет письмо. Срок действия кода — по умолчанию 3 дня, настраивается независимо от ACTIVATE ([EmailRequest](01-system-model.md#email-request)). Успех → 200 с сообщением об отправке.
2. Письмо содержит ссылку reset/page?code=…; адрес Server строится из текущего запроса. Переход по ссылке возвращает 501: форма восстановления не реализована. POST этой страницы также возвращает 501 и не меняет пароль.
3. Отдельный JSON reset/confirm API работает: внешний клиент передаёт code и новый непустой пароль длиной 4–20. Android такой запрос не предоставляет.
4. Server проверяет назначение, used и срок кода. В одной транзакции меняет User.passwordHash, помечает текущий код и reset-коды пользователя, созданные в пределах срока действия PASSWORD_RESET-кода, использованными.
5. Возвращает 200. Последующий login использует новый пароль и обычные enabled/banned проверки.

Пароль меняется только после успешного JSON confirm. Ссылка из письма сама цепочку до смены пароля не доводит.

### Развилки и условия

Неизвестный пользователь/отсутствующий email → 400; email из пробелов → validation 400, отдельной проверки формата email у reset/request нет. Невалидный, использованный, просроченный код или код другого назначения → 400. Прежний способ confirm только через query-параметры не заменяет JSON-запрос.

### Ошибки и recovery

Успех SMTP не удостоверяет доставку; при ошибке отправки код мог сохраниться. Reset resend — STUB 501 без отправки письма. Повторное использование кода штатно отклоняется, но однократная обработка при конкурентных запросах не гарантирована.

### Текущие ограничения

Access и refresh при reset не отзываются. Сброс не активирует неактивный аккаунт и не является ban/unban операцией. В Android нет forgot/reset/resend UI; повторный reset/request существует отдельно, но завершённого восстановления через страницу из письма нет.

### Нерешённый вопрос

Пользовательский путь восстановления при недоставленном письме и заглушке страницы не определён. Продуктовая политика прекращения действующих сессий при смене пароля также не принята.

### Связанное TO-BE после реализации AUTH-REG

Reset и register согласуют конкурентные изменения одного User; окончательный пароль определяется порядком commit. Повтор регистрации инвалидирует только ACTIVATE, reset confirm — только PASSWORD_RESET. Общие почтовые socket timeout становятся конечными. Если письмо reset/request не удалось сформировать или SMTP его не принял, Server возвращает `503` с сообщением, что письмо восстановления не отправлено и запрос стоит повторить позже; созданный PASSWORD_RESET-код сохраняется. Собственный срок reset-кодов и окно их аннулирования, независимые от срока ACTIVATE, HTTP API, отсутствие активации/отзыва токенов и заглушки reset сохраняются. Нерешённые вопросы reset выше этим изменением не закрываются.

<a id="auth-block"></a>

## AUTH-BLOCK — Неактивный или заблокированный аккаунт

**Status:** IMPLEMENTING

**Availability:** END_TO_END

### Назначение

Описать влияние состояния аккаунта на новый вход и уже существующий доступ.

### Текущее поведение

Login выполняется для неактивного или заблокированного пользователя либо защищённый запрос/refresh использует ранее выданную сессию такого пользователя.

1. При login Server проверяет enabled и banned и возвращает 401 при запрете. Android показывает обычную ошибку login.
2. Refresh повторно проверяет enabled и banned: неактивному или заблокированному пользователю новый access и новый refresh не выдаются, ответ — 401 `INVALID_REFRESH_TOKEN`. Android считает его окончательным отказом и очищает пару ([AUTH-REFRESH](02-account-and-auth.md#auth-refresh)). Запись refresh при этом не отзывается.
3. Access эти флаги не проверяет: уже выданный access действует до истечения своего срока (до 24 часов при сроке по умолчанию).

Блокировка прекращает продление доступа, но не уже выданный access. После снятия блокировки ещё не истёкший refresh снова работает, если он сохранился у клиента; Android после отказа свою пару уже удалил.

### Текущие ограничения

API административного управления, блокировки/разблокировки и соответствующий Android UI отсутствуют. Здесь описано поведение при имеющихся флагах, это не операция управления блокировкой. Действующие роли USER/ADMIN не дают обхода проверки владельца.

### Нерешённый вопрос

Прекращение уже выданного access при блокировке и общая политика паролей и сессий не определены как целевое поведение.
