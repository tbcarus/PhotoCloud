## System Model rule

Scenario может использовать только сущность и системно значимое поле, уже определённые в [01-system-model.md](01-system-model.md). Это единственное каноническое место определения их состава, типов, смысла и связей. Сценарий описывает, как операция использует или меняет данные, и не вводит структуру сущности заново.

Если функция требует нового поля или состояния, сначала или одновременно обновляется System Model, затем сценарий. Проверяются и явные обращения Entity.field, и свойства, упомянутые обычным текстом. Новое определение должно иметь подтверждение в текущем As-Is либо относиться к явно утверждённому будущему изменению; нельзя дописывать предполагаемые поля как существующие.

System Model полна на системном уровне: identity, ownership, состояния, данные операций, API-visible свойства, routing, dedup и recovery. Аннотации, индексы, SQL-типы, wiring и внутренние helper fields остаются в коде и тестах компонентов; системные имена сопоставлены с моделями кода, а не заменяют их.

## Scenario ID и ссылки

ID обозначает смысл поведения, а не версию: AUTH-REG, BACKUP-UPLOAD, FILES-DELETE. Числовых суффиксов, v1/V1 и счётчиков ревизий нет. ID уникален во всей System SPEC, не зависит от номера файла, сохраняется при изменении этого поведения и не переиспользуется для другого.

Два разных поведения получают разные осмысленные ID, например FILES-DELETE-LOCAL и FILES-DELETE-REMOTE. Каждый сценарий имеет explicit anchor с ID в нижнем регистре. При переименовании файлов/ID обновляются ссылки и активный reference index. Полагаться только на автоматически полученный anchor заголовка нельзя.

## Status: решение и проверка поведения

| Status | Значение |
| --- | --- |
| `AS-IS` | Текущее подтверждённое поведение |
| `ACCEPTED` | Текущее поведение просмотрено владельцем продукта и принято как целевое |
| `TO-BE` | Утверждено другое или новое целевое поведение |
| `OPEN` | Решение по поведению ещё не принято |
| `DEFERRED` | Изменение осознанно отложено |
| `REMOVE` | Функциональность должна исчезнуть |
| `IMPLEMENTING` | Утверждённое изменение реализуется |
| `IMPLEMENTED` | Реализация заявлена завершённой; итоговое соответствие ещё требует CHECK |
| `CHECK` | Активная проверка соответствия System SPEC, System Model и фактического production code затронутых компонентов |

Codex не назначает ACCEPTED и не принимает продуктовые решения самостоятельно. Наличие AS-IS описания заглушки или отсутствия функции не означает принятия этого состояния как целевого.

## Availability: что реализовано сейчас

| Availability | Значение |
| --- | --- |
| `END_TO_END` | Реализован описанный путь через Android и Server, с указанными ограничениями и внешними шагами |
| `ANDROID_ONLY` | Локальная реализация Android без участия Server в этом действии |
| `SERVER_ONLY` | Server реализует действие, отдельного пользовательского Android flow нет |
| `STUB` | Есть достижимая заглушка UI/API, но заявленная операция не выполняется |
| `NOT_PRESENT` | Функции сейчас нет вообще: нет работающего end-to-end поведения и нет функциональной реализации или заглушки, которую можно считать этой функцией |

Availability отвечает только на вопрос о существующей реализации. Она независима от целевого решения, не является оценкой надёжности и не меняется от появления TO-BE. Изменение Availability следует за появлением и проверкой соответствующей реализации.

Например, TO-BE + NOT_PRESENT означает утверждённую, ещё отсутствующую функцию; IMPLEMENTING + SERVER_ONLY может описывать уже проверенную серверную часть при отсутствии Android; ACCEPTED + END_TO_END — принятую проверенную реализацию обеих сторон. Это примеры будущей работы, не новые сценарии этого пакета.

Availability относится к сценарию: ROOT/children участвуют в сквозном backup, но пользовательский просмотр дерева остаётся SERVER_ONLY. Activation — внешний SERVER_ONLY шаг onboarding; reset API работает на Server, а страница из письма и resend остаются заглушками внутри этого пути.

## Лёгкий формат сценария

Обязательны ID и понятное название, Status, Availability, «Назначение» и «Текущее поведение».

```markdown
<a id="auth-reg"></a>

## AUTH-REG — Регистрация пользователя

**Status:** AS-IS
**Availability:** END_TO_END

### Назначение

Кратко объяснить, для чего нужна функция.

### Текущее поведение

Описать событие, необходимые условия и последовательность действий пользователя,
Android и Server до результата.
```

«Развилки и условия», «Ошибки и recovery», «Текущие ограничения» и «Нерешённый вопрос» добавляются только при содержательной необходимости. Trigger, Preconditions и Result не нужны как обязательные разделы: их смысл включается в последовательность или условия. Ошибки регистрации, refresh, upload и move остаются рядом со своими операциями; общий recovery содержит только сквозные механизмы.

Подробные определения модели не дублируются. Служебные ссылки не входят в сценарии. Не добавляются версии, timestamps, owners, approval tables, changelog и статусы отдельных полей. История остаётся в Git.

## Изменение поведения и lifecycle

```text
AS-IS / ACCEPTED → TO-BE → IMPLEMENTING → IMPLEMENTED → CHECK → ACCEPTED
```

OPEN, DEFERRED и REMOVE возможны в зависимости от решения владельца продукта. IMPLEMENTED не завершает lifecycle: после заявления о завершённой реализации требуется CHECK.

При утверждённом изменении сценарий получает TO-BE и раздел «Целевое поведение», а «Текущее поведение» сохраняется. Во время проектирования читатель видит оба состояния. Сейчас ни одному сценарию целевое поведение не добавлено.

После успешного CHECK и принятия результата владельцем продукта:
1. Целевое поведение становится новым текущим.
2. Развилки, ошибки, ограничения и System Model приводятся к подтверждённому состоянию.
3. Прежнее текущее поведение и отдельный раздел целевого поведения удаляются из актуальной SPEC.
4. Сценарий получает ACCEPTED; история прежнего поведения остаётся в Git.

## CHECK

CHECK означает проверку сценария целиком. Сам статус не утверждает наличие bug, неверность описания/кода или необходимость менять продукт.

В будущей проверке сопоставляются:
1. Текущее и, если есть, целевое поведение System SPEC.
2. Все используемые System Model entities/fields.
3. Production Server code, если сценарий затрагивает Server.
4. Production Android code, если сценарий затрагивает Android.
5. Фактические API, данные и переходы состояний, включая отсутствие скрытых новых полей.

После реализации сравниваются Target behaviour ↔ System Model ↔ production code. CHECK можно назначить существующему поведению: AS-IS → CHECK или ACCEPTED → CHECK.

Результат требует решения: подтверждённое и принятое поведение → ACCEPTED; устаревшее описание → обновление As-Is; утверждённое изменение кода → TO-BE. Codex не выбирает продуктовый исход самостоятельно. CHECK требует проверки соответствия System SPEC, System Model и фактического production code в пределах всего сценария. Тесты и успешные отдельные испытания сами не переводят сценарий из CHECK в AS-IS или ACCEPTED: решение о статусе принимается после проверки сценария целиком.

## Implementation workflow

Прочитать сценарий и модель → получить целевое решение → обновить модель и целевое поведение → определить влияние и затронутые компоненты → IMPLEMENTING → реализация → необходимые тесты → IMPLEMENTED → CHECK → принятие и обновление текущего поведения.

Изменение не обязано затрагивать оба компонента. Перед существенным изменением проводится architecture/impact review: identity, модель данных, API, persistence, обратная совместимость и зависимые сценарии. Сейчас такое проектирование не выполнялось.

Отдельные спецификации Server и Android не ведутся: системное поведение описывается в этой спецификации, а технические детали, не требующие системного описания, остаются в коде и тестах. Расхождение кода с System Model сначала явно фиксируется, а не обходится скрытым добавлением поля.

## Authority и служебная навигация

System SPEC — единственная поддерживаемая спецификация PhotoCloud: system/ задаёт читаемую форму поведения и каноническую системную модель. Расхождения спецификации и кода нельзя разрешать самостоятельно или скрывать редактурой: они фиксируются и согласуются.

История удалённых reference и migration maps, frozen System As-Is и прежних спецификаций Server и Android доступна в Git; эти документы не поддерживаются и не восстанавливаются.
