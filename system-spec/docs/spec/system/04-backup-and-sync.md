# Backup и синхронизация

Текущий backup копирует доступные фотографии с устройства на Server. Android хранит локальную очередь и вывод о результате; удалённую библиотеку он не зеркалит. Ниже описан полный путь фотографии, включая условия и восстановление после ошибок.

Используемая модель: [DeviceMedia](01-system-model.md#device-media), [LocalMedia](01-system-model.md#local-media), [SyncState](01-system-model.md#sync-state), [FailureReason](01-system-model.md#failure-reason) и [RemoteFile](01-system-model.md#remote-file).

<a id="backup-new"></a>

## BACKUP-NEW — Полный путь новой фотографии

**Status:** IMPLEMENTING

**Availability:** END_TO_END

### Назначение

Сохранить на Server содержимое нового видимого Android изображения.

### Текущее поведение

На устройстве появляется фотография; обработку запускает observer в живом процессе, наблюдатель MediaStore (системное ожидание изменения Images, работает без живого процесса и может сам запустить процесс), разовый Поставщик при старте процесса приложения или периодическая задача (periodic) Поставщика. Один факт появления ещё не гарантирует немедленного запуска. Обработка разделена на две части с общей очередью LocalMedia ([BACKUP-BACKGROUND](04-backup-and-sync.md#backup-background))): Поставщик выполняет локальную обработку и требует только полного доступа к изображениям — сеть, URL и авторизация ему не нужны; Загрузчик выполняет серверную обработку и требует сохранённой пары, URL из сохранённых настроек, успешного public ping и того же доступа для чтения файлов.

1. Поставщик восстанавливает допустимые ошибки прошлого прогона и сканирует доступные изображения области scan — DCIM и временно Pictures. Новая LocalMedia сохраняется с состоянием PENDING и локальными сведениями ([BACKUP-DISCOVER](04-backup-and-sync.md#backup-discover)).
2. Поставщик читает содержимое и вычисляет SHA-256; успех даёт CHECKSUM_READY — локальная обработка завершена ([BACKUP-CHECKSUM](04-backup-and-sync.md#backup-checksum)). Если в очереди есть записи для Загрузчика и сохранена пара, Поставщик ставит разовый Загрузчик — уже после первой готовой партии, не дожидаясь конца очереди. Большую очередь Поставщик проходит несколькими прогонами, ограниченными по времени.
3. Загрузчик получает ROOT и ищет CAMERA; при её наличии проверяет checksum в этой папке ([BACKUP-TARGET](04-backup-and-sync.md#backup-target)).
4. Ответ existing переводит локальную запись в SYNCED без upload; missing либо отсутствие CAMERA — в PENDING_UPLOAD ([BACKUP-EXISTING](04-backup-and-sync.md#backup-existing)).
5. Перед upload Android повторно ищет CAMERA, проверяет локальный MIME и доступность потока, отправляет файл. Server вычисляет свойства принятых байтов и определяет папку назначения.
6. Для нового содержимого Server сохраняет байты и RemoteFile; для duplicate возвращает прежний файл. Android принимает 2xx с id>0, сохраняет serverFileId и SYNCED ([BACKUP-UPLOAD](04-backup-and-sync.md#backup-upload), [BACKUP-DUPLICATE](04-backup-and-sync.md#backup-duplicate)).
7. Обработка продолжается для следующих файлов, затем Загрузчик публикует общий результат прогона. Большую очередь Загрузчик, как и Поставщик, проходит несколькими прогонами, ограниченными по времени.

Для обработанной строки сохраняется локальный результат по критерию [SYNCED](01-system-model.md#synced). Результаты pre-check и upload применяются только к той же версии строки (status, checksum, size, lastModified): фотография, изменённая во время серверной обработки, проходит путь заново. Нет единого атомарного подтверждения Android + Server + физические байты.

### Развилки и условия

Existing и duplicate — нормальные успешные ветки. Ошибка отдельного файла может оставить FAILED при успешном завершении прогона; временная ошибка может остановить текущую стадию и отложить продолжение.

### Ошибки и recovery

Конкретные отказы описаны в сценариях обнаружения, вычисления checksum, pre-check и upload; правила повторного прогона — [BACKUP-RETRY](04-backup-and-sync.md#backup-retry), прерывание и перезагрузка — [BACKUP-RESTART](04-backup-and-sync.md#backup-restart). При потере сессии действует [AUTH-REFRESH](02-account-and-auth.md#auth-refresh).

### Текущие ограничения

Нет ручной команды Sync now и общей server sync session. Ошибка локальной стадии не останавливает Загрузчик; ошибка pre-check откладывает upload уже ожидающих файлов до повтора Загрузчика.

### Нерешённый вопрос

Какой пользовательский смысл должно иметь подтверждение «синхронизировано», в том числе при потерянном ответе и отсутствии физических байтов, ещё не принято. Это не меняет текущий критерий.

<a id="backup-discover"></a>

## BACKUP-DISCOVER — Обнаружение и повторное сканирование локальных фото

**Status:** IMPLEMENTING

**Availability:** ANDROID_ONLY

### Назначение

Поддерживать сохранённый индекс доступных локальных изображений и очередь обработки.

### Текущее поведение

Обнаружение выполняет только прогон Поставщика, синхронизацию — фоновые задачи; Files лишь отображает состояние очереди и результаты и сам scan не запускает. Одновременно выполняется один scan: прогоны Поставщика применяют снимки по очереди. Нужен полный доступ к внешней коллекции изображений: API 29–32 — READ_EXTERNAL_STORAGE, API 33+ — READ_MEDIA_IMAGES. Частичный доступ Android 14+ (выбранные фото, READ_MEDIA_VISUAL_USER_SELECTED без READ_MEDIA_IMAGES) считается отсутствием разрешения: scan и удаление строк не выполняются. Worker сам разрешение не запрашивает. Сеть, URL и авторизация для scan не нужны.

Разрешения запрашиваются только на Settings и только по нажатию; при открытии Settings, Files и других экранов системных запросов нет. Settings показывает фактическое состояние, читая его у Android при открытии экрана, после ответа на запрос и при каждом возврате в приложение; собственной копии состояния приложение не хранит. Отозвать разрешения можно только в системных настройках Android; отзыв Android завершает процесс приложения.

1. Блок «Доступ к фотографиям». Без доступа активна кнопка «Разрешить доступ к фотографиям»: запрос включает разрешение чтения по версии Android, на Android 14+ — READ_MEDIA_IMAGES вместе с READ_MEDIA_VISUAL_USER_SELECTED. При частичном доступе показывается статус «Доступ только к выбранным фотографиям» и кнопка запроса доступа ко всем. При полном доступе кнопка зелёная и неактивна. Появление полного доступа в Settings — по ответу на запрос или при возврате из настроек Android — пересматривает фон и сразу ставит разовый Поставщик ([BACKUP-BACKGROUND](04-backup-and-sync.md#backup-background)).
2. Блок «Геоданные фотографий» — необязательное ACCESS_MEDIA_LOCATION (доступ к оригиналу с геоданными, [DeviceMedia](01-system-model.md#device-media)). Пока нет полного доступа к фото, блок неактивен с кнопкой «Сначала разрешите доступ к фотографиям», и ACCESS_MEDIA_LOCATION не проверяется — даже если он выдан. При полном доступе: без разрешения активна кнопка «Разрешить доступ к геоданным», с разрешением кнопка зелёная и неактивна. Отказ в геоданных не останавливает scan, Поставщик, Загрузчик и periodic; при полном доступе без геоданных Files поясняет, что координаты съёмки могут не сохраниться в копии.
3. Если Android больше не показывает системный диалог, кнопка запроса заменяется переходом в системные настройки приложения. Блокировкой считается отказ без возможности объяснения (rationale) только если до запроса rationale был либо запрос этого разрешения уже отклонялся с момента открытия экрана; одиночный отказ без rationale так не трактуется — так же выглядят первый запрос и закрытый без ответа диалог. Смена разрешения сбрасывает эту историю.

На эмуляторе API 36 при выданном полном доступе к фото запрос геоданных удовлетворяется без отдельного диалога, а READ_MEDIA_VISUAL_USER_SELECTED выдаётся вместе с полным доступом и остаётся после отзыва READ_MEDIA_IMAGES, поэтому такой отзыв Settings показывает как частичный доступ.

1. Android одним запросом читает полный снимок внешней коллекции Images с относительными путями DCIM/% и — временно, для испытаний A4.3 на эмуляторе, — Pictures/%, включая подпапки. Каждое изображение входит в снимок один раз.
2. Для каждого положительного media ID сохраняет данные [DeviceMedia](01-system-model.md#device-media) в LocalMedia. Новая строка получает status=PENDING, checksum=null, serverFileId=null, failureReason=null, retryCount=0 и lastFailureAt=null.
3. Для уже известного ID сравнивает размер и lastModified. Изменение запускает [BACKUP-CHANGE](04-backup-and-sync.md#backup-change); иначе обновляются локальные сведения без сброса обработки. Локальные сведения и сброс обработки записываются одним изменением строки, поэтому параллельное вычисление checksum не видит промежуточного состояния. Снимок записывается в индекс порциями по 500 изображений, каждая — одной транзакцией; общей транзакции на весь архив нет.
4. Строки, отсутствующие в полном снимке, удаляются из локального индекса по [BACKUP-DELETE](04-backup-and-sync.md#backup-delete). Снимок полный, если запрос выполнен, прочитаны все его строки и основное хранилище подключено. Если полный снимок пуст при непустом индексе или в нём нет большой части индекса (не меньше 10 строк и не меньше половины), через 5 секунд выполняется повторный снимок: удаляются только строки, отсутствующие в обоих. Неудачный или неполный повтор ничего не удаляет до следующего scan. Удаление выполняется только после записи всех порций снимка: scan, прерванный между порциями, оставляет уже записанные порции согласованными и ничего не удаляет, а следующий полный scan дописывает остальное.

Индекс соответствует успешно прочитанной видимой области в пределах завершённых записей. Повторное сканирование при прежних ID, размере и lastModified не вызывает повторного вычисления checksum и повторного backup.

### Развилки и условия

Пустое имя заменяется на image_ID, пустой MIME — image/*, неизвестный размер — 0. Время выбирается из DATE_TAKEN, затем DATE_MODIFIED, затем DATE_ADDED, затем текущего времени. При отсутствии пригодных дат повторный scan может снова обнаруживать изменение.

### Ошибки и recovery

Нет полного доступа → стадия не выполняется, строки не меняются. Отсутствие результата чтения (null cursor) либо ошибка запроса/перебора строк возвращает Error. Неподключённое основное хранилище делает снимок неполным. Это не пустой успешный снимок, поэтому удаление строк на этом основании не начинается. Ошибка чтения отдельной строки исключает её из снимка и делает снимок неполным: остальные строки обрабатываются, отсутствующие не удаляются. Ошибка применения снимка может оставить частичные изменения.

### Текущие ограничения

Видео и изображения вне DCIM (и временно Pictures) не обнаруживаются; Pictures включает и Pictures/Screenshots. После исключения Pictures его строки удалит следующий полный scan как отсутствующие — только из Room. Нет выбора альбомов, томов или источника через SAF; каждый scan читает всю область. Явных фильтров для pending/trashed media нет; окончательную видимость определяет ОС. Полнота определяется по ошибкам запроса и строк и по состоянию основного хранилища. Недоступный съёмный том и другие пропуски, о которых ОС не сообщает ошибкой, не распознаются: массовое исчезновение только перепроверяется через паузу, и строки, отсутствующие в обоих снимках, удаляются; меньшие пропуски удаляются сразу. Удалённые так строки при возвращении файлов создаются заново и проходят hash и pre-check; повторный upload при existing не выполняется. Весь снимок читается целиком. В Files нет отдельной ручной Scan кнопки и кнопок запроса разрешений; при возврате на Files пересматриваются только пояснения о разрешениях.

### Нерешённый вопрос

Продуктовый охват типов/папок/размеров не принят. Отдельной selected-photo модели в Android нет: частичный доступ не обрабатывается. Поведение системных диалогов разрешений проверено только на эмуляторе API 36; на устройствах и других версиях Android не проверено.

<a id="backup-checksum"></a>

## BACKUP-CHECKSUM — Вычисление checksum

**Status:** IMPLEMENTING

**Availability:** ANDROID_ONLY

### Назначение

Получить SHA-256 конкретного чтения изображения устройства для проверки existing.

### Текущее поведение

После scan Поставщика в очереди есть PENDING; могут сохраниться и прерванные HASHING. Требуется полный доступ к изображениям; сеть и Server не нужны.

1. В начале стадии оставшиеся HASHING возвращаются в PENDING.
2. Поставщик последовательно выбирает партии по 100 строк PENDING в порядке FIFO по mediaStoreId (без приоритета по дате съёмки или новизне), отмечает строку HASHING, только если она всё ещё PENDING с прочитанными checksum, size и lastModified, и открывает её content URI по правилу [DeviceMedia](01-system-model.md#device-media): оригинал при ACCESS_MEDIA_LOCATION, иначе обычный поток.
3. Вычисляет SHA-256 потока. При успехе, если строка всё ещё HASHING с прежними size и lastModified, сохраняет LocalMedia.checksum и status=CHECKSUM_READY, очищает failureReason и lastFailureAt, обнуляет retryCount.
4. После каждой партии, давшей хотя бы один CHECKSUM_READY, ставит разовый Загрузчик по правилу [BACKUP-BACKGROUND](04-backup-and-sync.md#backup-background); Загрузчик может отправлять готовые строки, пока Поставщик хеширует следующие.
5. Перед каждым файлом проверяет бюджет прогона — 420 секунд от начала работы Поставщика, scan тоже его расходует. Исчерпанный бюджет не прерывает начатое чтение файла, но следующий файл не начинается.
6. Продолжает до исчерпания очереди, бюджета, ошибки стадии или партии, в которой не удалось взять ни одной строки. Если бюджет исчерпан, в прогоне был взят хотя бы один файл и PENDING остались, Поставщик регистрирует продолжение ([BACKUP-BACKGROUND](04-backup-and-sync.md#backup-background)) и завершается успешно; иначе остаток обрабатывает следующий прогон по событию или periodic.

CHECKSUM_READY означает завершение локальной обработки и границу передачи Загрузчику. Checksum относится к прочитанному содержимому, а не к имени, ID или неизменяемой версии файла.

### Ошибки и recovery

Отказ Android в оригинале ошибкой не считается: читается обычный поток. Отсутствие потока (null) или файла (FileNotFound) → FAILED FILE_NOT_FOUND; отказ доступа при чтении → FAILED PERMISSION; IOException → FAILED CHECKSUM_IO; прочие ошибки файла → FAILED UNKNOWN. Причина, счётчик и время сохраняются при том же условии, что и успех; обработка следующих файлов продолжается. Если scan сбросил строку во время чтения, результат отбрасывается, а строка снова хэшируется как PENDING. Автоматический возврат возможен только для ограниченного CHECKSUM_IO ([BACKUP-RETRY](04-backup-and-sync.md#backup-retry)). Отсутствие разрешения на входе останавливает стадию без вычисления checksum.

### Текущие ограничения

Приватная неизменяемая копия байтов не создаётся. Во время upload URI читается заново; гонка чтений и проверка принятых байтов описаны в [BACKUP-UPLOAD](04-backup-and-sync.md#backup-upload).

<a id="backup-target"></a>

## BACKUP-TARGET — Выбор CAMERA и первый backup

**Status:** IMPLEMENTING

**Availability:** END_TO_END

### Назначение

Определить папку проверки и назначения последующей отправки.

### Текущее поведение

Загрузчик доходит до pre-check, а затем отдельно до подготовки upload. Его начальные проверки пройдены; защищённые запросы папок требуют авторизации.

1. Android запрашивает ROOT. Server возвращает существующую либо лениво создаёт ROOT; CAMERA и FILES этим запросом не создаются.
2. Android получает прямых потомков ROOT и выбирает первую папку с Folder.folderType=CAMERA; имя папки в выборе не участвует.
3. Если CAMERA есть, её ID используется для [BACKUP-EXISTING](04-backup-and-sync.md#backup-existing). Если её нет, все CHECKSUM_READY с checksum, отличной от null, становятся PENDING_UPLOAD без existing-запроса.
4. Перед стадией upload Android повторяет ROOT/children lookup; найденный ID используется для всей отправки данного прогона. При отсутствии CAMERA или ошибке этого второго lookup folderId не передаётся.
5. Server без явной папки определяет тип принятых байтов: IMAGE/VIDEO → CAMERA, остальное → FILES; нужную системную папку создаёт при необходимости. Явно выбранной папкой может быть любая папка пользователя.

Проверка existing относится к найденной CAMERA; фактическая папка upload задаётся отдельным решением перед отправкой.

### Развилки и условия

- Ошибка первого lookup останавливает Загрузчик с retry; upload не начинается. Отсутствие тела ROOT считается ошибкой, а отсутствие тела children Android считает пустым списком.
- Ошибка второго lookup не останавливает upload и не показывается как отдельная ошибка: используется default routing.
- Первый upload обычного изображения при отсутствующей CAMERA создаёт её штатно; Android create-folder не вызывает.

### Ошибки и recovery

Ошибка поиска папки или проверки existing вызывает ERROR и повтор Загрузчика; локальная обработка от неё не зависит. При папке по умолчанию возможен конфликт имени вне CAMERA, который обрабатывается как upload 409 ([BACKUP-UPLOAD](04-backup-and-sync.md#backup-upload)).

### Текущие ограничения

Локальные подпапки DCIM не превращаются в дерево папок Server; ID не кэшируется. После успешного CAMERA pre-check, ошибки второго lookup и отличия server detection от IMAGE/VIDEO файл может попасть в FILES, хотя Android пропустил его по image/ MIME. Android папку из ответа не проверяет и может поставить SYNCED. Стабильный первый upload обычного IMAGE сам по себе этого расхождения не создаёт.

### Нерешённый вопрос

Целевые правила первого выбора CAMERA, запасного назначения и конфликтов имён, Unicode и регистра за пределами установленного As-Is не определены.

<a id="backup-existing"></a>

## BACKUP-EXISTING — Pre-check: existing или missing

**Status:** IMPLEMENTING

**Availability:** END_TO_END

### Назначение

Не отправлять содержимое, уже представленное логической записью в целевой CAMERA.

### Текущее поведение

Checksum готова, CAMERA найдена в [BACKUP-TARGET](04-backup-and-sync.md#backup-target).

1. Android берёт максимум 500 строк CHECKSUM_READY с checksum в порядке FIFO по mediaStoreId, приводит суммы к нижнему регистру и объединяет совпадающие. Перед каждым запросом проверяется бюджет прогона Загрузчика ([BACKUP-BACKGROUND](04-backup-and-sync.md#backup-background)): исчерпан — новый запрос не начинается.
2. Отправляет folderId и список checksum. Server проверяет свою папку, формат SHA-256 и максимум 500 исходных значений, затем возвращает existing/missing для текущего user и folder.
3. Existing → Android меняет только status на SYNCED, если строка всё ещё CHECKSUM_READY с прочитанными checksum, size и lastModified; upload не выполняется.
4. Missing → PENDING_UPLOAD при том же условии; затем применяется [BACKUP-UPLOAD](04-backup-and-sync.md#backup-upload). Партии продолжаются до завершения, исчерпания бюджета или партии без применённых переходов. Если бюджет исчерпан на pre-check, upload в этом прогоне не начинается: стадии не чередуются, оставшиеся CHECKSUM_READY проверит следующий прогон.

Existing подтверждает логическую запись Server на момент запроса. Ответ не содержит FileId. Изменение только status оставляет LocalMedia.serverFileId прежним; в обычном новом пути он остаётся null.

### Развилки и условия

Локальные строки с одинаковым hash в партии получают один результат. Если некорректный ответ содержит hash в обеих группах, Android предпочитает existing; если ни в одной — оставляет CHECKSUM_READY. При отсутствии прогресса завершает стадию без отдельного запроса повтора. Строку, которую Поставщик успел сбросить или обновить, ответ не меняет: она пройдёт hash и pre-check заново. Server для валидного запроса формирует полное разделение.

### Ошибки и recovery

При ошибке доступа к папке, HTTP, сети, разбора ответа или отсутствии тела pre-check останавливается и запрашивает повтор Загрузчика. Результаты уже обработанных партий сохраняются.

### Текущие ограничения

Existing не проверяет физические байты и не резервирует файл до upload. Логическая запись может существовать при потерянных байтах; SYNCED этого не обнаруживает и их не восстанавливает. Обычные SYNCED повторно не сверяются с Server.

<a id="backup-upload"></a>

## BACKUP-UPLOAD — Отправка ожидающего изображения

**Status:** IMPLEMENTING

**Availability:** END_TO_END

### Назначение

Отправить изображение, отсутствующее по результату pre-check, и сохранить ответ Server локально.

### Текущее поведение

После pre-check остаются PENDING_UPLOAD. Загрузчик прошёл проверки пары, URL, ping и полного доступа к изображениям. Папка назначения определяется повторным lookup из [BACKUP-TARGET](04-backup-and-sync.md#backup-target).

1. При входе в upload оставшиеся UPLOADING возвращаются в PENDING_UPLOAD. Upload начинается, только если после полного pre-check бюджет прогона не исчерпан. Android выбирает строки PENDING_UPLOAD в порядке FIFO по mediaStoreId, без приоритета по дате съёмки или новизне, последовательно партиями по 20 и отправляет по одному файлу. Перед каждым файлом проверяется бюджет: исчерпан — следующий файл не начинается, а уже начатая передача не прерывается и ограничена прежними тайм-аутами HTTP; отправленные файлы остаются SYNCED.
2. Для файла проверяет MIME с префиксом image/ и возможность открыть/закрыть URI. Затем отмечает UPLOADING, только если строка всё ещё PENDING_UPLOAD с прочитанными checksum, size и lastModified (иначе пропускает её в этом прогоне), и заново читает URI для multipart upload. Проверка и отправка выбирают поток по тому же правилу, что и checksum ([DeviceMedia](01-system-model.md#device-media)); отказ Android в оригинале не переводит файл в FAILED.
3. Server принимает поток, вычисляет фактические SHA-256 и размер, определяет MIME и тип по байтам. Принятые байты не перекодируются и не изменяются: определение типа и извлечение метаданных только читают их. Пустой файл отвергается; допустимо до 104857600 байтов включительно (100 MiB).
4. Server пытается извлечь метаданные изображения и определяет папку; отсутствие метаданных не отменяет upload. Если user/folder/checksum уже существует, выполняет [BACKUP-DUPLICATE](04-backup-and-sync.md#backup-duplicate).
5. Для нового checksum вне CAMERA проверяет занятость имени без учёта регистра. В CAMERA одинаковые имена разрешены. При отсутствии конфликта публикует итоговые байты без перезаписи существующего файла ([SYSTEM-STORAGE](07-system-rules-and-recovery.md#system-storage)) в каталоге [StoredObject.filePath](01-system-model.md#stored-object): для CAMERA — `{userId}/camera/{YYYY}` по году capturedAt ([BACKUP-METADATA](04-backup-and-sync.md#backup-metadata)), для остальных папок — временный `{userId}/files`. Затем в одной транзакции сохраняет RemoteFile, StoredObject и доступную FileMetadata.
6. После commit возвращает 200 с [FileItemDto](01-system-model.md#api-projections), включая ID файла, папку, нормализованное имя, checksum и доступные метаданные.
7. Android принимает любой 2xx с id>0 и, если строка всё ещё UPLOADING той же версии, сохраняет этот serverFileId, ставит SYNCED и обнуляет retryCount, очищает failureReason и lastFailureAt. Остальные поля ответа не сверяет и не переносит в локальные сведения.

Обычный новый upload создаёт удалённые записи и байты; Android сохраняет положительный FileId. Создание файла и ответ duplicate одинаково считаются успехом.

### Развилки и условия

- Локальный MIME не image/ → FAILED NOT_IMAGE.
- При проверке открытия отсутствие потока/файла → FAILED FILE_NOT_FOUND, отказ доступа → FAILED PERMISSION.
- Upload 400/409/413 → FAILED HTTP_400/409/413; следующий файл обрабатывается. 409 относится к занятому имени нового содержимого вне CAMERA, а обычный duplicate возвращает 200.
- Прочие HTTP, в том числе окончательный 401/403/404/429/5xx, IOException при передаче (включая временный отказ refresh) или 2xx без id>0 → PENDING_UPLOAD, остановка upload и запрос retry. Окончательный 401 после отказа refresh очищает пару, и следующий прогон останавливает фон ([BACKUP-BACKGROUND](04-backup-and-sync.md#backup-background)).
- Иное исключение после начала отправки может оставить UPLOADING до recovery.
- Все переходы стадии (FAILED, SYNCED, возврат в PENDING_UPLOAD) применяются только к той же версии строки. Если Поставщик сбросил строку во время отправки, ответ её не меняет: новая версия проходит hash, pre-check и upload заново, а принятая копия прежней версии остаётся на Server.
- Нет полного доступа к изображениям → Загрузчик завершается до pre-check без изменения очереди и без retry; строки не переходят в FAILED PERMISSION.

### Ошибки и recovery

При потере ответа Server уже мог завершить сохранение; это не доказывает откат. Повтор передаёт весь поток и может получить duplicate. Занятый физический путь или другая ошибка физической записи даёт 500 INTERNAL_ERROR без изменения существующих файлов; для Android это временная ошибка, повтор получает новое физическое имя. Прерывание и локальное подтверждение — [BACKUP-RESTART](04-backup-and-sync.md#backup-restart); расхождение БД и байтов — [SYSTEM-STORAGE](07-system-rules-and-recovery.md#system-storage). 400/409/413 автоматически не повторяются; ручного повтора нет.

### Текущие ограничения

Вычисление checksum и upload независимо читают URI, содержимое которого может измениться. Условный переход защищает только от изменения, уже обнаруженного scan по size/lastModified. При изменении байтов между чтениями локальная checksum и pre-check могут относиться к другому содержимому, чем принятый объект, несмотря на SYNCED с ID: checksum, size и папка ответа не проверяются. Тот же случай возникает, если ACCESS_MEDIA_LOCATION выдано или отозвано между checksum и upload: отправляется оригинал или доступная версия, отличная от прочитанной при checksum. Нет продолжения частичной загрузки, отправки по частям, побайтового прогресса, неизменяемого снимка или сквозного восстановления целостности. Локальной проверки максимального размера нет; серверный предел multipart 110 MB дополняет ограничение обработки потока 100 MiB. Server не ограничивает MIME списком разрешённых типов и не проверяет файлы на вирусы. HTTP-логирование Android тела не читает: в debug-сборке пишутся только метод, URL, код и длительность, в release HTTP-логов нет. Поток файла читается один раз на каждую попытку отправки, в том числе при повторе после refresh. Общей серверной квоты нет.

### Нерешённый вопрос

Соответствие заявленного SIZE длине потока и момент прекращения действий upload после отмены зависят от условий выполнения и не проверены.

<a id="backup-duplicate"></a>

## BACKUP-DUPLICATE — Duplicate и потерянное подтверждение

**Status:** IMPLEMENTING

**Availability:** END_TO_END

### Назначение

Завершить повторную отправку того же содержимого в ту же папку без создания нового RemoteFile.

### Текущее поведение

Server получает upload с уже существующим сочетанием user + folder + SHA-256; например, Android повторяет отправку после потери ответа.

1. Server всё равно читает входящие байты и вычисляет checksum.
2. Находит прежнюю логическую запись в выбранной папке, пытается убрать временные байты и возвращает прежний DTO с 200.
3. Android принимает положительный ID, сохраняет его и SYNCED как при обычном upload.

В обычной duplicate-ветке возвращается прежний FileItem ID. Новое имя, метаданные, даты и байты не заменяют существующие.

### Развилки и условия

Тот же checksum в другой папке или у другого пользователя не является этим duplicate: обычный upload создаёт отдельные RemoteFile, StoredObject и байты. При checksum-конфликте конкурентного upload транзакция проигравшего запроса откатывается, Server удаляет только собственные опубликованные байты, затем пытается перечитать запись и вернуть её; если не находит — пробрасывает ошибку. Байты успешного запроса не затрагиваются.

### Ошибки и recovery

Duplicate не проверяет читаемость и не восстанавливает потерянные физические байты. Условие возврата прежнего ID исчезает после перемещения/удаления на Server или смены пользователя, папки или содержимого; глобальная гарантия однократного сохранения отсутствует.

### Текущие ограничения

Устранение дубликатов ограничено сочетанием user/folder/checksum. Между папками физические байты не объединяются. Побайтового сравнения при одинаковом SHA-256 нет. При потере последующей локальной записи возможна ещё одна полная попытка.

<a id="backup-metadata"></a>

## BACKUP-METADATA — Имена, время и метаданные фотографии

**Status:** IMPLEMENTING

**Availability:** END_TO_END

### Назначение

Объяснить, какие сведения сохраняются на устройстве и на Server вместе с изображением.

### Текущее поведение

Обнаружение изображения формирует локальные сведения, а успешный новый upload — серверные.

1. Android берёт имя, относительный путь, MIME, размер и время из локального снимка изображения; свои createdAt/lastModified не передаёт как capturedAt.
2. Server определяет MIME и размер по принятому потоку, нормализует имя и извлекает доступные EXIF/GPS. Байты сохраняются как приняты, без перекодирования и правки метаданных, и download возвращает их без изменений. FileMetadata.width и FileMetadata.height поддержаны для JPEG/PNG.
3. Server задаёт RemoteFile.capturedAt — локальные календарные дату и время съёмки из EXIF DateTimeOriginal, а при отсутствии пригодного значения — из DateTimeDigitized, как они записаны в файле, с долями секунды до микросекунд. Часовой пояс Server и EXIF-смещение (OffsetTime) время не сдвигают, поэтому год на границе 31 декабря сохраняется. Непригодны отсутствующее, нераспознанное значение и несуществующая дата, например заглушка 0000:00:00 00:00:00; ограничений по году нет. Без пригодной EXIF-даты capturedAt равен uploadedAt: дату создания исходного файла upload не передаёт. Ответные даты не содержат offset.
4. Android оставляет собственные сведения; ответ Server их не заменяет.

Локальные и удалённые имя, время и метаданные могут различаться при успешном backup.

### Ошибки и recovery

Ошибка извлечения данных изображения не отменяет upload: FileMetadata может отсутствовать. Возможность отсутствия GPS не объясняет, почему его нет у конкретного файла.

### Текущие ограничения

Android сам не извлекает и не редактирует EXIF/GPS и не подтверждает побайтовую идентичность оригиналу. При выданном ACCESS_MEDIA_LOCATION он отправляет оригинал вместе с EXIF/GPS; без него backup продолжается, но Android 10+ может отдать копию с затёртыми геоданными, и Server сохраняет её как есть. Фактические байты зависят от ОС, provider и выданных разрешений.

Выдача ACCESS_MEDIA_LOCATION не восстанавливает геоданные в уже загруженных копиях: строки SYNCED и подготовленные строки с прежними size и lastModified повторно не хэшируются и не отправляются, массовой пересинхронизации нет. Повторная проверка архива — отдельная будущая задача. Server может принимать VIDEO, но не извлекает метаданные или длительность видео; Android видео не обнаруживает.

capturedAt — местное время камеры без пояса: снимки, сделанные в разных часовых поясах, упорядочиваются по местному времени, а не по абсолютному моменту. Значения capturedAt, сохранённые до этого правила, не пересчитываются и могут быть сдвинуты на разницу между поясом Server и UTC, а при наличии EXIF-смещения — между поясом Server и этим смещением.

### Нерешённый вопрос

Общий пользовательский смысл имён, времени и геопозиции и ожидаемая полнота оригинальной копии не определены; сохранение GPS снимков с геометками на эмуляторе и устройствах не проверено. Как Server интерпретирует затёртый Android блок GPS (отсутствие координат или нулевые значения), не проверено.

<a id="backup-background"></a>

## BACKUP-BACKGROUND — Автоматический и периодический backup

**Status:** IMPLEMENTING

**Availability:** END_TO_END

### Назначение

Продвигать очередь без ручных команд пользователя.

### Текущее поведение

Обработку запускает изменение Images, старт процесса приложения, периодическая задача, сигнал Поставщика, login или повтор ранее неуспешного прогона. Фон разделён на две независимые части с общей очередью LocalMedia: Поставщик ведёт локальную обработку ([BACKUP-DISCOVER](04-backup-and-sync.md#backup-discover), [BACKUP-CHECKSUM](04-backup-and-sync.md#backup-checksum)), Загрузчик — серверную ([BACKUP-TARGET](04-backup-and-sync.md#backup-target), [BACKUP-EXISTING](04-backup-and-sync.md#backup-existing), [BACKUP-UPLOAD](04-backup-and-sync.md#backup-upload)). Поставщик не вызывает Загрузчик напрямую: он оставляет подготовленные строки в очереди и запрашивает разовую работу.

1. Android пересматривает настройку фона при создании Network UI, успешном login, полученном результате logout, входе на Files или появлении полного доступа к фото на Settings, а также в Загрузчике без пары. При полном доступе к изображениям включает наблюдатель MediaStore, observer и periodic Поставщика независимо от входа; иначе отменяет наблюдатель и periodic Поставщика и останавливает observer. Повторный пересмотр не создаёт второго наблюдателя. Если дополнительно есть пара и URL, включает periodic Загрузчика; иначе отменяет его.
2. На изменения внешней Images-коллекции реагируют два механизма; событие само не фильтруется по области scan, её определяет scan. Observer в живом процессе после 3 секунд без нового события ставит разовый Поставщик. Независимо от живого процесса действует наблюдатель MediaStore — одноразовое системное ожидание изменения внешней коллекции Images и вложенных URI, которое при необходимости само запускает процесс; сеть, URL и пара ему не нужны. Android запускает его после 3 секунд без новых изменений, но не позже 30 секунд от первого. Без полного доступа сработавший наблюдатель завершается, не ставя следующего ожидания. Иначе он сначала заменяет себя новым ожиданием — под своим именем всегда одна задача, без цепочек, — затем ставит разовый Поставщик. Если наблюдателя нет, его восстанавливает любой прогон Поставщика с полным доступом, в том числе periodic.
3. При каждом старте процесса приложения, в том числе запущенного наблюдателем MediaStore в фоне, Android при полном доступе к изображениям ставит разовый Поставщик; без полного доступа ничего не ставится. Ожидающий или выполняющийся Поставщик при этом не дублируется. Этот прогон обрабатывает изменение, событие о котором могло быть потеряно при восстановлении фоновых задач на холодном старте (см. «Текущие ограничения»). Открытие UI не требуется.
4. Разовый Поставщик условий не имеет; периодический настроен на 30 минут и требует достаточного заряда (batteryNotLow). Сеть Поставщику не нужна. Фактическое время periodic выбирает Android; он выполняется независимо от событий и сигналов и остаётся резервным механизмом при потерянном событии. После появления полного доступа на Settings Android сразу ставит разовый Поставщик, не дожидаясь periodic.
5. Поставщик проверяет полный доступ к изображениям, восстанавливает допустимые ошибки ([BACKUP-RETRY](04-backup-and-sync.md#backup-retry)), выполняет scan и hash. После каждой готовой партии hash и в конце прогона, если в очереди есть CHECKSUM_READY с checksum, PENDING_UPLOAD или UPLOADING и сохранена пара, он ставит разовый Загрузчик (KEEP: ожидающий или выполняющийся Загрузчик не дублируется). Без пары Загрузчик не ставится, подготовленные строки остаются в очереди.
6. Разовый Загрузчик ждёт доступной сети (CONNECTED); периодический настроен на 30 минут, дополнительно требует batteryNotLow и, как periodic Поставщика, запускается в выбранное Android время независимо от событий. Сети с тарификацией и мобильный интернет разрешены; подключение к зарядке или только Wi-Fi не требуются. После успешного login Android сразу ставит разовый Загрузчик для накопленной очереди.
7. Загрузчик сначала проверяет наличие сохранённой пары (см. «Ошибки и recovery»). Перед первым сетевым обращением он перечитывает сохранённые IP/port и формирует URL по единому правилу [SETTINGS-NETWORK](03-profile-and-settings.md#settings-network); при отсутствии или некорректности настроек адрес очищается, прежний URL из памяти не используется. Затем проверяет доступность Server через public ping и полный доступ к изображениям и выполняет pre-check и upload по [BACKUP-NEW](04-backup-and-sync.md#backup-new). MediaStore он не сканирует и checksum не вычисляет. Бюджет прогона — 420 секунд от начала работы Загрузчика; его расходуют ping, pre-check и upload вместе.

Очередь может продвигаться в фоне при выполнении условий. Интервал periodic и debounce — настройки, не гарантированный срок сохранения фото. На эмуляторе новое фото, в том числе после завершения процесса командой am kill или смахиванием из недавних, доходило до Server примерно за 5–10 секунд; это результат испытания, а не гарантия.

### Развилки и условия

Пока разовая работа части не завершена, новая работа той же части не ставится (KEEP), в том числе в период ожидания повторной попытки.

Продолжение Поставщика и Загрузчика. Прогон части, завершившийся штатно с оставшейся очередью и прогрессом в этом прогоне, регистрирует следующий запуск до своего успешного завершения; текущий прогон не отменяется. Для Поставщика очередь — PENDING, прогресс — хотя бы один взятый в хеширование файл. Для Загрузчика очередь — CHECKSUM_READY с checksum, PENDING_UPLOAD и UPLOADING, прогресс — хотя бы одна строка, переведённая pre-check, или один начатый в upload файл; очередь может остаться и потому, что Поставщик подготовил новые строки во время прогона. Разовая задача добавляет продолжение в свою же цепочку (APPEND_OR_REPLACE): оно начнётся только после успешного завершения текущей, и под именем разовой задачи ожидает не больше одного продолжения; продолжению Загрузчика, как и любому разовому Загрузчику, нужна сеть. Внешние сигналы (наблюдатель MediaStore, observer, старт процесса, Settings, сигнал Поставщика, login) в это время ничего не добавляют (KEEP). Periodic части продолжение не добавляет к своей задаче, а ставит разовую задачу той же части с KEEP: идущая разовая цепочка продолжит себя сама. Временная ошибка Загрузчика (недоступный Server, ошибка pre-check, временная ошибка upload) сохраняет прежний повтор с backoff и продолжение не регистрирует. Завершённые записи цепочки удаляет следующая постановка после её окончания. Без прогресса продолжение не регистрируется — бесконечной цепочки нет, остаток ждёт события или periodic. Если прогон остановлен до регистрации, его повторяет WorkManager как прерванную работу; повтор после регистрации добавляет не больше одного лишнего прогона. Ошибка регистрации считается ошибкой прогона (повтор с backoff). Постановка продолжения не гарантирует немедленного запуска: время выбирает Android.

Изображение, появившееся после scan текущего Поставщика, ждёт следующего события, продолжения или periodic Поставщика: каждый прогон продолжения заново выполняет scan и подхватывает изображения, события о которых были отброшены KEEP. Строки, подготовленные во время выполняющегося Загрузчика, ждут его продолжения, повтора или periodic Загрузчика. Признака обязательного последующего прогона, кроме продолжения части, нет. Periodic Загрузчика не зависит от backoff разовой задачи. Повторный пересмотр не создаёт новых periodic-заданий; отменённое задание ставится заново при следующем пересмотре с выполненными условиями.

### Ошибки и recovery

Поставщик: нет полного доступа к изображениям → задача завершается успешно без изменения очереди и без нового общего результата; это не успешный backup. Ошибка scan или hash → ERROR и retry Поставщика. Отсутствие сети, URL, Server и пары на Поставщика не влияет.

Загрузчик: недоступный URL/ping → SERVER_UNAVAILABLE и retry до pre-check/upload; нет полного доступа к изображениям → успешное завершение без изменения очереди; ошибка pre-check → ERROR и retry; временная ошибка upload → RETRY_SCHEDULED и retry. Подготовленная очередь во всех этих случаях сохраняется. Временный отказ refresh, в том числе неподтверждённая запись пары с новым refresh, приходит в стадии как IOException и ведёт к обычному retry ([AUTH-REFRESH](02-account-and-auth.md#auth-refresh)).

Прогон Загрузчика без сохранённой пары до любых сетевых запросов записывает ERROR, последним действием пересматривает фон (без пары periodic Загрузчика отменяется; Поставщик и observer продолжают работу при полном доступе к изображениям) и завершается успешно без retry; причина `no_session` доступна в выходных данных задачи. Если это сам periodic Загрузчика, отмена расписания останавливает уже завершающийся прогон, и он не повторяется. Пара, очищенная окончательным отказом refresh во время прогона, в том числе из-за истёкшего refresh или блокировки аккаунта ([AUTH-BLOCK](02-account-and-auth.md#auth-block)), приводит к такой остановке на следующем прогоне.

### Текущие ограничения

Observer живёт только в памяти; без живого процесса изменения обнаруживает наблюдатель MediaStore. Изменение, пришедшее, пока Поставщик уже выполняется, не вызывает нового прогона (KEEP): если его scan уже прошёл, изображение ждёт следующего события или periodic. Изменение между срабатыванием наблюдателя и постановкой следующего ожидания (доли секунды) обнаруживает только последующий scan. Немедленный запуск не гарантирован: планировщик Android, Doze и ограничения фона откладывают срабатывание. Изменение MediaStore может само запустить процесс приложения. При таком холодном старте после завершения процесса (проверены am kill и смахивание из недавних) исходное событие может быть потеряно при восстановлении фоновых задач, а ожидание наблюдателя ставится заново. Такое изменение подхватывает разовый Поставщик при старте процесса, а если этого прогона не было — periodic. Force Stop из настроек Android не равнозначен am kill: после него Android не запускает приложение — ни наблюдатель, ни periodic — до ручного запуска. Старт процесса сам Загрузчик не ставит: доставка на Server по-прежнему требует пары, сети, URL, ping и полного доступа. Пересмотр не вызывается при каждом изменении токенов, URL или разрешения; ручной Network Test и onResume сами его не вызывают. Files запрашивает разрешение только при входе с tokens+URL; без входа Поставщик работает, если доступ уже выдан. Поставщик и Загрузчик выполняются параллельно, разовая и periodic задачи одной части могут пересекаться. Scan выполняется по одному, hash, pre-check и upload защищены каждый своей блокировкой; поздние результаты hash, pre-check и upload применяются только к той же версии строки, а restore и записи scan безусловны; запись scan для одной строки атомарна. Ответ upload после удаления строки не обновит ничего. Отмена задачи не гарантирует остановки уже идущего HTTP-запроса или чтения; остановленная системой стадия продолжается следующими прогонами. Backup не выполняется как foreground/expedited работа; уведомления о ходе нет. Отдельного продления refresh по таймеру нет: фон обновляет токены только обычным refresh после 401, и замена refresh происходит, когда до его истечения остаётся не больше 30 дней. Пока фон или UI хоть раз делают refresh в этом окне, сессия не истекает; если прогоны прекратились, она переживает от 30 до 180 дней после последнего refresh при сроках по умолчанию ([AUTH-REFRESH](02-account-and-auth.md#auth-refresh)).

### Нерешённый вопрос

На эмуляторе проверены доставка после am kill и смахивания из недавних, быстрые Поставщик и Загрузчик, доставка periodic при потерянном событии и сохранение наблюдателя после восстановления фоновых задач. Реальные задержки после reboot, Force Stop и в Doze, поведение на физических устройствах и OEM-прошивках, последовательности событий и поведение при переставших выполняться условиях задачи не измерены. Ожидания автономности, расхода трафика/батареи и уведомлений не приняты.

<a id="backup-retry"></a>

## BACKUP-RETRY — Повторы и FAILED без автоматического восстановления

**Status:** IMPLEMENTING

**Availability:** ANDROID_ONLY

### Назначение

Продолжить локальную обработку после тех ошибок, для которых существует автоматическое восстановление.

### Текущее поведение

Следующий прогон Поставщика при полном доступе к изображениям, в том числе повтор задачи, начинает восстановление; сеть и Server для этого не нужны. Истечение пяти минут само по себе задачу не запускает.

1. Один раз перед scan выбираются максимум 500 LocalMedia со status=FAILED, failureReason=CHECKSUM_IO, retryCount<3 и lastFailureAt не менее 5 минут назад.
2. Они возвращаются в PENDING; failureReason и lastFailureAt очищаются, retryCount, checksum и serverFileId сохраняются.
3. Следуют scan/hash/pre-check/upload. Успешный hash/upload и обнаруженное изменение содержимого обнуляют retryCount.
4. Ошибка локальной стадии запрашивает повтор Поставщика, ошибка pre-check или временная ошибка upload — повтор Загрузчика; завершённые локальные записи сохраняются.

Восстанавливаются только допустимые строки. Успех всего прогона может сосуществовать с FAILED без автоматического восстановления и CHECKSUM_READY без прогресса.

### Развилки и условия

- Три накопленные ошибки вычисления checksum прекращают автоматическое восстановление CHECKSUM_IO. Выдержка между ошибкой и восстановлением зависит от часов устройства и следующего worker, а не отдельного таймера.
- FILE_NOT_FOUND, PERMISSION, NOT_IMAGE, HTTP_400/409/413, UNKNOWN и исторические FAILED без пригодных failureReason/lastFailureAt автоматически не восстанавливаются. Выдача разрешения сама по себе такие строки не сбрасывает.
- Изменение размера/mtime либо исчезновение и повторное discovery могут начать обработку заново. В UI нет ручного повтора, сброса или отмены.

### Ошибки и recovery

Upload при временной ошибке останавливается на первом неудавшемся файле, выбранном в порядке от новых к старым. Повторяемая ошибка нового файла может задерживать старые pending. Число попыток всего прогона приложением не ограничено и не учитывается в retryCount файла; Retry-After и server error codes не управляют retry.

### Текущие ограничения

Задержку повтора определяют стандартные настройки WorkManager: экспоненциальный рост от 30 секунд до 5 часов. Реальные запуски зависят от ОС и условий задачи; заданный срок запуска не гарантируется. При пересечении восстановлений лимит не гарантирует однократный выбор каждой строки. В UI нет ручного восстановления, счётчиков retry и полного описания фоновой ошибки; монитор описан в [FILES-LOCAL](05-file-library.md#files-local).

### Нерешённый вопрос

Ожидаемые ручное восстановление FAILED, задержки и пользовательские сообщения не определены.

<a id="backup-restart"></a>

## BACKUP-RESTART — Остановка процесса, перезагрузка и прерванные стадии

**Status:** IMPLEMENTING

**Availability:** ANDROID_ONLY

### Назначение

Описать фактическое продолжение сохранённой очереди после остановки процесса.

### Текущее поведение

Процесс останавливается, устройство перезагружается либо прерывается вычисление checksum/upload.

1. Завершённые записи очереди, настроек (в том числе IP/port) и токенов, а также расписание задач могут сохраниться. URL в памяти, observer и последняя общая карточка sync находятся в памяти процесса и теряются. Задание наблюдателя MediaStore хранится в расписании задач; системное ожидание изменения перезагрузку не переживает и планируется заново при восстановлении фоновых задач; при холодном старте после завершения процесса оно также может быть поставлено заново.
2. Загрузчик, в том числе в процессе без открытого UI, перед первым сетевым обращением восстанавливает URL из сохранённых IP/port по правилу [SETTINGS-NETWORK](03-profile-and-settings.md#settings-network); значение в памяти при этом заменяется, так что после смены адреса используется новое сохранённое. Если настроек нет или они некорректны, адрес очищается, прогон завершается SERVER_UNAVAILABLE с retry без pre-check/upload и прежний адрес не используется. Поставщику URL не нужен.
3. Network UI восстанавливает URL тем же правилом до своего ping и пересматривает фон. Для работы worker открытие Network UI не требуется.
4. Каждый старт процесса при полном доступе к изображениям ставит разовый Поставщик ([BACKUP-BACKGROUND](04-backup-and-sync.md#backup-background)), в том числе для изменения, событие о котором могло быть потеряно при восстановлении фоновых задач.
5. В начале стадии checksum Поставщика после проверки разрешения HASHING возвращается в PENDING — независимо от доступности Server. Уже вычисленные CHECKSUM_READY не пересчитываются; прерванный между порциями scan восстанавливается следующим полным scan ([BACKUP-DISCOVER](04-backup-and-sync.md#backup-discover)). UPLOADING возвращается в PENDING_UPLOAD в начале стадии upload Загрузчика, после проверок пары, URL, ping, разрешения и успешного pre-check. Строки, уже переведённые pre-check в SYNCED или PENDING_UPLOAD, повторно не проверяются; прогон, остановленный бюджетом между pre-check и upload, оставляет PENDING_UPLOAD следующему прогону.

После восстановления URL и прохождения начальных проверок сохранённая очередь может продолжиться. Запуск приложения сам по себе не сбрасывает прерванные состояния.

### Ошибки и recovery

При фиксации Server без полученного ответа или локальной отметки следующая отправка может получить [BACKUP-DUPLICATE](04-backup-and-sync.md#backup-duplicate). Ранее пройденные локальные стадии не откатываются. Неуспех pre-check откладывает upload recovery.

### Текущие ограничения

Собственного boot receiver нет; без открытия приложения новые изображения обнаруживает наблюдатель MediaStore, а при его отсутствии — periodic Поставщика ([BACKUP-BACKGROUND](04-backup-and-sync.md#backup-background)). После am kill и смахивания из недавних восстановление наблюдателя и доставка фото проверены на эмуляторе; восстановление после перезагрузки и на физических устройствах не проверено. После Force Stop из настроек Android, в отличие от am kill, фоновая обработка не возобновляется до ручного запуска приложения. Запрос отмены не гарантирует остановки уже выполняемых действий. Реальное восстановление ключа/пары/очереди после восстановления резервной копии, переноса установки или обновления не проверено; это не равнозначно обычному перезапуску процесса.

### Нерешённый вопрос

Поведение OS/OEM scheduling и реальные исторические состояния DB/ключей после restore/upgrade остаются неизвестными. [SYSTEM-SCOPE](07-system-rules-and-recovery.md#system-scope) описывает ограничение identity при переносе контекста.

<a id="backup-change"></a>

## BACKUP-CHANGE — Изменение известного изображения

**Status:** IMPLEMENTING

**Availability:** END_TO_END

### Назначение

Заново обработать файл, для которого scan обнаружил изменение.

### Текущее поведение

У того же LocalMedia.mediaStoreId обнаружен другой size или lastModified.

1. Поставщик одним изменением строки сбрасывает LocalMedia.status в PENDING из любого состояния, в том числе SYNCED, очищает checksum, serverFileId, failureReason и lastFailureAt, обнуляет retryCount и записывает новые size, lastModified и остальные локальные сведения.
2. Поставщик повторяет hash до CHECKSUM_READY; затем Загрузчик выполняет target/pre-check и при необходимости upload.
3. Новое содержимое может создать новый RemoteFile; прежняя удалённая копия не удаляется.

Получен новый локальный результат для обнаруженного изменения. История серверных копий не оформляется как цепочка версий.

### Развилки и условия

Переименование/перемещение при прежнем ID, размере и mtime обновляет только локальные сведения; не вызывает remote rename/move или повторную отправку. При прежнем checksum нормальны existing/duplicate ветки.

### Ошибки и recovery

Применяются обычные ошибки стадий. Поздний результат hash, pre-check или upload прежней версии сброшенную строку не перезаписывает. При изменении байтов без изменения размера/lastModified новый backup может не начаться; для такого изменения гонка между вычислением checksum и upload сохраняется ([BACKUP-UPLOAD](04-backup-and-sync.md#backup-upload)).

### Текущие ограничения

Нет проверки версии байтов, перезаписи или автоматической очистки прежней удалённой копии; удалённые имя и папка не зеркалят локальные.

### Нерешённый вопрос

Продуктовые правила хранения прежних версий/копий и роль удалённых изменений не приняты.

<a id="backup-delete"></a>

## BACKUP-DELETE — Исчезновение или удаление локального изображения

**Status:** IMPLEMENTING

**Availability:** ANDROID_ONLY

### Назначение

Убрать из локального индекса изображение, отсутствующее в полностью прочитанной области.

### Текущее поведение

Положительный mediaStoreId исчезает из полного снимка области scan, полученного Поставщиком при полном доступе к изображениям ([BACKUP-DISCOVER](04-backup-and-sync.md#backup-discover)).

1. Android удаляет LocalMedia целиком, независимо от её текущего status.
2. Remote DELETE не отправляется; серверная копия сохраняется. Приложение само не удаляет и не редактирует оригинал устройства.
3. При повторном появлении ID создаётся новая LocalMedia со status=PENDING и снова проходит обычный pipeline.

Локальная история строки исчезает, удалённая копия остаётся. Удаление с устройства не распространяется на Server.

### Развилки и условия

Причиной может быть удаление оригинала, выход за пределы области scan или потеря видимости, о которой ОС не сообщила ошибкой. Отсутствие ID не доказывает физического удаления. Scan Error, ошибка чтения отдельной строки, неподключённое основное хранилище и отсутствие полного доступа (в том числе частичный доступ Android 14+) удаление не начинают. Пустой снимок при непустом индексе и исчезновение большой части индекса удаляются, только если их подтверждает повторный снимок через паузу ([BACKUP-DISCOVER](04-backup-and-sync.md#backup-discover)).

### Ошибки и recovery

Ошибка применения снимка может оставить частичные изменения. После повторного discovery возможно existing без serverFileId; восстановление прежней локальной истории не гарантировано.

### Текущие ограничения

LOCAL_DELETED не записывается активным flow; локальная отметка удалённого объекта не сохраняется. Android не отслеживает remote delete/rename/move ([FILES-RECONCILE](05-file-library.md#files-reconcile)).

### Нерешённый вопрос

Правила хранения после локального удаления и направления синхронизации остаются продуктовым вопросом; текущее сохранение удалённой копии этим не меняется.
