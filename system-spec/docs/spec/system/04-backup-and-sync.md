# Backup и синхронизация

Текущий backup копирует доступные фотографии с устройства на Server. Android хранит локальную очередь и вывод о результате; удалённую библиотеку он не зеркалит. Ниже описан полный путь фотографии, включая условия и восстановление после ошибок. Автоматическое резервирование выбранных Android-папок включает подключение и регистрацию источника, обход и передачу файлов, архивирование изменённых версий и отключение ([BACKUP-SOURCE-CONNECT](04-backup-and-sync.md#backup-source-connect), [BACKUP-SOURCE-REGISTER](04-backup-and-sync.md#backup-source-register), [BACKUP-SOURCE-SYNC](04-backup-and-sync.md#backup-source-sync), [BACKUP-SOURCE-ARCHIVE](04-backup-and-sync.md#backup-source-archive), [BACKUP-SOURCE-DISABLE](04-backup-and-sync.md#backup-source-disable)).

Используемая модель: [DeviceMedia](01-system-model.md#device-media), [LocalMedia](01-system-model.md#local-media), [SyncState](01-system-model.md#sync-state), [FailureReason](01-system-model.md#failure-reason) и [RemoteFile](01-system-model.md#remote-file).

<a id="backup-new"></a>

## BACKUP-NEW — Полный путь новой фотографии

**Status:** IMPLEMENTING

**Availability:** END_TO_END

### Назначение

Сохранить на Server содержимое нового видимого Android изображения.

### Текущее поведение

На устройстве появляется фотография; обработку запускает observer в живом процессе, наблюдатель MediaStore (системное ожидание изменения Images, работает без живого процесса и может сам запустить процесс), разовый Поставщик при старте процесса приложения или периодическая задача (periodic) Поставщика. Один факт появления ещё не гарантирует немедленного запуска. Обработка разделена на две части с общей очередью LocalMedia ([BACKUP-BACKGROUND](04-backup-and-sync.md#backup-background))): Поставщик выполняет локальную обработку и требует только полного доступа к изображениям — сеть, URL и авторизация ему не нужны; Загрузчик выполняет серверную обработку и требует сохранённой пары, URL из сохранённых настроек, успешного public ping и того же доступа для чтения файлов.

1. Поставщик восстанавливает допустимые ошибки прошлого прогона и сканирует доступные изображения области scan — DCIM и временно Pictures. Новая LocalMedia сохраняется с состоянием PENDING и локальными сведениями ([BACKUP-DISCOVER](04-backup-and-sync.md#backup-discover)).
2. Поставщик читает содержимое и вычисляет SHA-256; успех даёт CHECKSUM_READY — локальная обработка завершена ([BACKUP-CHECKSUM](04-backup-and-sync.md#backup-checksum)). Если в очереди есть записи для Загрузчика и сохранена пара, Поставщик ставит разовый Загрузчик — уже после первой готовой партии, не дожидаясь конца очереди. Большую очередь Поставщик проходит несколькими прогонами, ограниченными по времени.
3. Загрузчик получает ROOT и ищет CAMERA; при её наличии проверяет checksum в этой папке ([BACKUP-TARGET](04-backup-and-sync.md#backup-target)).
4. Ответ existing переводит локальную запись в SYNCED без upload; missing либо отсутствие CAMERA — в PENDING_UPLOAD ([BACKUP-EXISTING](04-backup-and-sync.md#backup-existing)).
5. Перед upload Android повторно ищет CAMERA, проверяет локальный MIME и доступность потока, отправляет файл. Server вычисляет свойства принятых байтов и определяет папку назначения.
6. Для нового содержимого Server сохраняет байты и RemoteFile; для duplicate возвращает прежний файл. Android принимает 2xx с id>0, сохраняет serverFileId и SYNCED ([BACKUP-UPLOAD](04-backup-and-sync.md#backup-upload), [BACKUP-DUPLICATE](04-backup-and-sync.md#backup-duplicate)).
7. Обработка продолжается для следующих файлов, затем Загрузчик сохраняет итог прогона ([SyncRunResults](01-system-model.md#sync-run-results)). Большую очередь Загрузчик, как и Поставщик, проходит несколькими прогонами, ограниченными по времени.

Для обработанной строки сохраняется локальный результат по критерию [SYNCED](01-system-model.md#synced). Результаты pre-check и upload применяются только к той же версии строки (status, checksum, size, lastModified): фотография, изменённая во время серверной обработки, проходит путь заново. Нет единого атомарного подтверждения Android + Server + физические байты.

### Развилки и условия

Existing и duplicate — нормальные успешные ветки. Ошибка отдельного файла может оставить FAILED при успешном завершении прогона; временная ошибка может остановить текущую стадию и отложить продолжение.

### Ошибки и recovery

Конкретные отказы описаны в сценариях обнаружения, вычисления checksum, pre-check и upload; правила повторного прогона — [BACKUP-RETRY](04-backup-and-sync.md#backup-retry), прерывание и перезагрузка — [BACKUP-RESTART](04-backup-and-sync.md#backup-restart). При потере сессии действует [AUTH-REFRESH](02-account-and-auth.md#auth-refresh).

### Текущие ограничения

Нет ручной команды Sync now и общей server sync session. Ошибка локальной стадии не останавливает Загрузчик; ошибка pre-check откладывает upload уже ожидающих файлов до повтора Загрузчика.

### Нерешённый вопрос

Какой пользовательский смысл должно иметь подтверждение «синхронизировано», в том числе при потерянном ответе и отсутствии физических байтов, ещё не принято. Это не меняет текущий критерий.

<a id="backup-discover"></a>

## BACKUP-DISCOVER — Обнаружение и повторное сканирование локальных фото

**Status:** IMPLEMENTING

**Availability:** ANDROID_ONLY

### Назначение

Поддерживать сохранённый индекс доступных локальных изображений и очередь обработки.

### Текущее поведение

Обнаружение выполняет только прогон Поставщика, синхронизацию — фоновые задачи; Files лишь отображает состояние очереди и результаты и сам scan не запускает. Одновременно выполняется один scan: прогоны Поставщика применяют снимки по очереди. Нужен полный доступ к внешней коллекции изображений: API 29–32 — READ_EXTERNAL_STORAGE, API 33+ — READ_MEDIA_IMAGES. Частичный доступ Android 14+ (выбранные фото, READ_MEDIA_VISUAL_USER_SELECTED без READ_MEDIA_IMAGES) считается отсутствием разрешения: scan и удаление строк не выполняются. Worker сам разрешение не запрашивает. Сеть, URL и авторизация для scan не нужны.

Разрешения запрашиваются только на Settings и только по нажатию; при открытии Settings, Files и других экранов системных запросов нет. Settings показывает фактическое состояние, читая его у Android при открытии экрана, после ответа на запрос и при каждом возврате в приложение; собственной копии состояния приложение не хранит. Отозвать разрешения можно только в системных настройках Android; отзыв Android завершает процесс приложения.

1. Блок «Доступ к фотографиям». Без доступа активна кнопка «Разрешить доступ к фотографиям»: запрос включает разрешение чтения по версии Android, на Android 14+ — READ_MEDIA_IMAGES вместе с READ_MEDIA_VISUAL_USER_SELECTED. При частичном доступе показывается статус «Доступ только к выбранным фотографиям» и кнопка запроса доступа ко всем. При полном доступе кнопка зелёная и неактивна. Появление полного доступа в Settings — по ответу на запрос или при возврате из настроек Android — пересматривает фон и сразу ставит разовый Поставщик ([BACKUP-BACKGROUND](04-backup-and-sync.md#backup-background)).
2. Блок «Геоданные фотографий» — необязательное ACCESS_MEDIA_LOCATION (доступ к оригиналу с геоданными, [DeviceMedia](01-system-model.md#device-media)). Пока нет полного доступа к фото, блок неактивен с кнопкой «Сначала разрешите доступ к фотографиям», и ACCESS_MEDIA_LOCATION не проверяется — даже если он выдан. При полном доступе: без разрешения активна кнопка «Разрешить доступ к геоданным», с разрешением кнопка зелёная и неактивна. Отказ в геоданных не останавливает scan, Поставщик, Загрузчик и periodic; при полном доступе без геоданных Files поясняет, что координаты съёмки могут не сохраниться в копии.
3. Если Android больше не показывает системный диалог, кнопка запроса заменяется переходом в системные настройки приложения. Блокировкой считается отказ без возможности объяснения (rationale) только если до запроса rationale был либо запрос этого разрешения уже отклонялся с момента открытия экрана; одиночный отказ без rationale так не трактуется — так же выглядят первый запрос и закрытый без ответа диалог. Смена разрешения сбрасывает эту историю.

На эмуляторе API 36 при выданном полном доступе к фото запрос геоданных удовлетворяется без отдельного диалога, а READ_MEDIA_VISUAL_USER_SELECTED выдаётся вместе с полным доступом и остаётся после отзыва READ_MEDIA_IMAGES, поэтому такой отзыв Settings показывает как частичный доступ.

1. Android одним запросом читает полный снимок внешней коллекции Images с относительными путями DCIM/% и — временно, для испытаний A4.3 на эмуляторе, — Pictures/%, включая подпапки. Каждое изображение входит в снимок один раз.
2. Для каждого положительного media ID сохраняет данные [DeviceMedia](01-system-model.md#device-media) в LocalMedia. Новая строка получает status=PENDING, checksum=null, serverFileId=null, failureReason=null, retryCount=0 и lastFailureAt=null.
3. Для уже известного ID сравнивает размер и lastModified. Изменение запускает [BACKUP-CHANGE](04-backup-and-sync.md#backup-change); иначе обновляются локальные сведения без сброса обработки. Локальные сведения и сброс обработки записываются одним изменением строки, поэтому параллельное вычисление checksum не видит промежуточного состояния. Снимок записывается в индекс порциями по 500 изображений, каждая — одной транзакцией; общей транзакции на весь архив нет.
4. Строки, отсутствующие в полном снимке, удаляются из локального индекса по [BACKUP-DELETE](04-backup-and-sync.md#backup-delete). Снимок полный, если запрос выполнен, прочитаны все его строки и основное хранилище подключено. Если полный снимок пуст при непустом индексе или в нём нет большой части индекса (не меньше 10 строк и не меньше половины), через 5 секунд выполняется повторный снимок: удаляются только строки, отсутствующие в обоих. Неудачный или неполный повтор ничего не удаляет до следующего scan. Удаление выполняется только после записи всех порций снимка: scan, прерванный между порциями, оставляет уже записанные порции согласованными и ничего не удаляет, а следующий полный scan дописывает остальное.

Индекс соответствует успешно прочитанной видимой области в пределах завершённых записей. Повторное сканирование при прежних ID, размере и lastModified не вызывает повторного вычисления checksum и повторного backup.

### Развилки и условия

Пустое имя заменяется на image_ID, пустой MIME — image/*, неизвестный размер — 0. Время выбирается из DATE_TAKEN, затем DATE_MODIFIED, затем DATE_ADDED, затем текущего времени. При отсутствии пригодных дат повторный scan может снова обнаруживать изменение.

### Ошибки и recovery

Нет полного доступа → стадия не выполняется, строки не меняются. Отсутствие результата чтения (null cursor) либо ошибка запроса/перебора строк возвращает Error. Неподключённое основное хранилище делает снимок неполным. Это не пустой успешный снимок, поэтому удаление строк на этом основании не начинается. Ошибка чтения отдельной строки исключает её из снимка и делает снимок неполным: остальные строки обрабатываются, отсутствующие не удаляются. Ошибка применения снимка может оставить частичные изменения.

### Текущие ограничения

Видео и изображения вне DCIM (и временно Pictures) не обнаруживаются; Pictures включает и Pictures/Screenshots. После исключения Pictures его строки удалит следующий полный scan как отсутствующие — только из Room. Нет выбора альбомов, томов или источника через SAF; каждый scan читает всю область. Явных фильтров для pending/trashed media нет; окончательную видимость определяет ОС. Полнота определяется по ошибкам запроса и строк и по состоянию основного хранилища. Недоступный съёмный том и другие пропуски, о которых ОС не сообщает ошибкой, не распознаются: массовое исчезновение только перепроверяется через паузу, и строки, отсутствующие в обоих снимках, удаляются; меньшие пропуски удаляются сразу. Удалённые так строки при возвращении файлов создаются заново и проходят hash и pre-check; повторный upload при existing не выполняется. Весь снимок читается целиком. В Files нет отдельной ручной Scan кнопки и кнопок запроса разрешений; при возврате на Files пересматриваются только пояснения о разрешениях.

### Нерешённый вопрос

Продуктовый охват типов/папок/размеров не принят. Отдельной selected-photo модели в Android нет: частичный доступ не обрабатывается. Поведение системных диалогов разрешений проверено только на эмуляторе API 36; на устройствах и других версиях Android не проверено.

<a id="backup-checksum"></a>

## BACKUP-CHECKSUM — Вычисление checksum

**Status:** IMPLEMENTING

**Availability:** ANDROID_ONLY

### Назначение

Получить SHA-256 конкретного чтения изображения устройства для проверки existing.

### Текущее поведение

После scan Поставщика в очереди есть PENDING; могут сохраниться и прерванные HASHING. Требуется полный доступ к изображениям; сеть и Server не нужны.

1. В начале стадии оставшиеся HASHING возвращаются в PENDING.
2. Поставщик последовательно выбирает партии по 100 строк PENDING в порядке FIFO по mediaStoreId (без приоритета по дате съёмки или новизне), отмечает строку HASHING, только если она всё ещё PENDING с прочитанными checksum, size и lastModified, и открывает её content URI по правилу [DeviceMedia](01-system-model.md#device-media): оригинал при ACCESS_MEDIA_LOCATION, иначе обычный поток.
3. Вычисляет SHA-256 потока. При успехе, если строка всё ещё HASHING с прежними size и lastModified, сохраняет LocalMedia.checksum и status=CHECKSUM_READY, очищает failureReason и lastFailureAt, обнуляет retryCount.
4. После каждой партии, давшей хотя бы один CHECKSUM_READY, ставит разовый Загрузчик по правилу [BACKUP-BACKGROUND](04-backup-and-sync.md#backup-background); Загрузчик может отправлять готовые строки, пока Поставщик хеширует следующие.
5. Перед каждым файлом проверяет бюджет прогона — 420 секунд от начала работы Поставщика, scan тоже его расходует. Исчерпанный бюджет не прерывает начатое чтение файла, но следующий файл не начинается.
6. Продолжает до исчерпания очереди, бюджета, ошибки стадии или партии, в которой не удалось взять ни одной строки. Если бюджет исчерпан, в прогоне был взят хотя бы один файл и PENDING остались, Поставщик регистрирует продолжение ([BACKUP-BACKGROUND](04-backup-and-sync.md#backup-background)) и завершается успешно; иначе остаток обрабатывает следующий прогон по событию или periodic.

CHECKSUM_READY означает завершение локальной обработки и границу передачи Загрузчику. Checksum относится к прочитанному содержимому, а не к имени, ID или неизменяемой версии файла.

### Ошибки и recovery

Отказ Android в оригинале ошибкой не считается: читается обычный поток. Отсутствие потока (null) или файла (FileNotFound) → FAILED FILE_NOT_FOUND; отказ доступа при чтении → FAILED PERMISSION; IOException → FAILED CHECKSUM_IO; прочие ошибки файла → FAILED UNKNOWN. Причина, счётчик и время сохраняются при том же условии, что и успех; обработка следующих файлов продолжается. Если scan сбросил строку во время чтения, результат отбрасывается, а строка снова хэшируется как PENDING. Автоматический возврат возможен только для ограниченного CHECKSUM_IO ([BACKUP-RETRY](04-backup-and-sync.md#backup-retry)). Отсутствие разрешения на входе останавливает стадию без вычисления checksum.

### Текущие ограничения

Приватная неизменяемая копия байтов не создаётся. Во время upload URI читается заново; гонка чтений и проверка принятых байтов описаны в [BACKUP-UPLOAD](04-backup-and-sync.md#backup-upload).

<a id="backup-target"></a>

## BACKUP-TARGET — Выбор CAMERA и первый backup

**Status:** IMPLEMENTING

**Availability:** END_TO_END

### Назначение

Определить папку проверки и назначения последующей отправки.

### Текущее поведение

Загрузчик прошёл проверки пары, URL, ping и полного доступа к изображениям. Папка определяется до pre-check и до отправки первого файла; защищённые запросы папок требуют авторизации.

1. Android отправляет `POST /api/v1/folders/camera`. Server под блокировкой структуры пользователя находит CAMERA либо создаёт отсутствующие ROOT и CAMERA и возвращает FolderDto с 200. Запрос идемпотентен: параллельные запросы получают одну и ту же папку.
2. Android сохраняет полученный ID только на текущий прогон и использует его в [BACKUP-EXISTING](04-backup-and-sync.md#backup-existing) и [BACKUP-UPLOAD](04-backup-and-sync.md#backup-upload). Запрос выполняется один раз за прогон.
3. Каждый файл отправляется с явным folderId. Без полученного ID Android ничего не отправляет: pre-check и upload в этом прогоне не начинаются.
4. С явным ID CAMERA Server принимает файл независимо от определённого типа содержимого; определение типа на выбор папки не влияет.
5. Upload без folderId остаётся в API для других клиентов: IMAGE/VIDEO → CAMERA (создаётся при необходимости), остальное → 400 без сохранения файла. Явно выбранной папкой может быть любая папка пользователя, кроме контейнера AutoUploads ([FOLDERS-AUTO-UPLOADS](05-file-library.md#folders-auto-uploads)); системной папки для обычных файлов нет.

Проверка existing и upload одного прогона относятся к одной и той же CAMERA.

### Развилки и условия

- Ошибка или недоступность запроса CAMERA, отсутствие ID в ответе → ERROR и retry Загрузчика. Файлы остаются в CHECKSUM_READY и PENDING_UPLOAD, в FAILED не переводятся.
- ID устарел, запрос existing или upload получил 404 → ERROR либо RETRY_SCHEDULED с повтором Загрузчика. Следующий прогон заново получает ID; в одном прогоне запрос CAMERA не повторяется, поэтому цикла нет, а частоту ограничивает backoff WorkManager.
- Первый upload больше не создаёт CAMERA для Android: она существует до отправки первого файла. Upload без folderId создаёт её только для других клиентов.

### Ошибки и recovery

Ошибка получения папки или проверки existing вызывает ERROR и повтор Загрузчика; локальная обработка от неё не зависит. Ни одна из этих ошибок не создаёт FAILED.

### Текущие ограничения

Локальные подпапки DCIM не превращаются в дерево папок Server; ID между прогонами не хранится. Клиенту нужен Server с `POST /api/v1/folders/camera`, поэтому Server обновляется первым. 401 от несовместимого Server сам по себе не очищает пару: Android применяет [AUTH-REFRESH](02-account-and-auth.md#auth-refresh). Пара очищается только при окончательном отказе refresh — `401 INVALID_REFRESH_TOKEN` или `403 REFRESH_TOKEN_REVOKED`, если она не сменилась за время запроса. Повторный 401 исходного запроса пару не очищает; получение CAMERA завершается ошибкой с повтором Загрузчика. После очистки пары следующий прогон останавливает фон до нового входа.

### Нерешённый вопрос

Целевые правила первого выбора CAMERA, запасного назначения и конфликтов имён, Unicode и регистра за пределами установленного As-Is не определены.

<a id="backup-existing"></a>

## BACKUP-EXISTING — Pre-check: existing или missing

**Status:** IMPLEMENTING

**Availability:** END_TO_END

### Назначение

Не отправлять содержимое, уже представленное логической записью в целевой CAMERA.

### Текущее поведение

Checksum готова, CAMERA найдена в [BACKUP-TARGET](04-backup-and-sync.md#backup-target).

1. Android берёт максимум 500 строк CHECKSUM_READY с checksum в порядке FIFO по mediaStoreId, приводит суммы к нижнему регистру и объединяет совпадающие. Перед каждым запросом проверяется бюджет прогона Загрузчика ([BACKUP-BACKGROUND](04-backup-and-sync.md#backup-background)): исчерпан — новый запрос не начинается.
2. Отправляет folderId и список checksum. Server проверяет свою папку, формат SHA-256 и максимум 500 исходных значений, затем возвращает existing/missing для текущего user и folder.
3. Existing → Android меняет только status на SYNCED, если строка всё ещё CHECKSUM_READY с прочитанными checksum, size и lastModified; upload не выполняется.
4. Missing → PENDING_UPLOAD при том же условии; затем применяется [BACKUP-UPLOAD](04-backup-and-sync.md#backup-upload). Партии продолжаются до завершения, исчерпания бюджета или партии без применённых переходов. Если бюджет исчерпан на pre-check, upload в этом прогоне не начинается: стадии не чередуются, оставшиеся CHECKSUM_READY проверит следующий прогон.

Existing подтверждает логическую запись Server на момент запроса. Ответ не содержит FileId. Изменение только status оставляет LocalMedia.serverFileId прежним; в обычном новом пути он остаётся null.

### Развилки и условия

Локальные строки с одинаковым hash в партии получают один результат. Если некорректный ответ содержит hash в обеих группах, Android предпочитает existing; если ни в одной — оставляет CHECKSUM_READY. При отсутствии прогресса завершает стадию без отдельного запроса повтора. Строку, которую Поставщик успел сбросить или обновить, ответ не меняет: она пройдёт hash и pre-check заново. Server для валидного запроса формирует полное разделение.

### Ошибки и recovery

При ошибке доступа к папке, HTTP, сети, разбора ответа или отсутствии тела pre-check останавливается и запрашивает повтор Загрузчика. Результаты уже обработанных партий сохраняются.

### Текущие ограничения

Existing не проверяет физические байты и не резервирует файл до upload. Логическая запись может существовать при потерянных байтах; SYNCED этого не обнаруживает и их не восстанавливает. Обычные SYNCED повторно не сверяются с Server — только по ручной команде [BACKUP-CAMERA-CHECK](04-backup-and-sync.md#backup-camera-check).

<a id="backup-upload"></a>

## BACKUP-UPLOAD — Отправка ожидающего изображения

**Status:** IMPLEMENTING

**Availability:** END_TO_END

### Назначение

Отправить изображение, отсутствующее по результату pre-check, и сохранить ответ Server локально.

### Текущее поведение

После pre-check остаются PENDING_UPLOAD. Загрузчик прошёл проверки пары, URL, ping и полного доступа к изображениям и получил ID CAMERA ([BACKUP-TARGET](04-backup-and-sync.md#backup-target)); он передаётся с каждым файлом.

1. При входе в upload оставшиеся UPLOADING возвращаются в PENDING_UPLOAD. Upload начинается, только если после полного pre-check бюджет прогона не исчерпан. Android выбирает строки PENDING_UPLOAD в порядке FIFO по mediaStoreId, без приоритета по дате съёмки или новизне, последовательно партиями по 20 и отправляет по одному файлу. Перед каждым файлом проверяется бюджет: исчерпан — следующий файл не начинается, а уже начатая передача не прерывается и ограничена прежними тайм-аутами HTTP; отправленные файлы остаются SYNCED.
2. Для файла проверяет MIME с префиксом image/ и возможность открыть/закрыть URI. Затем отмечает UPLOADING, только если строка всё ещё PENDING_UPLOAD с прочитанными checksum, size и lastModified (иначе пропускает её в этом прогоне), и заново читает URI для multipart upload. Проверка и отправка выбирают поток по тому же правилу, что и checksum ([DeviceMedia](01-system-model.md#device-media)); отказ Android в оригинале не переводит файл в FAILED.
3. Server принимает поток, вычисляет фактические SHA-256 и размер, определяет MIME и тип по байтам. Принятые байты не перекодируются и не изменяются: определение типа и извлечение метаданных только читают их. Пустой файл отвергается; допустимо до 104857600 байтов включительно (100 MiB).
4. Server пытается извлечь метаданные изображения и определяет папку; отсутствие метаданных не отменяет upload. Если в CAMERA уже есть этот checksum, выполняет [BACKUP-DUPLICATE](04-backup-and-sync.md#backup-duplicate).
5. В CAMERA одинаковые имена разрешены. В обычной библиотеке ([имена](01-system-model.md#library-names)) имя проверяется по правилам и должно быть свободно в общем пространстве файлов и папок: то же имя с тем же checksum возвращает существующий файл, иначе занятое имя даёт 409, а тот же checksum под другим именем не мешает создать новый файл. Затем в одной транзакции под блокировкой структуры пользователя Server повторяет проверку, сохраняет RemoteFile, StoredObject и доступную FileMetadata и публикует итоговые байты без перезаписи существующего файла ([SYSTEM-STORAGE](07-system-rules-and-recovery.md#system-storage)): для CAMERA — в `{userId}/camera/{YYYY}` по году capturedAt ([BACKUP-METADATA](04-backup-and-sync.md#backup-metadata)), для остальных папок — по пути, вычисленному из дерева папок и имени ([PhysicalBytes](01-system-model.md#physical-bytes)). Имя, занятое только на диске, в библиотеке даёт 409.
6. После commit возвращает 200 с [FileItemDto](01-system-model.md#api-projections), включая ID файла, папку, нормализованное имя, checksum и доступные метаданные.
7. Android принимает любой 2xx с id>0 и, если строка всё ещё UPLOADING той же версии, сохраняет этот serverFileId, ставит SYNCED и обнуляет retryCount, очищает failureReason и lastFailureAt. Остальные поля ответа не сверяет и не переносит в локальные сведения.

Обычный новый upload создаёт удалённые записи и байты; Android сохраняет положительный FileId. Создание файла и ответ duplicate одинаково считаются успехом.

### Развилки и условия

- Локальный MIME не image/ → FAILED NOT_IMAGE.
- При проверке открытия отсутствие потока/файла → FAILED FILE_NOT_FOUND, отказ доступа → FAILED PERMISSION.
- Upload 400/409/413 → FAILED HTTP_400/409/413; следующий файл обрабатывается. С явным ID CAMERA 400 остаётся только для пустого файла и некорректного запроса; 409 в CAMERA не возникает, а обычный duplicate возвращает 200.
- IOException при передаче (обрыв соединения, потеря ответа, тайм-аут, включая временный отказ refresh) → одна немедленная повторная отправка того же файла с чтением исходного потока заново, если Worker не остановлен и бюджет прогона не исчерпан. Успешный повтор обрабатывается как обычный ответ, в том числе duplicate. Повторный IOException или повтор, не начатый из-за бюджета, → PENDING_UPLOAD, остановка upload и запрос retry; остановка Worker прерывает прогон без повтора.
- Прочие HTTP, в том числе окончательный 401/403/404/429/5xx, или 2xx без id>0 → PENDING_UPLOAD, остановка upload и запрос retry; немедленно HTTP-ответы не повторяются. Сам 401 upload пару не очищает. Только окончательный отказ refresh (`401 INVALID_REFRESH_TOKEN` или `403 REFRESH_TOKEN_REVOKED`) очищает отвергнутую пару, если она ещё текущая ([AUTH-REFRESH](02-account-and-auth.md#auth-refresh)); тогда следующий прогон останавливает фон ([BACKUP-BACKGROUND](04-backup-and-sync.md#backup-background)).
- Иное исключение после начала отправки может оставить UPLOADING до recovery.
- Все переходы стадии (FAILED, SYNCED, возврат в PENDING_UPLOAD) применяются только к той же версии строки. Если Поставщик сбросил строку во время отправки, ответ её не меняет: новая версия проходит hash, pre-check и upload заново, а принятая копия прежней версии остаётся на Server.
- Нет полного доступа к изображениям → Загрузчик завершается до pre-check без изменения очереди и без retry; строки не переходят в FAILED PERMISSION.

### Ошибки и recovery

При потере ответа Server уже мог завершить сохранение; это не доказывает откат. Повтор передаёт весь поток и может получить duplicate. Занятый физический путь или другая ошибка физической записи даёт 500 INTERNAL_ERROR без изменения существующих файлов; для Android это временная ошибка, повтор получает новое физическое имя. Прерывание и локальное подтверждение — [BACKUP-RESTART](04-backup-and-sync.md#backup-restart); расхождение БД и байтов — [SYSTEM-STORAGE](07-system-rules-and-recovery.md#system-storage). 400/409/413 автоматически не повторяются; ручного повтора нет.

### Текущие ограничения

Вычисление checksum и upload независимо читают URI, содержимое которого может измениться. Условный переход защищает только от изменения, уже обнаруженного scan по size/lastModified. При изменении байтов между чтениями локальная checksum и pre-check могут относиться к другому содержимому, чем принятый объект, несмотря на SYNCED с ID: checksum, size и папка ответа не проверяются. Тот же случай возникает, если ACCESS_MEDIA_LOCATION выдано или отозвано между checksum и upload: отправляется оригинал или доступная версия, отличная от прочитанной при checksum. Нет продолжения частичной загрузки, отправки по частям, побайтового прогресса, неизменяемого снимка или сквозного восстановления целостности. Локальной проверки максимального размера нет; серверный предел multipart 110 MB дополняет ограничение обработки потока 100 MiB. Server не ограничивает MIME списком разрешённых типов и не проверяет файлы на вирусы. HTTP-логирование Android тела не читает: в debug-сборке пишутся только метод, URL, код и длительность, в release HTTP-логов нет. Поток файла читается один раз на каждую попытку отправки, в том числе при повторе после refresh. Общей серверной квоты нет.

### Нерешённый вопрос

Соответствие заявленного SIZE длине потока и момент прекращения действий upload после отмены зависят от условий выполнения и не проверены.

<a id="backup-duplicate"></a>

## BACKUP-DUPLICATE — Duplicate и потерянное подтверждение

**Status:** IMPLEMENTING

**Availability:** END_TO_END

### Назначение

Завершить повторную отправку того же содержимого в CAMERA без создания нового RemoteFile.

### Текущее поведение

Server получает upload в CAMERA с уже существующим сочетанием user + folder + SHA-256; например, Android повторяет отправку после потери ответа. Для обычной библиотеки действует другое правило ([BACKUP-UPLOAD](04-backup-and-sync.md#backup-upload)).

1. Server всё равно читает входящие байты и вычисляет checksum.
2. Находит прежнюю логическую запись в выбранной папке, пытается убрать временные байты и возвращает прежний DTO с 200.
3. Android принимает положительный ID, сохраняет его и SYNCED как при обычном upload.

В обычной duplicate-ветке возвращается прежний FileItem ID. Новое имя, метаданные, даты и байты не заменяют существующие.

### Развилки и условия

Тот же checksum в другой папке или у другого пользователя не является этим duplicate: обычный upload создаёт отдельные RemoteFile, StoredObject и байты. Конкурентные upload одного checksum проходят сохранение по очереди под блокировкой структуры пользователя: проигравший запрос находит запись победителя, откатывает свою транзакцию, не публикуя байты, удаляет свой временный файл и возвращает найденную запись. Байты успешного запроса не затрагиваются. Уникального ограничения БД здесь нет: одинаковые checksum допустимы в обычных папках.

### Ошибки и recovery

Duplicate не проверяет читаемость и не восстанавливает потерянные физические байты. Условие возврата прежнего ID исчезает после удаления на Server или смены пользователя, папки или содержимого; глобальная гарантия однократного сохранения отсутствует.

### Текущие ограничения

Устранение дубликатов ограничено сочетанием user/folder/checksum в CAMERA. Между папками физические байты не объединяются. Побайтового сравнения при одинаковом SHA-256 нет. При потере последующей локальной записи возможна ещё одна полная попытка.

<a id="backup-metadata"></a>

## BACKUP-METADATA — Имена, время и метаданные фотографии

**Status:** IMPLEMENTING

**Availability:** END_TO_END

### Назначение

Объяснить, какие сведения сохраняются на устройстве и на Server вместе с изображением.

### Текущее поведение

Обнаружение изображения формирует локальные сведения, а успешный новый upload — серверные.

1. Android берёт имя, относительный путь, MIME, размер и время из локального снимка изображения; свои createdAt/lastModified не передаёт как capturedAt.
2. Server определяет MIME и размер по принятому потоку, нормализует имя и извлекает доступные EXIF/GPS. Байты сохраняются как приняты, без перекодирования и правки метаданных, и download возвращает их без изменений. FileMetadata.width и FileMetadata.height поддержаны для JPEG/PNG.
3. Server задаёт RemoteFile.capturedAt — локальные календарные дату и время съёмки из EXIF DateTimeOriginal, а при отсутствии пригодного значения — из DateTimeDigitized, как они записаны в файле, с долями секунды до микросекунд. Часовой пояс Server и EXIF-смещение (OffsetTime) время не сдвигают, поэтому год на границе 31 декабря сохраняется. Непригодны отсутствующее, нераспознанное значение и несуществующая дата, например заглушка 0000:00:00 00:00:00; ограничений по году нет. Без пригодной EXIF-даты capturedAt равен uploadedAt: дату создания исходного файла upload не передаёт. Ответные даты не содержат offset.
4. Android оставляет собственные сведения; ответ Server их не заменяет.

Локальные и удалённые имя, время и метаданные могут различаться при успешном backup.

### Ошибки и recovery

Ошибка извлечения данных изображения не отменяет upload: FileMetadata может отсутствовать. Возможность отсутствия GPS не объясняет, почему его нет у конкретного файла.

### Текущие ограничения

Android сам не извлекает и не редактирует EXIF/GPS и не подтверждает побайтовую идентичность оригиналу. При выданном ACCESS_MEDIA_LOCATION он отправляет оригинал вместе с EXIF/GPS; без него backup продолжается, но Android 10+ может отдать копию с затёртыми геоданными, и Server сохраняет её как есть. Фактические байты зависят от ОС, provider и выданных разрешений.

Выдача ACCESS_MEDIA_LOCATION не восстанавливает геоданные в уже загруженных копиях: строки SYNCED и подготовленные строки с прежними size и lastModified повторно не хэшируются и не отправляются, массовой пересинхронизации нет. Повторная проверка архива — отдельная будущая задача. Server может принимать VIDEO, но не извлекает метаданные или длительность видео; Android видео не обнаруживает.

capturedAt — местное время камеры без пояса: снимки, сделанные в разных часовых поясах, упорядочиваются по местному времени, а не по абсолютному моменту. Значения capturedAt, сохранённые до этого правила, не пересчитываются и могут быть сдвинуты на разницу между поясом Server и UTC, а при наличии EXIF-смещения — между поясом Server и этим смещением.

### Нерешённый вопрос

Общий пользовательский смысл имён, времени и геопозиции и ожидаемая полнота оригинальной копии не определены; сохранение GPS снимков с геометками на эмуляторе и устройствах не проверено. Как Server интерпретирует затёртый Android блок GPS (отсутствие координат или нулевые значения), не проверено.

<a id="backup-background"></a>

## BACKUP-BACKGROUND — Автоматический и периодический backup

**Status:** IMPLEMENTING

**Availability:** END_TO_END

### Назначение

Продвигать очередь без ручных команд пользователя.

### Текущее поведение

Обработку запускает изменение Images, старт процесса приложения, периодическая задача, сигнал Поставщика, login или повтор ранее неуспешного прогона. Фон разделён на две независимые части с общей очередью LocalMedia: Поставщик ведёт локальную обработку ([BACKUP-DISCOVER](04-backup-and-sync.md#backup-discover), [BACKUP-CHECKSUM](04-backup-and-sync.md#backup-checksum)), Загрузчик — серверную ([BACKUP-TARGET](04-backup-and-sync.md#backup-target), [BACKUP-EXISTING](04-backup-and-sync.md#backup-existing), [BACKUP-UPLOAD](04-backup-and-sync.md#backup-upload)). Поставщик не вызывает Загрузчик напрямую: он оставляет подготовленные строки в очереди и запрашивает разовую работу.

1. Android пересматривает настройку фона при создании Network UI, успешном login, полученном результате logout, входе на Files или появлении полного доступа к фото на Settings, а также в Загрузчике без пары. При полном доступе к изображениям включает наблюдатель MediaStore, observer и periodic Поставщика независимо от входа; иначе отменяет наблюдатель и periodic Поставщика и останавливает observer. Повторный пересмотр не создаёт второго наблюдателя. Если дополнительно есть пара и URL, включает periodic Загрузчика; иначе отменяет его.
2. На изменения внешней Images-коллекции реагируют два механизма; событие само не фильтруется по области scan, её определяет scan. Observer в живом процессе после 3 секунд без нового события ставит разовый Поставщик. Независимо от живого процесса действует наблюдатель MediaStore — одноразовое системное ожидание изменения внешней коллекции Images и вложенных URI, которое при необходимости само запускает процесс; сеть, URL и пара ему не нужны. Android запускает его после 3 секунд без новых изменений, но не позже 30 секунд от первого. Без полного доступа сработавший наблюдатель завершается, не ставя следующего ожидания. Иначе он сначала заменяет себя новым ожиданием — под своим именем всегда одна задача, без цепочек, — затем ставит разовый Поставщик. Если наблюдателя нет, его восстанавливает любой прогон Поставщика с полным доступом, в том числе periodic.
3. При каждом старте процесса приложения, в том числе запущенного наблюдателем MediaStore в фоне, Android при полном доступе к изображениям ставит разовый Поставщик; без полного доступа ничего не ставится. Ожидающий или выполняющийся Поставщик при этом не дублируется. Этот прогон обрабатывает изменение, событие о котором могло быть потеряно при восстановлении фоновых задач на холодном старте (см. «Текущие ограничения»). Открытие UI не требуется.
4. Разовый Поставщик условий не имеет; периодический настроен на 30 минут и требует достаточного заряда (batteryNotLow). Сеть Поставщику не нужна. Фактическое время periodic выбирает Android; он выполняется независимо от событий и сигналов и остаётся резервным механизмом при потерянном событии. После появления полного доступа на Settings Android сразу ставит разовый Поставщик, не дожидаясь periodic.
5. Поставщик проверяет полный доступ к изображениям, восстанавливает допустимые ошибки ([BACKUP-RETRY](04-backup-and-sync.md#backup-retry)), выполняет scan и hash. После каждой готовой партии hash и в конце прогона, если в очереди есть CHECKSUM_READY с checksum, PENDING_UPLOAD или UPLOADING и сохранена пара, он ставит разовый Загрузчик (KEEP: ожидающий или выполняющийся Загрузчик не дублируется). Без пары Загрузчик не ставится, подготовленные строки остаются в очереди.
6. Разовый Загрузчик ждёт доступной сети (CONNECTED); периодический настроен на 30 минут, дополнительно требует batteryNotLow и, как periodic Поставщика, запускается в выбранное Android время независимо от событий. Сети с тарификацией и мобильный интернет разрешены; подключение к зарядке или только Wi-Fi не требуются. После успешного login Android сразу ставит разовый Загрузчик для накопленной очереди.
7. Загрузчик сначала проверяет наличие сохранённой пары (см. «Ошибки и recovery»). Перед первым сетевым обращением он перечитывает сохранённые IP/port и формирует URL по единому правилу [SETTINGS-NETWORK](03-profile-and-settings.md#settings-network); при отсутствии или некорректности настроек адрес очищается, прежний URL из памяти не используется. Затем проверяет доступность Server через public ping и полный доступ к изображениям и выполняет pre-check и upload по [BACKUP-NEW](04-backup-and-sync.md#backup-new). MediaStore он не сканирует и checksum не вычисляет. Бюджет прогона — 420 секунд от начала работы Загрузчика; его расходуют ping, pre-check и upload вместе.

Очередь может продвигаться в фоне при выполнении условий. Интервал periodic и debounce — настройки, не гарантированный срок сохранения фото. На эмуляторе новое фото, в том числе после завершения процесса командой am kill или смахиванием из недавних, доходило до Server примерно за 5–10 секунд; это результат испытания, а не гарантия.

### Развилки и условия

Пока разовая работа части не завершена, новая работа той же части не ставится (KEEP), в том числе в период ожидания повторной попытки.

Продолжение Поставщика и Загрузчика. Прогон части, завершившийся штатно с оставшейся очередью и прогрессом в этом прогоне, регистрирует следующий запуск до своего успешного завершения; текущий прогон не отменяется. Для Поставщика очередь — PENDING, прогресс — хотя бы один взятый в хеширование файл. Для Загрузчика очередь — CHECKSUM_READY с checksum, PENDING_UPLOAD и UPLOADING, прогресс — хотя бы одна строка, переведённая pre-check, или один начатый в upload файл; очередь может остаться и потому, что Поставщик подготовил новые строки во время прогона. Продолжение разового или periodic прогона добавляется в конец разовой цепочки части (APPEND_OR_REPLACE): оно начнётся только после успешного завершения идущей работы цепочки, выполняющийся прогон не отменяется, а без активной цепочки ставится новая. Разовый прогон оставляет в ожидании не больше одного продолжения; каждый periodic с прогрессом, пока цепочка не завершена, добавляет ещё один запуск, а запуски без прогресса завершаются и новых не ставят; продолжению Загрузчика, как и любому разовому Загрузчику, нужна сеть. Внешние сигналы (наблюдатель MediaStore, observer, старт процесса, Settings, сигнал Поставщика, login) в это время ничего не добавляют (KEEP). Periodic части не выполняет продолжение сам: оно идёт разовой задачей той же части. Это нужно и при идущей разовой задаче: простояв весь бюджет на занятой стадии, она завершится без прогресса и своего продолжения не поставит. Временная ошибка Загрузчика (недоступный Server, ошибка pre-check, временная ошибка upload) сохраняет прежний повтор с backoff и продолжение не регистрирует. Завершённые записи цепочки удаляет следующая постановка с KEEP после её окончания; продолжение их не удаляет. Без прогресса продолжение не регистрируется — бесконечной цепочки нет, остаток ждёт события или periodic. Если прогон остановлен до регистрации, его повторяет WorkManager как прерванную работу; повтор после регистрации добавляет не больше одного лишнего прогона. Ошибка регистрации считается ошибкой прогона (повтор с backoff). Постановка продолжения не гарантирует немедленного запуска: время выбирает Android.

Изображение, появившееся после scan текущего Поставщика, ждёт следующего события, продолжения или periodic Поставщика: каждый прогон продолжения заново выполняет scan и подхватывает изображения, события о которых были отброшены KEEP. Строки, подготовленные во время выполняющегося Загрузчика, ждут его продолжения, повтора или periodic Загрузчика. Признака обязательного последующего прогона, кроме продолжения части, нет. Periodic Загрузчика не зависит от backoff разовой задачи. Повторный пересмотр не создаёт новых periodic-заданий; отменённое задание ставится заново при следующем пересмотре с выполненными условиями.

### Ошибки и recovery

Поставщик: нет полного доступа к изображениям → задача завершается успешно без изменения очереди и без сохранения итога; это не успешный backup. Ошибка scan или hash → ERROR и retry Поставщика. Отсутствие сети, URL, Server и пары на Поставщика не влияет.

Итоги прогонов сохраняются раздельно по частям ([SyncRunResults](01-system-model.md#sync-run-results)): ошибки ниже — как проблема Загрузчика, кроме отсутствия пары и адреса; успешный прогон снимает проблему своей части.

Пока ручная сверка Camera не завершена ([BACKUP-CAMERA-CHECK](04-backup-and-sync.md#backup-camera-check)), Загрузчик без её серверной стадии завершается успешно до сетевых запросов, а обычные pre-check и upload не начинаются ни в одном виде запуска: разовом, periodic, продолжении, после login, по сигналу Поставщика или после ручного повтора FAILED. Прогон, начатый до проверки, читает паузу перед каждой партией pre-check и каждым файлом upload: отправленный запрос завершается, следующий не начинается. Поставщик при этом продолжает scan и hash.

Загрузчик: недоступный URL/ping → SERVER_UNAVAILABLE и retry до pre-check/upload; нет полного доступа к изображениям → успешное завершение без изменения очереди; ошибка pre-check → ERROR и retry; временная ошибка upload → RETRY_SCHEDULED и retry. Подготовленная очередь во всех этих случаях сохраняется. Временный отказ refresh, в том числе неподтверждённая запись пары с новым refresh, приходит в стадии как IOException и ведёт к обычному retry ([AUTH-REFRESH](02-account-and-auth.md#auth-refresh)).

Прогон Загрузчика без сохранённой пары до любых сетевых запросов, не сохраняя итога, последним действием пересматривает фон (без пары periodic Загрузчика отменяется; Поставщик и observer продолжают работу при полном доступе к изображениям) и завершается успешно без retry; причина `no_session` доступна в выходных данных задачи. Если это сам periodic Загрузчика, отмена расписания останавливает уже завершающийся прогон, и он не повторяется. Пара, очищенная окончательным отказом refresh во время прогона, в том числе из-за истёкшего refresh или блокировки аккаунта ([AUTH-BLOCK](02-account-and-auth.md#auth-block)), приводит к такой остановке на следующем прогоне.

### Текущие ограничения

Observer живёт только в памяти; без живого процесса изменения обнаруживает наблюдатель MediaStore. Изменение, пришедшее, пока Поставщик уже выполняется, не вызывает нового прогона (KEEP): если его scan уже прошёл, изображение ждёт следующего события или periodic. Изменение между срабатыванием наблюдателя и постановкой следующего ожидания (доли секунды) обнаруживает только последующий scan. Немедленный запуск не гарантирован: планировщик Android, Doze и ограничения фона откладывают срабатывание. Изменение MediaStore может само запустить процесс приложения. При таком холодном старте после завершения процесса (проверены am kill и смахивание из недавних) исходное событие может быть потеряно при восстановлении фоновых задач, а ожидание наблюдателя ставится заново. Такое изменение подхватывает разовый Поставщик при старте процесса, а если этого прогона не было — periodic. Force Stop из настроек Android не равнозначен am kill: после него Android не запускает приложение — ни наблюдатель, ни periodic — до ручного запуска. Старт процесса сам Загрузчик не ставит: доставка на Server по-прежнему требует пары, сети, URL, ping и полного доступа. Пересмотр не вызывается при каждом изменении токенов, URL или разрешения; ручной Network Test и onResume сами его не вызывают. Files запрашивает разрешение только при входе с tokens+URL; без входа Поставщик работает, если доступ уже выдан. Поставщик и Загрузчик выполняются параллельно, разовая и periodic задачи одной части могут пересекаться. Scan выполняется по одному, hash, pre-check и upload защищены каждый своей блокировкой; поздние результаты hash, pre-check и upload применяются только к той же версии строки, а restore и записи scan безусловны; запись scan для одной строки атомарна. Ответ upload после удаления строки не обновит ничего. Отмена задачи не гарантирует остановки уже идущего HTTP-запроса или чтения; остановленная системой стадия продолжается следующими прогонами. Backup не выполняется как foreground/expedited работа; уведомления о ходе нет. Отдельного продления refresh по таймеру нет: фон обновляет токены только обычным refresh после 401, и замена refresh происходит, когда до его истечения остаётся не больше 30 дней. Пока фон или UI хоть раз делают refresh в этом окне, сессия не истекает; если прогоны прекратились, она переживает от 30 до 180 дней после последнего refresh при сроках по умолчанию ([AUTH-REFRESH](02-account-and-auth.md#auth-refresh)).

### Нерешённый вопрос

На эмуляторе проверены доставка после am kill и смахивания из недавних, быстрые Поставщик и Загрузчик, доставка periodic при потерянном событии и сохранение наблюдателя после восстановления фоновых задач. Реальные задержки после reboot, Force Stop и в Doze, поведение на физических устройствах и OEM-прошивках, последовательности событий и поведение при переставших выполняться условиях задачи не измерены. Ожидания автономности, расхода трафика/батареи и уведомлений не приняты.

<a id="backup-retry"></a>

## BACKUP-RETRY — Повторы и FAILED без автоматического восстановления

**Status:** IMPLEMENTING

**Availability:** ANDROID_ONLY

### Назначение

Продолжить локальную обработку после тех ошибок, для которых существует автоматическое восстановление.

### Текущее поведение

Следующий прогон Поставщика при полном доступе к изображениям, в том числе повтор задачи, начинает восстановление; сеть и Server для этого не нужны. Истечение пяти минут само по себе задачу не запускает.

1. Один раз перед scan выбираются максимум 500 LocalMedia со status=FAILED, failureReason=CHECKSUM_IO, retryCount<3 и lastFailureAt не менее 5 минут назад.
2. Они возвращаются в PENDING; failureReason и lastFailureAt очищаются, retryCount, checksum и serverFileId сохраняются.
3. Следуют scan/hash/pre-check/upload. Успешный hash/upload и обнаруженное изменение содержимого обнуляют retryCount.
4. Ошибка локальной стадии запрашивает повтор Поставщика, ошибка pre-check или временная ошибка upload — повтор Загрузчика; завершённые локальные записи сохраняются.

Восстанавливаются только допустимые строки. Успех всего прогона может сосуществовать с FAILED без автоматического восстановления и CHECKSUM_READY без прогресса.

**Ручной повтор.** Пока в индексе есть FAILED, на Files под карточкой состояния показывается кнопка «Повторить ошибки» ([FILES-LOCAL](05-file-library.md#files-local)); индивидуальных повторов нет.

1. Нажатие проверяет полный доступ к изображениям. Без него FAILED не меняются; показывается сообщение с переходом на Settings.
2. Все строки, которые в этот момент FAILED, с любой причиной, одним условным обновлением Room возвращаются в PENDING: checksum, serverFileId, failureReason и lastFailureAt очищаются, retryCount обнуляется. Прежний checksum актуальность файла не подтверждает: файл читается и хешируется заново. Строки в других состояниях, включая SYNCED и находящиеся в обработке, не меняются; FAILED, записанный обработкой после обновления, остаётся FAILED.
3. Регистрируется продолжение Поставщика, как после исчерпанного бюджета ([BACKUP-BACKGROUND](04-backup-and-sync.md#backup-background)): выполняющийся прогон не заменяется, следующий начинается после него, без активного прогона — сразу. Дальше обычный путь: scan (исчезнувший файл удаляется из индекса), hash, сигнал Загрузчику, pre-check и upload.
4. Пока нажатие обрабатывается, кнопка неактивна; повторные нажатия выполняются по очереди и FAILED уже не находят, поэтому ни сброс, ни продолжение не дублируются.
5. Сообщение под кнопкой называет число возвращённых файлов. Если продолжение не удалось записать в WorkManager, строки остаются PENDING в Room и обрабатываются при следующем старте процесса, periodic Поставщика или изменении MediaStore.

retryCount обнуляется только ручным повтором, успешным hash/upload и обнаруженным изменением содержимого. Повторная ошибка после ручного повтора снова даёт FAILED с retryCount=1; дальше действует прежнее автоматическое восстановление: только CHECKSUM_IO, не больше трёх попыток. Автоматического повторного нажатия нет, поэтому бесконечного цикла нет.

### Развилки и условия

- Три накопленные ошибки вычисления checksum прекращают автоматическое восстановление CHECKSUM_IO. Выдержка между ошибкой и восстановлением зависит от часов устройства и следующего worker, а не отдельного таймера.
- FILE_NOT_FOUND, PERMISSION, NOT_IMAGE, HTTP_400/409/413, UNKNOWN и исторические FAILED без пригодных failureReason/lastFailureAt автоматически не восстанавливаются. Единственное исключение — однократная миграция БД приложения с версии 3 на 4: прежний HTTP_400 мог означать upload без папки, поэтому строки FAILED HTTP_400 с checksum возвращаются в CHECKSUM_READY, очищают failureReason и lastFailureAt и сохраняют retryCount. Отличить такой отказ от настоящего нельзя; повторный 400 снова терминален. Выдача статуса вручную отсутствует.
- Изменение размера/mtime либо исчезновение и повторное discovery могут начать обработку заново. Кроме ручного повтора всех FAILED, в UI нет сброса или отмены обработки.

### Ошибки и recovery

Upload при временной ошибке останавливается на первом неудавшемся файле, выбранном в порядке FIFO по mediaStoreId ASC. Повторяемая ошибка файла может задерживать следующие за ним pending. Число попыток всего прогона приложением не ограничено и не учитывается в retryCount файла; Retry-After и server error codes не управляют retry.

### Текущие ограничения

Задержку повтора определяют стандартные настройки WorkManager: экспоненциальный рост от 30 секунд до 5 часов. Реальные запуски зависят от ОС и условий задачи; заданный срок запуска не гарантируется. При пересечении восстановлений лимит не гарантирует однократный выбор каждой строки. В UI нет ручного восстановления, счётчиков retry и полного описания фоновой ошибки; монитор описан в [FILES-LOCAL](05-file-library.md#files-local).

### Нерешённый вопрос

Ожидаемые задержки автоматического восстановления и пользовательские сообщения для отдельных причин FAILED не определены.

<a id="backup-camera-check"></a>

## BACKUP-CAMERA-CHECK — Ручная сверка Camera с Server

**Status:** IMPLEMENTING

**Availability:** END_TO_END

### Назначение

По команде пользователя проверить, есть ли на текущем Server логическая запись каждого доступного Android изображения Camera, включая уже SYNCED, и загрузить отсутствующие только после его подтверждения.

### Текущее поведение

На Files в карточке «Проверка копий» пользователь нажимает «Проверить копии» ([FILES-LOCAL](05-file-library.md#files-local)). Отдельного механизма синхронизации нет: локальные стадии выполняет Поставщик, серверную — Загрузчик ([BACKUP-BACKGROUND](04-backup-and-sync.md#backup-background)); состояние хранит [CameraCheck](01-system-model.md#camera-check).

1. Android проверяет полный доступ к изображениям, наличие пары и корректного адреса Server и отсутствие другой незавершённой проверки; иначе показывает причину и ничего не меняет. Затем одной транзакцией сохраняет новую проверку (RUNNING, SCAN) с назначением serverUrl + accountId и регистрирует продолжение Поставщика. С этого момента новые Camera upload приостановлены; файл или партия pre-check, уже отправляемые Загрузчиком, завершаются, следующие не берутся.
2. **Сканирование Camera.** Первый scan Поставщика, начатый после запуска, по завершении создаёт набор [CameraCheckItem](01-system-model.md#camera-check-item) из всех LocalMedia, кроме LOCAL_DELETED. Неполный снимок либо неподтверждённое массовое исчезновение строк набора не создают: ERROR SCAN_INCOMPLETE, сверка не начинается.
3. **Вычисление checksum.** После своего hash Поставщик заполняет checksum набора: из LocalMedia той же версии (CHECKSUM_READY, PENDING_UPLOAD, UPLOADING, SYNCED, FAILED с checksum); PENDING и HASHING ждут обычного hash; для FAILED без checksum файл читается сверкой, а status, failureReason и retryCount строки не меняются. Нечитаемый файл — UNVERIFIABLE, удалённая строка исключается из набора. Перед каждым файлом проверяется бюджет прогона; остаток продолжает следующий прогон Поставщика. Когда checksum есть у всех строк, стадия становится SERVER и один раз на этот переход регистрируется прогон Загрузчика в цепочке ручных прогонов (см. «Повторить» в «Ошибки и recovery»): разовая цепочка может ждать backoff, а сверка его не ждёт.
4. **Сверка с Server.** Загрузчик после пары, URL, ping, доступа к изображениям и получения CAMERA и после окончания уже идущей отправки файла другим прогоном (на паузе это не больше одного файла) ([BACKUP-TARGET](04-backup-and-sync.md#backup-target)) сверяет назначение: адрес и subject совпадают с сохранёнными, а CAMERA — с первой полученной. Затем отправляет checksum-exists ([BACKUP-EXISTING](04-backup-and-sync.md#backup-existing)) партиями по 500 строк без результата; бюджет проверяется перед каждым запросом. Исчерпав бюджет после успешной партии, прогон регистрирует продолжение в цепочке ручных прогонов (см. «Повторить» ниже): оно продолжает ту же проверку (runId и результаты в Room) с первой партии без результата и не ждёт backoff разовой цепочки. После ответа назначение сверяется повторно; результат партии и снятие ошибки записываются одной транзакцией, только если проверка не отменена: existing → EXISTS, missing → MISSING, hash без ответа остаётся без результата. Строка, изменившаяся после получения checksum, — UNVERIFIABLE. Для CHECKSUM_READY той же версии existing выполняет обычный переход в SYNCED; остальные статусы, в том числе SYNCED при missing, не меняются.
5. **Завершение.** Когда результат есть у всех строк, итог сохраняется в CameraCheck. Без MISSING ручной режим завершается (FINISHED), набор удаляется, пауза снимается, и тот же прогон Загрузчика продолжает обычную синхронизацию. С MISSING проверка ждёт решения (AWAITING_DECISION).
6. Итог показывает: проверено файлов, подтверждено на сервере, не найдено на сервере, не удалось проверить; при отсутствующих — «Загрузить N файлов» (число и слово согласованы: 1 файл, 2 файла, 5 файлов) и «Позже». Пустой набор (в Camera нет фото) завершается FINISHED с текстом «Нет фотографий для проверки».
7. **«Загрузить N файлов».** При полном доступе и том же назначении одной транзакцией для каждой MISSING-строки той же версии: SYNCED с тем же checksum → CHECKSUM_READY; FAILED → ручной повтор этой строки (PENDING, checksum, serverFileId и сведения об ошибке очищаются, retryCount обнуляется); PENDING … UPLOADING не трогаются; изменённые после проверки строки обрабатывает обычная синхронизация. Набор удаляется, проверка становится FINISHED с числом возвращённых файлов, пауза снимается, регистрируются продолжения Загрузчика и, при сброшенных FAILED, Поставщика. Обычный pre-check заново спрашивает Server, поэтому появившиеся там файлы не отправляются, а повтор уже существующего пресекает серверная идемпотентность ([BACKUP-DUPLICATE](04-backup-and-sync.md#backup-duplicate)).
8. **«Позже».** Результат и пауза сохраняются; карточка свёрнута до строки о том, что автоматическая загрузка Camera приостановлена и сколько файлов ждут решения, с действиями «Загрузить N файлов» и «Отказаться от проверки»; полный итог открывается и скрывается кнопкой «Показать результат» / «Скрыть результат» (не сохраняется после перезапуска).
9. **«Отменить проверку» / «Отказаться от проверки».** Доступны на любой стадии и при ожидании решения. Запись проверки и набор удаляются одной транзакцией, пауза снимается, регистрируется продолжение Загрузчика; если проверка была в ERROR (разовая цепочка обычно ждёт backoff), дополнительно — немедленная попытка в цепочке ручных прогонов. Работающий или ждущий прогон не отменяется; уже поставленное продолжение ручной цепочки после отмены сверку не продолжает и выполняет только обычную синхронизацию. Статусы LocalMedia проверка до подтверждения не понижала, поэтому SYNCED сохраняются, ложных PENDING_UPLOAD и FAILED нет. Интерфейс предупреждает, что обычная синхронизация может загрузить недостающие файлы.

Проверка подтверждает логическую запись RemoteFile в CAMERA текущего user по checksum, а не наличие или целостность физических байтов ([SYNCED](01-system-model.md#synced)).

### Развилки и условия

- Прогресс: сканирование — неопределённый индикатор; checksum — строки с checksum или итогом из всех строк набора; сверка — строки с результатом из строк с checksum; проценты только при известном объёме. Значения читаются из Room и переживают закрытие экрана.
- Повторное «Проверить копии» при незавершённой проверке отклоняется; одновременные нажатия создают одну проверку и одно продолжение Поставщика. Действия пользователя выполняются по очереди; второе нажатие отмены ничего не находит.
- Отмена, пришедшая во время scan, hash или HTTP-запроса, не прерывает их: следующая запись стадии не применяется, новые партии не начинаются. Отмена и завершение партии разделены транзакциями: применяется то, что произошло раньше.
- Изображения, появившиеся после scan проверки, в набор не входят и обрабатываются обычной синхронизацией после снятия паузы.
- Пауза не затрагивает автоматическое резервирование папок ([BACKUP-SOURCE-SYNC](04-backup-and-sync.md#backup-source-sync)), Library и ручную передачу.

### Ошибки и recovery

- Нет доступа к изображениям, ошибка или неполный scan → ERROR на локальной стадии; следующий успешный прогон Поставщика её снимает.
- Нет пары или адреса, недоступный ping, ошибка получения CAMERA, сетевая ошибка, HTTP-ошибка (401/403 — AUTH), пустой ответ или ответ без единого разрешённого hash → ERROR на стадии SERVER; ничего не помечается отсутствующим, результаты прежних партий сохраняются. Временные причины повторяет WorkManager с backoff, успешная партия снимает ошибку; карточка предлагает «Повторить» (продолжение с той же стадии) и «Отменить проверку». «Повторить» на стадии SERVER ставит отдельный ручной прогон Загрузчика (KEEP — не больше одного), который не ждёт накопленного backoff: ожидающий или работающий автоматический прогон не отменяется, серверную стадию прогоны выполняют по очереди, а не параллельно. Временную ошибку ручной прогон сам не повторяет: он ставит разовую цепочку с KEEP (уже ждущая backoff не трогается, новая стартует через первую задержку backoff, а не сразу) и завершается, поэтому немедленных повторов подряд нет, а повтор с backoff сохраняется; следующее «Повторить» снова запускает прогон сразу. Продолжения после исчерпания бюджета и после отмены в ERROR идут в той же цепочке ручных прогонов (APPEND_OR_REPLACE: одна регистрация — один запуск после текущего). Повторное нажатие, пока проверка не вернулась в ERROR, ничего не ставит.
- Смена адреса, аккаунта или CAMERA → DESTINATION_CHANGED: ответ не применяется, повтор Загрузчика не запрашивается. Возврат прежнего назначения позволяет продолжить; «Повторить» запускает новую проверку. Подтверждение под другим назначением отклоняется.
- Перезапуск процесса: состояние в Room, задачи — в WorkManager. Старт процесса ставит Поставщика; на стадии SERVER он запрашивает Загрузчика: при RUNNING — прогон в цепочке ручных прогонов с KEEP (без ожидания backoff разовой цепочки, ждущий или работающий ручной прогон не дублируется), при ERROR — разовую цепочку с KEEP, как прежде. Ожидание решения и пауза сохраняются.

### Текущие ограничения

Проверяется только индекс Camera (область scan Поставщика). Существование подтверждается логической записью, без serverFileId и без проверки байтов. Отсутствие файла в другой папке Server не учитывается. Набор фиксируется один раз; изменённые позже файлы учитываются как UNVERIFIABLE или обрабатываются обычной синхронизацией. На паузе новые фото готовятся Поставщиком, но не отправляются до решения. На эмуляторе проверены миграция БД с сохранением индекса, полная сверка с прогрессом стадий, отмена во время запроса, «Позже» с перезапуском, подтверждение и недоступность Server (Q-01). Прогресс внутри стадии с несколькими партиями сверки на устройстве не проверялся.

<a id="backup-restart"></a>

## BACKUP-RESTART — Остановка процесса, перезагрузка и прерванные стадии

**Status:** IMPLEMENTING

**Availability:** ANDROID_ONLY

### Назначение

Описать фактическое продолжение сохранённой очереди после остановки процесса.

### Текущее поведение

Процесс останавливается, устройство перезагружается либо прерывается вычисление checksum/upload.

1. Завершённые записи очереди, настроек (в том числе IP/port) и токенов, сохранённые итоги прогонов Поставщика и Загрузчика ([SyncRunResults](01-system-model.md#sync-run-results)), а также расписание задач могут сохраниться. URL в памяти и observer находятся в памяти процесса и теряются. Задание наблюдателя MediaStore хранится в расписании задач; системное ожидание изменения перезагрузку не переживает и планируется заново при восстановлении фоновых задач; при холодном старте после завершения процесса оно также может быть поставлено заново.
2. Загрузчик, в том числе в процессе без открытого UI, перед первым сетевым обращением восстанавливает URL из сохранённых IP/port по правилу [SETTINGS-NETWORK](03-profile-and-settings.md#settings-network); значение в памяти при этом заменяется, так что после смены адреса используется новое сохранённое. Если настроек нет или они некорректны, адрес очищается, прогон завершается SERVER_UNAVAILABLE с retry без pre-check/upload и прежний адрес не используется. Поставщику URL не нужен.
3. Network UI восстанавливает URL тем же правилом до своего ping и пересматривает фон. Для работы worker открытие Network UI не требуется.
4. Каждый старт процесса при полном доступе к изображениям ставит разовый Поставщик ([BACKUP-BACKGROUND](04-backup-and-sync.md#backup-background)), в том числе для изменения, событие о котором могло быть потеряно при восстановлении фоновых задач.
5. В начале стадии checksum Поставщика после проверки разрешения HASHING возвращается в PENDING — независимо от доступности Server. Уже вычисленные CHECKSUM_READY не пересчитываются; прерванный между порциями scan восстанавливается следующим полным scan ([BACKUP-DISCOVER](04-backup-and-sync.md#backup-discover)). UPLOADING возвращается в PENDING_UPLOAD в начале стадии upload Загрузчика, после проверок пары, URL, ping, разрешения и успешного pre-check. Строки, уже переведённые pre-check в SYNCED или PENDING_UPLOAD, повторно не проверяются; прогон, остановленный бюджетом между pre-check и upload, оставляет PENDING_UPLOAD следующему прогону.

После восстановления URL и прохождения начальных проверок сохранённая очередь может продолжиться. Запуск приложения сам по себе не сбрасывает прерванные состояния.

### Ошибки и recovery

При фиксации Server без полученного ответа или локальной отметки следующая отправка может получить [BACKUP-DUPLICATE](04-backup-and-sync.md#backup-duplicate). Ранее пройденные локальные стадии не откатываются. Неуспех pre-check откладывает upload recovery.

### Текущие ограничения

Собственного boot receiver нет; без открытия приложения новые изображения обнаруживает наблюдатель MediaStore, а при его отсутствии — periodic Поставщика ([BACKUP-BACKGROUND](04-backup-and-sync.md#backup-background)). После am kill и смахивания из недавних восстановление наблюдателя и доставка фото проверены на эмуляторе; восстановление после перезагрузки и на физических устройствах не проверено. После Force Stop из настроек Android, в отличие от am kill, фоновая обработка не возобновляется до ручного запуска приложения. Запрос отмены не гарантирует остановки уже выполняемых действий. Реальное восстановление ключа/пары/очереди после восстановления резервной копии, переноса установки или обновления не проверено; это не равнозначно обычному перезапуску процесса.

### Нерешённый вопрос

Поведение OS/OEM scheduling и реальные исторические состояния DB/ключей после restore/upgrade остаются неизвестными. [SYSTEM-SCOPE](07-system-rules-and-recovery.md#system-scope) описывает ограничение identity при переносе контекста.

<a id="backup-change"></a>

## BACKUP-CHANGE — Изменение известного изображения

**Status:** IMPLEMENTING

**Availability:** END_TO_END

### Назначение

Заново обработать файл, для которого scan обнаружил изменение.

### Текущее поведение

У того же LocalMedia.mediaStoreId обнаружен другой size или lastModified.

1. Поставщик одним изменением строки сбрасывает LocalMedia.status в PENDING из любого состояния, в том числе SYNCED, очищает checksum, serverFileId, failureReason и lastFailureAt, обнуляет retryCount и записывает новые size, lastModified и остальные локальные сведения.
2. Поставщик повторяет hash до CHECKSUM_READY; затем Загрузчик выполняет target/pre-check и при необходимости upload.
3. Новое содержимое может создать новый RemoteFile; прежняя удалённая копия не удаляется.

Получен новый локальный результат для обнаруженного изменения. История серверных копий не оформляется как цепочка версий.

### Развилки и условия

Переименование/перемещение при прежнем ID, размере и mtime обновляет только локальные сведения; не вызывает remote rename/move или повторную отправку. При прежнем checksum нормальны existing/duplicate ветки.

### Ошибки и recovery

Применяются обычные ошибки стадий. Поздний результат hash, pre-check или upload прежней версии сброшенную строку не перезаписывает. При изменении байтов без изменения размера/lastModified новый backup может не начаться; для такого изменения гонка между вычислением checksum и upload сохраняется ([BACKUP-UPLOAD](04-backup-and-sync.md#backup-upload)).

### Текущие ограничения

Нет проверки версии байтов, перезаписи или автоматической очистки прежней удалённой копии; удалённые имя и папка не зеркалят локальные.

### Нерешённый вопрос

Продуктовые правила хранения прежних версий/копий и роль удалённых изменений не приняты.

<a id="backup-delete"></a>

## BACKUP-DELETE — Исчезновение или удаление локального изображения

**Status:** IMPLEMENTING

**Availability:** ANDROID_ONLY

### Назначение

Убрать из локального индекса изображение, отсутствующее в полностью прочитанной области.

### Текущее поведение

Положительный mediaStoreId исчезает из полного снимка области scan, полученного Поставщиком при полном доступе к изображениям ([BACKUP-DISCOVER](04-backup-and-sync.md#backup-discover)).

1. Android удаляет LocalMedia целиком, независимо от её текущего status.
2. Remote DELETE не отправляется; серверная копия сохраняется. Приложение само не удаляет и не редактирует оригинал устройства.
3. При повторном появлении ID создаётся новая LocalMedia со status=PENDING и снова проходит обычный pipeline.

Локальная история строки исчезает, удалённая копия остаётся. Удаление с устройства не распространяется на Server.

### Развилки и условия

Причиной может быть удаление оригинала, выход за пределы области scan или потеря видимости, о которой ОС не сообщила ошибкой. Отсутствие ID не доказывает физического удаления. Scan Error, ошибка чтения отдельной строки, неподключённое основное хранилище и отсутствие полного доступа (в том числе частичный доступ Android 14+) удаление не начинают. Пустой снимок при непустом индексе и исчезновение большой части индекса удаляются, только если их подтверждает повторный снимок через паузу ([BACKUP-DISCOVER](04-backup-and-sync.md#backup-discover)).

### Ошибки и recovery

Ошибка применения снимка может оставить частичные изменения. После повторного discovery возможно existing без serverFileId; восстановление прежней локальной истории не гарантировано.

### Текущие ограничения

LOCAL_DELETED не записывается активным flow; локальная отметка удалённого объекта не сохраняется. Android не отслеживает remote delete/rename/move ([FILES-RECONCILE](05-file-library.md#files-reconcile)).

### Нерешённый вопрос

Правила хранения после локального удаления и направления синхронизации остаются продуктовым вопросом; текущее сохранение удалённой копии этим не меняется.

<a id="backup-source-register"></a>

## BACKUP-SOURCE-REGISTER — Регистрация автоматического источника

**Status:** IMPLEMENTING

**Availability:** END_TO_END

### Назначение

До начала автоматического резервирования выбранной Android-папки получить на Server её корневую папку и сохранить её ID: в неё будут загружаться файлы источника с сохранением вложенности. Это односторонний backup, а не синхронизация файловой системы; Camera/A8 работает по прежней модели.

### Текущее поведение

Клиент отправляет `POST /api/v1/folders/backup` с именем источника и созданным клиентом UUID ([Folder](01-system-model.md#folder).backupSource). Android отправляет его при подключении папки и явном повторе ([BACKUP-SOURCE-CONNECT](04-backup-and-sync.md#backup-source-connect)).

1. Server проверяет имя по правилам библиотеки ([имена](01-system-model.md#library-names)) без изменения и наличие корректного UUID.
2. Под блокировкой структуры пользователя ищет его папку с этим backupSource. Найдена с тем же именем (точное сравнение, с учётом регистра) — возвращает её с прежним ID; с другим именем — 409, источник не переименовывается.
3. Иначе находит системный контейнер AutoUploads ([FolderType](01-system-model.md#folder-type)) — прямой потомок ROOT — либо создаёт его вместе с ROOT при отсутствии. Папка или файл ROOT с именем AutoUploads без учёта регистра, не являющиеся контейнером, системными не становятся и не меняются: регистрация получает 409.
4. Проверяет, что имя свободно в AutoUploads без учёта регистра, создаёт в нём USER-папку с переданными именем и backupSource и её физический каталог `{userId}/files/AutoUploads/{имя}` ([PhysicalBytes](01-system-model.md#physical-bytes)), затем возвращает 200 с [FolderDto](01-system-model.md#api-projections). Суффиксы к имени не добавляются.

Повтор после потерянного ответа и параллельные запросы с тем же UUID и именем получают одну папку; одновременные регистрации проходят очередь структурных изменений пользователя, контейнер создаётся один. Источники разных пользователей независимы: одинаковые имена и UUID допустимы, чужие папки недоступны (404).

### Ошибки и recovery

Некорректное или пустое имя, отсутствующий или некорректный UUID → 400 без изменений. Имя, занятое другим источником, в том числе отличающееся только регистром либо занятое только на диске, тот же UUID с другим именем, конфликт имени AutoUploads в ROOT или каталог AutoUploads, существующий только на диске → 409 без изменений. Чужие каталоги на диске не удаляются и не присваиваются. Если фиксация не удалась, каталоги, созданные этой операцией, убираются, только если повторное чтение не нашло их записей ([SYSTEM-STORAGE](07-system-rules-and-recovery.md#system-storage)).

### Текущие ограничения

Загрузки файлов источника и сохранения прежних версий нет. Зарегистрированный источник активен: его дерево защищено ([FOLDERS-MANAGED-TREE](05-file-library.md#folders-managed-tree)), отключение — [BACKUP-SOURCE-DISABLE](04-backup-and-sync.md#backup-source-disable). Повтор регистрации отключённого источника с прежними UUID и именем его не восстанавливает: бывший корень занимает имя, ответ 409. Тот же UUID с новым именем, свободным в AutoUploads, регистрирует новый источник: прежние UUID не запоминаются.

<a id="backup-source-disable"></a>

## BACKUP-SOURCE-DISABLE — Отключение автоматического источника

**Status:** IMPLEMENTING

**Availability:** END_TO_END

### Назначение

Прекратить автоматическое резервирование источника и снять защиту его дерева, сохранив все уже загруженные папки и файлы.

### Текущее поведение

Клиент отправляет `DELETE /api/v1/folders/{id}/backup` с ID корня источника. Android делает это из Settings и из Library одним общим действием (ниже).

1. Под блокировкой структуры пользователя Server находит свою папку и проверяет, что это USER-папка — прямой потомок AutoUploads.
2. Если у неё задан [Folder](01-system-model.md#folder).backupSource, очищает его. Папка, её имя, расположение, содержимое, ID папок и файлов и физические байты не меняются.
3. Возвращает 204 без тела. Повтор для уже отключённой папки также даёт 204 без изменений.

После отключения бывший источник — обычная USER-папка: в ней доступны обычные создание папок, upload, rename, move, copy и delete, а саму папку можно переименовать, удалить или перенести из AutoUploads в обычную библиотеку ([FOLDERS-AUTO-UPLOADS](05-file-library.md#folders-auto-uploads)). Операции механизма резервирования с прежним UUID получают 409 FOLDER_MANAGED ([FOLDERS-MANAGED-TREE](05-file-library.md#folders-managed-tree)). Активность источника определяет только Server.

<a id="backup-source-disable-android"></a>

Android:

1. **Settings.** В разделе «Автоматическая загрузка папок» у ACTIVE-источника есть «Отключить резервирование». У PENDING_REGISTRATION и REGISTRATION_FAILED его нет: там остаются повтор и отмена регистрации ([BACKUP-SOURCE-CONNECT](04-backup-and-sync.md#backup-source-connect)).
2. **Library.** На экране самой корневой папки активного источника (папка с backupSource) под путём показываются отметка «Источник автоматической загрузки» и «Отключить резервирование». В ROOT, Camera, AutoUploads, вложенных папках источника, обычных и отключённых папках действия нет. Запись [BackupSource](01-system-model.md#backup-source) на этом устройстве не нужна: достаточно ID папки и текущей сессии, поэтому отключить можно и источник другого телефона.
3. Оба экрана сначала показывают подтверждение «Отключить автоматическую загрузку папки «<имя>»?» с пояснением, что новые и изменённые файлы больше не будут отправляться, а сохранённые файлы и предыдущие версии останутся в AutoUploads; кнопки «Отмена» и «Отключить». «Отмена» ничего не отправляет.
4. Общее действие фиксирует Server и аккаунт, в которых пользователь видел источник (для Settings — из записи источника, для Library — сессию открытой папки), ID корня и UUID. Если текущий контекст уже другой, DELETE не отправляется. Одновременно выполняется одно действие с источниками.
5. Только ответ 204 считается отключением. Если за время запроса контекст сменился, ответ не применяется и показывается просьба повторить. Иначе запись Room текущих Server и аккаунта с этим serverRootFolderId (и UUID, если он известен) в состоянии ACTIVE получает REMOTE_DISABLED без причины. Запись, UUID, URI, serverRootFolderId, [BackupFolder](01-system-model.md#backup-folder), [BackupFile](01-system-model.md#backup-file) и сохранённое разрешение SAF не удаляются: тот же URI может использоваться другим источником.
6. Settings показывает источник отключённым: «Отключён: новые и изменённые файлы не отправляются, сохранённые остаются на сервере», без кнопок; счётчики файлов остаются.
7. Library остаётся в той же папке: она перечитывается уже без backupSource, отметка и действие исчезают, появляется кнопка ручной загрузки, в том числе во вложенных папках ([FILES-BROWSE](05-file-library.md#files-browse)). Папки, файлы и архивные версии продолжают отображаться.

Отключённый источник Worker больше не берёт ([BACKUP-SOURCE-SYNC](04-backup-and-sync.md#backup-source-sync)): прогон обрабатывает только ACTIVE-записи, а перед каждым ходом перечитывает состояние источника в Room, поэтому отключение во время прогона останавливает его на следующем ходе. Запись, начатую раньше, Server принимает или отклоняет под блокировкой (ниже); после 409 FOLDER_MANAGED источник не обрабатывается. Регистрация не повторяется, ACTIVE автоматически не восстанавливается.

### Развилки и условия

Отключение и запись в дерево источника проходят одну очередь структурных изменений пользователя ([имена](01-system-model.md#library-names)). Операция резервирования, зафиксированная раньше отключения, сохраняется. Начатая, но не зафиксированная к этому моменту — в том числе upload, уже принявший байты во временный файл до ожидания блокировки, — повторно проверяет UUID под блокировкой, получает 409, и её байты не публикуются.

### Ошибки и recovery

Чужая или отсутствующая папка → 404. ROOT, CAMERA, AutoUploads, обычная папка и вложенная папка источника → 400 без изменений.

| Android: ситуация | Результат |
| --- | --- |
| Нет сети, timeout, 5xx | Ошибка «… Источник не отключён — повторите»; состояние, запись Room и разрешение SAF не меняются, действие доступно снова |
| Отключение выполнено, ответ потерян | Как при ошибке сети; повтор отправляет DELETE к тому же ID, 204 завершает операцию. Новый источник не создаётся |
| 401/403 | «Требуется вход»; локально источник не отключается |
| 404 | «Папка источника не найдена на сервере: отключение не подтверждено»; состояние не меняется |
| 400 | «Сервер отклонил отключение: …»; состояние не меняется |
| Аккаунт или Server сменились до запроса | DELETE не отправляется |
| Аккаунт или Server сменились во время запроса | Ответ не применяется к Room, просьба открыть источник заново и повторить |

### Текущие ограничения

Повторного подключения отключённого источника и повторного выбора URI нет: повтор регистрации с прежними UUID и именем даёт 409 ([BACKUP-SOURCE-REGISTER](04-backup-and-sync.md#backup-source-register)). Новая папка с занятым именем в AutoUploads тоже получает 409, суффиксы не добавляются.

Отключение с другого устройства или из Library без записи Room телефон-источник обнаруживает при прогоне резервирования ([BACKUP-SOURCE-SYNC](04-backup-and-sync.md#backup-source-sync)): read-only проверка не находит backupSource, источник получает REMOTE_DISABLED с причиной «Источник отключён на сервере», очередь Room сохраняется. Отсутствие связи отключением не считается. Settings показывает известное приложению состояние и для проверки к Server не обращается: до следующего прогона удалённо отключённый источник выглядит активным, а его кнопка отправит идемпотентный DELETE.

Запись в PENDING_REGISTRATION, чей источник Server успел создать (ответ потерян) и затем отключили из Library, остаётся в PENDING_REGISTRATION: её повтор получит 409. Проверено на эмуляторе API 36.

<a id="backup-source-connect"></a>

## BACKUP-SOURCE-CONNECT — Подключение Android-папки как источника

**Status:** IMPLEMENTING

**Availability:** END_TO_END

### Назначение

Выбрать на телефоне папку для будущего автоматического резервирования и надёжно связать её с корнем источника на Server. Файлы папки на этом этапе не сканируются, не хэшируются и не загружаются.

### Текущее поведение

Пользователь со входом и сохранённым адресом Server открывает Settings, раздел «Автоматическая загрузка папок». Без входа или адреса раздел только поясняет это, источники не показываются.

1. По «Добавить папку» Android открывает системный выбор каталога Storage Access Framework. Отказ от выбора ничего не меняет. Разрешений на всё хранилище приложение не запрашивает.
2. После выбора показываются имя выбранной папки и поле «Имя на сервере», заполненное этим именем; пользователь может его изменить. «Отмена» закрывает выбор без записи и без сохранения разрешения.
3. По «Подключить» Android проверяет имя по правилам библиотеки ([имена](01-system-model.md#library-names)) без исправления и то, что это дерево ещё не подключено в текущем аккаунте, сохраняет разрешение на чтение дерева и убеждается, что оно есть среди сохранённых. Затем создаёт [BackupSource](01-system-model.md#backup-source) с новым sourceUuid, адресом Server, subject пользователя и состоянием PENDING_REGISTRATION — до первого запроса.
4. Отправляет регистрацию ([BACKUP-SOURCE-REGISTER](04-backup-and-sync.md#backup-source-register)) с serverName и sourceUuid записи. Ответ принимается, только если у папки положительный ID, backupSource равен sourceUuid и имя равно serverName, а аккаунт не сменился за время запроса: тогда сохраняются serverRootFolderId и ACTIVE.
5. Список под кнопкой показывает источники текущих Server и пользователя: имя, папку на устройстве, «AutoUploads/<имя>» с ID на Server, состояние регистрации, состояние доступа и причину последнего неуспеха. У ACTIVE-источника есть «Отключить резервирование» ([BACKUP-SOURCE-DISABLE](04-backup-and-sync.md#backup-source-disable-android)).

Регистрация выполняется только по действию пользователя: при старте приложения и входе в аккаунт повторов нет. ACTIVE-источник повторно не регистрируется никогда, в том числе после выхода и возврата в аккаунт.

### Развилки и условия

- Потерянный ответ, сетевая ошибка, 5xx, некорректный или несоответствующий ответ, 401/403 → PENDING_REGISTRATION с причиной и кнопкой «Повторить». Повтор отправляет тот же sourceUuid с тем же именем: если Server успел создать папку, он вернёт её прежний ID. Пока исход неизвестен, имя изменить нельзя.
- 409 или 400 → REGISTRATION_FAILED с причиной; имя не меняется автоматически, суффиксы не добавляются. Пользователь может изменить имя и повторить с тем же sourceUuid (перед отправкой запись снова становится PENDING_REGISTRATION) либо освободить имя на Server и повторить, либо «Отменить» запись: она удаляется только в этом состоянии, Server её не содержит.
- Недопустимое имя, повторный выбор уже подключённого дерева, несохранённое разрешение, отсутствие входа или адреса → запись не создаётся, выбор остаётся для исправления.
- Источник другого Server или аккаунта не показывается и не регистрируется: повтор от имени другого пользователя отклоняется без запроса. Записи сохраняются для возврата к прежнему аккаунту; sourceUuid не меняется.
- При открытии Settings и каждом возврате на экран для источников аккаунта перечитывается доступ: нет сохранённого разрешения → PERMISSION_LOST; разрешение есть, но провайдер или папка не отвечают → UNAVAILABLE. Запись и серверная папка при этом не меняются, регистрация не повторяется.

### Ошибки и recovery

Запись и sourceUuid сохраняются до запроса, поэтому прерывание процесса между запросом и ответом оставляет PENDING_REGISTRATION; явный повтор разрешает неизвестный исход идемпотентно. Удалённое отключение ([BACKUP-SOURCE-DISABLE](04-backup-and-sync.md#backup-source-disable)) обнаруживает прогон резервирования ([BACKUP-SOURCE-SYNC](04-backup-and-sync.md#backup-source-sync)); источник заново не регистрируется.

### Текущие ограничения

Подключение ставит резервирование источника ([BACKUP-SOURCE-SYNC](04-backup-and-sync.md#backup-source-sync)). Нет повторного подключения отключённого источника и повторного выбора URI на Android. Адрес Server в записи — строка адреса из настроек: тот же Server под другим адресом считается другим. Поведение выбора папок, отзыва разрешений и перезагрузки проверено только на эмуляторе API 36.

<a id="backup-source-sync"></a>

## BACKUP-SOURCE-SYNC — Автоматическое резервирование новых файлов источника

**Status:** IMPLEMENTING

**Availability:** END_TO_END

### Назначение

Самостоятельно находить новые папки и файлы подключённых Android-папок и сохранять их на Server в дереве источника с исходной вложенностью. Это односторонний backup: локальное удаление ничего не удаляет на Server, изменённый после загрузки файл получает новую версию, а прежняя сохраняется под архивным именем ([BACKUP-SOURCE-ARCHIVE](04-backup-and-sync.md#backup-source-archive)).

### Текущее поведение

Прогон FolderBackupWorker запускают подключение источника ([BACKUP-SOURCE-CONNECT](04-backup-and-sync.md#backup-source-connect)), старт процесса приложения, вход и смена адреса Server, если у текущего аккаунта есть ACTIVE-источники, periodic раз в 30 минут и продолжение. Все запуски требуют сети (CONNECTED). Очередь WorkManager отдельная от Camera/A8: внешние запросы — KEEP, продолжение — APPEND_OR_REPLACE к разовой цепочке, как в [BACKUP-BACKGROUND](04-backup-and-sync.md#backup-background). Без ACTIVE-источников аккаунта periodic отменяется.

1. В начале прогона [BackupFile](01-system-model.md#backup-file) в UPLOADING возвращаются в PENDING. Берутся ACTIVE-источники текущих Server и пользователя ([BackupSource](01-system-model.md#backup-source)); перечитывается доступ к дереву, источники без AVAILABLE пропускаются без изменений.
2. Перед первой записью прогона для каждого источника read-only запросами ROOT → AutoUploads → его потомки проверяется, что папка serverRootFolderId есть в AutoUploads и её backupSource равен sourceUuid. Иначе источник получает REMOTE_DISABLED и останавливается; регистрация не выполняется. Нет ответа → повтор прогона.
3. Источники обрабатываются ходами по очереди: за ход — до 20 прочитанных папок, до 20 созданных на Server и до 10 обработанных файлов, затем следующий источник. Большой источник не задерживает остальные. Перед каждым ходом состояние источника перечитывается из Room: отключённый пользователем во время прогона ([BACKUP-SOURCE-DISABLE](04-backup-and-sync.md#backup-source-disable)) новых ходов не получает.
4. Обход: прогон с признаком полного обхода начинает новый обход (scanGeneration+1), если прежний завершён; продолжение только дочитывает начатый. Папки читаются через SAF по одной, в порядке обнаружения, без загрузки всего дерева в память; прочитанная папка отмечается в той же транзакции, что и её содержимое, поэтому прерванный обход продолжается с непрочитанных папок. Скрытые файлы и папки не исключаются, пустые папки учитываются. Повтор имени и ссылка папки на саму себя в ответе провайдера отбрасываются, глубина ограничена 64 уровнями.
5. Сведения файла: новый путь → PENDING. Изменение размера или времени, а у SYNCED также их отсутствие → PENDING с сохранением связи с копией на Server. FAILED при новом обходе → PENDING. ARCHIVING и ARCHIVED обходом не меняются. Остальные состояния сохраняются.
6. Завершённый обход без ошибок чтения папок отмечает не найденные файлы (missingSince). Записи и серверные копии не удаляются; при неполном обходе ничего не отмечается.
7. Папки: найденные обходом создаются на Server в порядке обнаружения через `POST /api/v1/folders` с backupSource источника, в том числе пустые. ID сохраняется в [BackupFolder](01-system-model.md#backup-folder). 409 → используется существующая папка с тем же именем среди потомков; имя, занятое иначе, недопустимое имя или 400 → problem, вложенные папки и файлы не создаются, ничего не переименовывается. Сохранённый ID, на который Server ответил 404, забывается и находится заново в следующем прогоне.
8. Очередь файлов — PENDING, CHANGED, ARCHIVING и ARCHIVED в порядке FIFO. Проверяются имя ([имена](01-system-model.md#library-names)), размер 0 и больше 100 МиБ; затем читается содержимое и вычисляется SHA-256. Если путь уже связан с копией на Server: тот же checksum → SYNCED без передачи, другой → архивирование прежней версии и загрузка новой ([BACKUP-SOURCE-ARCHIVE](04-backup-and-sync.md#backup-source-archive)).
9. Иначе файл отправляется upload с folderId папки назначения, backupSource, исходным именем и потоком документа; checksum прочитанного содержимого записывается до передачи. SYNCED ставится, только если checksum ответа равен вычисленному и сведения файла после передачи не изменились; иначе сохраняется связь с принятой копией и FAILED «изменился во время передачи» — следующий обход архивирует её как прежнюю версию.

Прогон ограничен бюджетом A8 (420 секунд): новая папка или файл не начинаются после его исчерпания. Остаток с прогрессом продолжает следующий прогон; без прогресса продолжения нет. Одновременно выполняется один прогон: пересекающийся periodic или разовый завершается сразу.

### Развилки и условия

| Ситуация | Результат |
| --- | --- |
| Новый файл | SHA-256, upload, serverFileId, SYNCED |
| Имя и checksum уже есть на Server | Прежний serverFileId, SYNCED |
| Потерян ответ upload | Одна немедленная повторная отправка; Server возвращает прежний файл |
| Имя занято файлом с checksum прошлого чтения этого пути (ответ upload был потерян) | Связь с этим файлом, CHANGED → архивирование |
| Имя занято файлом с содержимым, не читавшимся из этого пути, или папкой | CONFLICT без связи: совпадения имени недостаточно, ничего не меняется |
| Изменён после SYNCED | Архивирование прежней версии и загрузка новой ([BACKUP-SOURCE-ARCHIVE](04-backup-and-sync.md#backup-source-archive)) |
| Изменено только время, содержимое то же | SYNCED без передачи |
| Пустой, больше 100 МиБ, недопустимое имя, документ без содержимого, 400/413 | SKIPPED с причиной до изменения файла |
| Файл не читается, папка назначения не создана | FAILED, повтор при следующем обходе |
| Файл исчез | missingSince после полного обхода; серверная копия остаётся |
| 409 FOLDER_MANAGED | Проверка активности; отключённый источник — REMOTE_DISABLED, остановка без регистрации |
| Сеть, 5xx, 401/403 | Строка возвращается в PENDING, прогон завершается повтором WorkManager с backoff |

### Ошибки и recovery

Прерывание процесса, отмена Worker и перезагрузка оставляют записанное в Room: незавершённая отправка возвращается в очередь, прерванный обход продолжается, повтор того же имени и содержимого Server не дублирует. Смена аккаунта или Server во время прогона останавливает его до следующей записи: файлы другого аккаунта и Server не отправляются. Отзыв разрешения → PERMISSION_LOST, временная недоступность провайдера → UNAVAILABLE, ошибка отдельной папки — неполный обход без удаления отметок.

### Текущие ограничения

Rename и move на устройстве распознаются как исчезновение прежнего пути и новый путь. Удалённые изменения не отслеживаются: копии исчезнувших файлов и архивные версии остаются на Server без удаления и ограничения числа или срока хранения. Нет уведомлений, foreground-работы и ручного «Синхронизировать сейчас»; задержку определяют события запуска и periodic. Каталог провайдера читается целиком за один запрос. Поведение проверено на эмуляторе API 36 с небольшим деревом; большие архивы и физические устройства не проверены.

## BACKUP-SOURCE-ARCHIVE — Архивирование изменённых файлов источника

**Status:** IMPLEMENTING

**Availability:** END_TO_END

### Назначение

Когда ранее загруженный файл подключённой папки изменился, сохранить на Server и прежнюю, и новую версию: прежняя переименовывается с сохранением ID, новая загружается под исходным именем. Каждая успешно обработанная версия остаётся на Server; прерывания не создают дублей и повторных переименований. Это стадия обработки [BackupFile](01-system-model.md#backup-file) в том же прогоне FolderBackupWorker ([BACKUP-SOURCE-SYNC](04-backup-and-sync.md#backup-source-sync)), а не отдельная очередь. Ручная замена файла пользователем сюда не относится.

### Текущее поведение

Этапы — [BackupFileStatus](01-system-model.md#backup-file-status) CHANGED → ARCHIVING → ARCHIVED → SYNCED. Каждый этап записывается в Room до запроса, который его продолжает.

1. Источник уже подтверждён ACTIVE в этом прогоне (п. 2 BACKUP-SOURCE-SYNC). Локальный документ читается заново и вычисляется SHA-256; нечитаемый файл → FAILED без запросов к Server: архивирование, которое нельзя закончить, не начинается. Checksum равен syncedChecksum → SYNCED без архивирования.
2. Прежняя версия читается по ID: `GET /api/v1/files/{serverFileId}`. ID, папка (BackupFolder.serverFolderId), исходное имя и checksum (syncedChecksum) должны совпасть с записанными. Нет файла → CONFLICT «прежняя версия не найдена», иначе несовпадение → CONFLICT; переименования нет. Поиск по имени не выполняется.
3. Архивное имя ([правила](05-file-library.md#files-archive-names)) строится по времени начала архивирования (UTC, до секунды) и записывается вместе с archiveFileId и archiveChecksum: ARCHIVING.
4. `PATCH /api/v1/files/{archiveFileId}` с архивным именем и backupSource источника. Ответ с тем же ID и архивным именем подтверждает переименование.
5. 409 (имя занято): сначала читается прежняя версия по ID — если она уже под архивным именем, переименование выполнено; если под исходным, записывается следующее имя (`_2`, `_3`, … до 20) и выполняется новый PATCH. Существующие объекты не меняются.
6. Подтверждённое переименование: связь serverFileId снимается, ARCHIVED; повторно прежняя версия не переименовывается. Новая версия отправляется под исходным именем по правилам п. 9 BACKUP-SOURCE-SYNC; её подтверждение записывает новые serverFileId и syncedChecksum и очищает archive-поля: SYNCED.

### Развилки и условия

| Ситуация | Результат |
| --- | --- |
| Тот же checksum (изменилось только время) | SYNCED, запросов к Server нет |
| Прежняя версия не найдена по ID | CONFLICT, Server не меняется |
| ID, папка, имя или checksum прежней версии другие | CONFLICT, Server не меняется |
| Архивное имя занято | Проверка прежней версии по ID, затем следующее имя с числовым суффиксом; после 20 имён — CONFLICT |
| Два изменения за одну секунду | Вторая архивная версия получает `_2` |
| Файл изменился во время передачи новой версии | Принятая копия связывается, FAILED; следующий обход архивирует её как прежнюю версию |
| Ответ upload потерян, а файл снова изменился | Файл под исходным именем с checksum прошлого чтения опознаётся как своя копия: CHANGED → архивирование |
| 409 FOLDER_MANAGED на PATCH или upload | Проверка активности; отключённый источник — REMOTE_DISABLED, остановка без регистрации, существующие архивные версии остаются |
| Конфликт одного файла | Остальные файлы очереди обрабатываются |

### Ошибки и recovery

| Прерывание | Восстановление |
| --- | --- |
| До PATCH (имя записано) | Чтение по ID показывает исходное имя → PATCH с тем же архивным именем |
| PATCH выполнен, ответ потерян | Чтение по ID показывает архивное имя и прежний checksum → переименование завершено, новое имя не выбирается |
| Между PATCH и upload | ARCHIVED: продолжается загрузка, повторного переименования нет |
| Upload выполнен, ответ потерян | Повтор того же имени и содержимого возвращает уже загруженный файл (идемпотентность upload Server) → его ID, SYNCED |
| Гибель процесса после upload, до записи Room | Как потерянный ответ: дополнительной версии нет |

Обрыв сети, 5xx, 401/403 и неизвестный результат запроса возвращают строку в её этап, прогон завершается повтором WorkManager с backoff; при повторе архивное имя не меняется. Неизвестный результат PATCH не считается ни успехом, ни отказом, пока состояние прежней версии не прочитано с Server. Смена аккаунта или Server останавливает прогон до следующей записи. Начатое переименование файла, исчезнувшего локально, доводится до определённого результата; новая версия для него не отправляется. Конфликт не повторяется без изменения файла.

### Текущие ограничения

Прежние версии не удаляются; число и срок хранения не ограничены. Rename и move на устройстве не распознаются ([BACKUP-SOURCE-SYNC](04-backup-and-sync.md#backup-source-sync)). Повтор upload после потерянного ответа передаёт содержимое заново. Строки CHANGED, созданные до этой версии (прежняя реализация связывала файл по имени при 409), неотличимы от изменённых после загрузки и архивируются после той же сверки по ID. Своя копия после потерянного ответа опознаётся только по последнему записанному чтению. Конфликты не показываются по отдельности: в Settings они входят в число ошибок. Проверено на эмуляторе API 36 с одиночными файлами.
