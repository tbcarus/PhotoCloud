# Backup и синхронизация

Текущий backup копирует доступные фотографии с устройства на Server. Android хранит локальную очередь и вывод о результате; удалённую библиотеку он не зеркалит. Ниже описан полный путь фотографии, включая условия и восстановление после ошибок.

Используемая модель: [DeviceMedia](01-system-model.md#device-media), [LocalMedia](01-system-model.md#local-media), [SyncState](01-system-model.md#sync-state), [FailureReason](01-system-model.md#failure-reason) и [RemoteFile](01-system-model.md#remote-file).

<a id="backup-new"></a>

## BACKUP-NEW — Полный путь новой фотографии

**Status:** AS-IS

**Availability:** END_TO_END

### Назначение

Сохранить на Server содержимое нового видимого Android изображения.

### Текущее поведение

На устройстве появляется фотография; наблюдатель изменений (observer) или периодическая задача (periodic) запускает обработку. Один факт появления ещё не гарантирует немедленного запуска. Для фонового прогона нужны непустой URL в памяти процесса и успешный public ping; для обнаружения и вычисления checksum — разрешение чтения изображений; для Server операций — действующая авторизация.

1. После URL/ping Android восстанавливает допустимые ошибки прошлого прогона и сканирует доступные Images/DCIM. Новая LocalMedia сохраняется с состоянием PENDING и локальными сведениями ([BACKUP-DISCOVER](04-backup-and-sync.md#backup-discover)).
2. Android читает содержимое и вычисляет SHA-256; успех даёт CHECKSUM_READY ([BACKUP-CHECKSUM](04-backup-and-sync.md#backup-checksum)).
3. Получает ROOT и ищет CAMERA; при её наличии проверяет checksum в этой папке ([BACKUP-TARGET](04-backup-and-sync.md#backup-target)).
4. Ответ existing переводит локальную запись в SYNCED без upload; missing либо отсутствие CAMERA — в PENDING_UPLOAD ([BACKUP-EXISTING](04-backup-and-sync.md#backup-existing)).
5. Перед upload Android повторно ищет CAMERA, проверяет локальный MIME и доступность потока, отправляет файл. Server вычисляет свойства принятых байтов и определяет папку назначения.
6. Для нового содержимого Server сохраняет байты и RemoteFile; для duplicate возвращает прежний файл. Android принимает 2xx с id>0, сохраняет serverFileId и SYNCED ([BACKUP-UPLOAD](04-backup-and-sync.md#backup-upload), [BACKUP-DUPLICATE](04-backup-and-sync.md#backup-duplicate)).
7. Обработка продолжается для следующих файлов, затем публикуется общий результат прогона.

Для обработанной строки сохраняется локальный результат по критерию [SYNCED](01-system-model.md#synced). Нет единого атомарного подтверждения Android + Server + физические байты.

### Развилки и условия

Existing и duplicate — нормальные успешные ветки. Ошибка отдельного файла может оставить FAILED при успешном завершении прогона; временная ошибка может остановить текущую стадию и отложить продолжение.

### Ошибки и recovery

Конкретные отказы описаны в сценариях обнаружения, вычисления checksum, pre-check и upload; правила повторного прогона — [BACKUP-RETRY](04-backup-and-sync.md#backup-retry), прерывание и перезагрузка — [BACKUP-RESTART](04-backup-and-sync.md#backup-restart). При потере сессии действует [AUTH-REFRESH](02-account-and-auth.md#auth-refresh).

### Текущие ограничения

Нет ручной команды Sync now и общей server sync session. Вычисление checksum для всего прогона выполняется до pre-check и upload; ошибка ранней стадии может отложить уже ожидающие upload файлы.

### Нерешённый вопрос

Какой пользовательский смысл должно иметь подтверждение «синхронизировано», в том числе при потерянном ответе и отсутствии физических байтов, ещё не принято. Это не меняет текущий критерий.

<a id="backup-discover"></a>

## BACKUP-DISCOVER — Обнаружение и повторное сканирование локальных фото

**Status:** AS-IS

**Availability:** ANDROID_ONLY

### Назначение

Поддерживать сохранённый индекс доступных локальных изображений и очередь обработки.

### Текущее поведение

Фоновый прогон доходит до сканирования либо Files запускает его из UI после запроса разрешения. Доступ к внешней коллекции изображений: API 29–32 — READ_EXTERNAL_STORAGE, API 33+ — READ_MEDIA_IMAGES. Worker сам разрешение не запрашивает.

1. Android читает полный снимок внешней коллекции Images с относительным путём DCIM/%, включая подпапки.
2. Для каждого положительного media ID сохраняет данные [DeviceMedia](01-system-model.md#device-media) в LocalMedia. Новая строка получает status=PENDING, checksum=null, serverFileId=null, failureReason=null, retryCount=0 и lastFailureAt=null.
3. Для уже известного ID сравнивает размер и lastModified. Изменение запускает [BACKUP-CHANGE](04-backup-and-sync.md#backup-change); иначе обновляются локальные сведения без сброса обработки.
4. Строки, отсутствующие в успешном снимке, удаляются из локального индекса по [BACKUP-DELETE](04-backup-and-sync.md#backup-delete).

Индекс соответствует успешно прочитанной видимой области в пределах завершённых записей. Повторное сканирование при прежних ID, размере и lastModified не вызывает повторный backup.

### Развилки и условия

Пустое имя заменяется на image_ID, пустой MIME — image/*, неизвестный размер — 0. Время выбирается из DATE_TAKEN, затем DATE_MODIFIED, затем DATE_ADDED, затем текущего времени. При отсутствии пригодных дат повторный scan может снова обнаруживать изменение.

### Ошибки и recovery

Нет разрешения на чтение → стадия не выполняется. Отсутствие результата чтения (null cursor) либо ошибка запроса/перебора строк возвращает Error. Это не пустой успешный снимок, поэтому удаление строк на этом основании не начинается. Ошибка отдельной строки может исключить её из успешного снимка; ошибка применения снимка может оставить частичные изменения.

### Текущие ограничения

Видео и изображения вне DCIM не обнаруживаются. Нет выбора альбомов, томов или источника через SAF; каждый scan читает всю область. Явных фильтров для pending/trashed media нет; окончательную видимость определяет ОС. Успешный неполный снимок может удалить историю локальных строк даже при сохранённом оригинале. Весь снимок читается целиком. В Files нет отдельной ручной Scan кнопки и реакции onResume на смену permission.

### Нерешённый вопрос

Продуктовый охват типов/папок/размеров не принят. Фактическая видимость выбранных пользователем фотографий в текущей сборке на конкретной ОС неизвестна; отдельной selected-photo модели в Android нет.

<a id="backup-checksum"></a>

## BACKUP-CHECKSUM — Вычисление checksum

**Status:** AS-IS

**Availability:** ANDROID_ONLY

### Назначение

Получить SHA-256 конкретного чтения изображения устройства для проверки existing.

### Текущее поведение

После scan в очереди есть PENDING; могут сохраниться и прерванные HASHING. Для вычисления checksum требуется разрешение чтения изображений.

1. При достижении стадии оставшиеся HASHING возвращаются в PENDING.
2. Android последовательно выбирает партии по 100 строк, отмечает каждую HASHING и открывает её content URI.
3. Вычисляет SHA-256 потока. При успехе сохраняет LocalMedia.checksum и status=CHECKSUM_READY, очищает failureReason и lastFailureAt, обнуляет retryCount.
4. Продолжает до исчерпания очереди или ошибки стадии.

Checksum относится к прочитанному содержимому, а не к имени, ID или неизменяемой версии файла.

### Ошибки и recovery

Отсутствие потока (null) или файла (FileNotFound) → FAILED FILE_NOT_FOUND; отказ доступа при чтении → FAILED PERMISSION; IOException → FAILED CHECKSUM_IO; прочие ошибки файла → FAILED UNKNOWN. Причина, счётчик и время сохраняются; обработка следующих файлов продолжается. Автоматический возврат возможен только для ограниченного CHECKSUM_IO ([BACKUP-RETRY](04-backup-and-sync.md#backup-retry)). Отсутствие разрешения на входе останавливает стадию без вычисления checksum.

### Текущие ограничения

Приватная неизменяемая копия байтов не создаётся. Во время upload URI читается заново; гонка чтений и проверка принятых байтов описаны в [BACKUP-UPLOAD](04-backup-and-sync.md#backup-upload).

<a id="backup-target"></a>

## BACKUP-TARGET — Выбор CAMERA и первый backup

**Status:** AS-IS

**Availability:** END_TO_END

### Назначение

Определить папку проверки и назначения последующей отправки.

### Текущее поведение

Прогон доходит до pre-check, а затем отдельно до подготовки upload. Предыдущие стадии пройдены; защищённые запросы папок требуют авторизации.

1. Android запрашивает ROOT. Server возвращает существующую либо лениво создаёт ROOT; CAMERA и FILES этим запросом не создаются.
2. Android получает прямых потомков ROOT и выбирает первую папку с Folder.folderType=CAMERA; имя папки в выборе не участвует.
3. Если CAMERA есть, её ID используется для [BACKUP-EXISTING](04-backup-and-sync.md#backup-existing). Если её нет, все CHECKSUM_READY с checksum, отличной от null, становятся PENDING_UPLOAD без existing-запроса.
4. Перед стадией upload Android повторяет ROOT/children lookup; найденный ID используется для всей отправки данного прогона. При отсутствии CAMERA или ошибке этого второго lookup folderId не передаётся.
5. Server без явной папки определяет тип принятых байтов: IMAGE/VIDEO → CAMERA, остальное → FILES; нужную системную папку создаёт при необходимости. Явно выбранной папкой может быть любая папка пользователя.

Проверка existing относится к найденной CAMERA; фактическая папка upload задаётся отдельным решением перед отправкой.

### Развилки и условия

- Ошибка первого lookup останавливает прогон с retry; upload не начинается. Отсутствие тела ROOT считается ошибкой, а отсутствие тела children Android считает пустым списком.
- Ошибка второго lookup не останавливает upload и не показывается как отдельная ошибка: используется default routing.
- Первый upload обычного изображения при отсутствующей CAMERA создаёт её штатно; Android create-folder не вызывает.

### Ошибки и recovery

Ошибка поиска папки или проверки existing вызывает ERROR и повтор всего прогона. При папке по умолчанию возможен конфликт имени вне CAMERA, который обрабатывается как upload 409 ([BACKUP-UPLOAD](04-backup-and-sync.md#backup-upload)).

### Текущие ограничения

Локальные подпапки DCIM не превращаются в дерево папок Server; ID не кэшируется. После успешного CAMERA pre-check, ошибки второго lookup и отличия server detection от IMAGE/VIDEO файл может попасть в FILES, хотя Android пропустил его по image/ MIME. Android папку из ответа не проверяет и может поставить SYNCED. Стабильный первый upload обычного IMAGE сам по себе этого расхождения не создаёт.

### Нерешённый вопрос

Целевые правила первого выбора CAMERA, запасного назначения и конфликтов имён, Unicode и регистра за пределами установленного As-Is не определены.

<a id="backup-existing"></a>

## BACKUP-EXISTING — Pre-check: existing или missing

**Status:** AS-IS

**Availability:** END_TO_END

### Назначение

Не отправлять содержимое, уже представленное логической записью в целевой CAMERA.

### Текущее поведение

Checksum готова, CAMERA найдена в [BACKUP-TARGET](04-backup-and-sync.md#backup-target).

1. Android берёт максимум 500 строк CHECKSUM_READY с checksum, приводит суммы к нижнему регистру и объединяет совпадающие.
2. Отправляет folderId и список checksum. Server проверяет свою папку, формат SHA-256 и максимум 500 исходных значений, затем возвращает existing/missing для текущего user и folder.
3. Existing → Android меняет только status на SYNCED, upload не выполняется.
4. Missing → PENDING_UPLOAD; затем применяется [BACKUP-UPLOAD](04-backup-and-sync.md#backup-upload). Партии продолжаются до завершения или отсутствия прогресса.

Existing подтверждает логическую запись Server на момент запроса. Ответ не содержит FileId. Изменение только status оставляет LocalMedia.serverFileId прежним; в обычном новом пути он остаётся null.

### Развилки и условия

Локальные строки с одинаковым hash в партии получают один результат. Если некорректный ответ содержит hash в обеих группах, Android предпочитает existing; если ни в одной — оставляет CHECKSUM_READY. При отсутствии прогресса завершает стадию без отдельного запроса повтора. Server для валидного запроса формирует полное разделение.

### Ошибки и recovery

При ошибке доступа к папке, HTTP, сети, разбора ответа или отсутствии тела pre-check останавливается и запрашивает повтор прогона. Результаты уже обработанных партий сохраняются.

### Текущие ограничения

Existing не проверяет физические байты и не резервирует файл до upload. Логическая запись может существовать при потерянных байтах; SYNCED этого не обнаруживает и их не восстанавливает. Обычные SYNCED повторно не сверяются с Server.

<a id="backup-upload"></a>

## BACKUP-UPLOAD — Отправка ожидающего изображения

**Status:** AS-IS

**Availability:** END_TO_END

### Назначение

Отправить изображение, отсутствующее по результату pre-check, и сохранить ответ Server локально.

### Текущее поведение

После pre-check остаются PENDING_UPLOAD. Предыдущие стадии прогона выполнены. Папка назначения определяется повторным lookup из [BACKUP-TARGET](04-backup-and-sync.md#backup-target).

1. При входе в upload оставшиеся UPLOADING возвращаются в PENDING_UPLOAD. Android выбирает сначала более новые локальные изображения, последовательно партиями по 20; общего лимита 20 на прогон нет.
2. Для файла проверяет MIME с префиксом image/ и возможность открыть/закрыть URI. Затем отмечает UPLOADING и заново читает URI для multipart upload.
3. Server принимает поток, вычисляет фактические SHA-256 и размер, определяет MIME и тип по байтам. Пустой файл отвергается; допустимо до 104857600 байтов включительно (100 MiB).
4. Server пытается извлечь метаданные изображения и определяет папку; отсутствие метаданных не отменяет upload. Если user/folder/checksum уже существует, выполняет [BACKUP-DUPLICATE](04-backup-and-sync.md#backup-duplicate).
5. Для нового checksum вне CAMERA проверяет занятость имени без учёта регистра. В CAMERA одинаковые имена разрешены. При отсутствии конфликта сохраняет итоговые байты, затем в одной транзакции RemoteFile, StoredObject и доступную FileMetadata.
6. После commit возвращает 200 с [FileItemDto](01-system-model.md#api-projections), включая ID файла, папку, нормализованное имя, checksum и доступные метаданные.
7. Android принимает любой 2xx с id>0, сохраняет этот serverFileId, ставит SYNCED и обнуляет retryCount, очищает failureReason и lastFailureAt. Остальные поля ответа не сверяет и не переносит в локальные сведения.

Обычный новый upload создаёт удалённые записи и байты; Android сохраняет положительный FileId. Создание файла и ответ duplicate одинаково считаются успехом.

### Развилки и условия

- Локальный MIME не image/ → FAILED NOT_IMAGE.
- При проверке открытия отсутствие потока/файла → FAILED FILE_NOT_FOUND, отказ доступа → FAILED PERMISSION.
- Upload 400/409/413 → FAILED HTTP_400/409/413; следующий файл обрабатывается. 409 относится к занятому имени нового содержимого вне CAMERA, а обычный duplicate возвращает 200.
- Прочие HTTP, в том числе окончательный 401/403/404/429/5xx, IOException при передаче или 2xx без id>0 → PENDING_UPLOAD, остановка upload и запрос retry.
- Иное исключение после начала отправки может оставить UPLOADING до recovery.

### Ошибки и recovery

При потере ответа Server уже мог завершить сохранение; это не доказывает откат. Повтор передаёт весь поток и может получить duplicate. Прерывание и локальное подтверждение — [BACKUP-RESTART](04-backup-and-sync.md#backup-restart); расхождение БД и байтов — [SYSTEM-STORAGE](07-system-rules-and-recovery.md#system-storage). 400/409/413 автоматически не повторяются; ручного повтора нет.

### Текущие ограничения

Вычисление checksum и upload независимо читают URI, содержимое которого может измениться. При изменении байтов между чтениями локальная checksum и pre-check могут относиться к другому содержимому, чем принятый объект, несмотря на SYNCED с ID: checksum, size и папка ответа не проверяются. Нет продолжения частичной загрузки, отправки по частям, побайтового прогресса, неизменяемого снимка или сквозного восстановления целостности. Локальной проверки максимального размера нет; серверный предел multipart 110 MB дополняет ограничение обработки потока 100 MiB. Server не ограничивает MIME списком разрешённых типов и не проверяет файлы на вирусы. BODY logging может дополнительно читать/буферизовать поток, поэтому постоянная память не гарантирована; точные дополнительные затраты не измерены. Общей серверной квоты нет.

### Нерешённый вопрос

Соответствие заявленного SIZE длине потока, дополнительное чтение и буферизация, момент прекращения действий upload после отмены зависят от условий выполнения и не проверены.

<a id="backup-duplicate"></a>

## BACKUP-DUPLICATE — Duplicate и потерянное подтверждение

**Status:** AS-IS

**Availability:** END_TO_END

### Назначение

Завершить повторную отправку того же содержимого в ту же папку без создания нового RemoteFile.

### Текущее поведение

Server получает upload с уже существующим сочетанием user + folder + SHA-256; например, Android повторяет отправку после потери ответа.

1. Server всё равно читает входящие байты и вычисляет checksum.
2. Находит прежнюю логическую запись в выбранной папке, пытается убрать временные байты и возвращает прежний DTO с 200.
3. Android принимает положительный ID, сохраняет его и SYNCED как при обычном upload.

В обычной duplicate-ветке возвращается прежний FileItem ID. Новое имя, метаданные, даты и байты не заменяют существующие.

### Развилки и условия

Тот же checksum в другой папке или у другого пользователя не является этим duplicate: обычный upload создаёт отдельные RemoteFile, StoredObject и байты. При checksum-конфликте конкурентного upload Server после очистки пытается перечитать запись и вернуть её; если не находит — пробрасывает ошибку.

### Ошибки и recovery

Duplicate не проверяет читаемость и не восстанавливает потерянные физические байты. Условие возврата прежнего ID исчезает после перемещения/удаления на Server или смены пользователя, папки или содержимого; глобальная гарантия однократного сохранения отсутствует.

### Текущие ограничения

Устранение дубликатов ограничено сочетанием user/folder/checksum. Между папками физические байты не объединяются. Побайтового сравнения при одинаковом SHA-256 нет. При потере последующей локальной записи возможна ещё одна полная попытка.

<a id="backup-metadata"></a>

## BACKUP-METADATA — Имена, время и метаданные фотографии

**Status:** AS-IS

**Availability:** END_TO_END

### Назначение

Объяснить, какие сведения сохраняются на устройстве и на Server вместе с изображением.

### Текущее поведение

Обнаружение изображения формирует локальные сведения, а успешный новый upload — серверные.

1. Android берёт имя, относительный путь, MIME, размер и время из локального снимка изображения; свои createdAt/lastModified не передаёт как capturedAt.
2. Server определяет MIME и размер по принятому потоку, нормализует имя и извлекает доступные EXIF/GPS. FileMetadata.width и FileMetadata.height поддержаны для JPEG/PNG.
3. Server задаёт RemoteFile.capturedAt из EXIF Original/Digitized в системном часовом поясе либо использует uploadedAt. Ответные даты не содержат offset.
4. Android оставляет собственные сведения; ответ Server их не заменяет.

Локальные и удалённые имя, время и метаданные могут различаться при успешном backup.

### Ошибки и recovery

Ошибка извлечения данных изображения не отменяет upload: FileMetadata может отсутствовать. Возможность отсутствия GPS не объясняет, почему его нет у конкретного файла.

### Текущие ограничения

Android сам не извлекает и не редактирует EXIF/GPS, не запрашивает отдельный доступ к оригиналу или геопозиции и не подтверждает побайтовую идентичность оригиналу. Фактические байты и возможное удаление чувствительных данных зависят от ОС, provider и выданных разрешений. Server может принимать VIDEO, но не извлекает метаданные или длительность видео; Android видео не обнаруживает.

### Нерешённый вопрос

Общий пользовательский смысл имён, времени и геопозиции и ожидаемая полнота оригинальной копии не определены; фактические GPS и байты изображений с геометками не проверены.

<a id="backup-background"></a>

## BACKUP-BACKGROUND — Автоматический и периодический backup

**Status:** AS-IS

**Availability:** END_TO_END

### Назначение

Продвигать очередь без ручных команд пользователя.

### Текущее поведение

Обработку запускает изменение Images, периодическая задача или повтор ранее неуспешного прогона.

1. Android пересматривает настройку фона при создании Network UI, успешном login, полученном результате logout, входе на Files или выдаче там разрешения. Если есть пара, URL и разрешение на изображения, включает observer и periodic; иначе останавливает observer и отменяет periodic.
2. Observer в живом процессе реагирует на изменения внешней Images-коллекции; после 3 секунд без нового события ставится разовая задача (one-time). Событие само не фильтруется по DCIM, область определяется scan.
3. Разовая задача ждёт доступной сети (CONNECTED). Периодическая настроена на 1 час и дополнительно требует достаточного заряда (batteryNotLow). Сети с тарификацией и мобильный интернет разрешены; подключение к зарядке или только Wi-Fi не требуются.
4. Перед локальными стадиями каждый прогон проверяет URL в памяти процесса и доступность Server через public ping, затем следует [BACKUP-NEW](04-backup-and-sync.md#backup-new).

Очередь может продвигаться в фоне при выполнении условий. Час и debounce — настройки, не гарантированный срок сохранения фото.

### Развилки и условия

Пока разовая работа не завершена, новая отдельная работа не ставится (KEEP), в том числе в период ожидания повторной попытки. Событие после scan текущего прогона может ждать следующего события или periodic: отдельного признака для обязательного последующего прогона нет.

### Ошибки и recovery

Недоступный URL/ping → SERVER_UNAVAILABLE и retry до scan/hash/upload. При отсутствии разрешения до scan/hash задача завершается успешно без нового общего результата; это не успешный backup. Потеря сессии обрабатывается [AUTH-REFRESH](02-account-and-auth.md#auth-refresh); автоматическая очистка пары сама фон не пересматривает.

### Текущие ограничения

Observer живёт только в памяти. Пересмотр не вызывается при каждом изменении токенов, URL или разрешения; ручной Network Test и onResume сами его не вызывают. One-time и periodic могут пересекаться друг с другом и UI scan. Защита отдельных стадий не делает весь путь обработки атомарным: поздний existing/hash/restore может перезаписать изменённую строку, а ответ upload после её удаления не обновит ничего. Отмена задачи не гарантирует остановки уже идущего HTTP-запроса или чтения. Backup не выполняется как foreground/expedited работа; уведомления о ходе нет.

### Нерешённый вопрос

Реальные задержки после reboot/force-stop/Doze, последовательности событий на OS/OEM и поведение при переставших выполняться условиях задачи не измерены. Ожидания автономности, расхода трафика/батареи и уведомлений не приняты.

<a id="backup-retry"></a>

## BACKUP-RETRY — Повторы и FAILED без автоматического восстановления

**Status:** AS-IS

**Availability:** ANDROID_ONLY

### Назначение

Продолжить локальную обработку после тех ошибок, для которых существует автоматическое восстановление.

### Текущее поведение

После проверок URL и связи следующий разрешённый фоновый прогон, в том числе повтор задачи, начинает восстановление. Истечение пяти минут само по себе задачу не запускает.

1. Один раз перед scan выбираются максимум 500 LocalMedia со status=FAILED, failureReason=CHECKSUM_IO, retryCount<3 и lastFailureAt не менее 5 минут назад.
2. Они возвращаются в PENDING; failureReason и lastFailureAt очищаются, retryCount, checksum и serverFileId сохраняются.
3. Следуют scan/hash/pre-check/upload. Успешный hash/upload и обнаруженное изменение содержимого обнуляют retryCount.
4. Ошибка стадии или временная ошибка upload запрашивает повтор всего pipeline; завершённые локальные записи сохраняются.

Восстанавливаются только допустимые строки. Успех всего прогона может сосуществовать с FAILED без автоматического восстановления и CHECKSUM_READY без прогресса.

### Развилки и условия

- Три накопленные ошибки вычисления checksum прекращают автоматическое восстановление CHECKSUM_IO. Выдержка между ошибкой и восстановлением зависит от часов устройства и следующего worker, а не отдельного таймера.
- FILE_NOT_FOUND, PERMISSION, NOT_IMAGE, HTTP_400/409/413, UNKNOWN и исторические FAILED без пригодных failureReason/lastFailureAt автоматически не восстанавливаются. Выдача разрешения сама по себе такие строки не сбрасывает.
- Изменение размера/mtime либо исчезновение и повторное discovery могут начать обработку заново. В UI нет ручного повтора, сброса или отмены.

### Ошибки и recovery

Upload при временной ошибке останавливается на первом неудавшемся файле, выбранном в порядке от новых к старым. Повторяемая ошибка нового файла может задерживать старые pending. Число попыток всего прогона приложением не ограничено и не учитывается в retryCount файла; Retry-After и server error codes не управляют retry.

### Текущие ограничения

Задержку повтора определяют стандартные настройки WorkManager: экспоненциальный рост от 30 секунд до 5 часов. Реальные запуски зависят от ОС и условий задачи; заданный срок запуска не гарантируется. При пересечении восстановлений лимит не гарантирует однократный выбор каждой строки. В UI нет ручного восстановления, счётчиков retry и полного описания фоновой ошибки; монитор описан в [FILES-LOCAL](05-file-library.md#files-local).

### Нерешённый вопрос

Ожидаемые ручное восстановление FAILED, задержки и пользовательские сообщения не определены.

<a id="backup-restart"></a>

## BACKUP-RESTART — Остановка процесса, перезагрузка и прерванные стадии

**Status:** AS-IS

**Availability:** ANDROID_ONLY

### Назначение

Описать фактическое продолжение сохранённой очереди после остановки процесса.

### Текущее поведение

Процесс останавливается, устройство перезагружается либо прерывается вычисление checksum/upload.

1. Завершённые записи очереди, настроек и токенов, а также расписание задач могут сохраниться. URL, observer и последняя общая карточка sync находятся в памяти процесса и теряются.
2. Worker без открытого UI не читает сохранённые IP/port. До восстановления URL через Network UI он завершает начальную проверку как SERVER_UNAVAILABLE и просит retry, не выполняя scan/hash/upload.
3. Network UI восстанавливает URL до своего ping и пересматривает фон. Успешный повторный UI ping для назначения URL не нужен; worker имеет собственную проверку связи.
4. При достижении стадии вычисления checksum после проверки разрешения HASHING возвращается в PENDING. UPLOADING возвращается в PENDING_UPLOAD только при достижении upload stage после всех предыдущих стадий.

После восстановления URL и прохождения начальных проверок сохранённая очередь может продолжиться. Запуск приложения сам по себе не сбрасывает прерванные состояния.

### Ошибки и recovery

При фиксации Server без полученного ответа или локальной отметки следующая отправка может получить [BACKUP-DUPLICATE](04-backup-and-sync.md#backup-duplicate). Ранее пройденные локальные стадии не откатываются. Неуспех ранней стадии откладывает upload recovery.

### Текущие ограничения

Сохранённая фоновая задача не восстанавливает адрес Server приложения; собственного boot receiver нет. Запрос отмены не гарантирует остановки уже выполняемых действий. Реальное восстановление ключа/пары/очереди после восстановления резервной копии, переноса установки или обновления не проверено; это не равнозначно обычному перезапуску процесса.

### Нерешённый вопрос

Поведение OS/OEM scheduling и реальные исторические состояния DB/ключей после restore/upgrade остаются неизвестными. [SYSTEM-SCOPE](07-system-rules-and-recovery.md#system-scope) описывает ограничение identity при переносе контекста.

<a id="backup-change"></a>

## BACKUP-CHANGE — Изменение известного изображения

**Status:** AS-IS

**Availability:** END_TO_END

### Назначение

Заново обработать файл, для которого scan обнаружил изменение.

### Текущее поведение

У того же LocalMedia.mediaStoreId обнаружен другой size или lastModified.

1. Android сбрасывает LocalMedia.status в PENDING, очищает checksum, serverFileId, failureReason и lastFailureAt, обнуляет retryCount и обновляет локальные сведения.
2. Повторяет hash, target/pre-check и при необходимости upload.
3. Новое содержимое может создать новый RemoteFile; прежняя удалённая копия не удаляется.

Получен новый локальный результат для обнаруженного изменения. История серверных копий не оформляется как цепочка версий.

### Развилки и условия

Переименование/перемещение при прежнем ID, размере и mtime обновляет только локальные сведения; не вызывает remote rename/move или повторную отправку. При прежнем checksum нормальны existing/duplicate ветки.

### Ошибки и recovery

Применяются обычные ошибки стадий. При изменении байтов без изменения размера/lastModified новый backup может не начаться; гонка между вычислением checksum и upload сохраняется ([BACKUP-UPLOAD](04-backup-and-sync.md#backup-upload)).

### Текущие ограничения

Нет проверки версии байтов, перезаписи или автоматической очистки прежней удалённой копии; удалённые имя и папка не зеркалят локальные.

### Нерешённый вопрос

Продуктовые правила хранения прежних версий/копий и роль удалённых изменений не приняты.

<a id="backup-delete"></a>

## BACKUP-DELETE — Исчезновение или удаление локального изображения

**Status:** AS-IS

**Availability:** ANDROID_ONLY

### Назначение

Убрать из локального индекса изображение, отсутствующее в успешно прочитанной области.

### Текущее поведение

Положительный mediaStoreId исчезает из успешного снимка Images/DCIM.

1. Android удаляет LocalMedia целиком, независимо от её текущего status.
2. Remote DELETE не отправляется; серверная копия сохраняется. Приложение само не удаляет и не редактирует оригинал устройства.
3. При повторном появлении ID создаётся новая LocalMedia со status=PENDING и снова проходит обычный pipeline.

Локальная история строки исчезает, удалённая копия остаётся. Удаление с устройства не распространяется на Server.

### Развилки и условия

Причиной может быть удаление оригинала, выход за пределы DCIM, потеря видимости или пропущенная ошибочная строка снимка. Отсутствие ID не доказывает физического удаления. Scan Error до применения снимка не трактуется как отсутствие всех файлов.

### Ошибки и recovery

Ошибка применения снимка может оставить частичные изменения. После повторного discovery возможно existing без serverFileId; восстановление прежней локальной истории не гарантировано.

### Текущие ограничения

LOCAL_DELETED не записывается активным flow; локальная отметка удалённого объекта не сохраняется. Android не отслеживает remote delete/rename/move ([FILES-RECONCILE](05-file-library.md#files-reconcile)).

### Нерешённый вопрос

Правила хранения после локального удаления и направления синхронизации остаются продуктовым вопросом; текущее сохранение удалённой копии этим не меняется.
