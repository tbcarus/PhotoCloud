# Общие правила и сквозной recovery

Здесь только границы, пересекающие функциональные области. Потеря сессии и выход описаны в [account/auth](02-account-and-auth.md); проверки связи, повторы, остановка процесса, перезагрузка и восстановление URL — в [backup](04-backup-and-sync.md#backup-restart).

<a id="identity-authorities"></a>

## Где определяются системные факты

| Системный факт | Где определяется | Предел |
| --- | --- | --- |
| Аккаунт и действительность доступа | Server, его User и RefreshSession | Пара и отображаемый email Android не доказывают действительность доступа |
| Видимость изображений устройства | Хранилище устройства через ОС/MediaStore | Исчезновение из снимка не доказывает удаление оригинала |
| Локальная identity | Положительный MediaStore ID и content URI | Имя/checksum не являются MediaId; глобальная уникальность между устройствами не заявлена |
| Очередь и локальный вывод о backup | Сохранённое состояние Android | Очередь не является зеркалом Server |
| Удалённая identity и дерево папок | БД Server; RemoteFile.id и Folder.id | Число имеет смысл в контексте своей БД и владельца; checksum не равна FileId |
| Физические байты | Файловая система Server | Сохранённые checksum/size не доказывают последующую неизменность байтов |

Определения и связи [RemoteFile](01-system-model.md#remote-file), [StoredObject](01-system-model.md#stored-object) и [PhysicalBytes](01-system-model.md#physical-bytes) находятся в System Model. Здесь описаны границы согласованности этих объектов.

<a id="system-scope"></a>

## SYSTEM-SCOPE — Смена аккаунта, Server и контекста установки

**Status:** AS-IS

**Availability:** END_TO_END

### Назначение

Объяснить, к какому контексту относятся сохранённые очередь, ID и учётные данные.

### Текущее поведение

Пользователь выходит/входит в другой аккаунт, меняет адрес Server либо восстанавливает установку.

1. Android сохраняет одну очередь LocalMedia по mediaStoreId и одну TokenPair без разделения по аккаунту, Server, папке или устройству.
2. Logout и смена URL не очищают очередь; TokenPair не привязана к адресу Server.
3. Ожидающие запросы используют текущий адрес Server и пользователя, а старые SYNCED обычным путём обработки не перепроверяются.
4. Server продолжает ограничивать данные текущим пользователем и папкой; совпадение числового FileId на другом Server не означает тот же файл.

Локальная история остаётся прежней даже при смене контекста Server. Отдельной истории backup по аккаунтам и Server нет.

### Ошибки и recovery

Старый SYNCED может скрывать отсутствие backup в новом аккаунте или на другом Server; прежние учётные данные могут направиться по другому адресу. Автоматической миграции/сверки такого контекста нет.

### Текущие ограничения

MediaStore IDs и очередь не защищены от совпадений между устройствами. Реальное восстановление, перенос и обновление ключей, токенов и исторической БД не проверены; перенос локального вывода может связать его с другими media IDs. Это возможные последствия; их наличие в каждой установке не утверждается.

### Нерешённый вопрос

Сценарии нескольких аккаунтов/серверов/устройств и границы согласованности локального изображения и удалённой identity при пересечении обработки и смены сессии ещё не приняты.

<a id="system-storage"></a>

## SYSTEM-STORAGE — Расхождение записей каталога и физических байтов

**Status:** IMPLEMENTING

**Availability:** END_TO_END

### Назначение

Установить, что сохраняется при частичных отказах и что приложение способно восстановить.

### Текущее поведение

Ошибка/остановка Server между сохранением байтов и БД, потеря ответа, потеря физических байтов либо ошибка удаления.

1. Multipart upload и copy выполняют долгую запись во временный файл вне транзакции. БД, файловая система и подтверждение Android не входят в одну общую транзакцию: физическое действие выполняется внутри транзакции БД под блокировкой структуры пользователя, после записи в БД и перед COMMIT. Для resumable upload действует отдельный [SYSTEM-UPLOAD-RECOVERY](07-system-rules-and-recovery.md#system-upload-recovery); остальные ограничения этого раздела не устранены.
2. Байты сначала полностью записываются во временный файл, затем публикуются без перезаписи: конечное имя резервируется атомарным созданием пустого файла, и временный файл атомарно переносится поверх этой собственной заглушки. Если конечный путь уже занят, существующий файл не меняется и не удаляется: в обычной библиотеке операция завершается 409, в CAMERA — 500 INTERNAL_ERROR. Rename, move и перенос на удаление не заменяют существующие объекты; перенос между томами отклоняется. Если атомарный перенос невозможен (временный каталог на другой файловой системе), операция завершается ошибкой без записи в конечный каталог.
3. Компенсация удаляет только файлы, созданные самой операцией: временный — до публикации, собственную заглушку — при сбое публикации. Ошибка до физического действия откатывает транзакцию без изменений на диске. При сбое COMMIT rename и move возвращаются, только если повторное чтение БД под блокировкой подтвердило прежний путь; созданный пустой каталог удаляется. Компенсация выполняется по возможности, без гарантии успеха.
4. Если ошибка возникла при фиксации upload или copy (исход неизвестен) или уже после неё, опубликованные байты сохраняются: допускается файл без записи, но не запись без байтов. Аварийная остановка или потеря питания может обойти компенсацию.
5. **Идентичность источника при чтении.** Путь файла обычной библиотеки вычисляется из имён папок и имени файла, поэтому после проверки записи её прежний путь может освободиться и достаться другому объекту. Download (в том числе по USER-доступу и ссылке), миниатюра и copy перечитывают запись и открывают физический объект под общей блокировкой структуры владельца — той же, под которой выполняются все физические rename, move, delete и публикации. Открытый объект остаётся привязан к своим байтам при любых последующих изменениях путей; блокировка снимается сразу после открытия, передача и копирование идут без неё. Итог конкурентного изменения — байты этого же файла либо 404, но не байты другого объекта. Чтения не ждут друг друга; открытие ждёт текущего структурного изменения владельца, а изменение — завершения открытия, но не передачи. Camera адресуется неизменяемым ключом с UUID, правило действует и для неё. Аварийное восстановление этим не меняется.
6. При старте Server и затем с интервалом `storage.pending-delete-interval` фоновая очистка обрабатывает только `{storage root}/.pending-delete`. Объект `file-{id}` или `folder-{id}` без записи БД удаляется рекурсивно, без перехода по junction и символическим ссылкам. Если запись ещё есть, сервер остановился между переносом и COMMIT: под блокировкой проверяется, что объекта нет на прежнем месте, а у файла совпадает checksum; затем записи удаляются и очистка продолжается. Несовпадение оставляет объект и запись и пишется в журнал. Занятый файл обрабатывается на следующем проходе, неизвестные имена не затрагиваются. Помимо отдельного восстановления resumable-сессий ([SYSTEM-UPLOAD-RECOVERY](07-system-rules-and-recovery.md#system-upload-recovery)), общей сверки БД и файловой системы нет. Android использует обычные критерии existing/upload и не восстанавливает физическую целостность данных.

Возможны записи без читаемых байтов либо байты без доступного логического файла. Existing/duplicate могут подтвердить первый случай, а download вернуть 404. Потерянный ответ не означает, что сохранения не было.

### Ошибки и recovery

Повтор ожидающей отправки ограниченно восстанавливает подтверждение по [BACKUP-DUPLICATE](04-backup-and-sync.md#backup-duplicate), но не восстанавливает отсутствующие байты. Аварийная остановка между физическим rename или move и COMMIT оставляет байты под новым путём при прежней записи: данные не теряются, но файл или содержимое папки недоступны через API до ручной сверки; автоматического восстановления нет. Внешнее удаление записей БД само по себе не удаляет байты через приложение.

### Текущие ограничения

Нет общего журнала аварийного восстановления, периодической проверки checksum, квоты опубликованной Library или согласованного резервирования и восстановления Server. Для resumable-сессий отдельно заданы журнал публикации, бюджет незавершённых данных и TTL. Изменение корня хранилища может сделать старые пути недоступными без переноса байтов.

Байты лежат под корнем хранилища в каталогах пользователя: `{userId}/camera/{YYYY}` для объектов, созданных в CAMERA, и дерево `{userId}/files/...`, повторяющее папки библиотеки ([PhysicalBytes](01-system-model.md#physical-bytes)). Файлы библиотеки можно читать и копировать напрямую, без приложения и БД; изменение дерева в обход Server не поддерживается: сервер его не обнаруживает. Путь проверяется на выход из хранилища через `..`, junction и символические ссылки. В корне каталога пользователя при первой успешной физической публикации upload/copy создаётся маркер владельца `{safeEmail}.json` ([OwnerMarker](01-system-model.md#owner-marker)) — тем же способом без перезаписи. Ошибка его создания только логируется и не прерывает операцию. Временные файлы upload по умолчанию находятся в `tmp` того же корня, служебный каталог удаления `.pending-delete` — в корне хранилища на том же томе. Прежняя раскладка `users/{userId}/objects/…` больше не создаётся, ранее сохранённые байты не переносятся. Временный каталог должен находиться на той же файловой системе, что и корень хранилища. Успешный HTTP-ответ, фиксация БД и атомарное перемещение не удостоверяют сохранность после потери питания или хранилища.

После аварийной остановки, потери питания или неудачной очистки могут остаться временные файлы в `tmp`, пустые заглушки зарезервированных имён и опубликованные байты без записи (orphan-файлы), в том числе сохранённые при неизвестном исходе фиксации. Такой файл занимает имя в библиотеке: новый объект с этим именем получает 409, существующий объект не присваивается. Уникальность физического пути обеспечивается файловой системой при публикации, отдельного ограничения в БД нет. Логическая уникальность имён файлов и duplicate Camera обеспечиваются очередью структурных изменений пользователя ([имена](01-system-model.md#library-names)); запись БД, созданная в обход неё, ограничением не отклоняется.

Маркер владельца может отсутствовать: у пользователя без физических публикаций или после ошибки его записи; тогда он появится при следующей успешной публикации. Файл, уже занимающий имя маркера, не перезаписывается и не проверяется на корректность. Если БД пересоздана с сохранением хранилища и ID повторились, в каталоге `{userId}` может остаться маркер прежнего владельца рядом с новым. Маркер отражает email на момент создания и сейчас не обновляется.

### Нерешённый вопрос

Физические границы хранилища, правила хранения, согласованное резервирование/восстановление и допустимое окно потери данных (RPO) не определены как системная политика. Реальные тома, файловые системы и внешний процесс резервирования/восстановления неизвестны; отсутствие задач приложения не доказывает отсутствие внешней эксплуатации.

<a id="system-diagnostics"></a>

## SYSTEM-DIAGNOSTICS — Диагностика и сохранение сведений об ошибках

**Status:** IMPLEMENTING

**Availability:** END_TO_END

### Назначение

Объяснить, какие сведения о результате доступны и насколько они конфиденциальны.

### Текущее поведение

Пользователь выполняет операцию с аккаунтом или файлом либо фоновый backup получает результат или ошибку.

1. Android показывает результат явной операции, локальные причины ошибок и состояние резервного копирования ([FILES-LOCAL](05-file-library.md#files-local)).
2. Server пишет одну строку журнала на HTTP-запрос: метод, шаблон маршрута (например `/api/v1/files/{id}/download`), статус и длительность; при необработанном исключении вместо статуса — имя класса исключения без сообщения. Шаблон определяется и для запроса, отклонённого до контроллера (401). Если маршрут не определён (нет обработчика, неподдерживаемый метод), вместо пути пишется `[unmapped]`: фактический путь может содержать секрет. Тела запросов и ответов, заголовки, в том числе Authorization и Cookie, query-параметры и фактические значения параметров пути не пишутся ни для одного запроса, поэтому пароли, access и refresh JWT, коды из писем и байты файлов в журнал не попадают. Письмо активации или сброса пароля журналируется только типом и ID пользователя, без адреса, ссылки и кода.
3. Некоторые серверные ошибки содержат UUID, но Android не сохраняет его для структурированной связи ошибок и истории. Единой сохраняемой истории ошибок Android ↔ Server нет.

Пользователь видит ограниченный локальный результат, а эксплуатация может иметь текстовые логи. «Все обнаруженные фото сохранены» не является доказательством физической сохранности на Server.

### Ошибки и recovery

Не все ошибки framework или ввода-вывода имеют единый формат ответа Server; логирование также не гарантирует запись каждого запроса. Наличие логов не равно полной истории операций или доставке сообщения.

### Текущие ограничения

HTTP-логирование Android не записывает заголовки и тела запросов и ответов, а значит JWT, refresh-токены, пароли и байты файлов: в debug-сборке пишутся только метод, URL, код и длительность, в release HTTP-логов нет. HTTP-журнал Server передаёт запрос и ответ дальше без промежуточного буфера и ничего из тел не читает: upload, download, миниатюры и ответы на Range идут потоком, со статусами и заголовками обработчика. Защита основана на отказе от записи данных, а не на маскировании полей, поэтому новые маршруты, в том числе с секретом в пути, по умолчанию попадают в журнал только шаблоном: публичная ссылка пишется как `GET /s/{token}`, без секрета ([ACCESS-LINK-READ](06-sharing-and-access.md#access-link-read)). Ни секрет ссылки, ни ключ его шифрования в журнал не пишутся. Страница папки по ссылке не выводит секрет в консоль браузера и обращается только к тому же Server: CSP запрещает сторонние адреса, Referrer-Policy — передачу адреса страницы ([FILES-PUBLIC-READ](05-file-library.md#files-public-read)). Журналы внешних компонентов перед Server (reverse proxy, балансировщик) этим правилом не охватываются: они видят полный URL, в том числе секрет публичной ссылки, и заголовки и при публикации Server настраиваются отдельно. Доступ к логам и их внешнее хранение не определены. Проверки работоспособности и готовности, метрики, трассировка и устойчивый журнал аудита в приложении отсутствуют; public ping их не заменяет. Транспортная граница — [SETTINGS-NETWORK](03-profile-and-settings.md#settings-network).

### Нерешённый вопрос

Какие диагностические данные, круг доступа и сроки хранения относятся к эксплуатации, не определено.

<a id="system-upload-recovery"></a>

## SYSTEM-UPLOAD-RECOVERY — Восстановление серверной сессии загрузки

**Status:** IMPLEMENTED

**Availability:** SERVER_ONLY

### Назначение

Сохранить подтверждённые блоки и единственный результат регистрации при прерывании процесса, не расширяя восстановление остальных операций Library.

### Текущее поведение

Один экземпляр Server, PostgreSQL и локальный storage на файловой системе с поддержкой hard links. Распределённые блокировки и shared storage не поддерживаются. Сборка и принимаемый блок хранятся раздельно в `.upload-sessions`, за пределами пользовательских деревьев.

1. Блок полностью принимается без транзакции БД. Размер проверяется по фактическому потоку. После добавления к сборке Server вызывает `force(true)` и только затем сохраняет подтверждённое смещение. Обрыв блока оставляет прежний offset. Авария между append и фиксацией БД оставляет лишний хвост, который отбрасывается. Если файл короче подтверждённого смещения, сессия становится FAILED / STORAGE_INCONSISTENT; положительный ответ на продолжение не выдаётся.
2. `FINALIZING` — очередь в БД, которую Server перечитывает при старте и последующем обслуживании. SHA-256 рассчитывается потоком вне транзакции. Несовпадение завершает сессию FAILED / CHECKSUM_MISMATCH без публикации. Права на папку и backupSource повторно проверяются под существующей блокировкой ROOT.
3. До физической публикации конечный путь записывается в сессию отдельной короткой транзакцией. Hard link атомарно создаёт новое конечное имя и оставляет файл сборки на месте. Сохранение FileItem/StoredObject и `COMPLETED` с квитанцией происходит в одной транзакции. Это устраняет потерю исходных байтов при rollback и возможность второго файла после потерянного ответа.
4. Перед изменением дерева владельца, а также перед повторной финализацией/очисткой под блокировкой ROOT проверяется журнал публикации. Если сессия COMPLETED, конечный файл сохраняется. Иначе удаляется только ссылка, для которой `isSameFile` подтверждает тождество с файлом сборки. Чужое занятое имя не присваивается и не удаляется. Очистка журнала фиксируется отдельно от последующей Library-операции. Неудачное восстановление отклоняет изменение дерева: перемещение родительской папки не может спрятать незавершённую публикацию от журнала.
5. При неизвестном исходе COMMIT повтор читает состояние сессии из БД: COMPLETED возвращает прежний результат, FINALIZING проходит восстановление и повторную регистрацию. Ошибки инфраструктуры повторяются фоновым обслуживанием. Общая компенсация multipart/copy/rename/move/delete (Q-03) не расширялась.
6. Отмена, получение блока и финализация одной сессии сериализованы в процессе Server. Занятая сессия возвращает 409 UPLOAD_BUSY, отмена в таком ответе ещё не принята. Если CANCELLED зафиксирована первой, публикации не будет; после COMPLETED отмена возвращает 409 и файл Library сохраняется. GET остаётся доступным во время длительной работы.
7. Неактивные сессии истекают через `upload.inactivity-ttl` (30 суток); GET не продлевает срок. Терминальные результаты сохраняются `upload.result-ttl` (30 суток от finishedAt). Ошибка удаления байтов не теряет задание очистки: запись и её резерв остаются до успешного повторного удаления. Служебные файлы не удаляются до разрешения журнала публикации.

`upload.max-reserved-bytes` по умолчанию 40 GiB ограничивает сумму объявленных размеров неочищенных сессий, позволяя держать два файла по 20 GiB. `upload.max-concurrent-chunks=4` ограничивает активные приёмники и одновременно принимаемые блоки суммарно 64 MiB. Неудалённые при ошибке временные блоки могут временно добавлять расход диска; резерв сессии остаётся занятым до очистки. Это не общая квота опубликованной Library. Проверка свободного места не резервирует диск от сторонних процессов.

Обслуживание начинается при запуске Server и повторяется через `upload.maintenance-interval` (10 секунд). Обрабатываются ограниченные страницы записей, в памяти не накапливается очередь больших файлов; хеширование выполняет один отдельный поток. Процессные блокировки не являются долговременным состоянием, после рестарта источником истины остаются БД и проверяемые файлы.

Восстановление проверено для прерывания процесса и потерянных ответов, включая физическую публикацию до COMMIT. Потеря питания/носителя, ручное изменение storage и перенос storage root с незавершённым журналом не покрываются этими гарантиями. Hard links должны поддерживаться локальным томом; копирования всего файла как fallback нет. Android Camera использует сессии с устойчивым clientRequestId и сверкой offset по GET; SAF и ручная Library пока не подключены.

## Граница подтверждения

Baseline составлен по прежним спецификациям компонентов и исторической System As-Is, которые больше не поддерживаются; фактическая работа конкретной установки этим не удостоверяется. Отдельные тесты Server не доказывают совместный Android ↔ Server сценарий; A1 дополнен изолированным Robolectric smoke с настоящим S1 Server, временными PostgreSQL и storage, двумя блоками и проверкой скачанных байтов. Он не подтверждает поведение на устройстве. В Android-клиенте есть unit- и Robolectric-тесты, в том числе конвейера синхронизации и восстановления фоновых задач WorkManager; они не означают полного интеграционного покрытия системы. Сценарии A4.3 — am kill, смахивание из недавних и доставка фотографии на Server — дополнительно проверены вручную на эмуляторе; поведение после перезагрузки устройства, в Doze и на физических устройствах не подтверждено. Поддерживаемые устройства, объёмы архива и критерии продуктовой доступности/проверки не определены, реальная нагрузка не измерена. Неизвестные условия размещения Server и работы ОС не объявляются гарантиями.
