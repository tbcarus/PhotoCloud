# PhotoCloud Product Behavior

## Назначение

Этот каталог — **первый уровень спецификации PhotoCloud**: компактное описательное представление продукта.

Он отвечает на вопрос: **что делает приложение и как оно ведёт себя для пользователя в основных и существенных альтернативных ситуациях**.

Здесь намеренно нет технической реализации: API, DTO, классов, полей моделей, БД, Room, WorkManager, механизмов хранения и других деталей компонентов. Если такая деталь нужна для точного системного контракта, она находится на втором или третьем уровне.

## Три уровня спецификации

1. **Product Behavior** — продуктовая логика и пользовательские ветвления. Этот каталог.
2. **System Specification** — точное поведение системы, System Model, состояния, данные, ограничения, ошибки и взаимодействие Android/Server: [`../system/`](../system/README.md).
3. **Server / Android Specifications** — техническая реализация конкретных компонентов.

Направление проектирования изменений:

`Product Behavior → System Specification → Component Specifications → Code`

Проверка завершённого изменения выполняется в обратную сторону и заканчивается сквозным `CHECK` от кода до Product Behavior.

## Структура

- [`01-account-and-access.md`](01-account-and-access.md) — регистрация, подтверждение, вход, сессии, выход, восстановление доступа.
- [`02-profile-and-settings.md`](02-profile-and-settings.md) — профиль, пользовательские настройки и выбор Server.
- [`03-backup-and-sync.md`](03-backup-and-sync.md) — автоматический backup фотографий, повторы, перезапуск, изменения и удаления.
- [`04-file-library.md`](04-file-library.md) — локальный экран Files и возможности удалённой библиотеки.
- [`05-sharing-and-access.md`](05-sharing-and-access.md) — владение и совместный доступ.

Отдельной сводной `product-map` нет: эти файлы и являются компактной картой продукта. Это исключает дублирование одного и того же поведения в двух местах первого уровня.

## Формат пункта

Каждый самостоятельный пункт имеет локальный номер, название, `Status`, `Availability` и ссылки на один или несколько сценариев System Specification.

Пример:

```markdown
## 1. Регистрация

**Status:** AS-IS  
**Availability:** END_TO_END  
**System:** [AUTH-REG](../system/02-account-and-auth.md#auth-reg)

Пользователь ...
```

Номер предназначен для удобства чтения и обсуждения внутри файла. Он **не является стабильным ID** и может меняться при перестройке документа. Стабильными точками связи между уровнями остаются semantic scenario IDs второго уровня (`AUTH-REG`, `BACKUP-UPLOAD`, `FILES-DELETE` и т. п.).

Один пункт Product Behavior может ссылаться на несколько System scenarios. Обратное соответствие не требуется: технически или системно значимый сценарий второго уровня может не иметь отдельного продуктового пункта, если он не добавляет самостоятельного смысла на первом уровне.

Если один продуктовый пункт пришлось бы описывать разными несовместимыми `Availability` или разными продуктовыми решениями, его следует разделить на несколько пунктов, а не скрывать различие под одним статусом.
`Availability` относится к основной продуктовой возможности пункта. Дополнительная ссылка на System scenario может использоваться для объяснения ограничения или соседней ветки и не обязана иметь тот же Availability, если она не является самостоятельной реализацией этого пункта.

## Status

Используется та же система статусов, что и на втором уровне:

- `AS-IS` — зафиксированное текущее поведение, ещё не принято как окончательное продуктовое решение;
- `ACCEPTED` — текущее поведение рассмотрено и принято;
- `OPEN` — вопрос или вариант изменения обсуждается, решения ещё нет;
- `TO-BE` — целевое продуктовое поведение утверждено;
- `DEFERRED` — решение осознанно отложено;
- `REMOVE` — существующая продуктовая функция должна исчезнуть;
- `IMPLEMENTING` — утверждённое изменение реализуется на нижних уровнях;
- `IMPLEMENTED` — реализация заявлена завершённой, но сквозная проверка ещё не выполнена;
- `CHECK` — выполняется обязательная проверка соответствия Product Behavior → System SPEC → Component SPEC → Code.

Status первого уровня относится к **продуктовому решению**. Он не вычисляется механически из статусов отдельных System scenarios, хотя связанные уровни должны находиться в логически согласованном состоянии.

## Availability

`Availability` описывает фактическую доступность текущего поведения:

- `END_TO_END` — функция существует как сквозное поведение продукта;
- `SERVER_ONLY` — соответствующая возможность существует только на Server и не доведена до Android-пользователя;
- `ANDROID_ONLY` — поведение существует только на Android и не имеет соответствующей серверной части;
- `STUB` — точка функции существует, но рабочий пользовательский сценарий не реализован;
- `NOT_PRESENT` — функции сейчас нет.

Availability отражает **реальность**, а не намерение. Поэтому новая утверждённая функция нормально выглядит как `Status: TO-BE` + `Availability: NOT_PRESENT`.

## Как начинается изменение

Если меняется смысл продукта, работа начинается здесь.

- Для новой идеи создаётся новый пункт или дополняется существующий.
- Пока решение обсуждается, `Status: OPEN`; текущее поведение не переписывается под гипотезу.
- После принятия решения `Status: TO-BE`, а рядом явно фиксируется целевое продуктовое поведение.
- После этого изменение декомпозируется во второй уровень: определяются затронутые System scenarios и System Model.

Подробный порядок перехода через System SPEC, component specs, код и обязательный CHECK закреплён в регламенте работы со спецификациями в Miro.

## Правило изменения уровней

Product Behavior меняется только тогда, когда меняется **смысл поведения продукта** или уточняется ранее неверно описанный продуктовый факт.

Технический рефакторинг Server/Android, изменение библиотеки, внутреннего класса или реализации алгоритма не требует изменения первого уровня, если продуктовая логика остаётся прежней.

Если изменение нижнего уровня неожиданно требует изменить смысл продукта, работа возвращается наверх: сначала пересматривается Product Behavior, затем System Specification, и только после этого продолжается техническая реализация.
